    LTS 25: Kompakte Quelldateien

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich kleine Werkzeuge ohne Build und ohne Klassengerüst schreiben und starten, damit ich für ein Skript nicht zu einer anderen Sprache greifen muss.

    Lernziele

    • Du startest ein Programm aus mehreren Quelldateien direkt mit java, ohne vorher zu übersetzen.
    • Du schreibst eine kompakte Quelldatei mit einer Instanzmethode main und ohne Importe aus java.base.
    • Du benennst, was eine kompakte Quelldatei nicht kann.
    • Du bewertest, wofür sich kompakte Quelldateien in Deinem Umfeld eignen.

    Definition of Done

    • Du hast Bericht.java aus mehreren Quelldateien und Hallo.java als kompakte Quelldatei mit JDK 25 gestartet.
    • skript/Lagerliste.java ist eine kompakte Quelldatei ohne Klassendeklaration und ohne Importe, und LagerlisteTest ist mit JDK 25 unverändert grün.
    • Du hast Voraussetzungen, Vorteile, Herausforderungen und den Nutzen je Anwendungsart notiert.
    • Du hast die Kontrollfragen beantwortet

    Mit JDK 25. Die Übung braucht ein JDK 25. Mit JDK 21 startet keines der Beispiele.

    Seit Java 11 startet java Datei.java ein Programm direkt aus dem Quelltext. Java 22 und 25 machen daraus ein Werkzeug für mehr als eine Datei – und für Programme, die ganz ohne Klassengerüst auskommen.

    Arbeitsschritte

    Worum es geht

    Ein kleines Werkzeug in Java braucht unter Java 8 eine Klasse, public static void main(String[] args), Importe und einen Build. Seit Java 22 startet java auch ein Programm, das aus mehreren Quelldateien in einem Ordner besteht (JEP 458). Seit Java 25 darf eine Quelldatei ganz ohne Klassendeklaration auskommen: main ist eine Instanzmethode ohne Parameter, alles aus dem Modul java.base ist importiert, und die Klasse IO schreibt und liest auf der Konsole (JEP 512). Beides trägt die LTS-Marke 25. Wo die Features in der Geschichte von Java stehen, zeigt die LTS-Evolution.

    Ein Release stellst Du in dieser Übung nicht hoch: Die Features betreffen den Start mit java, nicht den Build.

    Ausprobieren

    Im Modul neuerungen/kompakte-quelldateien liegen unter beispiel/ zwei Programme. Sie gehören zu keinem Build, Java startet sie direkt aus dem Quelltext.

    Kommandozeile

    Starte im Wurzelordner des Übungsprojekts das Programm aus mehreren Dateien:

    java neuerungen/kompakte-quelldateien/beispiel/mehrere/Bericht.java

    Starte danach die kompakte Quelldatei:

    java neuerungen/kompakte-quelldateien/beispiel/Hallo.java
    IntelliJ

    Öffne über View → Tool Windows → Terminal ein Terminal im Wurzelordner des Projekts und starte beide Beispiele dort mit den Befehlen aus dem Reiter „Kommandozeile“. Die Beispiele gehören zu keinem Build und haben deshalb keine Run Configuration.

    Eclipse

    Öffne über Window → Show View → Terminal ein Terminal im Wurzelordner des Projekts und starte beide Beispiele dort mit den Befehlen aus dem Reiter „Kommandozeile“. Die Beispiele gehören zu keinem Build und haben deshalb keine Run Configuration.

    Lies die Quelltexte und die Ausgaben:

    • Bericht.java nutzt Position und Format. Woher kennt java die beiden Klassen? Was passiert, wenn Du Format.java umbenennst?
    • Welche Importe fehlen in Hallo.java, obwohl es List und LocalDate nutzt?
    • Nimm die Kommentarzeichen vor der markierten Zeile am Ende von main weg und starte noch einmal. Was meldet der Compiler – und was folgt daraus für eine kompakte Quelldatei?

    Die Vorlage umbauen

    Im selben Modul liegt skript/Lagerliste.java, ein kleines Werkzeug im Stil von Java 8: eine Klasse, public static void main(String[] args), Importe und System.out. Schreib es zu einer kompakten Quelldatei um – ohne Klassendeklaration, mit void main(), ohne Importe und mit IO.println. Die Ausgabe muss gleich bleiben.

    Kommandozeile

    Starte das Werkzeug im Wurzelordner des Übungsprojekts:

    java neuerungen/kompakte-quelldateien/skript/Lagerliste.java

    Lass danach den Test des Moduls laufen, der das Werkzeug startet und seine Ausgabe prüft:

    mvn clean verify -pl neuerungen/kompakte-quelldateien -am
    IntelliJ

    Starte das Werkzeug im Terminal mit dem ersten Befehl aus dem Reiter „Kommandozeile“. Starte danach die Run Configuration neuerungen-kompakte-quelldateien. Sie baut mit clean und lässt LagerlisteTest laufen.

    Eclipse

    Starte das Werkzeug im Terminal mit dem ersten Befehl aus dem Reiter „Kommandozeile“. Starte danach unter Run → Run Configurations… → Maven Build die Konfiguration neuerungen-kompakte-quelldateien. Sie baut mit clean und lässt LagerlisteTest laufen.

    LagerlisteTest bleibt unverändert und muss grün bleiben. Er startet das Werkzeug mit dem JDK, auf dem die Tests laufen, und vergleicht die Ausgabe.

    Lösungsweg
    • Die Zeile public class Lagerliste { und die schließende Klammer am Ende entfallen.
    • Aus public static void main(String[] args) wird void main().
    • Die vier Importe aus java.util entfallen: Eine kompakte Quelldatei importiert das ganze Modul java.base.
    • System.out.println(…) wird IO.println(…).
    • Mit Java 25 dürfen außerdem List.of(…), var und merge stehen – die Ausgabe bleibt gleich.

    Bewerten

    Halte für Dich fest, kurz und in Stichworten:

    • Voraussetzungen: Welches JDK brauchen alle, die das Werkzeug starten? Was unterstützen IDE und Werkzeuge der statischen Analyse schon?
    • Vorteile: Wofür greifst Du heute zu einem Shell-Skript oder einer anderen Sprache, wofür jetzt Java reichen würde?
    • Herausforderungen: Was geht in einer kompakten Quelldatei nicht – Pakete, Abhängigkeiten aus Maven, Aufruf aus anderem Code?
    • Betrifft mich das? Wie hoch ist der Nutzen für einen REST-Microservice, ein Batch-Programm und eine Server-Anwendung (Java EE/Jakarta EE) – gering, mittel oder hoch?

    Reflexionsfragen

    • Ab wann lohnt sich für ein Werkzeug doch ein Maven-Projekt? Woran merkst Du, dass die Grenze erreicht ist?
    • Eine kompakte Quelldatei importiert ganz java.base. Was gewinnst Du dadurch, und was verlierst Du beim Lesen fremden Codes?
    • Wer im Team müsste JDK 25 haben, damit Ihr Eure Hilfsskripte so schreiben könnt?
