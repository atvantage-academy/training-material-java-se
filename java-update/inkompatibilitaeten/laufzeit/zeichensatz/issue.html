    UTF-8 als Standard-Zeichensatz

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich wissen, warum Dateien plötzlich mit falschen Umlauten gelesen werden, damit meine Datei-Schnittstellen nach dem Umstieg dieselben Daten liefern.

    Lernziele

    • Du erkennst einen Bruch zur Laufzeit, der vom Betriebssystem abhängt.
    • Du erklärst, woher die JVM ihren Standard-Zeichensatz bis Java 17 und seit Java 18 nimmt.
    • Du gibst den Zeichensatz einer Datei im Code an, statt ihn der JVM zu überlassen.
    • Du beurteilst, auf welchem System der Kompatibilitätsschalter das alte Verhalten zurückholt.

    Definition of Done

    • Das Modul inkompatibilitaeten/laufzeit/zeichensatz übersetzt mit Release 21, und seine Tests sind grün.
    • Der Kundenimport liest die Datei mit einem ausdrücklich angegebenen Zeichensatz.
    • Du hast für REST-Microservice, Batch-Programm und Server-Anwendung je ein Risiko notiert.
    • Du hast die Kontrollfragen beantwortet

    Jede Nacht legt ein Altsystem die Kundenliste als CSV-Datei ab, und die Bestellabwicklung liest sie ein. Das Altsystem lief auf einem deutschen Windows-Server. Prüfe, ob der Import auf einem neuen JDK noch dieselben Namen liest.

    Arbeitsschritte

    Das Problem ansehen

    Öffne im Übungsprojekt das Modul inkompatibilitaeten/laufzeit/zeichensatz und darin die Klasse KundenImport, ihren Test und die Testdatei kunden-altsystem.csv. Mit welchem Zeichensatz liest der FileReader die Datei? Sieh Dir auch die pom.xml des Moduls an: Was stellt das Profil altsystem-windows nach, und für welche JDKs?

    Auf Deinem JDK bauen

    Das Modul wird noch für Java 8 übersetzt. Baue es und lass die Tests laufen:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl inkompatibilitaeten/laufzeit/zeichensatz -am
    IntelliJ

    Starte die Run Configuration laufzeit-zeichensatz. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration laufzeit-zeichensatz. Sie baut mit clean.

    Der Test ist rot: Aus „Müller“ wird „M�ller“. Auf JDK 8 mit dem Windows-Altsystem war er grün. Ein Bruch zur Laufzeit.

    Optional, mit JDK 8: Hast Du zusätzlich ein JDK 8 als Toolchain eingerichtet (Anleitung), kannst Du den Stand vorher selbst sehen. Das Profil jdk8 lässt die Tests auf JDK 8 laufen, übersetzt wird weiter mit Deinem JDK:

    Kommandozeile

    Baue das Modul mit dem Profil jdk8 und lass seine Tests laufen:

    mvn clean verify -pl inkompatibilitaeten/laufzeit/zeichensatz -am -Pjdk8
    IntelliJ

    Starte die Run Configuration laufzeit-zeichensatz-jdk8. Sie baut mit clean und dem Profil jdk8.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration laufzeit-zeichensatz-jdk8. Sie baut mit clean und dem Profil jdk8.

    Das Release hochstellen

    Öffne inkompatibilitaeten/laufzeit/zeichensatz/pom.xml und stell die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 21. Baue das Modul erneut, wie oben. Ändert sich etwas?

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell – und der Bruch bleibt unsichtbar.

    Was dahintersteckt

    Bis Java 17 nahm die JVM ihren Standard-Zeichensatz vom Betriebssystem – auf einem deutschen Windows windows-1252, unter Linux und macOS meist UTF-8. Seit Java 18 ist er überall UTF-8 (JEP 400), LTS-Marke 21. Wer eine Datei ohne Angabe des Zeichensatzes liest, liest sie jetzt anders – auf Windows-Servern.

    Das Profil altsystem-windows stellt für JDKs bis 17 den Windows-Zeichensatz nach, damit Du den Bruch auch unter Linux und macOS siehst. Unter Windows brauchst Du es nicht.

    Den Bruch beheben

    Lies die Datei mit dem Zeichensatz, in dem sie geschrieben ist, und baue das Modul mit Release 21, bis der Test grün ist.

    Die Datei ist in windows-1252 geschrieben, und dieser Zeichensatz gehört in den Code. Zu ändern ist nur die Klasse KundenImport (src/main/java/kompatibilitaet/zeichensatz/KundenImport.java).

    Ergänze nach Zeile 6 (import java.io.IOException;) den Import:

    import java.nio.charset.Charset;

    Ergänze nach Zeile 14 (public final class KundenImport {) eine Konstante:

        private static final Charset ALTSYSTEM = Charset.forName("windows-1252");

    Ersetze Zeile 24, in der Methode lies:

            BufferedReader leser = new BufferedReader(new FileReader(datei, ALTSYSTEM));

    Den Konstruktor FileReader(File, Charset) gibt es seit Java 11. Auf Java 8 geht Files.newBufferedReader(datei.toPath(), ALTSYSTEM). Das Profil darf bleiben: Der Test ist jetzt mit jedem Standard-Zeichensatz grün.

    Den Kompatibilitätsschalter prüfen

    Für diesen Bruch gibt es den Schalter -Dfile.encoding=COMPAT: Er holt das Verhalten bis Java 17 zurück, also den Zeichensatz des Betriebssystems. Stell den Code zurück und probier ihn aus:

    Kommandozeile

    Baue das Modul mit dem Schalter und lass seine Tests laufen:

    mvn clean verify -pl inkompatibilitaeten/laufzeit/zeichensatz -am -DargLine=-Dfile.encoding=COMPAT
    IntelliJ

    Starte die Run Configuration laufzeit-zeichensatz-compat. Sie baut mit clean und übergibt den Tests den Schalter.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration laufzeit-zeichensatz-compat. Sie baut mit clean und übergibt den Tests den Schalter.

    Unter Linux und macOS bleibt der Test rot – dort war der Zeichensatz des Betriebssystems schon immer UTF-8. Auf dem Windows-Server des Altsystems würde der Schalter wirken. Er ist eine Notlösung, die nur so gut ist wie das System, auf dem sie läuft.

    Das Risiko bewerten

    Halte für Dich fest, kurz und in Stichworten:

    • Betrifft mich das? Gibt es diese Stelle in Deinem Code oder in einer Bibliothek, die Du einsetzt? Welche Klassen und Methoden in Deinem Bestand verlassen sich auf den Standard-Zeichensatz? Unter Linux und macOS war er schon vor Java 18 UTF-8 – wen trifft der Bruch also?
    • Wo fiele es auf? Beim Übersetzen, im Test, in der Abnahme oder erst in Produktion?
    • Je Anwendungsart: Wie hoch ist das Risiko für einen REST-Microservice, ein Batch-Programm und eine Server-Anwendung (Java EE/Jakarta EE) – gering, mittel oder hoch? Warum ist dieser Bruch für Batch-Programme gefährlicher als für einen REST-Microservice?

    Reflexionsfragen

    • -Dfile.encoding=COMPAT macht den Test auf Deinem Rechner vielleicht nicht grün. Warum nicht – und wo würde der Schalter wirken?
