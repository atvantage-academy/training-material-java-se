    Der Security Manager

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich wissen, was aus dem Security Manager geworden ist, damit ich rechtzeitig einen Ersatz für den Schutz plane, den er bisher geleistet hat.

    Lernziele
    • Du erkennst einen Bruch zur Laufzeit, für den das JDK keinen Ersatz anbietet.
    • Du setzt den Kompatibilitätsschalter ein und nennst, bis zu welchem Release er trägt.
    • Du entwirfst einen Ersatz, der denselben Schutz außerhalb des Security Managers leistet.
    Definition of Done
    • Das Modul inkompatibilitaeten/laufzeit/security-manager übersetzt mit Release 21, und seine Tests sind ohne Kompatibilitätsschalter grün.
    • Ein Plugin, das System.exit ruft, beendet die Anwendung nicht.
    • Du hast für REST-Microservice, Batch-Programm und Server-Anwendung je ein Risiko notiert.
    • Du hast die Kontrollfragen beantwortet

    Die Bestellabwicklung führt Plugins von Drittanbietern aus. Ruft ein Plugin System.exit(…), soll nicht die ganze Anwendung enden. Das verhindert bisher ein Security Manager, der genau diesen Aufruf abfängt. Prüfe, ob das auf einem neuen JDK noch funktioniert.

    Arbeitsschritte

    Das Problem ansehen

    Öffne im Übungsprojekt das Modul inkompatibilitaeten/laufzeit/security-manager und darin die Klasse PluginAusfuehrer und ihren Test. Wie verhindert die Klasse, dass ein Plugin die Anwendung beendet?

    Optional: Den Stand vorher mit JDK 8 sehen

    Hast Du ein JDK 8 als Toolchain eingerichtet (Anleitung), siehst Du zuerst, wie es vor dem Umstieg war. Das Profil jdk8 lässt die Tests auf JDK 8 laufen, übersetzt wird weiter mit Deinem JDK:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts mit dem Profil jdk8 und lass seine Tests laufen:

    mvn clean verify -pl inkompatibilitaeten/laufzeit/security-manager -am -Pjdk8
    IntelliJ

    Starte die Run Configuration laufzeit-security-manager-jdk8. Sie baut mit clean und dem Profil jdk8.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration laufzeit-security-manager-jdk8. Sie baut mit clean und dem Profil jdk8.

    VS Code

    Starte über Terminal → Run Task… den Task laufzeit-security-manager-jdk8. Er baut mit clean und dem Profil jdk8.

    Beide Tests sind grün – so lief der Code bisher. Ohne JDK 8 übergehst Du diesen Schritt: Auf JDK 8 sind die Tests grün.

    Auf Deinem JDK bauen

    Baue das Modul jetzt mit Deinem aktuellen JDK. Das Release ist immer noch 8: Übersetzt wird gegen die API von Java 8.

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl inkompatibilitaeten/laufzeit/security-manager -am
    IntelliJ

    Starte die Run Configuration laufzeit-security-manager. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration laufzeit-security-manager. Sie baut mit clean.

    VS Code

    Starte über Terminal → Run Task… den Task laufzeit-security-manager. Er baut mit clean.

    Beide Tests sind rot: UnsupportedOperationException beim Setzen des Security Managers. Auf JDK 8 waren sie grün. Ein Bruch zur Laufzeit.

    Das Release hochstellen

    Öffne inkompatibilitaeten/laufzeit/security-manager/pom.xml und stell die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 21. Baue das Modul erneut, wie oben.

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell – und der Bruch bleibt unsichtbar.

    Achte jetzt auch auf die Warnungen des Compilers: Was meldet er zu SecurityManager?

    Was dahintersteckt

    Der Security Manager ist seit Java 17 zur Entfernung vorgesehen (JEP 411), seit Java 18 lässt er sich nur noch mit -Djava.security.manager=allow einschalten, und seit Java 24 ist er dauerhaft abgeschaltet (JEP 486) – LTS-Marken 17 für die Ankündigung, 21 für den Bruch, 25 für das Ende. Einen Ersatz im JDK gibt es nicht.

    Den Kompatibilitätsschalter ausprobieren

    Lass die Tests mit dem Schalter laufen, der den Security Manager noch einmal erlaubt:

    Kommandozeile

    Baue das Modul mit dem Schalter und lass seine Tests laufen:

    mvn clean verify -pl inkompatibilitaeten/laufzeit/security-manager -am -DargLine=-Djava.security.manager=allow
    IntelliJ

    Starte die Run Configuration laufzeit-security-manager-allow. Sie baut mit clean und übergibt den Tests den Schalter.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration laufzeit-security-manager-allow. Sie baut mit clean und übergibt den Tests den Schalter.

    VS Code

    Starte über Terminal → Run Task… den Task laufzeit-security-manager-allow. Er baut mit clean und übergibt den Tests den Schalter.

    Auf JDK 21 werden die Tests grün, auf JDK 25 nicht. Der Schalter trägt nur bis Java 23.

    Einen Ersatz entwerfen

    Entwirf einen Weg, auf dem ein Plugin die Anwendung nicht beenden kann – ohne Security Manager. Setz ihn um und baue das Modul mit Release 21, bis die Tests ohne Schalter grün sind. Passe den Test an, wo er den Security Manager voraussetzt, aber nicht an dem, was er prüft.

    Das Plugin läuft in einer eigenen JVM, gestartet über ProcessBuilder. Ein System.exit beendet nur diese; der Status kommt als Exit-Code zurück, und der Ausführer meldet ihn als PluginBeendetException. Die Abgrenzung übernimmt damit das Betriebssystem – oder ein Container.

    Leg dazu neben PluginAusfuehrer die Klasse PluginStarter an. Sie ist das Programm, das in der neuen JVM ein Plugin startet:

    package kompatibilitaet.securitymanager;

public final class PluginStarter {

    private PluginStarter() {
    }

    public static void main(String[] args) throws ReflectiveOperationException {
        Class<?> plugin = Class.forName(args[0]);
        ((Runnable) plugin.getDeclaredConstructor().newInstance()).run();
    }
}

    In PluginAusfuehrer ersetze Zeilen 15 bis 23, die Methode führeAus. Sie bekommt jetzt die Klasse des Plugins statt einer Instanz – eine Instanz lässt sich nicht an eine andere JVM übergeben:

        private static final long ZEITLIMIT_SEKUNDEN = 30;

    /**
     * @return was das Plugin ausgegeben hat
     * @throws PluginBeendetException wenn das Plugin mit einem Status ungleich 0 endet
     */
    public static String führeAus(Class<? extends Runnable> plugin) throws IOException, InterruptedException {
        Process prozess = new ProcessBuilder(
                Path.of(System.getProperty("java.home"), "bin", "java").toString(),
                "-cp", System.getProperty("java.class.path"),
                PluginStarter.class.getName(), plugin.getName())
                .redirectErrorStream(true)
                .start();
        String ausgabe;
        try (InputStream ein = prozess.getInputStream()) {
            ausgabe = new String(ein.readAllBytes(), StandardCharsets.UTF_8).strip();
        }
        if (!prozess.waitFor(ZEITLIMIT_SEKUNDEN, TimeUnit.SECONDS)) {
            prozess.destroyForcibly();
            throw new IllegalStateException("Plugin " + plugin.getName() + " hat das Zeitlimit überschritten");
        }
        if (prozess.exitValue() != 0) {
            throw new PluginBeendetException(prozess.exitValue());
        }
        return ausgabe;
    }

    Dazu in derselben Klasse:

    • Zeile 3: Statt java.security.Permission brauchst Du java.io.IOException, java.io.InputStream, java.nio.charset.StandardCharsets, java.nio.file.Path und java.util.concurrent.TimeUnit.
    • Zeile 28: PluginBeendetException erbt von RuntimeException statt von SecurityException.
    • Zeilen 44 bis 55: Die Klasse ExitVerhinderer entfällt.

    Im Test PluginAusfuehrerTest werden die beiden Plugins zu benannten Klassen, damit die neue JVM sie laden kann:

        public static class GrüßendesPlugin implements Runnable {

        @Override
        public void run() {
            System.out.println("Hallo aus dem Plugin");
        }
    }

    public static class BeendendesPlugin implements Runnable {

        @Override
        public void run() {
            System.exit(3);
        }
    }

    Die Tests rufen PluginAusfuehrer.führeAus(GrüßendesPlugin.class) und PluginAusfuehrer.führeAus(BeendendesPlugin.class) auf. Was sie prüfen, bleibt gleich: Das Plugin läuft, und sein System.exit(3) kommt als PluginBeendetException mit Status 3 zurück.

    Das ist eine Entwurfsentscheidung, keine Behebung im Kleinen: Sie kostet Startzeit und verlangt, dass Plugins als eigenes Programm startbar sind.

    Das Risiko bewerten

    Halte für Dich fest, kurz und in Stichworten:

    • Betrifft mich das? Gibt es diese Stelle in Deinem Code oder in einer Bibliothek, die Du einsetzt? Wofür wurde der Security Manager in Deinen Anwendungen oder auf Deinem Server genutzt – und wer leistet diesen Schutz künftig?
    • Wo fiele es auf? Beim Übersetzen, im Test, in der Abnahme oder erst in Produktion?
    • Je Anwendungsart: Wie hoch ist das Risiko für einen REST-Microservice, ein Batch-Programm und eine Server-Anwendung (Java EE/Jakarta EE) – gering, mittel oder hoch?

    Reflexionsfragen

    • Der eigene Prozess kostet Startzeit und Speicher. Wann ist das vertretbar, und welche Alternativen gibt es?
    • Warum reicht es nicht, auf Java 21 mit -Djava.security.manager=allow zu bleiben?
