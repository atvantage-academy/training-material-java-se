    Datumsformate mit CLDR

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich verstehen, warum formatierte Datums- und Geldbeträge plötzlich anders aussehen, damit keine Schnittstelle bricht, die diesen Text einliest.

    Lernziele

    • Du erkennst einen Bruch zur Laufzeit, den kein Compiler meldet.
    • Du erklärst, woher das JDK seit Java 9 seine Locale-Daten bezieht.
    • Du findest einen unsichtbaren Unterschied, indem Du erwarteten und tatsächlichen Wert zeichengenau vergleichst.
    • Du entscheidest, ob ein Textformat ein Vertrag ist, und behebst den Bruch entsprechend.
    • Du setzt einen Kompatibilitätsschalter ein und nennst, wie lange er trägt.

    Definition of Done

    • Das Modul inkompatibilitaeten/laufzeit/datumsformat übersetzt mit Release 21, und seine Tests sind ohne Kompatibilitätsschalter grün.
    • Du kannst begründen, warum Du das Format festgelegt oder den Test angepasst hast.
    • Du hast für REST-Microservice, Batch-Programm und Server-Anwendung je ein Risiko notiert.
    • Du hast die Kontrollfragen beantwortet

    Der Lieferschein der Bestellabwicklung beginnt mit einer Kopfzeile: Bestellnummer, Lieferdatum, Betrag – in deutscher Schreibweise. Das Lagersystem liest diese Zeile ein. Prüfe, ob sie auf einem neuen JDK noch genauso aussieht.

    Arbeitsschritte

    Das Problem ansehen

    Öffne im Übungsprojekt das Modul inkompatibilitaeten/laufzeit/datumsformat und darin die Klasse Lieferschein und ihren Test LieferscheinTest. Womit formatiert die Klasse Datum und Betrag, und welche Kopfzeile erwartet der Test?

    Auf Deinem JDK bauen

    Das Modul wird noch für Java 8 übersetzt. Baue es und lass die Tests laufen:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl inkompatibilitaeten/laufzeit/datumsformat -am
    IntelliJ

    Starte die Run Configuration laufzeit-datumsformat. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration laufzeit-datumsformat. Sie baut mit clean.

    VS Code

    Starte über Terminal → Run Task… den Task laufzeit-datumsformat. Er baut mit clean.

    Der Test ist rot, obwohl Du nichts geändert hast: Auf JDK 8 war er grün, auf Deinem JDK nicht. --release 8 legt nur fest, gegen welche API übersetzt wird – laufen tut der Code auf Deinem JDK. Das ist ein Bruch zur Laufzeit.

    Optional, mit JDK 8: Hast Du zusätzlich ein JDK 8 als Toolchain eingerichtet (Anleitung), kannst Du den Stand vorher selbst sehen. Das Profil jdk8 lässt die Tests auf JDK 8 laufen, übersetzt wird weiter mit Deinem JDK:

    Kommandozeile

    Baue das Modul mit dem Profil jdk8 und lass seine Tests laufen:

    mvn clean verify -pl inkompatibilitaeten/laufzeit/datumsformat -am -Pjdk8
    IntelliJ

    Starte die Run Configuration laufzeit-datumsformat-jdk8. Sie baut mit clean und dem Profil jdk8.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration laufzeit-datumsformat-jdk8. Sie baut mit clean und dem Profil jdk8.

    VS Code

    Starte über Terminal → Run Task… den Task laufzeit-datumsformat-jdk8. Er baut mit clean und dem Profil jdk8.

    Das Release hochstellen

    Öffne inkompatibilitaeten/laufzeit/datumsformat/pom.xml und stell die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 21. Baue das Modul erneut, wie oben. Ändert sich etwas?

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell – und der Bruch bleibt unsichtbar.

    Es bleibt beim selben roten Test: Das Release hat mit diesem Bruch nichts zu tun. Vergleiche erwartete und tatsächliche Kopfzeile in der Meldung. Was ist anders?

    Was dahintersteckt

    Seit Java 9 stammen die Locale-Daten des JDK aus dem Unicode CLDR (Common Locale Data Repository) statt aus den eigenen Tabellen des JDK – JEP 252, LTS-Marke 11. Das CLDR schreibt deutsche Abkürzungen mit Punkt („Mo.“), den September als „Sept.“ – und setzt vor das €-Zeichen ein geschütztes Leerzeichen (U+00A0) statt eines normalen. Das letzte siehst Du in der Meldung nicht.

    Den Bruch beheben

    Entscheide zuerst: Ist die Kopfzeile ein Vertrag – liest ein anderes System sie ein –, oder ist sie nur für Menschen gedacht? Behebe den Bruch dann entsprechend und baue das Modul mit Release 21, bis der Test grün ist.

    Hier liest das Lagersystem die Zeile ein; ihre Form ist ein Vertrag. Dann gehört das Format in den eigenen Code statt in die Locale-Daten des JDK. Zu ändern ist nur die Klasse Lieferschein (src/main/java/kompatibilitaet/datumsformat/Lieferschein.java).

    Ersetze die Importe in Zeilen 3 bis 7:

    import java.math.BigDecimal;
import java.text.DecimalFormat;
import java.text.DecimalFormatSymbols;
import java.time.LocalDate;
import java.time.format.DateTimeFormatter;
import java.time.format.DateTimeFormatterBuilder;
import java.time.temporal.ChronoField;
import java.util.Locale;
import java.util.Map;

    Ersetze Zeile 14, das Datumsformat. Die Abkürzungen stehen jetzt selbst im Code:

        private static final Map<Long, String> WOCHENTAGE = Map.of(
            1L, "Mo", 2L, "Di", 3L, "Mi", 4L, "Do", 5L, "Fr", 6L, "Sa", 7L, "So");

    private static final Map<Long, String> MONATE = Map.ofEntries(
            Map.entry(1L, "Jan"), Map.entry(2L, "Feb"), Map.entry(3L, "Mär"), Map.entry(4L, "Apr"),
            Map.entry(5L, "Mai"), Map.entry(6L, "Jun"), Map.entry(7L, "Jul"), Map.entry(8L, "Aug"),
            Map.entry(9L, "Sep"), Map.entry(10L, "Okt"), Map.entry(11L, "Nov"), Map.entry(12L, "Dez"));

    private static final DateTimeFormatter DATUM = new DateTimeFormatterBuilder()
            .appendText(ChronoField.DAY_OF_WEEK, WOCHENTAGE)
            .appendPattern(", d. ")
            .appendText(ChronoField.MONTH_OF_YEAR, MONATE)
            .appendPattern(" yyyy")
            .toFormatter(Locale.GERMANY);

    Ersetze Zeilen 20 und 21, den Rumpf von kopfzeile. Der Betrag bekommt ein festes Muster – mit einem gewöhnlichen Leerzeichen vor dem €:

            // DecimalFormat ist nicht threadsicher – deshalb je Aufruf neu.
        DecimalFormat euro = new DecimalFormat("#,##0.00 €", DecimalFormatSymbols.getInstance(Locale.GERMANY));
        return "Lieferschein " + bestellnummer + " vom " + DATUM.format(lieferdatum)
                + " über " + euro.format(betrag);

    Ist der Text nur für Menschen gedacht, ist die andere Antwort genauso richtig: das neue Format übernehmen und den Test anpassen – zeichengenau, mit dem geschützten Leerzeichen (\u00A0) vor dem €.

    Den Kompatibilitätsschalter ausprobieren

    Stell den Code zurück (oder probier es vor der Behebung) und lass den Test mit dem Schalter laufen, der die alten Locale-Daten zurückholt:

    Kommandozeile

    Baue das Modul mit dem Schalter und lass seine Tests laufen:

    mvn clean verify -pl inkompatibilitaeten/laufzeit/datumsformat -am -DargLine=-Djava.locale.providers=COMPAT
    IntelliJ

    Starte die Run Configuration laufzeit-datumsformat-compat. Sie baut mit clean und übergibt den Tests den Schalter.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration laufzeit-datumsformat-compat. Sie baut mit clean und übergibt den Tests den Schalter.

    VS Code

    Starte über Terminal → Run Task… den Task laufzeit-datumsformat-compat. Er baut mit clean und übergibt den Tests den Schalter.

    Der Test wird grün. Der Schalter ist eine Notlösung: Er muss überall stehen, wo der Code läuft, und es gibt ihn nur bis Java 22. Seit Java 23 sind die alten Locale-Daten aus dem JDK entfernt.

    Das Risiko bewerten

    Halte für Dich fest, kurz und in Stichworten:

    • Betrifft mich das? Gibt es diese Stelle in Deinem Code oder in einer Bibliothek, die Du einsetzt?
    • Wo fiele es auf? Beim Übersetzen, im Test, in der Abnahme oder erst in Produktion?
    • Je Anwendungsart: Wie hoch ist das Risiko für einen REST-Microservice, ein Batch-Programm und eine Server-Anwendung (Java EE/Jakarta EE) – gering, mittel oder hoch?

    Hinweis: Überleg dazu, wo in Deinen Anwendungen formatierte Datums- oder Geldbeträge in einer Datei, einer Nachricht oder einer Datenbank landen.

    Reflexionsfragen

    • Wann ist ein formatierter Text ein Vertrag, den Du im Code festlegen musst, und wann darf er sich mit dem JDK ändern?
    • Warum ist der Schalter -Djava.locale.providers=COMPAT keine wirkliche Lösung?
