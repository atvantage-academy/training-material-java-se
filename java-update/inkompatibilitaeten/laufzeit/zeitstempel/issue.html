    Genauere Zeitstempel

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich verstehen, warum Zeitstempel nach dem Speichern nicht mehr gleich sind, damit Vergleiche, Schlüssel und Prüfungen in meiner Anwendung weiter stimmen.

    Lernziele
    • Du erkennst einen Bruch zur Laufzeit, der von Betriebssystem und JDK abhängt.
    • Du erklärst, warum Instant.now() auf neueren JDKs genauer ist als eine Millisekunde.
    • Du legst die Genauigkeit der Zeit in der Anwendung fest, statt sie dem JDK zu überlassen.
    Definition of Done
    • Das Modul inkompatibilitaeten/laufzeit/zeitstempel übersetzt mit Release 21, und seine Tests sind grün.
    • Die Anwendung bestimmt die Genauigkeit ihrer Zeitstempel selbst.
    • Du hast für REST-Microservice, Batch-Programm und Server-Anwendung je ein Risiko notiert.
    • Du hast die Kontrollfragen beantwortet

    Die Bestellabwicklung speichert Ereignisse – „bestellt“, „versandt“ – mit ihrem Zeitpunkt. In der Datenbank landet der Zeitpunkt als Millisekunden seit 1970. Prüfe, ob ein Ereignis nach dem Laden noch dasselbe ist wie vor dem Speichern.

    Arbeitsschritte

    Das Problem ansehen

    Öffne im Übungsprojekt das Modul inkompatibilitaeten/laufzeit/zeitstempel und darin die Klassen Ereignis, EreignisSpeicher und den Test EreignisSpeicherTest. Woher bekommt ein neues Ereignis seinen Zeitpunkt, und wie genau wird er gespeichert?

    Optional: Den Stand vorher mit JDK 8 sehen

    Hast Du ein JDK 8 als Toolchain eingerichtet (Anleitung), siehst Du zuerst, wie es vor dem Umstieg war. Das Profil jdk8 lässt die Tests auf JDK 8 laufen, übersetzt wird weiter mit Deinem JDK:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts mit dem Profil jdk8 und lass seine Tests laufen:

    mvn clean verify -pl inkompatibilitaeten/laufzeit/zeitstempel -am -Pjdk8
    IntelliJ

    Starte die Run Configuration laufzeit-zeitstempel-jdk8. Sie baut mit clean und dem Profil jdk8.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration laufzeit-zeitstempel-jdk8. Sie baut mit clean und dem Profil jdk8.

    VS Code

    Starte über Terminal → Run Task… den Task laufzeit-zeitstempel-jdk8. Er baut mit clean und dem Profil jdk8.

    Der Test ist grün – so lief der Code bisher. Ohne JDK 8 übergehst Du diesen Schritt: Auf JDK 8 ist der Test grün.

    Auf Deinem JDK bauen

    Baue das Modul jetzt mit Deinem aktuellen JDK. Das Release ist immer noch 8: Übersetzt wird gegen die API von Java 8.

    Der Test ist rot: Das geladene Ereignis gleicht dem gespeicherten nicht mehr. Auf JDK 8 war er grün. Ein Bruch zur Laufzeit – das Release hat damit nichts zu tun.

    Das Release hochstellen

    Öffne inkompatibilitaeten/laufzeit/zeitstempel/pom.xml und stell die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 21. Baue das Modul erneut, wie oben. Ändert sich etwas?

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell – und der Bruch bleibt unsichtbar.

    Vergleiche die beiden Zeitpunkte in der Meldung. Wie viele Nachkommastellen hat der erwartete, wie viele der geladene?

    Was dahintersteckt

    Bis Java 8 lieferte Instant.now() die Zeit auf die Millisekunde genau. Seit Java 9 nutzt die Systemuhr die Genauigkeit des Betriebssystems – unter Linux und macOS Mikrosekunden (JDK-8068730), seit Java 15 unter Linux sogar Nanosekunden (JDK-8242504). Für diese Änderung gibt es keinen JEP; sie steht in den Release Notes. Gespeichert werden weiter Millisekunden – nach dem Laden fehlt der Rest, und das Ereignis ist ein anderes.

    Im Code sind es drei Stellen, die erst zusammen den Fehler ergeben:

    • Ereignis.jetzt() holt den Zeitpunkt mit Instant.now() – auf Deinem JDK samt Mikro- oder Nanosekunden.
    • EreignisSpeicher.speichere() legt nur toEpochMilli() ab und schneidet den Rest ab; lade() baut daraus mit Instant.ofEpochMilli() einen Zeitpunkt auf die Millisekunde genau.
    • Ereignis.equals() vergleicht die beiden Instant exakt, also auch die abgeschnittenen Stellen.

    Den Bruch beheben

    Sorg dafür, dass ein Ereignis nur so genau ist, wie es gespeichert werden kann, und baue das Modul mit Release 21, bis der Test grün ist.

    Die Anwendung legt die Genauigkeit fest, nicht das JDK: Ein neues Ereignis holt seine Zeit von einer Uhr mit Millisekunden-Takt. Zu ändern ist nur die Klasse Ereignis (src/main/java/kompatibilitaet/zeitstempel/Ereignis.java).

    Ersetze in Zeile 20, in der Methode jetzt, den Aufruf Instant.now():

            return new Ereignis(art, Instant.now(Clock.tickMillis(ZoneOffset.UTC)));

    Ergänze dazu nach Zeile 3 (import java.time.Instant;) die beiden Importe:

    import java.time.Clock;
import java.time.ZoneOffset;

    Clock.tickMillis gibt es seit Java 9. Wer auf Java 8 bleiben muss, schneidet in Zeile 20 stattdessen ab: Instant.now().truncatedTo(ChronoUnit.MILLIS) (Import java.time.temporal.ChronoUnit). Einen Kompatibilitätsschalter gibt es nicht.

    Das Risiko bewerten

    Halte für Dich fest, kurz und in Stichworten:

    • Betrifft mich das? Gibt es diese Stelle in Deinem Code oder in einer Bibliothek, die Du einsetzt?
    • Wo fiele es auf? Beim Übersetzen, im Test, in der Abnahme oder erst in Produktion?
    • Je Anwendungsart: Wie hoch ist das Risiko für einen REST-Microservice, ein Batch-Programm und eine Server-Anwendung (Java EE/Jakarta EE) – gering, mittel oder hoch?
