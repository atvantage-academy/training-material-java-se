    Java-Update/Umstellen und messen
    ca. 40 MinutenVirtual ThreadsPinningJava Flight Recorder

    Umstellen und messen

    Als Entwickler:in, deren Anwendung viel Zeit mit Warten auf andere Systeme verbringt, möchte ich wissen, was virtuelle Threads bei uns bringen und was sie bremst, damit ich die Umstellung begründen und ihre Risiken einschätzen kann.

    Im Altbestand warten zwei Stellen auf Fremdsysteme: Der Batch-Import prüft jede Bestellung bei einer Auskunftei (50 ms), die REST-Schnittstelle fragt für jede neue Bestellung beim Lager nach (100 ms). Beide arbeiten mit einem festen Thread-Pool. Ihr stellt sie um und messt – auf Eurem JDK.

    Lernziele

    Du …

    • misst Batch-Import und REST-Schnittstelle vor und nach der Umstellung und hältst die Werte fest.
    • stellst einen festen Thread-Pool auf virtuelle Threads um.
    • weist mit Java Flight Recorder nach, ob virtuelle Threads gepinnt werden, und behebst es unter Java 21.
    • erkennst, dass nach einem beseitigten Engpass der nächste sichtbar wird.

    Definition of Done

    • Batch-Import und REST-Schnittstelle nutzen virtuelle Threads; ./mvnw clean verify ist grün.
    • Eure Zeile in der Messtabelle im Board ist ausgefüllt – mit JDK-Version.
    • Ihr habt geprüft, ob Pinning auftritt, und könnt die Ursache benennen.
    • Du hast die Reflexionsfragen schriftlich beantwortet.

    Arbeitsschritte

    Ausgangsstand messen

    Du arbeitest auf Deinem Stand nach „Den Visitor ablösen“ oder auf dem Branch loesung/pattern-matching. Bau beide Module und miss sie einmal so, wie sie sind:

    ./mvnw -q install -DskipTests -pl altbestand/bestellung-rest,altbestand/bestellung-batch -am
./mvnw -q -pl altbestand/bestellung-batch exec:java
./mvnw -q -pl altbestand/bestellung-rest exec:java -Dexec.mainClass=bestellung.rest.Lasttest

    Der Batch-Import nennt seine Dauer in der ersten Zeile, der Lasttest am Ende. Trag beide Werte mit Deiner JDK-Version in die Messtabelle ein:

    JDK Stand Batch REST
      fester Pool    
      virtuelle Threads    
      … und was Ihr danach noch ändert    

    Hinweis: Miss jeden Stand zweimal und nimm den zweiten Wert – beim ersten Lauf wärmt sich die JVM noch auf. Vor jeder Messung nach einer Änderung wieder install wie oben.

    Den Batch-Import umstellen

    BestellImport erzeugt einen festen Pool mit Executors.newFixedThreadPool(threads). Stell ihn so um, dass jede Bonitätsprüfung ihren eigenen virtuellen Thread bekommt. Die Poolgröße braucht dann niemand mehr – entferne sie aus dem Konstruktor und aus BatchAnwendung und BestellImportTest.

    Hinweis: Ein ExecutorService ist seit Java 19 AutoCloseable. Mit try-with-resources wartet close(), bis alle Aufgaben fertig sind.

    Miss erneut. Was hast Du erwartet, was kam heraus?

    Die REST-Schnittstelle umstellen

    RestAnwendung gibt dem Server einen festen Pool mit zehn Threads. Gib ihm stattdessen einen Executor, der für jede Anfrage einen virtuellen Thread startet, und miss mit dem Lasttest.

    Ist das Ergebnis so gut, wie die Rechnung verspricht – 200 Anfragen, die alle gleichzeitig 100 ms warten? Wenn nicht: Wo stehen die Anfragen jetzt an? Sieh Dir an, wie RestAnwendung den HttpServer erzeugt, und lies in der Javadoc von HttpServer.create, was der zweite Parameter bedeutet.

    Pinning nachweisen

    Lass den Batch-Import mit Java Flight Recorder laufen und such nach gepinnten virtuellen Threads:

    MAVEN_OPTS="-XX:StartFlightRecording=filename=pinning.jfr" ./mvnw -q -pl altbestand/bestellung-batch exec:java
jfr print --events jdk.VirtualThreadPinned --stack-depth 8 pinning.jfr

    Gibt es Ereignisse? In welcher Methode? Sieh Dir diese Methode an und erkläre, warum der virtuelle Thread dort seinen Träger nicht freigibt. Die Simulation hilft (siehe Ressourcen).

    Hinweis: Unter Windows setzt Du die Variable in PowerShell mit $env:MAVEN_OPTS="-XX:StartFlightRecording=filename=pinning.jfr". jfr liegt im bin-Ordner Deines JDK.

    Mit JDK 21: Behebe das Pinning im eigenen Code – ohne synchronized, mit gleichem Schutz für den Zustand. Miss erneut und prüfe mit JFR, dass keine Ereignisse mehr kommen.

    Mit JDK 25: Du findest keine Ereignisse. Warum nicht? Vergleicht Eure Zahlen mit einem Paar, das JDK 21 hat.

    Kür

    • Mit JDK 25: Schreib in spielwiese/ ein Programm, das mehreren virtuellen Threads je eine Korrelations-ID über einen ScopedValue mitgibt und sie tief in einem Aufruf ausliest, ohne sie als Parameter durchzureichen.
    • Begrenze im Batch-Import die Zahl gleichzeitiger Anfragen an die Auskunftei auf 20, ohne zu einem festen Pool zurückzukehren.

    Hinweis: Die Musterlösung liegt im Branch loesung/virtual-threads, den Unterschied und eine Messtabelle zeigt ihr Pull Request. Sieh erst nach, wenn Du es selbst versucht hast.

    Reflexionsfragen

    • Warum hat das Umstellen auf virtuelle Threads unter JDK 21 im Batch zunächst wenig gebracht – und unter 25 viel?
    • Nach dem Umstellen war die REST-Schnittstelle immer noch nicht so schnell wie erwartet. Was lernt man daraus?
    • Würdet Ihr in Eurer Anwendung alle synchronized durch ReentrantLock ersetzen?
    • Wann bleibt Ihr bei reaktiver Programmierung?
