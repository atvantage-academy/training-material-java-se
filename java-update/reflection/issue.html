    Reflection auf JDK-Interna

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich wissen, was passiert, wenn Code per Reflection auf Interna des JDK zugreift, damit ich solche Stellen – auch in Bibliotheken – vor dem Umstieg erkenne und richtig behandle.

    Lernziele

    • Du erkennst einen Bruch zur Laufzeit, den die starke Kapselung des JDK auslöst.
    • Du setzt --add-opens als Notlösung ein und nennst, wo sie überall stehen muss.
    • Du unterscheidest eine Notlösung von einer Behebung an der Ursache.
    • Du erklärst, warum jdeps diesen Zugriff nicht findet.

    Definition of Done

    • Das Modul kompatibilitaet/reflection übersetzt mit Release 21, und seine Tests sind grün.
    • Die Notlösung steht im Build und ist im Code oder in der pom.xml als Notlösung gekennzeichnet.
    • Du hast notiert, wie die Frage, die der Monitor beantwortet, ohne Reflection zu beantworten wäre.
    • Du hast für REST-Microservice, Batch-Programm und Server-Anwendung je ein Risiko notiert.
    • Du hast die Kontrollfragen beantwortet

    Ein Monitoring soll Listen finden, die viel mehr Platz reservieren, als sie brauchen. Eine öffentliche Methode für die Kapazität einer ArrayList gibt es nicht – also liest der Monitor das interne Feld per Reflection. Prüfe, ob das auf einem neuen JDK noch geht.

    Arbeitsschritte

    Das Problem ansehen

    Öffne im Übungsprojekt das Modul kompatibilitaet/reflection und darin die Klasse Kapazitätsmonitor und ihren Test. Auf welches Feld greift der Monitor zu, und wem gehört es?

    Auf Deinem JDK bauen

    Das Modul wird noch für Java 8 übersetzt. Baue es und lass die Tests laufen:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl kompatibilitaet/reflection -am
    IntelliJ

    Starte die Run Configuration kompatibilitaet-reflection. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration kompatibilitaet-reflection. Sie baut mit clean.

    Der Test ist rot: Eine InaccessibleObjectException verhindert den Zugriff. Auf JDK 8 war er grün. Ein Bruch zur Laufzeit.

    Hinweis: Hast Du zusätzlich ein JDK 8 und in ~/.m2/toolchains.xml eingetragen, kannst Du den Stand vorher selbst sehen. Das Profil jdk8 lässt die Tests auf JDK 8 laufen, übersetzt wird weiter mit Deinem JDK (siehe README des Übungsprojekts):

    mvn clean verify -pl kompatibilitaet/reflection -am -Pjdk8

    Das Release hochstellen

    Öffne kompatibilitaet/reflection/pom.xml und stell die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 21. Baue das Modul erneut, wie oben. Ändert sich etwas?

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell – und der Bruch bleibt unsichtbar.

    Lies die Meldung genau: Welches Modul verweigert den Zugriff, und auf welches Paket?

    Was dahintersteckt

    Seit Java 9 ist das JDK in Module aufgeteilt, und jedes Modul legt fest, welche Pakete es für Reflection öffnet. Bis Java 15 hat das JDK unerlaubte Zugriffe noch mit einer Warnung durchgelassen. Seit Java 16 sind seine Interna standardmäßig gekapselt (JEP 396), seit Java 17 gibt es keinen Schalter mehr, der alles auf einmal öffnet (JEP 403) – LTS-Marke 17.

    Die Notlösung einsetzen

    Öffne das Paket java.util für Deinen Code. Probier es zuerst auf der Kommandozeile:

    mvn clean verify -pl kompatibilitaet/reflection -am "-DargLine=--add-opens java.base/java.util=ALL-UNNAMED"

    In IntelliJ oder Eclipse kopierst Du dazu die Run Configuration kompatibilitaet-reflection und hängst die Option -DargLine=… an die Goals an.

    Der Test wird grün. Trag die Option dann dauerhaft in die pom.xml des Moduls ein und kennzeichne sie dort als Notlösung.

    Lösungsweg

    In die pom.xml kommt das maven-surefire-plugin mit <argLine>--add-opens java.base/java.util=ALL-UNNAMED</argLine>, für ein ausführbares JAR zusätzlich der Manifest-Eintrag Add-Opens: java.base/java.util über das maven-jar-plugin. Ein Kommentar sagt, dass das eine Notlösung ist und warum.

    Die Option muss überall stehen, wo der Code läuft: im Test, im Startskript, im Container. Fehlt sie an einer Stelle, bricht es dort.

    Die Ursache benennen

    Eine Behebung im Code gibt es hier nicht: Das JDK bietet keine öffentliche API für die Kapazität einer ArrayList, und das private Feld darf es jederzeit umbauen. Notiere, wie die Frage „Wie viel Speicher ist reserviert?“ stattdessen zu beantworten wäre – außerhalb des Anwendungscodes.

    Lösungsweg

    Mit Werkzeugen der JVM statt mit Anwendungscode: ein Heap-Histogramm (jcmd «pid» GC.class_histogram) oder eine Aufzeichnung mit Java Flight Recorder. In echten Projekten steckt dieser Bruch fast immer in einer Bibliothek (alte Versionen von Lombok, Mockito, ByteBuddy, Hibernate, XStream) – dort heißt die Behebung: aktualisieren.

    Das Risiko bewerten

    Halte für Dich fest, kurz und in Stichworten:

    • Betrifft mich das? Gibt es diese Stelle in Deinem Code oder in einer Bibliothek, die Du einsetzt?
    • Wo fiele es auf? Beim Übersetzen, im Test, in der Abnahme oder erst in Produktion?
    • Je Anwendungsart: Wie hoch ist das Risiko für einen REST-Microservice, ein Batch-Programm und eine Server-Anwendung (Java EE/Jakarta EE) – gering, mittel oder hoch?

    Reflexionsfragen

    • Warum findet jdeps den Zugriff auf ArrayList.elementData nicht?
    • In echten Projekten steckt dieser Bruch meist nicht im eigenen Code. Wo dann, und wie heißt dort die Behebung?
    • Wann ist --add-opens vertretbar, und was muss dazu festgehalten werden?
    • Was ist das gemeinsame Muster hinter diesem Bruch und dem Wechsel von -source/-target auf --release?
