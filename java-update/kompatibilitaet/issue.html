    Bruchstellen auf Java 21 heben

    Als Entwickler:in in einem Team, das eine Java-8-Anwendung auf Java 21 heben soll, möchte ich wissen, was dabei bricht und wie ich es behebe, damit ich den Aufwand einschätzen kann und kein Bruch erst in Produktion auffällt.

    Lernziele

    • Du stellst das Release eines Maven-Moduls hoch und übersetzt es so neu, dass der Bruch sichtbar wird.
    • Du unterscheidest einen Bruch beim Übersetzen von einem Bruch zur Laufzeit und ordnest jeden einer Änderung im JDK zu.
    • Du behebst einen Bruch an seiner Ursache – oder kennzeichnest eine Notlösung als solche und nennst, wie lange sie trägt.
    • Du prüfst mit jdeprscan und jdeps, ob ein Werkzeug den Bruch vorher gefunden hätte.
    • Du hebst den Altbestand auf Release 21 und wertest die neuen Warnungen des Compilers aus.

    Definition of Done

    • Die Module Deines Pakets übersetzen mit --release 21, und ./mvnw clean verify ist für sie auf Deinem JDK grün.
    • Zu jedem Bruch Deines Pakets steht ein Steckbrief im gemeinsamen Board.
    • Der Altbestand übersetzt mit --release 21, seine Tests sind grün, und der Compiler meldet keine veraltete API mehr.
    • Du hast die Kontrollfragen beantwortet

    Im Ordner kompatibilitaet/ des Übungsprojekts liegt je Bruchstelle ein Modul. Jedes lief auf Java 8 und bricht genau einmal – beim Übersetzen, wenn Du das Release hochstellst, oder zur Laufzeit auf Deinem neuen JDK. Ihr arbeitet zu zweit an einem Paket aus ein oder zwei Modulen.

    Arbeitsschritte

    Dein Paket übernehmen

    Welches Paket Ihr bearbeitet, sagt Euch der Trainer:

    Paket Module
    A jaxb, zeitstempel
    B unterstrich, zeichensatz
    C sequenced, reflection
    D eingeschraenkte-bezeichner, datumsformat
    E security-manager

    Wechselt Euch ab: Eine Person tippt, die andere liest die Meldungen und sucht die Ursache. Nach dem ersten Modul tauscht Ihr.

    Den Bruch sichtbar machen

    Lass das Modul zuerst unverändert auf Deinem JDK laufen – noch übersetzt für Java 8:

    ./mvnw clean verify -pl kompatibilitaet/jaxb

    Ist der Test rot, hast Du einen Bruch zur Laufzeit gefunden. Ist er grün, stell das Release in der pom.xml des Moduls hoch – die Stelle ist markiert – und übersetze erneut. Bricht es jetzt, ist es ein Bruch beim Übersetzen. Finde heraus, ab welchem Release er auftritt; probier dafür auf der Kommandozeile einzelne Werte aus:

    ./mvnw clean verify -pl kompatibilitaet/jaxb -Dmaven.compiler.release=11

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell – und der Bruch bleibt unsichtbar.

    Prüfen, ob ein Werkzeug es vorher gesagt hätte

    Das JDK bringt zwei Werkzeuge mit, die übersetzte Klassen untersuchen, ohne sie auszuführen. Wende beide auf den Startstand Deiner Module an – übersetzt für Java 8, vor jeder Änderung am Code:

    ./mvnw clean package -DskipTests -pl kompatibilitaet/jaxb -Dmaven.compiler.release=8
jdeprscan --release 21 --for-removal kompatibilitaet/jaxb/target/classes
jdeps -verbose:package kompatibilitaet/jaxb/target/classes

    jdeprscan meldet, was zur Entfernung vorgesehen ist, jdeps, wovon die Klassen abhängen – und was es im JDK nicht gibt. Notiere, ob eines der beiden Deinen Bruch gefunden hätte.

    Hinweis: Beide liegen im bin-Ordner Deines JDK. Findet die Kommandozeile sie nicht, rufe sie mit vollem Pfad auf.

    Die Ursache finden

    Lies die Meldung genau und finde die Änderung im JDK, die dahintersteckt: Wie heißt sie, welcher JEP gehört dazu, in welchem Release kam sie, und zu welchem LTS-Release gehört sie damit? Der JEP-Index und die LTS-Evolution helfen dabei (siehe Ressourcen).

    Hinweis: Ein Test kann nach der ersten Korrektur aus einem zweiten Grund rot bleiben. Vergleiche erwarteten und tatsächlichen Wert zeichengenau.

    Den Bruch beheben

    Behebe den Bruch an seiner Ursache, nicht an seinem Symptom. Stell dann das Release in der pom.xml des Moduls auf 21 und prüfe, dass ./mvnw clean verify grün ist.

    Für manche Brüche gibt es einen Kompatibilitätsschalter – eine JVM-Option, die das alte Verhalten zurückholt. Probier ihn aus, wenn es einen gibt. Er ist keine Behebung, sondern eine Notlösung: Notiere, wo er überall stehen müsste und ab welchem Release es ihn nicht mehr gibt.

    Lässt sich ein Bruch im Code nicht beheben, ist das ein legitimes Ergebnis. Dann setzt Ihr die Notlösung ein, kennzeichnet sie im Code als solche und haltet fest, wie man die Ursache stattdessen angehen müsste.

    Hinweis: Wer JDK 25 hat, stellt zum Schluss eines der Module auf --release 25. Bei unterstrich lohnt sich das besonders: Was ist dort ab Java 22 wieder erlaubt, und was nicht?

    Den Steckbrief schreiben

    Halte je Bruch im gemeinsamen Board fest:

    • Symptom – die Meldung, wörtlich
    • Wann – beim Übersetzen oder zur Laufzeit, ab welchem Release
    • Ursache – die Änderung im JDK, mit JEP und LTS-Release
    • Behebung – was Ihr geändert habt
    • Notlösung – falls es eine gibt, und wie lange sie trägt
    • Werkzeug – hätte jdeps oder jdeprscan es gefunden?
    • Betrifft – welche Art von Anwendung am ehesten: REST-Microservice, Batch-Programm, Server-Anwendung

    Den Altbestand hochstellen

    Der Altbestand – die Bestellabwicklung, an der Ihr ab dem nächsten Block arbeitet – übersetzt bisher ebenfalls für Java 8. Stell das Release in der pom.xml im Wurzelordner auf 21 und baue ihn neu:

    ./mvnw clean verify -f altbestand/pom.xml

    Bricht etwas? Lies auch die Warnungen des Compilers: Was meldet er neu, und was kündigt er damit an? Behebe, was er als veraltet meldet.

    Hinweis: Die Musterlösung liegt im Branch loesung/kompatibilitaet, den Unterschied zum Startstand zeigt ihr Pull Request. Sieh erst nach, wenn Du es selbst versucht hast. Wirst Du mit dem Altbestand nicht fertig, checke den Branch aus – ab dem nächsten Block brauchst Du ihn auf Java 21.

    Reflexionsfragen

    • Sechs der neun Brüche zeigt erst die Laufzeit. Was heißt das für den Satz „Es kompiliert mit Java 21, also sind wir fertig“?
    • Wann ist ein Kompatibilitätsschalter wie --add-opens oder -Dfile.encoding=COMPAT vertretbar, und was muss dazu festgehalten werden?
    • Warum findet jdeps den Zugriff auf ArrayList.elementData im Modul reflection nicht?
    • Ist der Wechsel von javax.xml.bind auf jakarta.xml.bind eine Änderung von Java?
    • Welcher der neun Brüche hätte Deine eigene Anwendung getroffen – und wo hättet Ihr ihn bemerkt?
