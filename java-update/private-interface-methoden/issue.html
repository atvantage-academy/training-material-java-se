    Private Interface-Methoden

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich gemeinsamen Code von Default-Methoden verstecken können, damit die öffentliche API eines Interfaces nur das zeigt, was andere aufrufen sollen.

    Lernziele

    • Du ziehst gemeinsamen Code von Default-Methoden in eine private Methode des Interfaces.
    • Du unterscheidest private Instanz- und private statische Methoden in Interfaces.
    • Du begründest, warum eine öffentliche Hilfsmethode in einem Interface zur API gehört.
    • Du bewertest, wo sich der Umbau in Deinem Bestand lohnt.

    Definition of Done

    • Das Modul neuerungen/private-interface-methoden baut mit Release 11, und PreisregelTest ist unverändert grün.
    • Preisregel hat keine öffentliche Hilfsmethode mehr, und die Rechnung mit dem Steuersatz steht nur noch an einer Stelle.
    • Du hast Voraussetzungen, Vorteile, Herausforderungen und den Nutzen je Anwendungsart notiert.
    • Du hast die Kontrollfragen beantwortet

    Seit Java 8 dürfen Interfaces Default-Methoden haben. Teilen sich zwei davon Code, bleibt mit Java 8 nur eine Hilfsmethode, die öffentlich sein muss – und damit zur API des Interfaces gehört. Sieh Dir an, was neuere Releases dafür bieten, und räume die Preisregel des Shops damit auf.

    Arbeitsschritte

    Worum es geht

    Seit Java 9 darf ein Interface private Methoden haben, als Instanz- und als statische Methode (JEP 213, „Milling Project Coin“, LTS-Marke 11). Sie sind nur innerhalb des Interfaces sichtbar und dienen dem gemeinsamen Code seiner Default-Methoden. Wo das in der Geschichte von Java steht, zeigt die LTS-Evolution.

    Das Release hochstellen

    Öffne im Übungsprojekt das Modul neuerungen/private-interface-methoden. Stell in seiner pom.xml die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 11. Baue das Modul danach:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl neuerungen/private-interface-methoden -am
    IntelliJ

    Starte die Run Configuration neuerungen-private-interface-methoden. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration neuerungen-private-interface-methoden. Sie baut mit clean.

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell.

    Der Build ist grün: Code im Stil von Java 8 übersetzt auch mit Release 11.

    Ausprobieren

    Im Modul liegt unter beispiel/ das Programm Hilfsmethoden.java. Es gehört zu keinem Build, Java startet es direkt aus dem Quelltext:

    Kommandozeile

    Starte das Beispiel im Wurzelordner des Übungsprojekts:

    java neuerungen/private-interface-methoden/beispiel/Hilfsmethoden.java
    IntelliJ

    Öffne über View → Tool Windows → Terminal ein Terminal im Wurzelordner des Projekts und starte das Beispiel dort mit dem Befehl aus dem Reiter „Kommandozeile“. Das Beispiel gehört zu keinem Build und hat deshalb keine Run Configuration.

    Eclipse

    Öffne über Window → Show View → Terminal ein Terminal im Wurzelordner des Projekts und starte das Beispiel dort mit dem Befehl aus dem Reiter „Kommandozeile“. Das Beispiel gehört zu keinem Build und hat deshalb keine Run Configuration.

    Lies den Quelltext und die Ausgabe:

    • Welche Methoden des Interfaces Gruß sind privat, und wer ruft sie auf?
    • Nimm die Kommentarzeichen vor der markierten Zeile in main weg und starte noch einmal. Was meldet der Compiler?
    • Darf eine private Interface-Methode zugleich default sein? Probiere es aus.

    Die Vorlage umbauen

    Das Interface Preisregel im selben Modul ist im Stil von Java 8 geschrieben: Beide Default-Methoden rechnen den Steuersatz auf, und gerundet wird über eine öffentliche statische Methode. Baue es so um, dass die Hilfsmethoden privat sind und die Rechnung mit dem Steuersatz nur noch an einer Stelle steht. PreisregelTest sichert das Verhalten ab – er bleibt unverändert und muss grün bleiben. Baue danach das Modul erneut.

    Lösungsweg
    • aufCentRunden wird private static; die Aufrufe heißen dann einfach aufCentRunden(…).
    • Eine neue private BigDecimal mitSteuer(BigDecimal netto) rechnet aufCentRunden(netto.multiply(BigDecimal.ONE.add(steuersatz()))).
    • brutto liefert mitSteuer(netto), bruttoMitRabatt rechnet den Rabatt ab und ruft danach ebenfalls mitSteuer.

    Das Interface bleibt funktional: Es hat weiter genau eine abstrakte Methode.

    Bewerten

    Halte für Dich fest, kurz und in Stichworten:

    • Voraussetzungen: Welches Release brauchen alle, die den Code bauen und betreiben?
    • Vorteile: Was wird an der API des Interfaces klarer?
    • Herausforderungen: Was passiert mit Aufrufern einer Hilfsmethode, die bisher öffentlich war?
    • Betrifft mich das? Wie hoch ist der Nutzen für einen REST-Microservice, ein Batch-Programm und eine Server-Anwendung (Java EE/Jakarta EE) – gering, mittel oder hoch?

    Reflexionsfragen

    • Eine öffentliche statische Hilfsmethode wird privat. Wer könnte sie bisher aufgerufen haben, und woran merkst Du das?
    • Wann gehört gemeinsamer Code in eine private Interface-Methode, wann in eine abstrakte Klasse?
    • Was ändert sich für Klassen, die das Interface umsetzen – müssen sie neu übersetzt werden?
