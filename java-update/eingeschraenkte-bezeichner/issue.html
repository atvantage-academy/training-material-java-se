    Eingeschränkte Bezeichner (yield)

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich wissen, welche neuen Wörter der Sprache mit meinen Bezeichnern kollidieren, damit ich nicht unnötig umbenenne und nichts übersehe.

    Lernziele

    • Du machst einen Bruch beim Übersetzen sichtbar, der nur eine bestimmte Schreibweise trifft.
    • Du unterscheidest eingeschränkte Bezeichner von Schlüsselwörtern.
    • Du behebst den Bruch mit einem neuen Namen oder einem qualifizierten Aufruf.
    • Du begründest, warum var, record und yield als Variablennamen weiter übersetzen.

    Definition of Done

    • Das Modul kompatibilitaet/eingeschraenkte-bezeichner übersetzt mit Release 21, und seine Tests sind grün.
    • Die Variablen var, record und yield in Protokoll sind unverändert.
    • Du hast für REST-Microservice, Batch-Programm und Server-Anwendung je ein Risiko notiert.
    • Du hast die Kontrollfragen beantwortet

    Mit neuen Sprachmitteln kommen neue Wörter in die Sprache: var, yield, record, sealed, permits. Damit alter Code weiter übersetzt, sind die meisten davon keine Schlüsselwörter, sondern eingeschränkte Bezeichner – erlaubt, nur nicht überall. Prüfe an einem Modul, wo die Grenze verläuft.

    Arbeitsschritte

    Das Problem ansehen

    Öffne im Übungsprojekt das Modul kompatibilitaet/eingeschraenkte-bezeichner. Die Klasse Erzeuger hat eine Methode yield(…), die Unterklasse Quadratzahlen ruft sie auf. In Protokoll heißen Variablen var, record und yield. Welche dieser Stellen hältst Du für gefährdet?

    Auf Java 8 bauen

    Das Modul wird noch für Java 8 übersetzt. Baue es und lass die Tests laufen:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl kompatibilitaet/eingeschraenkte-bezeichner -am
    IntelliJ

    Starte die Run Configuration kompatibilitaet-eingeschraenkte-bezeichner. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration kompatibilitaet-eingeschraenkte-bezeichner. Sie baut mit clean.

    Der Build ist grün.

    Das Release hochstellen

    Öffne kompatibilitaet/eingeschraenkte-bezeichner/pom.xml und stell die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 21. Baue das Modul danach erneut:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl kompatibilitaet/eingeschraenkte-bezeichner -am
    IntelliJ

    Starte die Run Configuration kompatibilitaet-eingeschraenkte-bezeichner. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration kompatibilitaet-eingeschraenkte-bezeichner. Sie baut mit clean.

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell – und der Bruch bleibt unsichtbar.

    Jetzt übersetzt das Modul nicht mehr. Welche Zeile meldet der Compiler – die Deklaration der Methode, ihren Aufruf oder die Variablen in Protokoll?

    Was dahintersteckt

    Seit Java 14 liefert yield den Wert eines Zweigs einer Switch-Expression – JEP 361, LTS-Marke 17. Ein unqualifizierter Aufruf yield(x) liest sich für den Compiler deshalb als diese Anweisung, nicht als Methodenaufruf. Java 13 hat das mit einer Warnung angekündigt.

    yield ist aber kein Schlüsselwort, sondern ein eingeschränkter Bezeichner. Als Variablen- oder Methodenname bleibt er erlaubt; nur der unqualifizierte Aufruf ist mehrdeutig. Ähnlich var und record: Sie sind nur als Typname verboten.

    Den Bruch beheben

    Sorg dafür, dass der Aufruf wieder eindeutig ist, und baue das Modul mit Release 21, bis die Tests grün sind. Protokoll lässt Du dabei, wie es ist.

    Lösungsweg

    Die saubere Lösung: Die Methode bekommt einen neuen Namen, etwa liefere(…), und alle Aufrufer ziehen mit. Kleiner, aber unschöner ist der qualifizierte Aufruf this.yield(…) – er übersetzt, lässt aber den missverständlichen Namen stehen. Einen Kompatibilitätsschalter gibt es nicht.

    Das Risiko bewerten

    Halte für Dich fest, kurz und in Stichworten:

    • Betrifft mich das? Gibt es diese Stelle in Deinem Code oder in einer Bibliothek, die Du einsetzt?
    • Wo fiele es auf? Beim Übersetzen, im Test, in der Abnahme oder erst in Produktion?
    • Je Anwendungsart: Wie hoch ist das Risiko für einen REST-Microservice, ein Batch-Programm und eine Server-Anwendung (Java EE/Jakarta EE) – gering, mittel oder hoch?

    Reflexionsfragen

    • Warum bricht der Aufruf yield(…), aber nicht die Deklaration der Methode?
    • Was unterscheidet einen eingeschränkten Bezeichner wie var oder yield von einem Schlüsselwort wie _?
    • Welche Umbenennung ist die bessere: liefere(…) oder this.yield(…)? Woran machst Du das fest?
    • Wie wahrscheinlich ist dieser Bruch in Deinem Bestand, und welche Namen würdest Du darin suchen?
