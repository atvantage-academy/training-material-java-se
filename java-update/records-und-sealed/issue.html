    Die Bestelldomäne modellieren

    Als Entwickler:in, die ein gewachsenes Datenmodell pflegt, möchte ich Wertklassen ohne Boilerplate schreiben und dem Compiler sagen können, welche Unterarten es gibt, damit das Modell kürzer wird und Fehler beim Übersetzen statt im Betrieb auffallen.

    Im Altbestand stecken in altbestand/bestellung-domaene Klassen, wie man sie mit Java 8 schrieb: Position und Kunde mit handgeschriebenem equals, hashCode und toString, dazu eine abstrakte Klasse Zahlart mit vier Unterklassen, deren Javadoc zugibt: „Sicherstellen lässt sich das mit Java 8 nicht.“ Ihr baut das Modell um – sein Verhalten bleibt gleich.

    Lernziele

    Du …

    • machst aus einer Wertklasse einen Record und verlegst ihre Prüfungen in den kompakten Konstruktor.
    • versiegelst eine Hierarchie mit sealed und permits.
    • erkennst, wo das automatisch erzeugte toString eines Records schadet, und schreibst es dort selbst.
    • begründest, warum eine Klasse mit Identität und veränderlichem Zustand kein Record wird.

    Definition of Done

    • Position, Kunde und die vier Zahlarten sind Records.
    • Zahlart ist versiegelt und erlaubt genau diese vier.
    • DomänenmodellTest und alle bisherigen Tests sind grün: ./mvnw clean verify.
    • Du hast die Reflexionsfragen schriftlich beantwortet.

    Arbeitsschritte

    Ausgangsstand und Absicherung

    Du arbeitest auf Deinem Stand nach „Bau Dein eigenes STR“ oder auf dem Branch loesung/sprachmittel. Leg zuerst einen Test an, der festhält, was das Modell zusagt – DomänenmodellTest in altbestand/bestellung-domaene/src/test/java/bestellung/domaene/:

    package bestellung.domaene;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

import java.math.BigDecimal;
import java.time.YearMonth;

import org.junit.jupiter.api.Test;

class DomänenmodellTest {

    @Test
    void positionenMitGleichenWertenSindGleich() {
        var a = new Position("A-100", "Kaffeebohnen, 1 kg", 2, new BigDecimal("18.90"));
        var b = new Position("A-100", "Kaffeebohnen, 1 kg", 2, new BigDecimal("18.90"));
        assertEquals(a, b);
        assertEquals(a.hashCode(), b.hashCode());
    }

    @Test
    void einePositionOhneMengeGibtEsNicht() {
        assertThrows(IllegalArgumentException.class,
                () -> new Position("A-100", "Kaffeebohnen, 1 kg", 0, new BigDecimal("18.90")));
    }

    @Test
    void einenKundenOhneNamenGibtEsNicht() {
        assertThrows(NullPointerException.class, () -> new Kunde("K-1001", null, null));
    }

    @Test
    void dieKreditkarteVerrätIhreNummerNicht() {
        var karte = new Kreditkarte("4111 1111 1111 1111", YearMonth.of(2028, 3));
        assertFalse(karte.toString().contains("4111 1111"), karte.toString());
    }

    @Test
    void esGibtGenauVierZahlarten() {
        assertTrue(Zahlart.class.isSealed());
        assertEquals(4, Zahlart.class.getPermittedSubclasses().length);
    }
}

    ./mvnw clean verify -pl altbestand/bestellung-domaene

    Vier der fünf Tests sind grün. Der letzte ist rot – das ändert diese Übung.

    Positionen und Kunden als Records

    Mach aus Position einen Record. Die Prüfungen aus dem Konstruktor gehören in einen kompakten Konstruktor; getSumme() wird zu einer gewöhnlichen Methode summe(). Danach dasselbe für Kunde.

    Die Zugriffsmethoden eines Records heißen wie seine Komponenten – artikelnummer(), nicht getArtikelnummer(). Alle Aufrufer in Domäne, REST-Schnittstelle, Batch und Tests müssen nachziehen.

    Hinweis: Lass die IDE die Arbeit machen. In IntelliJ IDEA wandelt „Convert to record class“ die Klasse um und benennt die Aufrufer gleich mit.

    Die Zahlarten versiegeln

    Mach aus der abstrakten Klasse Zahlart ein versiegeltes Interface, das genau Rechnung, Lastschrift, Kreditkarte und PayPal erlaubt, und aus den vier Unterklassen Records. Die Methode accept für den Visitor bleibt.

    Hinweis: Ein Record kann keine Klasse erweitern, nur Interfaces umsetzen.

    Jetzt ist ein Test rot, der vorher grün war. Lies seine Meldung: Was hat der Record von sich aus anders gemacht als die alte Klasse? Behebe es.

    Ausprobieren: eine fünfte Zahlart

    Leg im Paket bestellung.domaene einen Record Gutschein(String code) an, der Zahlart umsetzt, und übersetze. Lies die Meldung des Compilers. Lösch den Gutschein danach wieder.

    Und die Bestellung?

    Sieh Dir Bestellung an. Sollte sie auch ein Record werden? Probier es nicht aus – begründe Deine Antwort mit dem, was beim Stornieren passiert, und mit ihrem equals.

    Hinweis: Die Musterlösung liegt im Branch loesung/records-und-sealed, den Unterschied zeigt ihr Pull Request. Sieh erst nach, wenn Du es selbst versucht hast. Wirst Du nicht fertig, checke den Branch aus – die nächste Übung setzt darauf auf.

    Reflexionsfragen

    • Warum bleibt Bestellung eine Klasse?
    • Warum musste Kreditkarte ihr toString behalten?
    • Was hat die Versiegelung von Zahlart heute schon gebracht – und was könnte sie bringen, wenn man über die Zahlarten eine Fallunterscheidung schreibt?
    • Wo in Eurem Projekt würdet Ihr Records einsetzen – und wo auf keinen Fall?
