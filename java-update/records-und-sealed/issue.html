    Records

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich Wertklassen ohne handgeschriebenes equals, hashCode und toString ausdrücken, damit nur die Fachlichkeit im Code steht.

    Lernziele

    • Du schreibst einen Record mit kompaktem Konstruktor für die Prüfungen.
    • Du benennst, was der Compiler für einen Record erzeugt und was ein Record nicht kann.
    • Du erkennst, wo das erzeugte toString schadet, und schreibst es dort selbst.
    • Du begründest, warum eine Klasse mit Identität und veränderlichem Zustand kein Record wird.

    Definition of Done

    • Das Modul neuerungen/records baut mit Release 17, und WertklassenTest ist unverändert grün.
    • Position, Kunde und Kreditkarte sind Records; Bestellung ist eine Klasse geblieben.
    • Du hast Voraussetzungen, Vorteile, Herausforderungen und den Nutzen je Anwendungsart notiert.
    • Du hast die Kontrollfragen beantwortet

    Mit Java 8 schreibt man eine Wertklasse mit vier Feldern in siebzig Zeilen: Konstruktor, Getter, equals, hashCode, toString. Fachlich ist davon kaum etwas. Sieh Dir an, was neuere Releases dafür mitbringen, und bau solche Klassen damit um.

    Arbeitsschritte

    Worum es geht

    Ein Record ist ein Datenträger mit festgelegten Komponenten: record Position(String artikelnummer, int menge, …). Konstruktor, Zugriffsmethoden, equals, hashCode und toString erzeugt der Compiler. Records sind seit Java 16 final (JEP 395, nach Previews in 14 und 15) und tragen die LTS-Marke 17. Was der Compiler erzeugt – und was er bewusst weglässt –, zeigt die Visualisierung Records.

    Das Release hochstellen

    Öffne im Übungsprojekt das Modul neuerungen/records. Stell in seiner pom.xml die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 17. Baue das Modul danach:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl neuerungen/records -am
    IntelliJ

    Starte die Run Configuration neuerungen-records. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration neuerungen-records. Sie baut mit clean.

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell.

    Der Build ist grün: Code im Stil von Java 8 übersetzt auch mit Release 17.

    Ausprobieren

    Im Modul liegt unter beispiel/ das Programm Wertobjekte.java. Es gehört zu keinem Build, Java startet es direkt aus dem Quelltext:

    Kommandozeile

    Starte das Beispiel im Wurzelordner des Übungsprojekts:

    java neuerungen/records/beispiel/Wertobjekte.java
    IntelliJ

    Öffne über View → Tool Windows → Terminal ein Terminal im Wurzelordner des Projekts und starte das Beispiel dort mit dem Befehl aus dem Reiter „Kommandozeile“. Das Beispiel gehört zu keinem Build und hat deshalb keine Run Configuration.

    Lies den Quelltext und die Ausgabe:

    • Wie heißen die Zugriffsmethoden von Geldbetrag, und wo steht die Zuweisung der Felder im kompakten Konstruktor?
    • Warum enthält die Lieferung am Ende zwei Artikel, die SichereLieferung nur einen?

    Die Vorlage umbauen

    Im selben Modul stehen Position, Kunde und Kreditkarte im Stil von Java 8, dazu Bestellung und Rechnungstext, die sie benutzen. Mach aus den drei Wertklassen Records:

    • Die Prüfungen aus den Konstruktoren gehören in einen kompakten Konstruktor.
    • getSumme() wird zur gewöhnlichen Methode summe().
    • Die Zugriffsmethoden eines Records heißen wie seine Komponenten – artikelnummer(), nicht getArtikelnummer(). Die Aufrufer in Bestellung und Rechnungstext ziehen nach.

    WertklassenTest sichert das Verhalten ab – er bleibt unverändert und muss grün bleiben. Baue danach das Modul erneut. Wird dabei ein Test rot, lies seine Meldung: Was macht der Record von sich aus anders als die alte Klasse?

    Hinweis: Die IDE nimmt Dir die Umwandlung ab, sobald das Projekt Release 17 kennt (in IntelliJ nach dem Neuladen des Maven-Projekts). IntelliJ IDEA markiert die Klasse über die Inspektion „Class can be record class“; mit Alt + Enter auf dem Klassennamen wählst Du „Convert to record class“. Ist dort „Suggest renaming accessor methods“ eingeschaltet (Standard), benennt IntelliJ getX() in x() um – samt Aufrufern. Eclipse bietet ab Version 2026-03 Refactor → Convert Class to Record an, auch als Quick Assist mit Strg + 1.

    • Kunde wird ebenso ein Record; der kompakte Konstruktor prüft Kundennummer und Namen, die E-Mail-Adresse darf null sein.
    • Kreditkarte wird ein Record mit eigenem toString: Das erzeugte zeigt die volle Kartennummer, und dieKreditkarteVerrätIhreNummerNicht wird rot.
    • In Bestellung und Rechnungstext werden aus getMenge(), getSumme(), getKartennummer() … die Aufrufe menge(), summe(), kartennummer() ….
    • Bestellung bleibt eine Klasse – warum, fragt die Reflexion.

    Bewerten

    Halte für Dich fest, kurz und in Stichworten:

    • Voraussetzungen: Welches Release brauchen alle, die den Code bauen und betreiben? Kennen Eure Frameworks Records – beim Serialisieren nach JSON, beim Binden von Formularen, beim Persistieren?
    • Vorteile: Wie viel Code fällt weg, und welche Fehler kann man in equals und hashCode jetzt nicht mehr machen?
    • Herausforderungen: Wo stört, dass jeder Aufrufer x() statt getX() schreibt, und wo das erzeugte toString?
    • Betrifft mich das? Wie hoch ist der Nutzen für einen REST-Microservice, ein Batch-Programm und eine Server-Anwendung (Java EE/Jakarta EE) – gering, mittel oder hoch?

    Reflexionsfragen

    • Warum bleibt Bestellung eine Klasse? Denk an stornieren() und an ihr equals.
    • Ein Record ist nur flach unveränderlich. Wann merkt man das, und was hilft?
    • Euer Framework erwartet Getter nach JavaBeans-Konvention oder einen Konstruktor ohne Parameter. Was heißt das für Records an dieser Stelle?
