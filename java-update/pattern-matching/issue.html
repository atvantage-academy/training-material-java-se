    Pattern Matching

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich Fallunterscheidungen über Typen ohne Casts schreiben, damit sie kürzer werden und der Compiler mehr davon prüft.

    Lernziele

    • Du ersetzt ein instanceof mit anschließendem Cast durch ein instanceof mit Muster.
    • Du schreibst einen switch über Typ-Muster mit case null und einem Wächter (when).
    • Du ordnest die Fälle so, dass kein Fall einen späteren verdeckt, und liest die Meldung des Compilers, wenn doch.
    • Du zerlegst einen Record mit einem Record-Pattern.
    • Du begründest, warum ein switch über eine offene Hierarchie einen default braucht.

    Definition of Done

    • Das Modul neuerungen/pattern-matching baut mit Release 21, und ZahlartBeschreibungTest ist unverändert grün.
    • ZahlartBeschreibung.beschreibe ist eine Switch-Expression über Typ-Muster, ohne Cast und ohne instanceof-Kette.
    • Du hast Voraussetzungen, Vorteile, Herausforderungen und den Nutzen je Anwendungsart notiert.
    • Du hast die Kontrollfragen beantwortet

    Mit Java 8 prüft man den Typ eines Objekts mit instanceof und castet danach – zweimal dasselbe, und der Cast kann trotzdem schiefgehen, wenn jemand die Bedingung ändert. Sieh Dir an, was neuere Releases dafür mitbringen, und bau eine solche Fallunterscheidung damit um.

    Arbeitsschritte

    Worum es geht

    Pattern Matching prüft den Typ und bindet das Ergebnis in einem Schritt: if (zahlart instanceof Rechnung rechnung). Das gibt es seit Java 16 (JEP 394, LTS 17). Seit Java 21 geht dasselbe im switch (JEP 441), samt case null und Wächtern mit when, und Record-Patterns zerlegen einen Record gleich in seine Komponenten (JEP 440) – beides LTS 21. Wie sich dasselbe Stück Code über die Releases verändert, zeigt die Pattern-Matching-Evolution.

    Das Release hochstellen

    Öffne im Übungsprojekt das Modul neuerungen/pattern-matching. Stell in seiner pom.xml die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 21. Baue das Modul danach:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl neuerungen/pattern-matching -am
    IntelliJ

    Starte die Run Configuration neuerungen-pattern-matching. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration neuerungen-pattern-matching. Sie baut mit clean.

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell.

    Der Build ist grün: Code im Stil von Java 8 übersetzt auch mit Release 21.

    Die Vorlage umbauen

    Die Klasse ZahlartBeschreibung im selben Modul beschreibt eine Zahlart mit einer Kette aus instanceof und Casts. Bau sie in zwei Schritten um, damit Du den Unterschied siehst:

    1. Ersetze jedes instanceof mit anschließendem Cast durch ein instanceof mit Muster.
    2. Mach daraus eine Switch-Expression über Typ-Muster. Die Rechnung ohne Zahlungsziel wird ein eigener Fall mit when, die fehlende Zahlart ein case null.

    ZahlartBeschreibungTest sichert das Verhalten ab – er bleibt unverändert und muss grün bleiben, auch für die unbekannte Zahlart. Baue danach das Modul erneut.

    Lösungsweg 
    return switch (zahlart) {
    case null -> "keine Zahlart angegeben";
    case Rechnung rechnung when rechnung.getZahlungszielTage() == 0 -> "Rechnung, sofort zahlbar";
    case Rechnung rechnung -> "Rechnung, zahlbar innerhalb von " + rechnung.getZahlungszielTage() + " Tagen";
    case Lastschrift lastschrift -> "Lastschrift von " + maskiere(lastschrift.getIban());
    case Kreditkarte kreditkarte -> "Kreditkarte " + maskiere(kreditkarte.getKartennummer())
            + ", gültig bis " + kreditkarte.getGültigBis().format(MONAT_JAHR);
    case PayPal payPal -> "PayPal (" + payPal.getKonto() + ")";
    default -> throw new IllegalArgumentException("Unbekannte Zahlart: " + zahlart);
};
    • Der Fall mit when steht vor dem allgemeinen Rechnung-Fall; umgekehrt meldet der Compiler, dass der Fall verdeckt ist.
    • Der default bleibt: Jede Klasse darf eine weitere Zahlart von Zahlart ableiten, der Compiler kennt also nicht alle Fälle. Ohne default übersetzt der switch nicht.
    • Record-Patterns wie case Rechnung(var tage) gehen hier nicht: Die Zahlarten sind Klassen, keine Records.

    Bewerten

    Halte für Dich fest, kurz und in Stichworten:

    • Voraussetzungen: Welches Release brauchen alle, die den Code bauen und betreiben – für instanceof mit Muster, für den switch, für Record-Patterns?
    • Vorteile: Was fällt weg, und welche Fehler meldet der Compiler jetzt?
    • Herausforderungen: Wo bleibt der default nötig, und was verdeckt er?
    • Betrifft mich das? Wie hoch ist der Nutzen für einen REST-Microservice, ein Batch-Programm und eine Server-Anwendung (Java EE/Jakarta EE) – gering, mittel oder hoch?

    Reflexionsfragen

    • Was passiert mit Deinem switch, wenn jemand eine neue Unterklasse von Zahlart anlegt – und wann merkst Du es?
    • Wann ist eine Methode in der Klasse besser als ein switch von außen?
    • Was ändert sich mit einem switch über zahlart, wenn zahlart null ist und es keinen case null gibt?
