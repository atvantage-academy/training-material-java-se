    Den Altbestand auf dem eigenen JDK bauen

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich wissen, mit welchem JDK ich arbeite und was es aus altem Code macht, damit ich beim Umstieg weiß, wovon ich ausgehe.

    Das Übungsprojekt enthält im Ordner altbestand/ eine Bestellabwicklung, wie sie mit Java 8 geschrieben wurde. Du baust sie jetzt zum ersten Mal – auf Deinem eigenen, neuen JDK.

    Lernziele

    Du …

    • bestimmst Anbieter, Feature-Release und Update Deines JDK und findest heraus, bis wann es gepflegt wird.
    • baust den Altbestand auf Deinem JDK und prüfst, für welche Java-Version der Bytecode übersetzt ist.
    • zeigst am Beispiel, dass --release die genutzte API prüft und -source/-target nicht.

    Definition of Done

    • Anbieter, Versionsnummer und Supportende Deines JDK stehen im gemeinsamen Board.
    • ./mvnw clean verify -f altbestand/pom.xml ist auf Deinem JDK grün.
    • Du weißt, welche major version der übersetzte Altbestand hat und was sie bedeutet.
    • Du hast eine Klasse einmal mit --release 8 und einmal mit -source 8 -target 8 übersetzt und kannst den Unterschied erklären.

    Arbeitsschritte

    Dein JDK kennenlernen

    Arbeite im Wurzelordner des Übungsprojekts auf dem Branch main. Lass Dir zeigen, womit Du arbeitest:

    java -version
java spielwiese/Versionsinfo.java

    Zerlege die Versionsnummer: Was ist das Feature-Release, was das Update? Ist es das neueste Update – oder liegst Du ein paar Quartale zurück? Such dann heraus, bis wann Dein Anbieter dieses Release mit Updates versorgt (siehe Ressourcen; für andere Anbieter deren Website). Trag Anbieter, Versionsnummer und Supportende ins Board ein.

    Hinweis: java spielwiese/Versionsinfo.java startet ein Programm direkt aus dem Quelltext, ohne javac vorher. Das geht seit Java 11.

    Den Altbestand bauen

    ./mvnw clean verify -f altbestand/pom.xml

    Unter Windows heißt der Aufruf mvnw.cmd. Ist der Build grün, sieh nach, welchen Bytecode Dein JDK erzeugt hat:

    javap -v altbestand/bestellung-domaene/target/classes/bestellung/domaene/Bestellung.class

    Such in der Ausgabe die Zeile major version. Jede Java-Version hat ihre eigene Nummer:

    Java 8 11 17 21 25
    major version 52 55 61 65 69

    Warum ist es nicht die Nummer Deines JDK? Sieh in der pom.xml im Wurzelordner nach.

    Hinweis: Findet die Kommandozeile javap nicht, liegt nur eine JRE im Pfad oder das JDK ist nur in der IDE eingetragen. Ruf es dann mit dem vollen Pfad zum bin-Ordner Deines JDK auf.

    --release gegen -source und -target

    Leg in spielwiese/ eine Datei Leerzeile.java an:

    public class Leerzeile {
    public static void main(String[] args) {
        String zeile = "   ";
        System.out.println("Leer? " + zeile.isBlank());
    }
}

    String.isBlank() gibt es seit Java 11. Übersetze die Klasse zweimal für Java 8 – einmal auf die neue, einmal auf die alte Art:

    javac --release 8 -d spielwiese/target/release spielwiese/Leerzeile.java
javac -source 8 -target 8 -d spielwiese/target/source-target spielwiese/Leerzeile.java

    Lies alle Meldungen, auch die Warnungen. Welcher Aufruf übersetzt? Starte, was übersetzt wurde:

    java -cp spielwiese/target/source-target Leerzeile

    Es läuft – auf Deinem JDK. Was würde passieren, wenn diese Klasse auf einem Server mit Java 8 liefe? Die Antwort zeigt der Trainer.

    Hinweis: Der Ordner target/ ist von Git ausgenommen – die übersetzten Klassen landen nicht im Repository.

    Kür: Wie weit zurück reicht Dein JDK?

    Übersetze dieselbe Klasse mit --release 7. Was sagt javac – und was kündigt die Warnung an, die bei --release 8 erscheint?

    Reflexionsfragen

    • Der Altbestand ist mit Deinem JDK gebaut und seine Tests sind grün. Ist er damit auf Java 21?
    • Warum warnt javac auch bei --release 8, der Wert sei „obsolete“ – und was bedeutet das für ein Team, das bei Java 8 bleiben will?
    • Warum gehört ein Preview-Feature nicht in Produktion?
