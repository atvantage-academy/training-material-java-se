Datenorientierte Programmierung

Warum Records, Sealed Classes und Pattern Matching zusammengehören · Java-Update

Viel Code trägt nur Daten von A nach B

Schnittstellen

JSON rein, JSON raus: die Bestellung als DTO – ohne eigenes Verhalten

Ereignisse

„Bestellung angelegt“, „Zahlung eingegangen“ – Fakten, die sich nicht mehr ändern

Ergebnisse mit Varianten

Gefunden, nicht gefunden, mehrdeutig – statt null und Ausnahmen

Zustände

Offen, bezahlt, erstattet – je Zustand nur die Daten, die dazugehören

Befehle und Regeln

Kommandozeilenoptionen, Filter, Rechenausdrücke – ein Baum aus Fällen

Werte

Geldbetrag, Zeitraum, IBAN – einmal geprüft, danach unveränderlich

Und genau dort tut Java-8-Code weh

  • Zeremonie: 50 Zeilen Klasse für drei Felder – Konstruktor, Getter, equals, hashCode, toString
  • Halbe Zustände: Felder, die nur manchmal gelten – und sonst null sind
  • Blinde Fallunterscheidung: Eine neue Variante übersieht die instanceof-Kette still
  • Umwege: der Visitor, damit der Compiler wenigstens irgendetwas prüft

Dieselbe Frage, zwei Antworten

Objektorientiert

interface Zahlart {
    String beschreibe();
}

final class Rechnung implements Zahlart {
    private final int tage;
    // Konstruktor …
    public String beschreibe() {
        return "zahlbar in " + tage + " Tagen";
    }
}

Datenorientiert

sealed interface Zahlart
        permits Rechnung, PayPal { }
record Rechnung(int tage) implements Zahlart { }
record PayPal(String konto) implements Zahlart { }

String beschreibe(Zahlart zahlart) {
    return switch (zahlart) {
        case Rechnung(var tage) -> "zahlbar in " + tage + " Tagen";
        case PayPal(var konto)  -> "PayPal (" + konto + ")";
    };
}
  • Objektorientiert wohnt das Verhalten im Typ
  • Datenorientiert sind die Daten nur Daten – die Operation steht daneben

Wer leicht wachsen darf, entscheidet das Modell

  • Philip Wadler, 1998: das Expression Problem – kein Modell macht beides billig
  • Datenorientiert lohnt sich, wo die Fälle feststehen und die Operationen wachsen

Die Idee ist älter als Java

  • Aus der funktionalen Programmierung: algebraische Datentypen und Muster darauf
  • Scala und Kotlin hatten es vor Java – Java holt es im Projekt Amber nach

Zwei Bausteine: UND und ODER

record Kreditkarte(String nummer, YearMonth gültigBis) implements Zahlart { }
sealed interface Zahlart permits Rechnung, Lastschrift, Kreditkarte, PayPal { }
  • Ein Record ist ein Produkttyp, ein versiegelter Typ ein Summentyp

Vier Grundsätze – und was Java dafür hat

Grundsatz In Java
Modelliere die Daten, die ganzen Daten und nichts als die Daten record – die Komponenten sind die ganze Klasse
Daten sind unveränderlich Die Felder eines Records sind final
Prüfe an der Grenze Der kompakte Konstruktor prüft einmal, beim Erzeugen
Mache ungültige Zustände nicht darstellbar sealed – je Zustand ein eigener Record

Brian Goetz: „Data Oriented Programming in Java“, InfoQ, Juni 2022

Ungültige Zustände gar nicht erst bauen können

Vorher

class Zahlung {
    Status status;        // OFFEN, BEZAHLT, ERSTATTET
    LocalDate bezahltAm;  // nur bei BEZAHLT, ERSTATTET
    BigDecimal erstattet; // nur bei ERSTATTET
}

Nachher

sealed interface Zahlung
        permits Offen, Bezahlt, Erstattet { }
record Offen() implements Zahlung { }
record Bezahlt(LocalDate am) implements Zahlung { }
record Erstattet(LocalDate am, BigDecimal betrag)
        implements Zahlung { }
  • Vorher sagt nur ein Kommentar, welche Felder gelten
  • Nachher lässt sich „erstattet, aber nie bezahlt“ nicht einmal hinschreiben

„Make illegal states unrepresentable“ – Yaron Minsky, „Effective ML“ (Jane Street)

Alles zusammen

sealed interface Zahlart permits Rechnung, Lastschrift, Kreditkarte, PayPal { }
record Rechnung(int tage) implements Zahlart { }
record Lastschrift(String iban) implements Zahlart { }
record Kreditkarte(String nummer, YearMonth gültigBis) implements Zahlart { }
record PayPal(String konto) implements Zahlart { }

static String beschreibe(Zahlart zahlart) {
    return switch (zahlart) {
        case Rechnung(var tage) when tage == 0 -> "Rechnung, sofort zahlbar";
        case Rechnung(var tage) -> "Rechnung, zahlbar in " + tage + " Tagen";
        case Lastschrift(var iban) -> "Lastschrift von " + iban;
        case Kreditkarte(var nummer, var gültigBis) -> "Kreditkarte bis " + gültigBis;
        case PayPal(var konto) -> "PayPal (" + konto + ")";
    };   // kein default: Eine neue Zahlart ist ein Übersetzungsfehler
}

Kein Ersatz für Objektorientierung

Klasse mit Verhalten

  • Fachobjekte mit Identität und Zustand – Bestellung, Konto
  • Neue Arten kommen von außen – Plugins, Frameworks
  • Grenzen ziehen und verteidigen – Kapselung, Invarianten

Records, sealed, switch

  • Werte, Nachrichten, DTOs, Ergebnisse
  • Die Fälle stehen fest, und der Compiler soll sie kennen
  • Viele Operationen über dieselben Daten – Darstellung, Export, Prüfung

Objektorientierung ist „at its best when it is defining and defending boundaries“ – Brian Goetz, InfoQ 2022
