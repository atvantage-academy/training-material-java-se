    LTS 25: Markdown in Javadoc

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich Dokumentationskommentare in Markdown schreiben, damit sie im Quelltext so lesbar sind wie in der erzeugten Dokumentation.

    Lernziele
    • Du schreibst einen Dokumentationskommentar mit /// in Markdown – mit Liste, Hervorhebung, Code und Verweis.
    • Du erzeugst die Dokumentation mit javadoc und vergleichst sie mit der HTML-Fassung.
    • Du erklärst, warum die Umstellung kein höheres Release braucht.
    • Du bewertest, ob sich die Umstellung in Deinem Bestand lohnt.
    Definition of Done
    • Die Kommentare von Rabattrechner stehen in Markdown, die Dokumentation entsteht ohne Meldung von doclint, und RabattrechnerTest ist unverändert grün.
    • Du hast die Kontrollfragen beantwortet

    Mit JDK 25. Die Übung braucht javadoc aus einem JDK 25; ein JDK 21 liest ///-Kommentare nicht als Dokumentation.

    Javadoc war bisher HTML im Kommentar: <p>, <ul>, <code>. Seit Java 23 darf ein Dokumentationskommentar in Markdown stehen – lesbar im Quelltext wie in der erzeugten Dokumentation.

    Arbeitsschritte

    Worum es geht

    Ein Dokumentationskommentar unter Java 8 ist /** … */ mit HTML darin: Absätze mit <p>, Listen mit <ul> und <li>, Code mit <code> oder {@code …}. Seit Java 23 darf er stattdessen aus Zeilen mit /// bestehen und in Markdown geschrieben sein (JEP 467, LTS-Marke 25). Block-Tags wie @param und @return bleiben; Verweise stehen in eckigen Klammern, etwa [java.math.BigDecimal]. Wo das Feature in der Geschichte von Java steht, zeigt die LTS-Evolution.

    Ein Release stellst Du in dieser Übung nicht hoch: Für den Compiler ist /// ein gewöhnlicher Zeilenkommentar. Nur das Werkzeug javadoc liest ihn als Dokumentation.

    Die Vorlage umbauen

    Die Klasse Rabattrechner im selben Modul trägt ihre Dokumentation in HTML. Stell alle drei Kommentare auf Markdown um: /// statt /** … */, Listen mit -, **fett**, `Code`, ein Codeblock statt <pre>{@code …}</pre>, ein Verweis in eckigen Klammern statt {@link …}.

    Die Lösung: Die Stellen sind in der Vorlage mit // Umbauen: markiert, jeweils mit dem Grund. Die Zeilennummern gelten für die Vorlage auf main; arbeite in jeder Datei von unten nach oben, dann stimmen sie bis zum Schluss.

    Ersetze in Rabattrechner.java die Zeilen 6–23 (die Dokumentation der Klasse) durch:

    /// Berechnet den Rabatt auf eine Bestellung.
///
/// Die Staffel richtet sich nach dem Warenwert:
///
/// - ab 100,00 € gibt es **5 %**,
/// - ab 500,00 € gibt es **10 %**.
///
/// Beispiel:
///
/// ```java
/// BigDecimal rabatt = Rabattrechner.rabatt(new BigDecimal("250.00"));
/// // 12.50
/// ```
///
/// @see java.math.BigDecimal

    Ersetze in Rabattrechner.java die Zeilen 32–42 (die Dokumentation von rabatt) durch:

        /// Der Rabatt für den Warenwert, auf Cent gerundet.
    ///
    /// Unter 100,00 € ist der Rabatt `0.00`. Gerundet wird kaufmännisch
    /// ([RoundingMode#HALF_UP]).
    ///
    /// @param warenwert der Warenwert in Euro, nicht negativ
    /// @return der Rabatt in Euro
    /// @throws IllegalArgumentException wenn der Warenwert negativ ist

    Ersetze in Rabattrechner.java die Zeilen 50–56 (die Dokumentation von satz) durch:

        /// Der Rabattsatz für den Warenwert, etwa `0.05` für 5 %.
    ///
    /// @param warenwert der Warenwert in Euro
    /// @return der Satz als Dezimalzahl

    Was sich geändert hat:

    HTML-Javadoc Markdown
    /** … */, jede Zeile mit * jede Zeile mit ///
    <p>…</p> Leerzeile zwischen Absätzen
    <ul><li>…</li></ul> - …
    <b>5 %</b> **5 %**
    <code>0.00</code> `0.00`
    <pre>{@code …}</pre> Codeblock mit ```java
    {@link RoundingMode#HALF_UP} [RoundingMode#HALF_UP]
    @param, @return, @throws, @see bleiben, wie sie sind

    Lass danach die Tests laufen und erzeuge die Dokumentation. Dabei laufen alle Prüfungen von javadoc (doclint); jede Meldung lässt den Lauf scheitern:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts, lass seine Tests laufen und erzeuge die Dokumentation:

    mvn clean verify javadoc:javadoc -pl neuerungen/syntax/markdown-javadoc -am
    IntelliJ

    Starte die Run Configuration syntax-markdown-javadoc-doku. Sie baut mit clean, lässt RabattrechnerTest laufen und erzeugt die Dokumentation.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration syntax-markdown-javadoc-doku. Sie baut mit clean, lässt RabattrechnerTest laufen und erzeugt die Dokumentation.

    VS Code

    Starte über Terminal → Run Task… den Task syntax-markdown-javadoc-doku. Er baut mit clean, lässt RabattrechnerTest laufen und erzeugt die Dokumentation.

    Der Lauf ist grün, und RabattrechnerTest bleibt unverändert. Öffne die erzeugte Seite neuerungen/syntax/markdown-javadoc/target/reports/apidocs/neuerungen/doku/Rabattrechner.html im Browser: Sie sieht aus wie vorher mit HTML. Wer vergleichen will, startet dieselbe Run Configuration einmal vor dem Umbau.

    • Ist Markdown in Javadoc generell sinnvoll? Gibt es Fälle, in denen Ihr lieber die bisherige Javadoc-Syntax mit HTML verwendet?
