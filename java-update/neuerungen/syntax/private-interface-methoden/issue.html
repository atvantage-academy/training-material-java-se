    Private Interface-Methoden

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich gemeinsamen Code von Default-Methoden verstecken können, damit die öffentliche API eines Interfaces nur das zeigt, was andere aufrufen sollen.

    Lernziele

    • Du ziehst gemeinsamen Code von Default-Methoden in eine private Methode des Interfaces.
    • Du unterscheidest private Instanz- und private statische Methoden in Interfaces.
    • Du begründest, warum eine öffentliche Hilfsmethode in einem Interface zur API gehört.
    • Du bewertest, wo sich der Umbau in Deinem Bestand lohnt.

    Definition of Done

    • Das Modul neuerungen/syntax/private-interface-methoden baut mit Release 11, und PreisregelTest ist unverändert grün.
    • Preisregel hat keine öffentliche Hilfsmethode mehr, und die Rechnung mit dem Steuersatz steht nur noch an einer Stelle.
    • Du hast die Kontrollfragen beantwortet

    Seit Java 8 dürfen Interfaces Default-Methoden haben. Teilen sich zwei davon Code, bleibt mit Java 8 nur eine Hilfsmethode, die öffentlich sein muss – und damit zur API des Interfaces gehört. Sieh Dir an, was neuere Releases dafür bieten, und räume die Preisregel des Shops damit auf.

    Arbeitsschritte

    Worum es geht

    Seit Java 9 darf ein Interface private Methoden haben, als Instanz- und als statische Methode (JEP 213, „Milling Project Coin“, LTS-Marke 11). Sie sind nur innerhalb des Interfaces sichtbar und dienen dem gemeinsamen Code seiner Default-Methoden. Wo das in der Geschichte von Java steht, zeigt die LTS-Evolution.

    Das Release hochstellen

    Öffne im Übungsprojekt das Modul neuerungen/syntax/private-interface-methoden. Stell in seiner pom.xml die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 11. Baue das Modul danach:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl neuerungen/syntax/private-interface-methoden -am
    IntelliJ

    Starte die Run Configuration syntax-private-interface-methoden. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration syntax-private-interface-methoden. Sie baut mit clean.

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell.

    Der Build ist grün: Code im Stil von Java 8 übersetzt auch mit Release 11.

    Die Vorlage umbauen

    Öffne im selben Modul das Interface src/main/java/neuerungen/interfaces/Preisregel.java. Es ist im Stil von Java 8 geschrieben: Beide Default-Methoden rechnen die Steuer auf und runden – zweimal dieselben zwei Zeilen, markiert mit // Doppelter Code!. Mit Java 8 ließe sich das nur in eine weitere öffentliche Methode auslagern, und die gehörte dann zur API des Interfaces. Seit Java 9 geht es in eine private Hilfsmethode, die nur das Interface selbst sieht.

    Füge diese private Methode ins Interface ein, etwa vor aufCentRunden:

        // Gemeinsamer Code der Default-Methoden – seit Java 9 privat (JEP 213).
    private BigDecimal mitSteuer(BigDecimal netto) {
        return aufCentRunden(netto.multiply(BigDecimal.ONE.add(steuersatz())));
    }

    Ersetze dann in brutto die zwei Zeilen unter // Doppelter Code! durch return mitSteuer(netto); und in bruttoMitRabatt durch return mitSteuer(rabattiert);, und lösch beide Kommentare. Baue das Modul danach erneut, wie oben. PreisregelTest sichert das Verhalten ab – er bleibt unverändert und muss grün bleiben.

    Auch die statische Hilfsmethode verstecken

    Über aufCentRunden steht // Könnte privat sein!. Die Methode ist nur für die Default-Methoden gedacht, aber mit Java 8 muss eine statische Methode im Interface öffentlich sein – so steht es auch in ihrer Javadoc. Seit Java 9 darf auch eine statische Methode im Interface privat sein. Ersetze ihre erste Zeile durch:

        private static BigDecimal aufCentRunden(BigDecimal betrag) {

    Lösch den Kommentar und die Javadoc darüber, die nicht mehr stimmt, und baue das Modul erneut. Von außen ist Preisregel.aufCentRunden(…) jetzt nicht mehr aufrufbar. Das Interface bleibt funktional: Es hat weiter genau eine abstrakte Methode.

    Reflexionsfragen

    • In welchem Kontext werden private Interface-Methoden verwendet?
    • Was ändert sich für Klassen, die das Interface umsetzen – müssen sie neu übersetzt werden?
