    Java-Update/_: von der Warnung zum Sprachmittel
    ca. 20 MinutenUnbenannte Variablen und MusterJEP 213JEP 456

    _: von der Warnung zum Sprachmittel

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich verstehen, warum „_“ erst verboten und dann neu erlaubt wurde, damit ich Variablen, die mein Code nie liest, als solche kennzeichnen kann.

    Lernziele

    • Du zeigst am Compiler, wie sich die Bedeutung von _ zwischen Release 8, 9 und 22 geändert hat.
    • Du ersetzt Variablen, die der Code nie liest, durch _ – in catch, Schleifen und Lambdas.
    • Du bewertest, wo sich der Umbau in Deinem Bestand lohnt.

    Definition of Done

    • Das Modul neuerungen/syntax/unbenannte-variablen baut mit Release 8 mit einer Warnung zu _ und scheitert mit Release 9; Du hast beide Meldungen verglichen.
    • Optional, mit JDK 25: Das Modul neuerungen/syntax/unbenannte-variablen baut mit Release 25, Auswertung nutzt _ für jede Variable, die der Code nie liest, und AuswertungTest ist unverändert grün.
    • Du hast die Kontrollfragen beantwortet

    Ein Unterstrich als Variablenname war in Java 8 erlaubt, aber schon mit einer Warnung versehen. Mit Java 9 wurde er zum Fehler, und seit Java 22 hat er eine neue Bedeutung. Verfolge den Weg am Compiler, und – mit JDK 25 – setze das neue Sprachmittel ein.

    Arbeitsschritte

    Worum es geht

    Bis Java 8 ist _ ein gewöhnlicher Bezeichner; der Compiler warnt nur. Java 9 macht ihn zum Schlüsselwort ohne Bedeutung (JEP 213, LTS-Marke 11) – Code mit _ als Namen übersetzt nicht mehr. Seit Java 22 steht _ für eine unbenannte Variable oder ein unbenanntes Muster: etwas, das der Code braucht, aber nie liest (JEP 456, LTS-Marke 25). Wo beides in der Geschichte von Java steht, zeigt die LTS-Evolution.

    Das Modul mit Java 8 bauen

    Im Modul neuerungen/syntax/unbenannte-variablen steht die Klasse Auswertung, im Stil von Java 8 geschrieben. Das Release steht noch auf 8. Baue das Modul:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl neuerungen/syntax/unbenannte-variablen -am
    IntelliJ

    Starte die Run Configuration syntax-unbenannte-variablen. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration syntax-unbenannte-variablen. Sie baut mit clean.

    Der Build ist grün, aber der Compiler warnt:

    [WARNING] …/Auswertung.java:[27,44] Ab Release 9 ist "_" ein Schlüsselwort und kann nicht als ID verwendet werden

    Sieh Dir Zeile 27 an: Die Ausnahme in anzahlZahlen heißt _ – so, wie man in Java 8 eine Variable nannte, die man nicht braucht.

    Das Release auf 9 stellen

    Stell in der pom.xml des Moduls die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 9. Baue das Modul danach wie oben.

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell.

    Jetzt scheitert der Build:

    [ERROR] …/Auswertung.java:[27,44] Unbenannte Variablen werden in -source 9 nicht unterstützt
  (Verwenden Sie -source 22 oder höher, um Unbenannte Variablen zu aktivieren)

    Aus der Warnung ist ein Fehler geworden. Lies die Meldung genau: Was schlägt der Compiler vor? Ein JDK 21 meldet an dieser Stelle noch etwas anderes – es kennt unbenannte Variablen nur als Preview.

    Stell das Release danach wieder auf 8 – oder mach mit JDK 25 im optionalen Schritt weiter.

    Mit JDK 25. Der folgende Schritt nutzt das Sprachmittel aus Java 22 und braucht ein JDK 25. Mit JDK 21 übersetzt kein Code mit unbenannten Variablen.

    Optional: Auf Java 25 umstellen und _ einsetzen

    Stell maven.compiler.release in der pom.xml des Moduls auf 25 und baue das Modul wie oben:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl neuerungen/syntax/unbenannte-variablen -am
    IntelliJ

    Starte die Run Configuration syntax-unbenannte-variablen. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration syntax-unbenannte-variablen. Sie baut mit clean.

    Der Build ist grün, und die Warnung ist weg: Seit Java 22 ist catch (NumberFormatException _) eine unbenannte Variable – genau, was der Code von Java 8 meinte.

    Die Klasse Auswertung hat weitere Variablen, die der Code braucht, aber nie liest; sie tragen Namen. Die Stellen sind in der Vorlage mit // Umbauen: markiert. Ersetze jede dieser Variablen durch _. AuswertungTest sichert das Verhalten ab – er bleibt unverändert und muss grün bleiben.

    Die Lösung: Die Zeilennummern gelten für die Vorlage auf main; arbeite von unten nach oben, dann stimmen sie bis zum Schluss.

    Ersetze in Auswertung.java die Zeilen 37–38 (in anzahlZeilen) durch:

            for (String _ : zeilen) {

    Ersetze in Auswertung.java die Zeilen 49–50 (in artikelJeKunde) durch:

                ergebnis.computeIfAbsent(felder[0], _ -> new ArrayList<String>()).add(felder[1]);

    Ersetze in Auswertung.java die Zeilen 58–59 (in gesamtmenge) durch:

            mengeJeArtikel.forEach((_, menge) -> summe[0] += menge);

    Die Variable text in anzahlZahlen bleibt: Der Code liest sie.

    Baue das Modul danach erneut, wie oben.

    Reflexionsfragen

    • Warum hat Java _ erst zum Fehler gemacht, bevor es eine neue Bedeutung bekam? Was wäre passiert, wenn es den Schritt übersprungen hätte?
    • Eine Variable, die nie gelesen wird, heißt bisher ignoriert oder unused. Was sagt _ mehr – oder weniger?
