    LTS 25: Scoped Values

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich Kontext wie die Kennung einer Anfrage ohne ThreadLocal weitergeben, damit nichts aus einer Anfrage in die nächste gerät.

    Lernziele
    • Du bindest einen Wert mit ScopedValue.where(…) für die Dauer eines Aufrufs.
    • Du erklärst, warum ein Scoped Value kein Aufräumen braucht und keinen Setter hat.
    • Du ersetzt eine ThreadLocal durch einen Scoped Value, ohne das Verhalten zu ändern.
    • Du bewertest, wo in Deinem Bestand Scoped Values eine ThreadLocal ablösen.
    Definition of Done
    • Das Modul neuerungen/api/scoped-values baut mit Release 25, Anfragekontext nutzt einen ScopedValue statt einer ThreadLocal, und AnfragekontextTest ist unverändert grün.
    • Du hast die Kontrollfragen beantwortet

    Mit JDK 25. Die Übung braucht ein JDK 25. Mit JDK 21 sind Scoped Values nur als Preview verfügbar.

    Wer Kontext wie die Kennung einer Anfrage durch alle Schichten reicht, ohne ihn als Parameter durchzugeben, greift unter Java 8 zur ThreadLocal – und muss sie nach jeder Anfrage aufräumen. Ein Scoped Value gilt für die Dauer eines Aufrufs und endet von selbst.

    Arbeitsschritte

    Worum es geht

    Eine ThreadLocal hält einen Wert je Thread, bis ihn jemand ändert oder entfernt. Vergisst der Code das Aufräumen, sieht die nächste Anfrage auf demselben Thread den alten Wert. Seit Java 25 gibt es Scoped Values (JEP 506, LTS-Marke 25): Ein Wert wird mit ScopedValue.where(…) für genau einen Aufruf gebunden, ist darin überall lesbar und danach wieder ungebunden – unveränderlich und ohne Aufräumen. Wo das Feature in der Geschichte von Java steht, zeigt die LTS-Evolution.

    Das Release hochstellen

    Stell in der pom.xml des Moduls neuerungen/api/scoped-values die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 25. Baue das Modul danach:

    Kommandozeile

    Baue das Modul im Wurzelordner des Übungsprojekts und lass seine Tests laufen:

    mvn clean verify -pl neuerungen/api/scoped-values -am
    IntelliJ

    Starte die Run Configuration api-scoped-values. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration api-scoped-values. Sie baut mit clean.

    VS Code

    Starte über Terminal → Run Task… den Task api-scoped-values. Er baut mit clean.

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell.

    Der Build ist grün: Am Code hat sich noch nichts geändert.

    Die Vorlage umbauen

    Sieh Dir zuerst die Visualisierung Scoped Values an: Sie zeigt, wie man einen Scoped Value anlegt, bindet und liest, wie eine Bindung entsteht und wieder endet – und was dabei schiefgehen kann.

    Die Klasse Anfragekontext im selben Modul hält die Kennung der Anfrage in einer ThreadLocal. bearbeite setzt sie, ruft die Aufgabe auf und stellt im finally den vorigen Wert wieder her. Ersetze die ThreadLocal durch einen ScopedValue. AnfragekontextTest sichert das Verhalten ab – auch für geschachtelte Anfragen und nach einem Fehler. Er bleibt unverändert und muss grün bleiben.

    Die Lösung: Die Stellen sind in der Vorlage mit // Umbauen: markiert, jeweils mit dem Grund. Die Zeilennummern gelten für die Vorlage auf main; arbeite in jeder Datei von unten nach oben, dann stimmen sie bis zum Schluss.

    Ersetze in Anfragekontext.java die Zeilen 14–15 (das Feld) durch:

        private static final ScopedValue<String> ANFRAGE = ScopedValue.newInstance();

    Ersetze in Anfragekontext.java die Zeilen 22–33 (der Rumpf von bearbeite) durch:

            return ScopedValue.where(ANFRAGE, anfrage).call(aufgabe::call);

    Ersetze in Anfragekontext.java die Zeilen 38–40 (der Rumpf von aktuelleAnfrage) durch:

            return ANFRAGE.orElse("–");

    call reicht die Ausnahme der Aufgabe weiter; das try/finally entfällt, denn die Bindung endet mit dem Aufruf von selbst. Protokoll bleibt unverändert.

    Baue das Modul danach erneut, wie oben.
