    Brüche finden, bevor der Test sie findet

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich Brüche finden, bevor ein Test oder die Produktion sie zeigt, damit ich den Umstieg planen kann, statt von ihm überrascht zu werden.

    Lernziele

    • Du lässt jdeps und jdeprscan über übersetzte Klassen laufen und liest ihre Ausgabe.
    • Du ordnest jedem Bruch zu, ob ein Werkzeug ihn vorher meldet – und wenn nicht, warum nicht.
    • Du erklärst, warum Werkzeuge, die Bytecode lesen, Tests auf dem Ziel-JDK nicht ersetzen.

    Definition of Done

    • Du hast jdeps und jdeprscan über alle Kompatibilitätsmodule laufen lassen.
    • Du hast für jeden der neun Brüche und für die Klassen in ueberblick/werkzeuge notiert, ob und mit welchem Werkzeug sie sich vorher finden lassen.
    • Du hast die Kontrollfragen beantwortet

    Die Bestellabwicklung soll von Java 8 auf ein aktuelles Release. Bevor Ihr Modul für Modul das Release hochstellt, wollt Ihr wissen, worauf Ihr Euch einstellen müsst. Das JDK bringt dafür zwei Werkzeuge mit, die übersetzte Klassen lesen, ohne sie auszuführen:

    • jdeps (seit Java 8) zeigt, wovon Klassen abhängen – und was davon im JDK fehlt.
    • jdeprscan (seit Java 9) findet Aufrufe von APIs, die das JDK abgekündigt hat, und sagt, welche davon entfernt werden sollen.

    Im Übungsprojekt liegt unter inkompatibilitaeten/ je Bruch ein Modul, alle noch für Java 8 übersetzt. Dazu kommen im Modul ueberblick/werkzeuge vier Klassen mit Code, wie er in Java-8-Anwendungen oft steht:

    • Nummernkreis vergibt Bestellnummern mit sun.misc.Unsafe, einer internen API des JDK.
    • Lagerbestand packt Zahlen mit new Integer(…) und new Double(…) ein.
    • Druckauftrag räumt seine temporäre Datei in finalize() auf.
    • Exportwächter bricht einen hängenden Export mit Thread.stop() ab.

    Lass beide Werkzeuge über alles laufen.

    Arbeitsschritte

    Fehlende Abhängigkeiten suchen

    Das Modul ueberblick/werkzeuge übersetzt alle Kompatibilitätsmodule und seine eigenen Klassen und lässt dann jdeps des laufenden JDK über sie laufen – einmal mit --missing-deps (was fehlt dem JDK?) und einmal mit --jdk-internals (welche Interna des JDK werden benutzt?):

    Kommandozeile

    Übersetze die Module im Wurzelordner des Übungsprojekts und lass jdeps laufen:

    mvn clean compile -pl ueberblick/werkzeuge -am -Pjdeps
    IntelliJ

    Starte die Run Configuration ueberblick-werkzeuge-jdeps.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration ueberblick-werkzeuge-jdeps.

    Zwischen den Zeilen von Maven steht die Ausgabe von jdeps. Die Werkzeuge antworten in der Sprache Deines Systems; auf Englisch heißt „nicht gefunden“ „not found“:

    classes -> nicht gefunden
   kompatibilitaet.jaxb.BestellungXml   -> javax.xml.bind.annotation.XmlAttribute   nicht gefunden
   kompatibilitaet.jaxb.BestellungXml   -> javax.xml.bind.annotation.XmlElement     nicht gefunden
   kompatibilitaet.jaxb.BestellungXml   -> javax.xml.bind.annotation.XmlRootElement nicht gefunden
   kompatibilitaet.jaxb.XmlExport       -> javax.xml.bind.JAXB                      nicht gefunden

    Welches Modul ist betroffen, und was fehlt ihm?

    Darunter folgt die Ausgabe von --jdk-internals, gekürzt:

    classes -> jdk.unsupported
   kompatibilitaet.werkzeuge.Nummernkreis   -> sun.misc.Unsafe   JDK internal API (jdk.unsupported)

JDK-interne API                          Vorgeschlagene Ersetzung
---------------                          ------------------------
sun.misc.Unsafe                          See https://openjdk.org/jeps/260

    Welche Klasse nutzt eine interne API, und was schlägt jdeps als Ersatz vor? Dass das Modul reflection hier fehlt, obwohl es auf ein privates Feld von ArrayList zugreift, merk Dir für die Bilanz.

    Hinweis: Nummernkreis lässt sich nur übersetzen, weil das Modul mit maven.compiler.source und maven.compiler.target 8 baut statt mit maven.compiler.release 8: Mit --release kennt javac nur die offizielle API von Java 8, und sun.misc.Unsafe gehört nicht dazu. So, gegen das installierte JDK, bauen viele Altprojekte.

    Abgekündigte APIs suchen

    jdeprscan prüft gegen ein Ziel-Release – hier --release 21 – und meldet mit --for-removal nur, was entfernt werden soll:

    Kommandozeile

    Übersetze die Module und lass jdeprscan laufen:

    mvn clean compile -pl ueberblick/werkzeuge -am -Pjdeprscan
    IntelliJ

    Starte die Run Configuration ueberblick-werkzeuge-jdeprscan.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration ueberblick-werkzeuge-jdeprscan.

    Für jedes Modul steht eine Zeile Verzeichnis … (englisch Directory …), darunter seine Funde. Für das Modul werkzeuge sieht das so aus:

    class ueberblick/werkzeuge/Druckauftrag verwendet die veraltete Methode java/lang/Object::finalize()V (forRemoval=true)
class ueberblick/werkzeuge/Druckauftrag setzt die veraltete Methode java/lang/Object::finalize()V (forRemoval=true) außer Kraft
class ueberblick/werkzeuge/Lagerbestand verwendet die veraltete Methode java/lang/Integer::<init>(I)V (forRemoval=true)
class ueberblick/werkzeuge/Lagerbestand verwendet die veraltete Methode java/lang/Double::<init>(Ljava/lang/String;)V (forRemoval=true)
class ueberblick/werkzeuge/Exportwächter verwendet die veraltete Methode java/lang/Thread::stop()V (forRemoval=true)

    <init> steht für einen Konstruktor. Welche Module nutzen noch etwas, das entfernt werden soll? Und was bedeutet die Zeile Fehler: Klasse javax/xml/bind/JAXB nicht gefunden?

    Optional: Ein Werkzeug selbst aufrufen

    Dieser Schritt geht nur auf der Kommandozeile; für die Bilanz brauchst Du ihn nicht. Maven nimmt Dir hier nur die Tipparbeit ab. In Deinem eigenen Projekt rufst Du die Werkzeuge direkt auf – auf ein Verzeichnis mit Klassen oder auf ein JAR. Öffne dazu ein Terminal im Wurzelordner des Übungsprojekts (in der IDE: das eingebaute Terminal).

    Lass Dir alle Pakete zeigen, von denen das Modul jaxb abhängt:

    jdeps -verbose:package inkompatibilitaeten/laufzeit/jaxb/target/classes

    Prüf das Modul security-manager gegen ein älteres Release:

    jdeprscan --release 11 --for-removal inkompatibilitaeten/laufzeit/security-manager/target/classes

    Prüf das Modul werkzeuge gegen ein neueres:

    jdeprscan --release 25 --for-removal ueberblick/werkzeuge/target/classes

    Was ändert sich jeweils gegenüber --release 21?

    Die Bilanz ziehen

    Notiere für jeden der neun Brüche und für die Klassen in werkzeuge, ob eines der Werkzeuge sie gemeldet hat. Für die, die keines findet: Warum nicht – und wann zeigt sich der Bruch stattdessen?

    Das Ergebnis, gemessen mit JDK 25:

    Bruch (Modul) jdeps jdeprscan Sonst sichtbar …
    jaxb ✓ javax.xml.bind fehlt bricht mit „nicht gefunden“ ab im Test, beim Übersetzen mit Release 11
    security-manager – ✓ SecurityManager, forRemoval=true im Test
    werkzeuge: Nummernkreis ✓ --jdk-internals: sun.misc.Unsafe – als Warnung beim Übersetzen und ab JDK 24 beim ersten Aufruf
    werkzeuge: Lagerbestand – ✓ bis Release 24; JDK 25 hat die Konstruktoren nicht mehr zum Entfernen vorgesehen als Warnung beim Übersetzen
    werkzeuge: Druckauftrag – ✓ finalize() als Warnung beim Übersetzen; läuft, bis die Finalisierung entfernt wird (JEP 421)
    werkzeuge: Exportwächter – ✓ Thread.stop() als Warnung beim Übersetzen; seit Java 20 eine UnsupportedOperationException – erst, wenn ein Export hängt
    reflection – – im Test: Das Feld elementData steht als Text im Code, nicht als Abhängigkeit im Bytecode
    unterstrich, eingeschraenkte-bezeichner, sequenced – – beim Übersetzen mit höherem Release: Der Bruch steckt im Quelltext, nicht im Bytecode
    datumsformat, zeitstempel, zeichensatz – – erst im Test oder in Produktion: Die API ist dieselbe, nur ihr Verhalten ist anders

    Zwei der neun Brüche, dazu alle Klassen in werkzeuge. Die Werkzeuge finden, was fehlt, was intern ist oder was verschwinden soll – nicht, was anders läuft. Sie ersetzen deshalb weder das Übersetzen mit dem neuen Release noch die Tests auf dem Ziel-JDK; sie sagen nur früher und ohne Ausführung, wo es sicher bricht.

    Reflexionsfragen

    • Beide Werkzeuge lesen Bytecode. Welche Arten von Brüchen können sie deshalb grundsätzlich nicht finden?
    • Wo im Build Eures Projekts würden jdeps und jdeprscan laufen – und was tut Ihr mit einem Fund in einer Bibliothek?
