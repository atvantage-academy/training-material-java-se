Die Laufzeitumgebung seit Java 8

Seit Java 8 hat sich die Laufzeitumgebung mindestens so stark verändert wie die Sprache – und das meiste wirkt, ohne dass Du eine Zeile Code änderst. Was Du wissen musst, sind vier Dinge: welchen Garbage Collector Du nimmst, was die JVM im Container entscheidet, wie der Start schneller wird und wie viel Speicher ein Objekt kostet.

1 · Der Garbage Collector entscheidet über Pausen

Jeder Collector räumt den Heap auf, aber er tut es anders: Mal hält er die Anwendung an und räumt alles auf einmal, mal räumt er nebenher. Wähle einen Collector – die Zeitleiste zeigt einen Lauf von Speicherlast aus dem Übungsprojekt.

Zahl, längste und mittlere Pause und die Dauer sind gemessen; wo die Pausen auf der Zeitleiste liegen, ist schematisch.

2 · Im Container rechnet die JVM mit dem Container

Seit Java 10 liest die JVM die Grenzen ihres Containers aus (in 8 und 11 nachgereicht) und richtet sich danach: Wie viele Kerne sie nutzt, wie groß der Heap werden darf und welchen Collector sie nimmt, wenn Du keinen wählst. Stell einen Container ein:

3 · Der Start: Was die JVM jedes Mal tut, lässt sich vorher erledigen

Bei jedem Start sucht die JVM dieselben Klassen, lädt und prüft sie, verknüpft sie miteinander und beobachtet, welche Methoden sich zu übersetzen lohnen. CDS (Class Data Sharing) legt geladene und geprüfte Klassen in einem Archiv ab. Der AOT-Cache legt sie außerdem schon verknüpft ab und speichert dazu Profile, welche Methoden oft laufen.     Ausblick: Mit Java 26 funktioniert der AOT-Cache mit jedem Garbage Collector (JEP 516), mit Java 28 legt er auch übersetzten Maschinencode ab (JEP 544). Beides gehört zu Project Leyden – dem Weg, die Startzeit im JDK selbst zu verkürzen, ohne die Regeln eines GraalVM Native Image.

    4 · Kompakte Objekt-Header: weniger Speicher je Objekt

    Jedes Objekt beginnt mit einem Header: einem Markwort (Sperren, Hashcode, Alter für den GC) und einem Zeiger auf seine Klasse. Bei vielen kleinen Objekten ist das ein großer Teil des Speichers. Seit Java 25 passt beides in 8 statt 12 Byte:

    Klassisch · 32 Byte

    Header 12Ref 4int 4long 84

    Kompakt · 24 Byte

    Header 8Ref 4int 4long 8

    Eine Bestellposition mit einer Referenz, einem int und einem long: klassisch 12 Byte Header plus 16 Byte Felder, aufgerundet auf ein Vielfaches von 8, also 32 Byte; kompakt 24 Byte. Gemessen mit drei Millionen solcher Positionen: 107 MB, mit kompakten Headern 84 MB.

    experimentell in 24 · JEP 450 LTS 25 · JEP 519 Standard ab 27 · JEP 534

    java -XX:+UseCompactObjectHeaders -jar app.jar
