    Die JVM unter die Lupe nehmen

    Als Entwickler:in, deren Anwendung im Container und unter Last läuft, möchte ich wissen, was die JVM von selbst entscheidet und wie ich ihr beim Starten und Messen helfe, damit ich die Optionen in Startskript und Dockerfile begründen kann.

    Lernziele

    • Du liest ab, welchen Garbage Collector und wie viel Heap die JVM wählt – ohne und mit knappen Ressourcen.
    • Du vergleichst die Garbage Collectors an Pausen und Laufzeit und begründest, welcher zu Deiner Anwendungsart passt.
    • Du erzeugst einen AOT-Cache (JDK 25) bzw. ein CDS-Archiv (JDK 21) und misst den Unterschied beim Start.
    • Du zeichnest einen Lasttest mit Java Flight Recorder auf und wertest ihn mit jfr view aus.
    • Du bewertest, welche JVM-Einstellungen in Eure Startskripte gehören.

    Definition of Done

    Ergonomie und Garbage Collector

    • Du kannst sagen, welchen GC und welche Heap-Größe die JVM mit einem Kern und 1 GB wählt.
    • Du hast mindestens drei Collectors an längster Pause und Laufzeit verglichen und einen für Deine Anwendungsart begründet gewählt.

    Start und Flight Recorder

    • Du hast die Startzeit mit und ohne Archiv bzw. Cache gemessen.
    • Du hast eine JFR-Aufzeichnung mit mindestens zwei Ansichten von jfr view ausgewertet.

    Bewertung

    • Du hast notiert, welche Optionen Ihr in Startskript oder Dockerfile setzen würdet – und welche Ihr streicht.

    Für die ganze Seite

    • Du hast die Kontrollfragen beantwortet

    Du änderst keinen Code – Du startest den Altbestand und zwei Programme aus der Spielwiese mit anderen JVM-Optionen und misst, was sich ändert. Wie die Collectors arbeiten, was die JVM im Container wählt und was CDS und AOT-Cache tun, zeigt die Visualisierung Die Laufzeitumgebung seit Java 8.

    Hinweis: Du brauchst JDK 21 oder 25. Wo ein Schritt nur mit einem der beiden geht, steht es dabei. Die Befehle mit JVM-Optionen laufen im Terminal – in IntelliJ über View → Tool Windows → Terminal, in Eclipse über Window → Show View → Terminal, jeweils im Wurzelordner des Übungsprojekts.

    Arbeitsschritte

    Den Altbestand bauen

    Danach liegen die Anwendungen als startbare JARs bereit, die REST-Schnittstelle in altbestand/bestellung-rest/target/bestellung-rest.jar.

    Kommandozeile

    Baue im Wurzelordner des Übungsprojekts:

    mvn clean verify -f altbestand/pom.xml
    IntelliJ

    Starte die Run Configuration altbestand.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration altbestand.

    Was wählt die JVM?

    Lass die JVM zeigen, wie sie sich eingerichtet hat:

    java -Xlog:gc,gc+init -version

    Lies ab: Welcher GC? Wie viele Prozessoren? Wie groß darf der Heap werden – und welcher Anteil Deines Arbeitsspeichers ist das?

    Stell einen kleinen Container nach, mit einem Kern und 1 GB:

    java -XX:ActiveProcessorCount=1 -XX:MaxRAM=1g -Xlog:gc,gc+init -version

    Was hat sich geändert, und warum?

    Hinweis: Wer Docker hat, probiert es im echten Container: docker run --rm --cpus 1 -m 1g eclipse-temurin:25 java -Xlog:gc,gc+init -version. Mit eclipse-temurin:27 sieht das Ergebnis anders aus.

    Die Garbage Collectors vergleichen

    spielwiese/Speicherlast.java hält drei Millionen Bestellpositionen im Speicher und erzeugt daneben viele kurzlebige – Arbeit für den Garbage Collector. Starte sie mit G1 und zeichne den Lauf mit dem Flight Recorder auf:

    java -XX:+UseG1GC -Xmx1g -XX:StartFlightRecording=filename=gc.jfr spielwiese/Speicherlast.java

    Sieh Dir die Pausen an:

    jfr view gc-pauses gc.jfr

    Wiederhole beides mit -XX:+UseSerialGC, -XX:+UseParallelGC und -XX:+UseZGC anstelle von -XX:+UseG1GC. Halte je Collector die Laufzeit, die Zahl der Pausen und die längste Pause fest.

    Recherchiere dann in der Visualisierung und im Garbage Collection Tuning Guide (unter den Ressourcen): Wie arbeitet jeder Collector, was kostet er, wann ist er sinnvoll? Welchen würdest Du für Eure Anwendung wählen?

    Hinweis: jfr liegt im bin-Ordner Deines JDK. Shenandoah fehlt in den Builds von Oracle; mit Temurin kannst Du ihn mit -XX:+UseShenandoahGC dazunehmen.

    Den Start verkürzen

    Als Messlatte dient der Lasttest mit einer Bestellung – er startet die REST-Schnittstelle, schickt eine Anfrage und endet. 100 ms davon wartet die Anfrage aufs Lager. Miss ihn mehrmals:

    time java -cp altbestand/bestellung-rest/target/bestellung-rest.jar bestellung.rest.Lasttest 1

    Mit JDK 25 lässt Du einen Trainingslauf einen AOT-Cache schreiben:

    java -XX:AOTCacheOutput=rest.aot -cp altbestand/bestellung-rest/target/bestellung-rest.jar bestellung.rest.Lasttest 1

    Starte dann mit dem Cache und miss wieder:

    time java -XX:AOTCache=rest.aot -cp altbestand/bestellung-rest/target/bestellung-rest.jar bestellung.rest.Lasttest 1

    Mit JDK 21 schreibt der erste Lauf ein CDS-Archiv:

    java -XX:ArchiveClassesAtExit=rest.jsa -cp altbestand/bestellung-rest/target/bestellung-rest.jar bestellung.rest.Lasttest 1

    Starte dann mit dem Archiv und miss wieder:

    time java -XX:SharedArchiveFile=rest.jsa -cp altbestand/bestellung-rest/target/bestellung-rest.jar bestellung.rest.Lasttest 1

    Wie viel schneller ist der Start? Und was müsste geschehen, damit Eure Anwendung beim Kunden mit genau diesem Cache startet?

    Hinweis: Unter Windows misst Du in PowerShell mit Measure-Command { java … }. Miss jeden Fall mehrmals; der erste Lauf nach dem Bauen ist immer langsamer.

    Mit dem Flight Recorder messen

    Zeichne einen größeren Lasttest auf; er dauert gut zehn Sekunden:

    java -XX:StartFlightRecording=filename=last.jfr,settings=profile -cp altbestand/bestellung-rest/target/bestellung-rest.jar bestellung.rest.Lasttest 1000

    Sieh nach, wo die Rechenzeit hingeht:

    jfr view hot-methods last.jfr

    Sieh nach, welche Klassen den meisten Speicher anlegen:

    jfr view allocation-by-class last.jfr

    Was überrascht Dich? jfr help view listet alle Ansichten – probiere eine weitere, etwa container-configuration im Container oder thread-count.

    Kür: kompakte Objekt-Header (JDK 25)

    Starte die Speicherlast mit und ohne kompakte Header und vergleiche, wie viel Speicher der Bestand belegt (letzte Zeile der Ausgabe):

    java -XX:+UseCompactObjectHeaders -Xmx1g spielwiese/Speicherlast.java

    Starte sie zum Vergleich ohne:

    java -XX:-UseCompactObjectHeaders -Xmx1g spielwiese/Speicherlast.java

    Wie viel spart es? Für welche Eurer Anwendungen zählt das?

    Kür: Pinning nachweisen (JDK 21 und 25)

    spielwiese/Angeheftet.java lässt 200 virtuelle Threads in einem synchronized-Block warten – wie die Fremdsysteme im Altbestand. Zeichne den Lauf auf:

    java -XX:StartFlightRecording=filename=angeheftet.jfr spielwiese/Angeheftet.java

    Sieh nach, welche virtuellen Threads ihren Träger festgehalten haben:

    jfr view pinned-threads angeheftet.jfr

    Vergleicht die Ausgabe und die Laufzeit auf JDK 21 und 25 – mit einem Paar, das das andere JDK hat. Was zeigt der Flight Recorder, und in welcher Methode?

    Bewerten

    Halte in Stichworten fest:

    • Ergonomie: Was wählt die JVM in Eurem Container – und würdet Ihr das so lassen?
    • Garbage Collector: Welchen nehmt Ihr für einen REST-Microservice, ein Batch-Programm, eine Server-Anwendung?
    • Start: Lohnt ein AOT-Cache bzw. ein CDS-Archiv bei Euch, und wo entstünde er?
    • Startskripte: Welche Optionen würdet Ihr setzen – und welche streichen?

    Reflexionsfragen

    • Eure Anwendung läuft im Container mit einem Kern und 1 GB. Was wählt die JVM – und ist das gut?
    • Warum nehmt Ihr nicht immer ZGC?
    • Wann lohnt ein AOT-Cache, und wo gehört der Trainingslauf hin?
    • Warum ist -Xmx2g im Dockerfile eine schlechte Idee?
    • Welche JVM-Optionen in Euren Startskripten stammen aus einer JVM, die es so nicht mehr gibt?
