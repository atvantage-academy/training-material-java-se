    ca. 40 MinutenVirtual ThreadsJEP 444Pinning

    Umstellen und messen

    Als Entwickler:in, deren Anwendung viel Zeit mit Warten auf andere Systeme verbringt, möchte ich wissen, was virtuelle Threads bei uns bringen und was sie bremst, damit ich die Umstellung begründen und ihre Risiken einschätzen kann.

    Lernziele
    • Du misst Batch-Import und REST-Schnittstelle vor und nach der Umstellung und hältst die Werte fest.
    • Du stellst einen festen Thread-Pool auf virtuelle Threads um.
    • Du erklärst, warum ein virtueller Thread unter Java 21 in synchronized seinen Träger festhält, und behebst es im eigenen Code.
    • Du bewertest, was virtuelle Threads für Eure Anwendungen bringen und wo sie nichts ändern.
    Definition of Done

    Umstellen und messen

    • Das Modul schwerpunkte/virtual-threads baut mit Release 21; Batch-Import und REST-Schnittstelle nutzen virtuelle Threads.
    • mvn clean verify -f schwerpunkte/virtual-threads/pom.xml ist grün.
    • Eure Zeile in der Messtabelle ist ausgefüllt – mit JDK-Version.

    Pinning

    • Du kannst die Methode benennen, in der unter Java 21 gepinnt wird, und erklären, warum.
    • Mit JDK 21: Der Batch-Import ist nach Deinem Umbau so schnell wie auf JDK 25.

    Bewertung

    • Du hast Voraussetzungen, Vorteile, Herausforderungen und den Nutzen je Anwendungsart notiert.

    Für die ganze Seite

    • Du hast die Kontrollfragen beantwortet

    In der Bestellabwicklung (Modul schwerpunkte/virtual-threads) warten zwei Stellen auf Fremdsysteme: Der Batch-Import prüft jede Bestellung bei einer Auskunftei (50 ms), die REST-Schnittstelle fragt für jede neue Bestellung beim Lager nach (100 ms). Beide arbeiten mit einem festen Thread-Pool. Du stellst sie auf virtuelle Threads um und misst, was es bringt – auf Deinem JDK.

    Arbeitsschritte

    Worum es geht

    Ein Server, der jeder Anfrage einen Thread gibt, bearbeitet höchstens so viele Anfragen gleichzeitig, wie er Threads hat. Wartet jede davon 100 ms auf ein anderes System, schafft ein Pool mit 10 Threads höchstens 100 Anfragen je Sekunde – egal, wie viele Kerne sich langweilen. Mehr Threads helfen nur begrenzt: Jeder ist ein Thread des Betriebssystems mit eigenem Stack.

    Virtuelle Threads (Java 21, JEP 444, LTS-Marke 21) lösen das, ohne den Code zu ändern: Wartet ein virtueller Thread, gibt er seinen Trägerthread frei. Wie das abläuft und wo es klemmt, zeigt die Simulation Plattform-Threads und virtuelle Threads.

    Hinweis: Für diese Übung brauchst Du JDK 21 oder 25. Mit welchem Du arbeitest, macht einen Unterschied – vergleicht Eure Zahlen mit einem Paar, das das andere hat.

    Passt der Wert der REST-Schnittstelle zur Rechnung oben?

    Das Release hochstellen

    Virtuelle Threads gibt es ab Java 21. Stell in schwerpunkte/virtual-threads/pom.xml die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen“ von 8 auf 21. Sie gilt für Domäne, REST-Schnittstelle und Batch-Import zusammen. Baue wie oben – der Build ist grün, noch hat sich nichts geändert.

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell. In der IDE lädst Du das Maven-Projekt danach neu (IntelliJ: Maven → Reload All Maven Projects, Eclipse: Maven → Update Project…).

    Den Batch-Import umstellen

    BestellImport erzeugt einen festen Pool mit acht Threads. Stell ihn so um, dass jede Bonitätsprüfung ihren eigenen virtuellen Thread bekommt.

    Ersetze in schwerpunkte/virtual-threads/bestellung-batch/src/main/java/bestellung/batch/BestellImport.java Zeile 32 (Executors.newFixedThreadPool(8)) durch:

            ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor();

    Mehr ist es nicht: Der übrige Code bleibt, wie er ist – blockierend, von oben nach unten. Baue und miss den Batch-Import erneut. Was hast Du erwartet, was kam heraus?

    Die REST-Schnittstelle umstellen

    RestAnwendung gibt dem Server einen festen Pool mit zehn Threads. Gib ihm stattdessen einen Executor, der für jede Anfrage einen virtuellen Thread startet.

    Ersetze in schwerpunkte/virtual-threads/bestellung-rest/src/main/java/bestellung/rest/RestAnwendung.java Zeile 47 (Executors.newFixedThreadPool(10)) durch:

            executor = Executors.newVirtualThreadPerTaskExecutor();

    Baue und miss mit dem Lasttest.

    Hinweis: Der Lasttest schickt höchstens 100 Bestellungen gleichzeitig. Schneller als zwei Runden zu je 100 ms geht es also nicht.

    Das Pinning finden

    Vergleicht Eure Messwerte mit einem Paar, das das andere JDK hat. Auf einem der beiden haben virtuelle Threads viel weniger gebracht, als die Rechnung verspricht.

    Beide Fremdsysteme fragst Du über Verbindung.sende an (Paket bestellung.extern in der Domäne). Sieh Dir die Methode an: Was tut sie, während sie wartet – und was hält sie dabei fest? Die Simulation zeigt im Ablauf „Pinning in synchronized“, was ein virtueller Thread dort unter Java 21 tut und was sich mit Java 24 geändert hat.

    Mit JDK 21: Behebe das Pinning in Verbindung – ohne synchronized, mit gleichem Schutz für den Zustand. Miss erneut.

    Mit JDK 25: Erkläre, warum Dein JDK hier nichts bremst. Würdest Du Verbindung trotzdem ändern?

    Bewerten

    Notiere für virtuelle Threads:

    • Voraussetzungen: Welches JDK, welcher Code, welche Bibliotheken?
    • Vorteile: Was gewinnt Ihr – und was bleibt am Code gleich?
    • Herausforderungen: Was bremst, was verschiebt sich?
    • Betrifft mich das? Für einen REST-Microservice, ein Batch-Programm und eine Anwendung auf einem Jakarta-EE-Server.

    Kür

    • Begrenze im Batch-Import die Zahl gleichzeitiger Anfragen an die Auskunftei auf 20, ohne zu einem festen Pool zurückzukehren. Wie lange dauert der Import dann?
    • Mit JDK 25: Viele virtuelle Threads und ThreadLocal vertragen sich schlecht. Wie es ohne geht, zeigt die Übung zu Scoped Values.

    Hinweis: Die Musterlösung liegt im Branch loesung/virtual-threads; den Unterschied und eine Messtabelle zeigt ihr Pull Request. Sieh erst nach, wenn Du es selbst versucht hast.

    Reflexionsfragen

    • Warum hat das Umstellen auf virtuelle Threads unter JDK 21 zunächst wenig gebracht – und unter 25 viel?
    • Warum sind virtuelle Threads ein so wichtiges Feature im Java-Ökosystem?
