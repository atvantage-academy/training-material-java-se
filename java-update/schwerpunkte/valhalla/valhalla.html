Project Valhalla: Objekte ohne Identität

Jedes Objekt in Java hat heute eine Identität: Zwei Objekte mit gleichem Inhalt sind trotzdem zwei. Für einen Geldbetrag, einen Zeitpunkt oder eine Koordinate ist das überflüssig – und es kostet Speicher und Zeit. Project Valhalla gibt Java Objekte ohne Identität. Seit Java 28 stecken sie als Preview im JDK.

Preview in 28 · JEP 401 Vorbereitung seit 16 · JEP 390 · LTS 17 Ausblick: LTS 29 oder später

1 · Was Identität bedeutet

Nimm zwei Objekte mit demselben Inhalt, etwa LocalDate.of(2026, 10, 23) zweimal. Was geschieht mit ihnen – heute und als Wertobjekt mit --enable-preview auf JDK 28?

value record Betrag(long cent, String währung) {}   // JDK 28, --enable-preview

var a = new Betrag(1999, "EUR");
var b = new Betrag(1999, "EUR");
IO.println(a == b);                    // true – gleicher Inhalt
IO.println(Objects.hasIdentity(a));    // false

2 · Wie Werte im Speicher liegen

Ein Array von Objekten enthält heute nur Zeiger; die Objekte selbst liegen irgendwo im Heap, jedes mit einem Header. Ohne Identität darf die JVM die Felder direkt ins Array legen. Wähle eine Ansicht – gezeigt sind vier Lagerplätze, gemessen wurde mit fünf Millionen.

Gemessen mit spielwiese/Wertklassen.java auf JDK 28 Early Access (28-ea+20): fünf Millionen Plätze, Reihenfolge gemischt, bester von zehn Durchläufen. Die Anordnung im Bild ist schematisch.

    4 · Was Du heute tun kannst

    Value Objects sind Preview – in Produktionscode gehören sie noch nicht. Aber der Code, der heute schon auf die Identität von Integer, LocalDate oder Optional setzt, ist morgen ein Bruch, und manchmal schon heute ein Fehler:

    • Die Warnungen des Compilers lesen. Seit Java 16 warnt javac beim synchronized auf einer wertbasierten Klasse (Kategorie synchronization, ab JDK 25 identity), ab JDK 25 auch bei WeakReference und WeakHashMap auf solchen Klassen.
    • Zur Laufzeit nachsehen. -XX:+UnlockDiagnosticVMOptions -XX:DiagnoseSyncOnValueBasedClasses=2 meldet jede Sperre auf einer wertbasierten Klasse, auch wo der Compiler den Typ nicht kennt; der Flight Recorder hält sie als jdk.SyncOnValueBasedClass fest.
    • equals statt == für Integer, Long, LocalDate und Co. – == ist schon heute ein Fehler, sobald der Wert außerhalb von −128 bis 127 liegt.
    • Werte als Records modellieren, unveränderlich, ohne Identität im Gebrauch: Ein Record ohne Sperren und ohne == wird später mit einem Wort zum Wert-Record.

    Merksatz: Ein Wert hat keine Identität. Wer heute schon so programmiert, gewinnt mit Valhalla Speicher und Tempo – wer auf == und synchronized setzt, bekommt einen Bruch.
