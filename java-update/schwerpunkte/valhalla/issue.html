    Valhalla heute schon vorbereiten

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich wissen, wo unser Code auf die Identität von Werten setzt und was Project Valhalla daran ändert, damit ich heute schon so programmiere, dass es später kein Bruch wird.

    Lernziele

    • Du erklärst, was ein Objekt ohne Identität von einem Objekt mit Identität unterscheidet.
    • Du findest mit den Warnungen des Compilers und der Diagnose der JVM die Stellen, die auf die Identität wertbasierter Klassen setzen.
    • Du behebst diese Stellen so, dass sie heute und mit Valhalla richtig arbeiten.
    • Du begründest, warum flach abgelegte Werte Speicher und Zeit sparen – und wann die JVM sie nicht flach ablegen kann.
    • Du bewertest, was Valhalla für Eure Anwendungen bedeutet und was Ihr heute schon tun könnt.

    Definition of Done

    Den Bestand prüfen

    • Du kannst für jede der vier Stellen in Wertbasiert sagen, warum sie auf Identität setzt und was ihre Ausgabe heute zeigt.
    • Du hast die Stellen behoben, und java spielwiese/Wertbasiert.java übersetzt ohne Warnung.

    Bewertung

    • Du hast Voraussetzungen, Vorteile, Herausforderungen und den Nutzen je Anwendungsart notiert.

    Für die ganze Seite

    • Du hast die Kontrollfragen beantwortet

    Value Objects sind Preview und gehören noch nicht in Produktionscode. Aber jeder Code, der heute auf die Identität von Integer, LocalDate oder Optional setzt, bekommt mit Valhalla einen Bruch – und manchmal ist er schon heute falsch. Du suchst solche Stellen und behebst sie. Wer will, probiert mit einem Early-Access-Build von JDK 28 aus, was Valhalla daraus macht.

    Hinweis: Für die Pflicht reicht JDK 21 oder 25. Die beiden Kür-Schritte brauchen einen Early-Access-Build von JDK 28 – nur, wenn Du ihn installieren darfst oder Docker hast. Die Befehle laufen im Terminal – in IntelliJ über View → Tool Windows → Terminal, in Eclipse über Window → Show View → Terminal, jeweils im Wurzelordner des Übungsprojekts.

    Arbeitsschritte

    Worum es geht

    Ein Objekt mit Identität ist mehr als sein Inhalt: Zwei Objekte mit gleichen Feldern sind trotzdem zwei, man kann auf jedem sperren, und es braucht einen Header im Speicher. Ein Wertobjekt ist nur sein Inhalt (JEP 401, Preview in Java 28). Vorbereitet ist das seit Java 16 (JEP 390, LTS-Marke 17): Integer, LocalDate, Optional und weitere sind als wertbasiert markiert, und der Compiler warnt, wo Code auf ihre Identität setzt. Was das im Speicher bedeutet und was davon abhängt, zeigt die Visualisierung Project Valhalla: Objekte ohne Identität.

    Den Bestand prüfen

    spielwiese/Wertbasiert.java enthält vier Stellen aus einem Bestellsystem, wie sie in echtem Code vorkommen: ein Lager, das auf seinem Zähler sperrt, einen Cache für Tageskurse, einen Vergleich zweier Mengen und einen Zähler je Artikelnummer. Starte das Programm:

    java spielwiese/Wertbasiert.java

    Lies zuerst die Warnungen des Compilers über der Ausgabe: Welche Stellen meldet er, und welche nicht? Lies dann die Ausgabe: Welches der vier Ergebnisse ist schon heute falsch? Starte das Programm mehrmals – bleibt der Bestand gleich?

    Hinweis: JDK 21 meldet die Kategorie synchronization, JDK 25 identity und warnt dort bei mehr Stellen.

    Zur Laufzeit nachsehen

    Der Compiler sieht nur Typen. Wo auf einer Variablen vom Typ Object gesperrt wird, die zur Laufzeit ein Integer hält, schweigt er. Die JVM meldet jede solche Sperre, und der Flight Recorder zeichnet sie auf. Starte das Programm mit Diagnose und Aufzeichnung:

    java -XX:+UnlockDiagnosticVMOptions -XX:DiagnoseSyncOnValueBasedClasses=2 -XX:StartFlightRecording=filename=wert.jfr spielwiese/Wertbasiert.java

    Die Konsole läuft dabei voll – je Sperre ein Eintrag. Lies die Aufzeichnung als Tabelle:

    jfr view SyncOnValueBasedClass wert.jfr

    In welcher Methode wird gesperrt, und auf welcher Klasse? Wie würdet Ihr so etwas in Eurem Bestand finden, etwa in einem Lasttest?

    Die Stellen beheben

    Behebe alle vier Stellen in spielwiese/Wertbasiert.java so, dass sie heute richtig arbeiten und mit Valhalla nicht brechen. Starte danach wieder:

    java spielwiese/Wertbasiert.java

    Erst wenn keine Warnung mehr kommt und die Ausgabe stimmt, bist Du fertig.

    Die Lösung: Ersetze den Inhalt von spielwiese/Wertbasiert.java durch:

    import java.math.BigDecimal;
import java.time.LocalDate;
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

/**
 * Vier Stellen, an denen Code stillschweigend auf die Identität einer wertbasierten
 * Klasse setzt – Integer, LocalDate und Co. (JEP 390, seit Java 16). Mit Project
 * Valhalla werden diese Klassen zu Wertklassen ohne Identität (JEP 401, Preview in
 * Java 28). Läuft ab Java 11:
 *
 *     java spielwiese/Wertbasiert.java
 *
 * Der Compiler warnt dabei schon heute. Wo zur Laufzeit auf einer wertbasierten Klasse
 * synchronisiert wird, meldet die JVM mit:
 *
 *     java -XX:+UnlockDiagnosticVMOptions -XX:DiagnoseSyncOnValueBasedClasses=2 spielwiese/Wertbasiert.java
 *
 * Mit einem Early-Access-Build von JDK 28 zeigt sich, was Valhalla daraus macht:
 *
 *     java --enable-preview spielwiese/Wertbasiert.java
 */
public class Wertbasiert {

    // 1 · Ein Lagerbestand, der auf seinem eigenen Zähler sperrt
    static class Lager {
        private final Object sperre = new Object();
        private int bestand = 0;

        void zubuchen(int menge) {
            synchronized (sperre) {
                bestand = bestand + menge;
            }
        }

        int bestand() {
            synchronized (sperre) {
                return bestand;
            }
        }
    }

    // 2 · Ein Cache für Tageskurse, der Einträge vergessen darf
    static final Map<LocalDate, BigDecimal> KURSE = new HashMap<>();

    // 3 · Ein Vergleich zweier Mengen
    static boolean gleicheMenge(Integer a, Integer b) {
        return a.equals(b);
    }

    // 4 · Ein Zähler je Artikelnummer, der Objekte statt Werte zählt
    static final Map<Integer, Integer> AUFRUFE = new HashMap<>();

    public static void main(String[] args) throws Exception {
        prüfe("1 · Lager", Wertbasiert::lager);
        prüfe("2 · Kurse", Wertbasiert::kurse);
        prüfe("3 · Mengen", () -> "100 == 100: " + gleicheMenge(100, 100)
                + ", 1000 == 1000: " + gleicheMenge(1000, 1000));
        prüfe("4 · Aufrufe", Wertbasiert::aufrufe);
    }

    static String lager() throws InterruptedException {
        Lager lager = new Lager();
        ExecutorService ausführer = Executors.newFixedThreadPool(4);
        for (int i = 0; i < 1_000; i++) {
            ausführer.submit(() -> lager.zubuchen(1));
        }
        ausführer.shutdown();
        ausführer.awaitTermination(1, TimeUnit.MINUTES);
        return "1000 Stück zugebucht, Bestand " + lager.bestand();
    }

    static String kurse() {
        KURSE.put(LocalDate.of(2026, 10, 23), new BigDecimal("1.0842"));
        return "Kurse im Cache: " + KURSE.size();
    }

    static String aufrufe() {
        for (int i = 0; i < 3; i++) {
            AUFRUFE.merge(Integer.valueOf(4711), 1, Integer::sum);
        }
        return "3 Aufrufe für Artikel 4711, Einträge: " + AUFRUFE.size();
    }

    interface Prüfung {
        String ergebnis() throws Exception;
    }

    static void prüfe(String name, Prüfung prüfung) {
        try {
            System.out.println(name + ": " + prüfung.ergebnis());
        } catch (Throwable fehler) {
            System.out.println(name + ": " + fehler);
        }
    }
}
    • Lager: Eine eigene Sperre, die sich nie ändert, und ein int als Zähler. Der alte Zähler bestand = bestand + menge erzeugte bei jeder Buchung ein neues Integer; wer darauf sperrt, sperrt jedes Mal auf etwas anderem und verliert Buchungen. Alternative: ein AtomicInteger.
    • Kurse: Eine WeakHashMap hält ihre Schlüssel über ihre Identität fest. Für Werte wie LocalDate passt eine gewöhnliche Map (HashMap, ConcurrentHashMap) mit einer ausdrücklichen Regel, wann Einträge entfallen.
    • Mengen: a.equals(b) statt a == b – oder gleich int. == auf Integer stimmt nur, solange der Cache für −128 bis 127 hilft.
    • Aufrufe: Eine HashMap statt der IdentityHashMap – gezählt werden soll je Artikelnummer, nicht je Objekt.

    Die Ausgabe lautet danach:

    1 · Lager: 1000 Stück zugebucht, Bestand 1000
2 · Kurse: Kurse im Cache: 1
3 · Mengen: 100 == 100: true, 1000 == 1000: true
4 · Aufrufe: 3 Aufrufe für Artikel 4711, Einträge: 1

    Kür: Valhalla ausprobieren (JDK 28 Early Access)

    Lade einen Early-Access-Build von JDK 28 von jdk.java.net/28, entpacke ihn in einen eigenen Ordner und rufe dessen bin/java mit dem vollen Pfad auf – er ersetzt Dein JDK nicht. Mit Docker geht es ohne Installation, im Wurzelordner des Übungsprojekts:

    docker run --rm -v "$PWD":/w -w /w openjdk:28-ea-jdk java --enable-preview spielwiese/Wertbasiert.java

    Starte zuerst den unveränderten Stand (git stash, danach git stash pop), dann Deine behobene Fassung, jeweils mit --enable-preview. Was geschieht mit den vier Stellen? Welche bricht beim Übersetzen, welche zur Laufzeit, und welche liefert plötzlich ein anderes Ergebnis?

    Kür: Werte im Speicher (JDK 28 Early Access)

    spielwiese/Wertklassen.java legt fünf Millionen Lagerplätze an – als gewöhnlichen Record und als Wert-Record – und misst Speicher und Durchlaufzeit. Starte es mit dem Early-Access-Build:

    java --enable-preview spielwiese/Wertklassen.java

    Mit Docker:

    docker run --rm -v "$PWD":/w -w /w openjdk:28-ea-jdk java --enable-preview spielwiese/Wertklassen.java

    Wie viel Speicher und Zeit spart der Wert-Record? Warum ist GroßerWertPlatz mit zwei int nicht kleiner, sondern größer? Die Visualisierung gibt die Antwort.

    Bewerten

    Halte in Stichworten fest:

    • Voraussetzungen: Was braucht es, bis Ihr Value Objects nutzen könnt – JDK, Ende der Preview, Frameworks, Werkzeuge?
    • Vorteile: Wo spart es bei Euch Speicher oder Zeit, wo bildet es die Domäne genauer ab?
    • Herausforderungen: Welche Stellen in Eurem Code oder Euren Bibliotheken setzen auf Identität?
    • Betrifft mich das? Nutzen gering, mittel oder hoch – für einen REST-Microservice, ein Batch-Programm, eine Server-Anwendung. Und was davon tut Ihr schon heute?

    Reflexionsfragen

    • Euer Code vergleicht an einer Stelle zwei Integer mit ==, und alle Tests sind grün. Warum ist das trotzdem ein Fehler – heute und mit Valhalla?
    • Welche Frameworks oder Bibliotheken in Eurem Bestand könnten auf die Identität von Objekten setzen – Caches, Sperren, Proxys, ORM?
    • Wo in Eurer Domäne stecken Werte, die heute Klassen mit Identität sind – Geldbeträge, Zeiträume, Adressen?
    • Value Objects sind Preview. Was müsste geschehen, bevor Ihr sie in Produktionscode einsetzt?
