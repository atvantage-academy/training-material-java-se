Das Modulsystem

Seit Java 9 kann ein JAR sagen, was es braucht und was es zeigt. Die JVM prüft das beim Start – statt mitten im Betrieb festzustellen, dass etwas fehlt. Das Modulsystem ist freiwillig; seine Kapselung des JDK betrifft trotzdem alle.

seit Java 9 LTS 11 JEP 261 jlink: JEP 282 Modul-Importe: LTS 25, JEP 511

1 · Worum es geht

Zwei JARs: app.jar enthält die Klasse Start, katalog.jar die Klassen Artikel und Cache – beide public, aber in verschiedenen Packages. Start braucht beide:

package shop.app;

import shop.katalog.Artikel;
import shop.katalog.intern.Cache;

public class Start {
    public static void main(String[] args) {
        Artikel artikel = new Artikel("Tasse");
        Cache.merken(artikel);
    }
}
Classloading bisher

app.jar

  • shop/app/Start.class

lädt→

katalog.jar

  • ✓ shop/katalog/Artikel.class – public
  • ✓ shop/katalog/intern/Cache.class – public

Gestartet wird über den Klassenpfad:

java -cp app.jar:katalog.jar shop.app.Start
  • Beide Klassen werden geladen. public heißt: für alle – dass Cache in einem Package intern liegt, schützt nur sein Name.
  • Geladen wird erst, wenn main eine Klasse braucht (Lazy Class Loading). Welche JARs Start braucht, steht nirgends. Fehlt katalog.jar, startet die Anwendung trotzdem und scheitert erst in Zeile 8:
Exception in thread "main" java.lang.NoClassDefFoundError: shop/katalog/Artikel
    at shop.app.Start.main(Start.java:8)
mit Modulen

app.jar

module app {
    requires katalog;
}
  • shop/app/Start.class

requires→

katalog.jar

module katalog {
    exports shop.katalog;
}
  • ✓ shop/katalog/Artikel.class – exportiert
  • ✗ shop/katalog/intern/Cache.class – public, aber nicht exportiert

Jedes JAR bringt eine module-info.java mit. Das Modul heißt katalog, sein Package shop.katalog: requires nennt das Modul, exports das Package. Auf dem Modulpfad schaltet die module-info.java das Modulsystem ein:

java -p app.jar:katalog.jar -m app/shop.app.Start
  • Nur das exportierte Package ist erreichbar. Artikel geht, Cache nicht – schon der Compiler lehnt Start ab:
error: package shop.katalog.intern is not visible
  (package shop.katalog.intern is declared in module katalog,
   which does not export it)
  • Geprüft wird beim Start, bevor main läuft. Die JVM löst die Module auf: Ist jedes requires erfüllt? Fehlt katalog.jar, startet die Anwendung gar nicht erst. Klassen werden weiter erst bei Bedarf geladen – aber dass ihre Module da sind, steht schon fest.
  • Die Abhängigkeiten sind deklarativ. Sie stehen im JAR selbst, statt sich erst aus dem Programmlauf zu ergeben. Maven kennt sie beim Bauen – mit Modulen kennen sie auch Compiler und JVM.

Was in einer module-info.java stehen kann

Pflicht ist nur der Name: module katalog { } ist ein gültiges Modul – es braucht nichts außer java.base und zeigt nichts. Alles andere sind Direktiven:

Direktive nennt bedeutet
requires geld; ein Modul Ich brauche dieses Modul.
requires transitive geld; ein Modul Wer mich liest, liest es mit.
requires static org.jspecify; ein Modul Nur zum Übersetzen nötig.
exports shop.katalog; ein Package Dieses Package ist meine API.
exports shop.katalog.intern to pdf; ein Package API nur für die genannten Module.
opens shop.katalog.daten; ein Package Reflection erlaubt, auch auf Privates – nur zur Laufzeit.
uses shop.katalog.export.Exportformat; ein Interface Ich suche Implementierungen über den ServiceLoader.
provides shop.katalog.export.Exportformat with shop.pdf.PdfFormat; ein Interface und eine Klasse Ich biete eine Implementierung an.

requires nennt Module, exports und opens nennen Packages. Ein Package lässt sich nicht anfordern – requires shop.katalog.intern; findet kein Modul dieses Namens:

error: module not found: shop.katalog.intern

Dazu kann statt module auch open module stehen: Dann sind alle Packages für Reflection geöffnet. Wie die Direktiven zusammenspielen, zeigt Teil 3.

Und wenn ein JAR keine module-info.java hat?

Der Katalog hat keine

app.jar

Modulpfad · benanntes Modul

module app {
    requires katalog;
}

requires→

katalog.jar

Modulpfad · automatisches Modul katalog

keine module-info.class

  • ✓ shop.katalog – exportiert
  • ✓ shop.katalog.intern – exportiert

Beide JARs liegen auf dem Modulpfad:

java -p app.jar:katalog.jar -m app/shop.app.Start
  • Der Katalog wird ein automatisches Modul. Sein Name kommt aus dem Eintrag Automatic-Module-Name im Manifest, sonst aus dem Dateinamen: aus katalog.jar wird katalog. Deshalb kann app ihn mit requires nennen – das ist die Brücke für Bibliotheken, die noch keine module-info.java haben.
  • Ein automatisches Modul exportiert alle seine Packages. Cache ist wieder erreichbar, Start läuft durch. Gekapselt ist nur, was ein JAR selbst erklärt.
  • Die Prüfung beim Start bleibt: Fehlt katalog.jar, startet app nicht.
Die Anwendung hat keine

app.jar

Klassenpfad · unbenanntes Modul

keine module-info.class

  • shop/app/Start.class

liest→

katalog.jar

Modulpfad · benanntes Modul

module katalog {
    exports shop.katalog;
}
  • ✓ shop.katalog – exportiert
  • ✗ shop.katalog.intern – nicht exportiert

Die Anwendung liegt auf dem Klassenpfad, der Katalog auf dem Modulpfad:

java -cp app.jar -p katalog.jar --add-modules katalog shop.app.Start
  • Die Anwendung läuft im unbenannten Modul. Es liest alle Module – aber nur die, die überhaupt aufgelöst werden. Weil niemand katalog mit requires nennt, muss man ihn mit --add-modules katalog dazunehmen. Ohne den Schalter fehlt das Modul, und es kommt wie bisher erst in Zeile 8 ein NoClassDefFoundError.
  • Die Kapselung des Katalogs gilt trotzdem. Artikel geht, Cache nicht. Der Compiler meldet es wie im Reiter „mit Modulen“; ein schon übersetztes Start lädt Artikel in Zeile 8 und scheitert erst in Zeile 9, mitten im Lauf:
Exception in thread "main" java.lang.IllegalAccessError:
  class shop.app.Start (in unnamed module @…) cannot access
  class shop.katalog.intern.Cache (in module katalog)
  because module katalog does not export
  shop.katalog.intern to unnamed module @…
Alles auf dem Klassenpfad

app.jar

Klassenpfad · unbenanntes Modul

  • shop/app/Start.class

lädt→

katalog.jar

Klassenpfad · unbenanntes Modul

  • ✗ module-info.class – ignoriert
  • ✓ shop/katalog/Artikel.class
  • ✓ shop/katalog/intern/Cache.class

Beide JARs liegen auf dem Klassenpfad – ob mit oder ohne module-info.class:

java -cp app.jar:katalog.jar shop.app.Start
  • Alles ist wie bisher. Auf dem Klassenpfad bilden alle JARs zusammen das unbenannte Modul; eine module-info.class darin wird ignoriert. Cache ist erreichbar, ein fehlendes JAR fällt erst beim Laden auf.
  • So läuft jeder Bestand, der nichts umstellt – auch auf Java 25. Das Modulsystem schaltet erst ein, wer den Modulpfad benutzt.

Für alle gilt: Das JDK ist gekapselt. Seit Java 9 besteht es selbst aus Modulen (JEP 200, 220). Seine Interna wie sun.misc oder die privaten Felder von java.util.ArrayList waren zuerst nur mit Warnung erreichbar (JEP 260), seit Java 16 standardmäßig gesperrt (JEP 396) und seit Java 17 ohne globalen Ausweg (JEP 403). Wer per Reflection hineingreift – oft eine Bibliothek, nicht der eigene Code –, braucht den Schalter --add-opens java.base/java.util=ALL-UNNAMED, auch ganz ohne eigene Module.

2 · Was der Modulpfad außerdem prüft

Ein fehlendes JAR und den Griff in ein internes Package zeigt Teil 1. Zwei weitere Pannen bemerkt der Klassenpfad gar nicht: Er legt die JARs einfach hintereinander und nimmt die erste Klasse, die er findet. Wähle eine Panne und vergleiche:

Jedes Modul beschreibt sich in einer Datei module-info.java im Wurzelordner seiner Quellen. Wähle eine Direktive – der Graph zeigt, welche Beziehung sie stiftet, der Code, wo sie steht.

4 · Das eigene Laufzeit-Image: jlink

jlink (JEP 282) baut aus Modulen eine Laufzeitumgebung, die nur enthält, was die Anwendung braucht – samt Startskript:

jlink --module-path target/module --add-modules app,pdf --strip-debug --no-header-files --no-man-pages --launcher shop=app/shop.app.Start --output target/bild
Klein

Gemessen mit Temurin 25: das ganze JDK 253 MB, ein Image aus java.base und drei eigenen Modulen 54 MB.

Nur benannte Module

Ein automatisches Modul nimmt jlink nicht:

Error: automatic module cannot be used with jlink:
       pdf from file:///…/pdf.jar
Dienste nur auf Zuruf

--add-modules app nimmt nur, was app mit requires erreicht. Ein Anbieter über provides fehlt im Image – ihn nennt man mit, oder --bind-services holt alle Anbieter, auch die des JDK.

Woraus jlink baut: JMOD-Dateien

Die Module des JDK liegen für jlink als JMOD-Dateien bereit – seit Java 9, im Ordner jmods/ des JDK, je Modul eine Datei (java.base.jmod, java.sql.jmod, …). Ein JMOD ist ein Format nur für jlink und den Compiler: Es nimmt alles auf, was ein Modul im fertigen Image braucht, auch das, was in kein JAR gehört.

Mehr als Klassen

Gemessen an java.base.jmod (JDK 25): Ordner classes/ mit 7323 Einträgen, dazu lib/ (native Bibliotheken), bin/ (Programme), conf/ (Konfiguration wie java.security), include/ (C-Header), man/ und legal/ (Lizenztexte). Ein JDK 25 mit jmods/ trägt 69 davon, zusammen gut 80 MB.

Nicht zum Starten

Übersetzen und Linken gehen mit JMODs, starten nicht:

Error occurred during initialization of boot layer
java.lang.module.FindException: JMOD format not supported
  at execution time: katalog.jmod
Eigene JMODs

Das Werkzeug jmod baut sie (jmod create --class-path … --libs … katalog.jmod). jlink nimmt JMODs und modulare JARs gemischt. Ein eigenes JMOD lohnt sich nur, wenn ein Modul native Bibliotheken oder Konfiguration mitbringt – sonst genügt das modulare JAR.

JDK ohne jmods

Seit Java 24 darf ein JDK ohne seinen Ordner jmods/ ausgeliefert werden (JEP 493) – rund 80 MB kleiner. jlink nimmt die Module dann aus dem laufenden JDK selbst. Temurin 25 tut das, der OpenJDK-Build von jdk.java.net nicht. Nur das Modul jdk.jlink selbst lässt sich dann nicht ins Image nehmen, und daran scheitert --bind-services:

Error: This JDK does not contain packaged modules and cannot
       be used to create another image with the jdk.jlink module

5 · Seit Java 25: ein ganzes Modul importieren

Die Modul-Importe (JEP 511, final in Java 25, LTS 25) holen alle Packages, die ein Modul exportiert, mit einer Zeile – auch in Code, der selbst kein Modul ist:

import module java.base;      // java.util, java.time, java.io, …

class Bericht {
    List<LocalDate> tage = new ArrayList<>();
}

6 · Use Cases: wer das Modulsystem nutzt – und wer nicht

Das Modulsystem gibt es seit Java 9, aber für Anwendungen ist es nicht zum Standard geworden. Ob es sich lohnt, hängt vor allem daran, wer die Laufzeit mitbringt: die Anwendung selbst, ein Framework oder ein Server.

Wo es Anwendung findet
  • Im JDK selbst. Es ist der größte Nutzer: rund 70 Module mit gekapselten Interna. Das betrifft jede Anwendung, auch ohne eigene Module (Teil 1).
  • In Desktop-Anwendungen mit JavaFX. Seit Version 11 kommt JavaFX nicht mehr mit dem JDK, sondern als eigene Module (javafx.controls, javafx.fxml, …). Eine modulare Anwendung baut mit jlink und jpackage (JEP 392, seit Java 16) ein Installationspaket mit eigener Laufzeit – auf dem Rechner der Anwender muss kein Java installiert sein. Lädt man JavaFX vom Klassenpfad, warnt es seit Version 16 beim Start vor einer nicht unterstützten Konfiguration.
  • In Werkzeugen, die ihre Laufzeit mitbringen – Kommandozeilenprogramme, Batch-Programme beim Kunden, Installer: überall dort, wo kein passendes JDK vorausgesetzt werden kann.
  • In Bibliotheken. Viele bringen eine module-info.class mit oder setzen zumindest Automatic-Module-Name im Manifest. Dann können modulare Anwendungen sie mit einem stabilen Namen nennen – auch wenn die meisten Nutzer auf dem Klassenpfad bleiben.
  • In großen Codebasen, die Grenzen zwischen Teilsystemen erzwingen wollen: exports macht die API eines Teilsystems prüfbar, schon beim Übersetzen.
  • Für eine schlanke Laufzeit – auch ohne eigene Module. jlink kann nur das JDK verkleinern; die Anwendung bleibt auf dem Klassenpfad. Gemessen mit Temurin 25 auf macOS: 43 MB statt 294 MB für das ganze JDK. Gut für schlanke Container-Images.

Ermittle, welche JDK-Module die JARs brauchen:

jdeps --print-module-deps --ignore-missing-deps app.jar katalog.jar

Bau aus diesen Modulen eine Laufzeit, hier nur aus java.base:

jlink --add-modules java.base --strip-debug --no-header-files --no-man-pages --output laufzeit

Starte die Anwendung mit dieser Laufzeit auf dem Klassenpfad:

laufzeit/bin/java -cp app.jar:katalog.jar shop.app.Start
Vorteile
  • Zuverlässige Konfiguration. Fehlende und doppelte Module und geteilte Packages fallen beim Start auf, nicht mitten im Betrieb (Teile 1 und 2).
  • Starke Kapselung. public heißt nicht mehr „für alle“. Interna bleiben intern, auch gegen Reflection – es sei denn, ein Package wird ausdrücklich geöffnet.
  • Deklarative Abhängigkeiten. Sie stehen im JAR und sind für Compiler, JVM und Werkzeuge wie jdeps lesbar, nicht nur für den Build.
  • Eine eigene, kleine Laufzeit. jlink nimmt nur die Module, die gebraucht werden: weniger Speicherplatz, weniger Angriffsfläche, kein vorinstalliertes JDK nötig (Teil 4).
Spring Boot, Quarkus und Server

Die großen Frameworks gehen eigene Wege – meist, um dasselbe Ziel zu erreichen: schneller starten, weniger Speicher, kleinere Auslieferung.

  • Spring Boot packt die Bibliotheken als verschachtelte JARs in ein ausführbares JAR und lädt sie mit einem eigenen Classloader. Die Anwendung läuft damit auf dem Klassenpfad, im unbenannten Modul. Für Start und Speicher setzt Spring auf Spring AOT mit GraalVM Native Image (seit Spring Boot 3) und auf CDS bzw. den AOT-Cache der JVM (JEP 483).
  • Quarkus verlegt Arbeit aus dem Start in den Build, lädt Klassen mit eigenem Classloading und baut Native Images mit GraalVM bzw. Mandrel. Eigene module-info.java sind dort nicht der vorgesehene Weg.
  • Jakarta-EE-Server bestimmen das Classloading selbst: Eine Anwendung wird als WAR oder EAR auf den Klassenpfad des Servers deployt. Mancher Server hat ein eigenes Modulsystem für seine Teile, etwa WildFly mit JBoss Modules.
  • Native Image geht weiter als jlink: Es baut ein natives Programm ohne JVM. Dafür verlangt es eine geschlossene Welt – was zur Laufzeit per Reflection gebraucht wird, muss beim Bauen bekannt sein.
Warum es kein Standard wird
  • Abwärtskompatibilität. Der Klassenpfad bleibt, damit jeder Bestand weiterläuft. Ein Pflicht-Umstieg würde genau das brechen, was Java verspricht.
  • Reflection-lastige Frameworks. Spring, CDI, JPA und JSON-Binding greifen zur Laufzeit auf Felder und Konstruktoren zu. Jedes betroffene Package braucht opens – oder das ganze Modul wird open module, und von der Kapselung bleibt wenig übrig.
  • Das Ökosystem zieht nicht vollständig mit. Bibliotheken mit geteilten Packages oder ohne module-info gibt es weiter. Automatische Module tragen wacklige Namen aus dem Dateinamen, und jlink nimmt sie nicht – eine nicht modulare Abhängigkeit verhindert das Image der ganzen Anwendung.
  • Doppelte Buchführung. Die Abhängigkeiten stehen in der POM bzw. im Gradle-Build und noch einmal in der module-info.java; Versionen kennt nur der Build.
  • Werkzeuge und Packaging. Tests auf dem Modulpfad brauchen Kunstgriffe (Surefire patcht die Testklassen ins Modul), Fat-JARs und Shading passen nicht zum Modulpfad.
  • Der Nutzen ist anderswo schon da. Abhängigkeiten prüft der Build, schlanke Auslieferung liefern Container-Images und Native Image, Architekturregeln Werkzeuge wie ArchUnit.
