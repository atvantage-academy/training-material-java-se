    Die Bestellexporte modularisieren

    Als Entwickler:in, die eine Java-8-Anwendung auf ein aktuelles Release heben soll, möchte ich wissen, was es kostet und was es bringt, die Anwendung in Module zu schneiden, damit ich entscheiden kann, ob sich das für unseren Bestand lohnt.

    Lernziele

    • Du deklarierst ein Modul mit module-info.java und legst fest, welche Module es liest und welche Packages es exportiert.
    • Du erklärst, warum ein public-Typ in einem nicht exportierten Package von außen nicht mehr erreichbar ist.
    • Du meldest einen Erweiterungspunkt mit uses und provides an und startest die Anwendung auf dem Modulpfad.
    • Du baust mit jlink eine eigene Laufzeitumgebung und erklärst, warum ein Dienstanbieter darin fehlen kann.
    • Du bewertest, wo das Modulsystem im Bestand Probleme macht und ob es sich für Eure Anwendungen lohnt.

    Definition of Done

    Module

    • schwerpunkte/modulsystem baut mit Release 11, und jeder der drei Teile hat eine module-info.java.
    • BestellungTest und ExportlaufTest sind unverändert grün.
    • Exportlauf läuft auf dem Modulpfad und findet das CSV-Format.

    Laufzeit-Image

    • Dein Image unter schwerpunkte/modulsystem/target startet exportlauf, und die Ausgabe enthält den CSV-Export.
    • Du kannst sagen, welche Module im Image liegen und wie groß es im Vergleich zum JDK ist.

    Bewertung

    • Du hast den Nutzen je Anwendungsart, Voraussetzungen, Vorteile und Herausforderungen notiert.

    Für die ganze Seite

    • Du hast die Kontrollfragen beantwortet

    Ein JAR auf dem Klassenpfad sagt nicht, was es braucht und was es anderen zeigen will. Das Modulsystem gibt ihm genau diese zwei Angaben – und die JVM prüft sie, bevor die Anwendung startet. Du schneidest ein kleines Programm aus drei Teilen in Module, startest es auf dem Modulpfad und baust daraus eine eigene Laufzeitumgebung.

    Arbeitsschritte

    Worum es geht

    Seit Java 9 besteht das JDK aus Modulen, und eigene Anwendungen können es ebenso (JEP 261, LTS-Marke 11). Ein Modul ist ein JAR mit einer module-info.class: Darin steht, welche anderen Module es liest (requires), welche seiner Packages von außen sichtbar sind (exports) und welche Dienste es nutzt oder anbietet (uses, provides). Was die Direktiven bewirken und was der Klassenpfad nicht merkt, zeigt die Visualisierung Das Modulsystem.

    Den Bestand ansehen und starten

    Das Modul schwerpunkte/modulsystem exportiert Bestellungen. Es hat drei Teile, jeder ein eigenes Maven-Modul und ein eigenes JAR:

    • modell – Bestellung, Position und Betrag im Package bestellwesen.modell, der Erweiterungspunkt Exportformat im Package bestellwesen.export und Betragsformat im Package bestellwesen.modell.intern.
    • csv – das Format CsvFormat, angemeldet in src/main/resources/META-INF/services/bestellwesen.export.Exportformat.
    • anwendung – Exportlauf fragt den ServiceLoader nach allen Exportformaten. Das CSV-Format kennt die Anwendung nicht beim Namen; es ist nur zur Laufzeit da (Scope runtime in ihrer pom.xml).

    Baue alle drei Teile:

    Kommandozeile

    Baue im Wurzelordner des Übungsprojekts und lass die Tests laufen:

    mvn clean verify -f schwerpunkte/modulsystem/pom.xml
    IntelliJ

    Starte die Run Configuration schwerpunkte-modulsystem. Sie baut mit clean.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration schwerpunkte-modulsystem. Sie baut mit clean.

    VS Code

    Starte über Terminal → Run Task… den Task schwerpunkte-modulsystem. Er baut mit clean.

    Die drei JARs liegen danach gemeinsam in schwerpunkte/modulsystem/target/module.

    Starte die Anwendung auf dem Klassenpfad:

    Kommandozeile

    Starte sie im Wurzelordner des Übungsprojekts:

    java -cp "schwerpunkte/modulsystem/target/module/*" bestellwesen.anwendung.Exportlauf

    Das Release hochstellen

    Stell in schwerpunkte/modulsystem/pom.xml die Property maven.compiler.release an der Stelle mit dem Kommentar „Hier hochstellen.“ von 8 auf 11. Sie gilt für alle drei Teile. Baue danach wie oben – der Build ist grün, noch hat sich nichts geändert.

    Hinweis: Immer mit clean. Ändert sich nur das Release, hält Maven die übersetzten Klassen für aktuell.

    Die JARs haben noch keine module-info.class. Starte sie trotzdem einmal auf dem Modulpfad:

    Kommandozeile

    Module deklarieren

    Leg in jedem der drei Teile unter src/main/java eine Datei module-info.java an – direkt in src/main/java, nicht in einem Package-Ordner. Die Module heißen bestellwesen.modell, bestellwesen.csv und bestellwesen.anwendung.

    • Das Modell exportiert seine API und den Erweiterungspunkt, aber nicht das Package intern.
    • CSV-Format und Anwendung lesen das Modell.

    Baue danach wie oben. Lies die Meldung des Compilers und behebe sie an der Ursache – ohne das Package intern für alle zu exportieren.

    Hinweis: In IntelliJ nach dem Hochstellen des Release einmal Load Maven Changes wählen, sonst übersetzt die IDE die module-info.java noch mit Release 8.

    Die Lösung: Leg diese drei Dateien an.

    schwerpunkte/modulsystem/modell/src/main/java/module-info.java:

    module bestellwesen.modell {
    exports bestellwesen.modell;
    exports bestellwesen.export;
}

    schwerpunkte/modulsystem/csv/src/main/java/module-info.java:

    module bestellwesen.csv {
    requires bestellwesen.modell;
}

    schwerpunkte/modulsystem/anwendung/src/main/java/module-info.java:

    module bestellwesen.anwendung {
    requires bestellwesen.modell;
}

    Der Compiler meldet danach „package bestellwesen.modell.intern is not visible“ – in Exportlauf. Die Anwendung nutzt stattdessen die API Betrag.alsEuro(…) aus bestellwesen.modell. Ersetze in schwerpunkte/modulsystem/anwendung/src/main/java/bestellwesen/anwendung/Exportlauf.java Zeile 12 durch:

    import bestellwesen.modell.Betrag;

    und Zeile 34 durch:

            System.out.println("Gesamt: " + Betrag.alsEuro(gesamt));

    Die Alternative wäre exports bestellwesen.modell.intern to bestellwesen.anwendung; – ein qualifizierter Export macht die Kopplung sichtbar, statt sie zu beseitigen.

    Den Erweiterungspunkt anmelden

    Jetzt übersetzt alles, aber ExportlaufTest ist rot. Lies die Meldung und ergänze die passende Direktive in der module-info.java der Anwendung. Baue erneut, bis die Tests grün sind.

    Starte im Wurzelordner des Übungsprojekts:

    VS Code

    Starte über Terminal → Run Task… den Task schwerpunkte-modulsystem-modulpfad. Er baut alle drei Teile und startet danach die Anwendung; seine Ausgabe steht am Ende des Protokolls.

    Die Tests sind grün, aber das Programm findet kein Format. Was fehlt dem CSV-Modul, und warum genügt die Datei unter META-INF/services nicht mehr? Ergänze es, baue und starte noch einmal.

    Die Lösung: Die Anwendung meldet mit uses, dass sie den Dienst nutzt – ohne meldet der ServiceLoader „module bestellwesen.anwendung does not declare uses“. Ersetze den Inhalt von schwerpunkte/modulsystem/anwendung/src/main/java/module-info.java durch:

    module bestellwesen.anwendung {
    requires bestellwesen.modell;

    uses bestellwesen.export.Exportformat;
}

    Das CSV-Format bietet den Dienst mit provides an; in einem benannten Modul beachtet die JVM META-INF/services nicht. Ersetze den Inhalt von schwerpunkte/modulsystem/csv/src/main/java/module-info.java durch:

    module bestellwesen.csv {
    requires bestellwesen.modell;

    provides bestellwesen.export.Exportformat with bestellwesen.csv.CsvFormat;
}

    Warum die Tests schon vorher grün waren: Surefire legt das CSV-JAR auf den Klassenpfad, weil die Anwendung es nicht mit requires nennt – und dort gilt die Datei unter META-INF/services. Lass sie deshalb stehen.

    Ein eigenes Laufzeit-Image bauen

    Baue mit jlink eine Laufzeitumgebung, die nur die Anwendung und das enthält, was sie braucht, und lass Dir zeigen, welche Module darin liegen:

    Kommandozeile

    Baue im Wurzelordner des Übungsprojekts das Image:

    jlink --module-path schwerpunkte/modulsystem/target/module --add-modules bestellwesen.anwendung --strip-debug --no-header-files --no-man-pages --launcher exportlauf=bestellwesen.anwendung/bestellwesen.anwendung.Exportlauf --output schwerpunkte/modulsystem/target/bild

    Lass Dir zeigen, welche Module im Image liegen:

    schwerpunkte/modulsystem/target/bild/bin/java --list-modules
    IntelliJ

    Starte die Run Configuration schwerpunkte-modulsystem-image. Sie baut alle drei Teile und das Image unter schwerpunkte/modulsystem/target/bild und zeigt die Module im Image; sie stehen am Ende des Protokolls.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration schwerpunkte-modulsystem-image. Sie baut alle drei Teile und das Image unter schwerpunkte/modulsystem/target/bild und zeigt die Module im Image; sie stehen am Ende des Protokolls.

    VS Code

    Starte über Terminal → Run Task… den Task schwerpunkte-modulsystem-image. Er baut alle drei Teile und das Image unter schwerpunkte/modulsystem/target/bild und zeigt die Module im Image; sie stehen am Ende des Protokolls.

    Starte das Image über sein Startskript – auf der Kommandozeile oder im Terminal der IDE (IntelliJ: View → Tool Windows → Terminal, Eclipse: Window → Show View → Terminal), im Wurzelordner des Übungsprojekts. Es braucht weder Maven noch ein installiertes JDK (unter Windows schwerpunkte\modulsystem\target\bild\bin\exportlauf.bat):

    schwerpunkte/modulsystem/target/bild/bin/exportlauf

    Das Image findet kein Format. Bau ein zweites unter schwerpunkte/modulsystem/target/bild-mit-csv, in dem das CSV-Format dabei ist, und vergleiche die Größe beider Images mit der Deines JDK.

    Die Lösung: --add-modules bestellwesen.anwendung nimmt nur, was die Anwendung mit requires erreicht – sie selbst, das Modell und java.base. Ein Anbieter über provides kommt nur mit, wenn man ihn nennt. Baue das zweite Image mit dem CSV-Format:

    Kommandozeile

    Baue im Wurzelordner des Übungsprojekts das zweite Image:

    jlink --module-path schwerpunkte/modulsystem/target/module --add-modules bestellwesen.anwendung,bestellwesen.csv --strip-debug --no-header-files --no-man-pages --launcher exportlauf=bestellwesen.anwendung/bestellwesen.anwendung.Exportlauf --output schwerpunkte/modulsystem/target/bild-mit-csv
    IntelliJ

    Starte die Run Configuration schwerpunkte-modulsystem-image-mit-csv. Sie baut alle drei Teile und beide Images, bild und bild-mit-csv unter schwerpunkte/modulsystem/target.

    Eclipse

    Starte unter Run → Run Configurations… → Maven Build die Konfiguration schwerpunkte-modulsystem-image-mit-csv. Sie baut alle drei Teile und beide Images, bild und bild-mit-csv unter schwerpunkte/modulsystem/target.

    VS Code

    Starte über Terminal → Run Task… den Task schwerpunkte-modulsystem-image-mit-csv. Er baut alle drei Teile und beide Images, bild und bild-mit-csv unter schwerpunkte/modulsystem/target.

    Starte es über sein Startskript, wieder auf der Kommandozeile:

    schwerpunkte/modulsystem/target/bild-mit-csv/bin/exportlauf
    • --bind-services würde alle Anbieter holen, auch die des JDK – auf einem JDK ohne jmods (seit Java 24 möglich, JEP 493) scheitert es daran.
    • Ein solches Image ist rund 40–55 MB groß, das JDK 250–300 MB.
    • Mit JARs ohne module-info hätte jlink abgelehnt: Automatische Module nimmt es nicht.

    Bewerten

    Halte für Dich fest, kurz und in Stichworten:

    • Betrifft mich das? Wie hoch ist der Nutzen für einen REST-Microservice (etwa mit Quarkus), ein Batch-Programm und eine Server-Anwendung (Java EE/Jakarta EE) – gering, mittel oder hoch?
    • Voraussetzungen: Was müssen alle Abhängigkeiten mitbringen, damit eine Anwendung ganz auf dem Modulpfad läuft? Was braucht jlink?
    • Vorteile: Was meldet die JVM jetzt beim Start statt mitten im Betrieb? Was kann niemand mehr aus Versehen nutzen?
    • Herausforderungen: Wo stößt Ihr im Bestand an – Packages, die in zwei JARs liegen, Frameworks mit Reflection, Bibliotheken ohne module-info?

    Reflexionsfragen

    • Wenn Ihr selbst keine Module schreibt: Welcher Teil des Modulsystems betrifft Euch trotzdem?
