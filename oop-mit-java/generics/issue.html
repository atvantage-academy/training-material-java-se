Ein generisches Repository bauen

Ein generisches Repository bauen

Als Entwickler:in möchte ich Kunden und Konten mit derselben, typsicheren Verwaltungslogik ablegen, damit ich Speicher-Code nicht für jeden Typ dupliziere.

Lernziele

Du…

  • definierst eine generische Klasse/ein Interface mit Typparameter.
  • schränkst einen Typparameter mit extends ein.
  • verwendest das generische Repository typsicher für zwei Typen.

Definition of Done

  • Es gibt ein generisches Repository<T extends Identifizierbar> mit save(T) und findById(String).
  • Intern speichert es die Elemente in einer Map<String, T> (ID → Element).
  • Es existieren ein Repository<Kunde> und ein Repository<Konto> ohne duplizierten Code.
  • Die Verwendung kommt ohne explizite Casts aus.
  • Du hast die Reflexionsfragen schriftlich beantwortet.

Arbeitsschritte

Das generische Repository definieren

Führe einen Typparameter T ein und schränke ihn auf Identifizierbar ein.

public class Repository<T extends Identifizierbar> {
  private final Map<String, T> elemente = new HashMap<>();

  public void save(T element) {
    elemente.put(element.getId(), element);
  }

  public T findById(String id) {
    return elemente.get(id);
  }
}

Hinweis: Nur wegen der Schranke extends Identifizierbar darfst Du innen element.getId() aufrufen.

Für zwei Typen verwenden

Erzeuge je ein Repository für Kunden und Konten und speichere/lies Objekte.

Repository<Kunde> kunden = new Repository<>();
kunden.save(anna);
Kunde gefunden = kunden.findById(anna.getId()); // kein Cast nötig

Hinweis: Beobachte, wie die IDE beim falschen Typ (kunden.save(konto)) schon vor dem Ausführen meckert – das ist Typsicherheit zur Compile-Zeit.

Reflexionsfragen

  • Was wäre der Nachteil eines Repositories, das intern Object speichert?
  • Warum brauchst Du die Typschranke extends Identifizierbar – was ginge ohne sie nicht?
  • An welcher anderen Stelle im Banking-System würde sich ein generischer Typ noch lohnen?
