Transaktionen und Konten in Collections verwalten

Als Entwickler:in möchte ich die Transaktionen eines Kontos geordnet festhalten und Konten nachschlagen können, damit die Domäne mehrere Objekte sauber verwaltet.

Lernziele

Du…

  • wählst eine passende Collection (List/Set/Map) für eine Aufgabe aus.
  • fügst Elemente hinzu und iterierst über die Collection.
  • gibst eine interne Liste als unveränderbare Sicht heraus.
  • legst fest, wann zwei Objekte fachlich gleich sind, und machst das für hash-basierte Strukturen nutzbar.

Definition of Done

  • Ein Konto führt seine Transaktionen in einer List<Buchung>.
  • Jede Ein-/Auszahlung ergänzt die Liste.
  • getBuchungen() liefert eine unveränderbare Sicht (kein direkter Schreibzugriff von außen).
  • Konten werden in einer Map<String, Konto> (IBAN → Konto) nachschlagbar gehalten.
  • Zwei Kunde-Objekte mit derselben Kundennummer gelten in einem HashSet als ein Element.
  • Du hast die Reflexionsfragen schriftlich beantwortet.

Arbeitsschritte

Transaktionen als Liste führen

Gib Konto ein Feld List<Buchung> und ergänze es bei jeder Buchung.

Hinweis: Eine ArrayList bewahrt die Reihenfolge – passend für einen chronologischen Buchungsverlauf.

Die Liste schützen

Gib die Liste nur als unveränderbare Sicht zurück.

public List<Buchung> getBuchungen() {
  return Collections.unmodifiableList(buchungen);
}

Hinweis: So kann außen niemand add/remove aufrufen; Buchungen laufen ausschließlich über die Konto-Methoden.

Konten nachschlagbar machen

Verwalte Konten in einer Map<String, Konto> und schlage per IBAN nach.

Hinweis: Frage Dich: brauche ich Reihenfolge (List), Eindeutigkeit (Set) oder schnellen Zugriff per Schlüssel (Map)?

Festlegen, wann zwei Kunden gleich sind

Leg zwei Kunde-Objekte mit derselben Kundennummer an, steck sie in ein HashSet und gib dessen Größe aus. Das Ergebnis wird Dich zunächst überraschen – sorg dafür, dass am Ende 1 herauskommt.

Hinweis: Ohne eigenes Zutun vergleicht Java Objekte über ihre Identität, so wie Du es an Tag 2 gesehen hast. Welche zwei Methoden musst Du überschreiben, damit stattdessen die fachliche Gleichheit zählt – und warum reicht eine davon allein nicht?

Hinweis: Nimm als Grundlage das Feld, das den Kunden eindeutig und dauerhaft ausmacht – nicht eines, das sich ändern kann.

Reflexionsfragen

  • Warum ist die IBAN ein guter Schlüssel für eine Map der Konten?
  • Welche Gefahr bestünde, wenn getBuchungen() die echte, veränderbare Liste zurückgäbe?
  • Für die Menge aller Kunden-IDs – welche Collection passt und warum?
  • Warum genügt es nicht, nur equals zu überschreiben?
  • Warum sollte in die Gleichheit ein Feld einfließen, das sich nicht mehr ändert?
