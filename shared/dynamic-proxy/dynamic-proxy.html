Dynamic Proxy

    Ein Dynamic Proxy ist ein Objekt, dessen Klasse erst zur Laufzeit entsteht. Es setzt ein Interface um und reicht jeden Aufruf an eine einzige Methode weiter – den InvocationHandler. Dort steht, was um jede Methode herum geschehen soll, genau einmal.

    java.lang.reflect.Proxy seit Java 1.3 nur für Interfaces

    Das Problem: dasselbe um jede Methode

    Manche Aufgaben gehören zu keiner einzelnen Methode, sondern zu allen: protokollieren, wer was aufruft; die Zeit messen; eine Transaktion öffnen und schließen; prüfen, ob der Aufrufer das überhaupt darf. Man nennt sie Querschnittsaufgaben.

    Von Hand landet so etwas in jeder Methode – und in jeder Implementierung erneut:

    @Override
public Optional<String> finde(String nummer) {
    long start = System.nanoTime();                      // Zeitmessung
    System.out.println("vorher:  finde[" + nummer + "]"); // Protokoll
    Optional<String> ergebnis = Optional.ofNullable(räume.get(nummer)); // die eigentliche Arbeit
    System.out.println("nachher: " + ergebnis);
    System.out.println((System.nanoTime() - start) + " ns");
    return ergebnis;
}

    Eine Zeile Fachlichkeit, vier Zeilen drumherum – und dasselbe noch einmal in anzahl(), in jeder weiteren Methode, in jeder weiteren Klasse. Gesucht ist ein Weg, das Drumherum einmal zu schreiben und um jede Methode zu legen, ohne die Implementierung anzufassen.

    Das Bild: der Weg eines Aufrufs

    Der Aufrufer hält ein Objekt vom Typ RaumKatalog in der Hand – aber nicht die echte Implementierung, sondern einen Stellvertreter (Proxy). Geh die Stationen eines Aufrufs von katalog.finde("R102") durch:

    1 · Der Aufrufer

    Er arbeitet gegen das Interface und merkt nicht, dass dazwischen jemand sitzt. Genau das ist der Trick: Weil der Aufrufer nur RaumKatalog kennt, darf man ihm statt der Implementierung jedes andere Objekt geben, das RaumKatalog umsetzt.

    RaumKatalog katalog = …;              // echt oder Proxy – für den Aufrufer gleich
Optional<String> raum = katalog.finde("R102");

    2 · Der Proxy

    Proxy.newProxyInstance erzeugt zur Laufzeit eine Klasse, die alle angegebenen Interfaces umsetzt, und liefert ein Objekt davon. Jede ihrer Methoden tut dasselbe: Sie ruft den Handler auf und gibt dessen Ergebnis zurück. Eigene Logik hat sie keine.

    RaumKatalog katalog = (RaumKatalog) Proxy.newProxyInstance(
        RaumKatalog.class.getClassLoader(),      // wo die neue Klasse geladen wird
        new Class<?>[] { RaumKatalog.class },   // welche Interfaces sie umsetzt
        new ProtokollHandler(ziel));             // wer die Aufrufe bekommt

    3 · Der InvocationHandler

    Ein funktionales Interface mit einer Methode. Für jeden Aufruf am Proxy bekommt sie drei Dinge: den Proxy selbst, die aufgerufene Methode als Method-Objekt und die Argumente als Object[] (null, wenn die Methode keine hat).

    public interface InvocationHandler {
    Object invoke(Object proxy, Method method, Object[] args) throws Throwable;
}

    Über method erfährt der Handler alles per Reflection: Name, Parametertypen, Rückgabetyp – und die Annotationen der Methode.

    4 · Die Entscheidung im Handler

    Der Handler entscheidet für jeden Aufruf, was geschieht:

    • Vorher und nachher etwas tun – protokollieren, messen, eine Transaktion öffnen und schließen – und dazwischen an das Ziel weitergeben.
    • Nur weitergeben – etwa bei Methoden, die nicht gemeint sind.
    • Selbst antworten – das Ziel wird gar nicht gefragt: ein Wert aus einem Zwischenspeicher, eine Ausnahme, weil die Berechtigung fehlt, oder eine eigene Antwort auf toString.
    (proxy, method, args) -> switch (method.getName()) {
    case "toString" -> "Proxy für " + ziel.getClass().getSimpleName();  // selbst antworten
    case "equals" -> proxy == args[0];
    case "hashCode" -> System.identityHashCode(proxy);
    default -> method.invoke(ziel, args);                               // weitergeben
}

    5 · Das Ziel

    Weitergeben heißt: dieselbe Methode per Reflection am echten Objekt aufrufen. method.invoke(ziel, args) liefert dessen Ergebnis; der Handler gibt es zurück, und der Proxy reicht es an den Aufrufer.

    Object ergebnis = method.invoke(ziel, args);   // InMemoryRaumKatalog.finde("R102")
return ergebnis;                                // zurück über Proxy zum Aufrufer

    Wirft das Ziel, kommt die Ausnahme verpackt an – in einer InvocationTargetException. Warum man sie auspackt, zeigt der Befund unten.

    Der Code: ein protokollierender Handler

    Protokolliert werden sollen nur Methoden, die das ausdrücklich wünschen. Das Zeichen dafür ist eine eigene Annotation – wie man sie anlegt und warum sie @Retention(RUNTIME) braucht, zeigt die Visualisierung Eigene Annotationen.

    Die Annotation

    @Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Protokolliert {
}

    Das Interface

    public interface RaumKatalog {
    @Protokolliert
    Optional<String> finde(String nummer);

    int anzahl();
}

    Die Implementierung InMemoryRaumKatalog ist gewöhnlich – sie weiß nichts vom Protokoll:

    public class InMemoryRaumKatalog implements RaumKatalog {
    private final Map<String, String> räume = Map.of("R101", "Seminar 1", "R102", "Seminar 2");

    @Override
    public Optional<String> finde(String nummer) {
        if (nummer.isBlank()) {
            throw new IllegalArgumentException("Raumnummer fehlt");
        }
        return Optional.ofNullable(räume.get(nummer));
    }

    @Override
    public int anzahl() {
        return räume.size();
    }
}

    Der Handler fragt per method.getAnnotation(…), ob die aufgerufene Methode @Protokolliert trägt, und legt nur dann das Protokoll um den Aufruf:

    public class ProtokollHandler implements InvocationHandler {
    private final Object ziel;

    public ProtokollHandler(Object ziel) {
        this.ziel = ziel;
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        boolean protokoll = method.getAnnotation(Protokolliert.class) != null;
        if (protokoll) {
            System.out.println("vorher:  " + method.getName() + Arrays.toString(args));
        }
        try {
            Object ergebnis = method.invoke(ziel, args);
            if (protokoll) {
                System.out.println("nachher: " + ergebnis);
            }
            return ergebnis;
        } catch (InvocationTargetException e) {
            throw e.getCause();
        }
    }
}

    Zusammenstecken und aufrufen:

    RaumKatalog ziel = new InMemoryRaumKatalog();
RaumKatalog katalog = (RaumKatalog) Proxy.newProxyInstance(
        RaumKatalog.class.getClassLoader(),
        new Class<?>[] { RaumKatalog.class },
        new ProtokollHandler(ziel));

System.out.println(katalog.finde("R102"));
System.out.println(katalog.anzahl());

    Ausgabe

    vorher:  finde[R102]
nachher: Optional[Seminar 2]
Optional[Seminar 2]
2

    finde trägt @Protokolliert und läuft mit Protokoll, anzahl ohne – beide aber durch denselben Handler. Eine weitere Methode im Interface bekommt das Protokoll, sobald sie die Annotation trägt; weder Handler noch Implementierung ändern sich.

    Was man sieht – gemessen

    Der Proxy ist ein gewöhnliches Objekt, das man befragen kann. Alle Ausgaben stammen aus einem Lauf mit OpenJDK 25; der Code liegt im Paket raum.

    Seine Klasse: ein RaumKatalog, aber kein InMemoryRaumKatalog

    System.out.println(katalog.getClass().getName());
System.out.println(katalog instanceof RaumKatalog);
System.out.println(katalog instanceof InMemoryRaumKatalog);
System.out.println(Proxy.isProxyClass(katalog.getClass()));
System.out.println(katalog.getClass().getSuperclass().getName());
System.out.println(Arrays.toString(katalog.getClass().getInterfaces()));

true
false

[interface raum.RaumKatalog]

    Die Klasse heißt $Proxy0 und liegt in einem eigens erzeugten Modul jdk.proxy1 (bis Java 15 hieß das Paket com.sun.proxy). Sie erbt von java.lang.reflect.Proxy und setzt nur das Interface um – mit InMemoryRaumKatalog ist sie nicht verwandt. Wer im Code auf die Implementierung castet, scheitert am Proxy.

    toString, equals, hashCode laufen durch den Handler

    Ein Handler, der jeden Aufruf meldet und dann weitergibt:

    RaumKatalog spion = (RaumKatalog) Proxy.newProxyInstance(
        RaumKatalog.class.getClassLoader(),
        new Class<?>[] { RaumKatalog.class },
        (proxy, method, args) -> {
            System.out.println("Handler: " + method.getDeclaringClass().getSimpleName()
                    + "." + method.getName());
            return method.invoke(ziel, args);
        });
System.out.println(spion.toString());
System.out.println(spion.hashCode() == ziel.hashCode());
System.out.println(spion.equals(spion));
System.out.println(spion.getClass().getSimpleName());

    Ausgabe (der Hashwert ändert sich je Lauf)

    Handler: Object.toString
raum.InMemoryRaumKatalog@4f023edb
Handler: Object.hashCode
true
Handler: Object.equals
false
$Proxy0

    Drei Methoden von Object gehen durch den Handler: toString, equals, hashCode. getClass() nicht – sie ist final. Und die Falle: spion.equals(spion) ist false. Der Handler fragt ziel.equals(spion), und das Ziel ist nicht der Proxy. Wer Proxys in Sets oder als Schlüssel verwendet, beantwortet equals und hashCode im Handler selbst (siehe Station 4):

    Ausgabe mit selbst beantworteten toString und equals

    Proxy für InMemoryRaumKatalog
true
2

    Ein Proxy für eine Klasse scheitert

    Proxy.newProxyInstance(
        InMemoryRaumKatalog.class.getClassLoader(),
        new Class<?>[] { InMemoryRaumKatalog.class },   // Klasse statt Interface
        new ProtokollHandler(ziel));

    Ausgabe

    java.lang.IllegalArgumentException: raum.InMemoryRaumKatalog is not an interface

    java.lang.reflect.Proxy erzeugt Klassen, die von Proxy erben – eine zweite Oberklasse ist nicht möglich. Deshalb geht es nur mit Interfaces. Für Klassen braucht es andere Werkzeuge (siehe Frameworks).

    InvocationTargetException: warum getCause() weitergeworfen wird

    Wirft das Ziel eine Ausnahme, verpackt method.invoke sie in eine InvocationTargetException. Ein Handler, der einfach weitergibt …

    (proxy, method, args) -> method.invoke(ziel, args)

    … liefert beim Aufruf naiv.finde(" ") dem Aufrufer eine doppelt verpackte Ausnahme:

    Ausgabe (e, e.getCause(), e.getCause().getCause())

    java.lang.reflect.UndeclaredThrowableException
  cause: java.lang.reflect.InvocationTargetException
  cause.cause: java.lang.IllegalArgumentException: Raumnummer fehlt

    finde deklariert keine InvocationTargetException; eine geprüfte Ausnahme, die die Methode nicht deklariert, verpackt der Proxy noch einmal in eine UndeclaredThrowableException. Ein catch (IllegalArgumentException e) beim Aufrufer greift nicht mehr. Der ProtokollHandler packt deshalb aus und wirft die ursprüngliche Ausnahme weiter – throw e.getCause();:

    Ausgabe mit dem ProtokollHandler

    vorher:  finde[ ]
java.lang.IllegalArgumentException: Raumnummer fehlt

    Der Aufrufer sieht dieselbe Ausnahme wie ohne Proxy.

    Wo Frameworks das nutzen

    Kaum jemand schreibt Proxy.newProxyInstance im Anwendungscode. Aber fast jedes Framework legt so etwas um Deine Objekte – immer dann, wenn eine Annotation etwas „einfach so“ bewirkt.

    Wo Was der Stellvertreter tut
    Spring AOP, @Transactional, @Cacheable öffnet und schließt die Transaktion, fragt den Cache – vor und nach dem Aufruf
    CDI-Interceptoren (@Interceptor, @AroundInvoke) legt eigene Querschnittsaufgaben um annotierte Methoden
    JPA Lazy Loading (z. B. getReference, @ManyToOne(fetch = LAZY)) steht für eine Entität, die erst beim ersten Zugriff aus der Datenbank geladen wird
    Deklarative HTTP-Clients (Feign, MicroProfile REST Client) setzt ein Interface ohne Implementierung um: Jeder Aufruf wird zu einer HTTP-Anfrage – der Handler antwortet selbst
    Mockito antwortet selbst mit vorbereiteten Werten und merkt sich die Aufrufe für verify

    Für Klassen statt Interfaces reicht java.lang.reflect.Proxy nicht. Spring (bei Klassen ohne Interface, in Spring Boot standardmäßig), CDI und Hibernate erzeugen dann mit Bytecode-Bibliotheken wie ByteBuddy oder CGLIB eine Unterklasse, die die Methoden überschreibt. Daraus folgt eine harte Regel: final stört. Eine finale Klasse hat keine Unterklasse, eine finale Methode lässt sich nicht überschreiben – sie läuft dann am Stellvertreter vorbei, ohne Transaktion, ohne Interceptor. (Mockito umgeht das seit Version 5, indem es die Klasse selbst umschreibt.)

    Und weil der Stellvertreter außen sitzt, erreicht ihn nur ein Aufruf von außen: Ruft eine Methode eine andere des eigenen Objekts über this auf, läuft der Aufruf am Proxy vorbei – ein @Transactional dort bleibt wirkungslos.

    Merksatz: Ein Dynamic Proxy ist eine zur Laufzeit erzeugte Klasse, die ein Interface umsetzt und jeden Aufruf an genau eine Methode reicht – invoke. Dort steht das Drumherum einmal für alle Methoden; wer weitergibt, ruft method.invoke(ziel, args) und packt getCause() aus.
