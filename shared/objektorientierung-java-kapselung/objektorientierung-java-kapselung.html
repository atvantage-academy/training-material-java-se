Objektorientierung mit Java (Kapselung)

Die Fortsetzung von Objektorientierung mit Java (einfach) – am selben Beispiel: aus offenen Klassen werden Objekte, die ihren Zustand schützen. Packages und Imports, die Sichtbarkeiten, final und der Konstruktor. Ausnahmen kommen später im Kurs; geprüft wird hier mit einem if.

1 Packages: Ordnung im Projekt

Eine Zeile, ein Ordner

// Datei: bibliothek/Buch.java
package bibliothek;

class Buch {
    String titel;
}

Die package-Zeile steht ganz oben, noch vor allem anderen. Sie muss zum Ordner passen: package bibliothek; gehört in den Ordner bibliothek.

Wozu das gut ist

Ordnung: Bei zwanzig Klassen findet man sonst nichts wieder.

Eindeutige Namen: Es darf zwei Klassen Kunde geben, solange sie in verschiedenen Packages liegen – der volle Name ist bibliothek.Kunde.

Und eine Grenze: Packages entscheiden mit darüber, wer was sehen darf – siehe Abschnitt 3.

In echten Projekten ist der Paketname die umgedrehte Internet-Adresse der Organisation, damit er weltweit eindeutig bleibt: com.example.bibliothek. Für Übungen genügt ein einfacher Name.

2 Imports: wann Du sie brauchst

Woher kommt die Klasse?import nötig?Beispiel
aus demselben PackageneinAutor in bibliothek.Buch
aus java.langnein – immer daString, System, Math
aus einem anderen Packagejaimport bibliothek.Buch;
aus einem anderen Package, einmaligoder voll ausschreibenjava.util.Objects.equals(a, b)

So sieht es im Programm aus

// Datei: anwendung/Main.java
package anwendung;

import bibliothek.Buch;      // andere Schublade → Import
import java.util.List;       // dasselbe für die Klassenbibliothek

class Main {
    public static void main(String[] args) {
        Buch erdsee = new Buch("978-3-453-52581-6", "Erdsee");
        System.out.println(erdsee);   // System: java.lang, kein Import
    }
}

Ein import holt nichts herbei und kostet nichts zur Laufzeit – er sagt dem Compiler nur, welches Buch gemeint ist.

3 Sichtbarkeit: die Grenze ziehen

Der objektorientierte Gedanke dahinter ist älter als Java: Ein Objekt zeigt nach außen, was es kann – nicht, wie es innen aussieht. Was innen liegt, darf sich ändern, ohne dass der Rest des Programms davon weiß. Java macht daraus vier Stufen.

SchreibweiseSichtbar fürWofür
privatenur die eigene KlasseInstanzvariablen und alles Innere – der Normalfall
(ohne Vorsatz)alle Klassen im selben Packagedie Voreinstellung; genau deshalb lief bisher alles
protectedPackage und Unterklassenergibt erst mit Vererbung Sinn – kommt später im Kurs
publicalleder Vertrag nach außen: Klasse, Konstruktor, fachliche Methoden

Die Faustregel: so eng wie möglich. Fang mit private an und öffne einzeln, was gebraucht wird – nicht umgekehrt. Was einmal public ist, benutzt irgendwann jemand.

4 Kontrollierter Zugriff statt offener Felder

✗ Offen

class Buch {
    int seiten;
}

erdsee.seiten = -100;

Niemand hindert das Programm daran, Unsinn hineinzuschreiben. Der Fehler fällt irgendwo später auf – weit weg von der Stelle, die ihn verursacht hat.

✓ Kontrolliert

class Buch {
    private int seiten;

    public int getSeiten() {
        return seiten;
    }

    public void setSeiten(int seiten) {
        if (seiten > 0) {          // erst prüfen …
            this.seiten = seiten;   // … dann übernehmen
        }
    }
}

Jede Änderung läuft durch Deinen Code – und damit durch Deine Regeln.

Nicht jedes Feld braucht einen Setter. Frag zweimal: Muss man den Wert von außen lesen können? Und muss man ihn von außen ändern können? Die zweite Frage wird seltener mit Ja beantwortet, als man denkt – manche Werte ändern sich nur über fachliche Methoden, andere gar nicht.

Zwei offene Enden – bewusst. Erstens erfährt der Aufrufer nichts davon, wenn sein Wert abgelehnt wurde; das saubere Werkzeug dafür sind Ausnahmen, die später im Kurs kommen. Zweitens: Was steht eigentlich in einem Feld, das nie gesetzt wurde? Bei Zahlen die 0, bei Referenzen null – der Wegweiser ins Nichts, an dem jeder Zugriff mit einer NullPointerException scheitert.

5 final: was sich nie ändern darf

Einmal gesetzt, nie wieder

class Buch {
    private final String isbn;   // identifiziert das Buch
    private String titel;        // darf korrigiert werden
    private int seiten;
}

Die ISBN gehört untrennbar zum Buch: Ändert sie sich, ist es ein anderes. Genau das schreibt final auf – und der Compiler wacht darüber.

Und jetzt klemmt es

Buch erdsee = new Buch();
erdsee.isbn = "978-…";   // geht nicht mehr

Zuweisen nach dem new lässt der Compiler nicht mehr zu – gesetzt werden muss das Feld trotzdem. Beides zusammen geht nur an einer einzigen Stelle: beim Erzeugen.

6 Der Konstruktor

Pflichtwerte kommen beim Erzeugen mit

class Buch {
    private final String isbn;
    private String titel;

    public Buch(String isbn, String titel) {   // heißt wie die Klasse, kein Rückgabetyp
        this.isbn = isbn;                      // this, weil Parameter und Feld gleich heißen
        this.titel = titel;
    }
}

Buch erdsee = new Buch("978-3-453-52581-6", "Erdsee");

Der Konstruktor läuft genau einmal – beim new. Danach ist das Objekt vollständig; ein halbfertiges Buch kann es nicht mehr geben.

Der geschenkte Konstruktor verschwindet

Buch erdsee = new Buch();   // geht jetzt nicht mehr

Den parameterlosen Konstruktor gibt es nur, solange die Klasse gar keinen eigenen hat. Schreibst Du einen, ist er weg – und alle Stellen, die new Buch() aufrufen, müssen mitziehen.

Vorsicht bei final

public Buch(String isbn) {
    if (isbn != null) {
        this.isbn = isbn;
    }
    // Fehler: variable isbn
    // might not have been initialized
}

Ein final-Feld muss der Konstruktor in jedem Fall setzen – ein if ohne else genügt nicht. Überleg Dir, was im Zweifel hineinkommt.

Der Satz, um den es hier geht: Ein Objekt ist ab dem Konstruktor gültig. Wer eines in die Hand bekommt, muss nicht mehr prüfen, ob es benutzbar ist.
