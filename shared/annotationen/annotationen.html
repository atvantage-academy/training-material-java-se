Eigene Annotationen

    Eine Annotation ist ein Etikett am Code. Sie tut nichts – sie wird gelesen. Wer sie liest und wann, entscheidet darüber, was sie bewirkt. Eine eigene Annotation zu schreiben ist deshalb schnell erledigt; der eigentliche Teil ist der Code, der sie auswertet.

    seit Java 5 @Repeatable seit Java 8

    Was eine Annotation ist

    Eine Annotation hängt Metadaten an eine Klasse, eine Methode, ein Feld oder einen Parameter. Am Verhalten des Codes ändert sie nichts: Eine Methode mit @Test läuft genauso wie ohne. Bedeutung bekommt sie erst durch einen Leser – und davon gibt es drei Arten:

    Beim Übersetzen

    der Compiler

    @Override verlangt, dass die Methode wirklich etwas überschreibt. Ein Tippfehler fällt sofort auf:

    @Override
public String tostring() {
    return "Raum";
}

    Raum.java:2: error: method does not override or implement a method from a supertype
    @Override
    ^

    Beim Übersetzen

    ein Annotation Processor

    Ein Programm, das sich in javac einklinkt, die Annotationen liest und daraus neuen Quelltext erzeugt oder Fehler meldet – etwa Lombok (@Getter) oder MapStruct (@Mapper). Zur Laufzeit ist von seiner Arbeit nur das Ergebnis da.

    Zur Laufzeit

    ein Framework per Reflection

    JUnit sucht in der Testklasse nach Methoden mit @Test und ruft sie auf:

    @Test
void suchtRaumNachNummer() { … }

    Ohne JUnit ist @Test nur ein Etikett, das niemand liest.

    Eine Annotation schreiben

    Eine Annotation deklariert man wie ein Interface, mit einem @ vor interface. Ihre Attribute sind Methoden ohne Parameter; der Rückgabetyp ist der Typ des Attributs.

    public @interface Protokolliert {      // eigene Datei: Protokolliert.java
    String value();                    // Attribut „value“ vom Typ String
    boolean mitArgumenten();           // Attribut „mitArgumenten“ vom Typ boolean
}

    Bei der Verwendung sehen die Attribute aus wie Zuweisungen – ausgelesen werden sie später wie Methoden: p.value(), p.mitArgumenten(). Implementieren muss man die Methoden nie; das erledigt Java.

    Attribute Schritt für Schritt

    Geh die Stufen durch. Jede zeigt dieselbe Annotation @Protokolliert am RaumKatalog: die Deklaration, eine gültige Verwendung und eine ungültige mit der Meldung des Compilers.

    1 · Nur Markierung

    Ohne Attribut ist die Annotation ein reines Etikett: Sie ist da oder nicht da.

    Deklaration

    public @interface Protokolliert {
}

    Gültig

    @Protokolliert
void raumSuchen() { }

    Ungültig – ein Wert, für den es kein Attribut gibt

    @Protokolliert("Raum suchen")
void raumSuchen() { }

    RaumKatalog.java:2: error: cannot find symbol
    @Protokolliert("Raum suchen")
                   ^
  symbol:   method value()
  location: @interface Protokolliert

    Der Compiler sucht eine Methode value() – ein erster Hinweis auf die nächste Stufe.

    2 · value – das besondere Attribut

    Heißt das einzige angegebene Attribut value, darf man den Namen weglassen: @Protokolliert("Raum suchen") ist die Kurzschreibweise für @Protokolliert(value = "Raum suchen"). Für jeden anderen Namen gilt das nicht.

    Deklaration

    public @interface Protokolliert {
    String value();
}

    Gültig

    @Protokolliert("Raum suchen")
void raumSuchen() { }

@Protokolliert(value = "Raum buchen")
void raumBuchen() { }

    Ungültig – das Attribut fehlt

    @Protokolliert
void raumSuchen() { }

    RaumKatalog.java:2: error: annotation @Protokolliert is missing a default value for the element 'value'
    @Protokolliert
    ^

    Ein Attribut ohne Default-Wert ist Pflicht. Die Meldung verrät schon, wie man das ändert.

    3 · Mehrere Attribute – dann mit Namen

    Sobald mehr als ein Attribut angegeben wird, braucht jedes seinen Namen, auch value. Die Reihenfolge ist frei.

    Deklaration

    public @interface Protokolliert {
    String value();
    boolean mitArgumenten();
}

    Gültig

    @Protokolliert(value = "Raum suchen", mitArgumenten = true)
void raumSuchen() { }

    Ungültig – Kurzschreibweise neben einem zweiten Attribut

    @Protokolliert("Raum suchen", mitArgumenten = true)
void raumSuchen() { }

    RaumKatalog.java:2: error: annotation values must be of the form 'name=value'
    @Protokolliert("Raum suchen", mitArgumenten = true)
                   ^
RaumKatalog.java:2: error: annotation @Protokolliert is missing a default value for the element 'value'
    @Protokolliert("Raum suchen", mitArgumenten = true)
    ^

    Und @Protokolliert("Raum suchen") allein geht jetzt auch nicht mehr: … is missing a default value for the element 'mitArgumenten'. Beide Attribute sind Pflicht.

    4 · Default-Werte

    Mit default wird ein Attribut optional. Was einen Default-Wert hat, darf man weglassen – und bleibt dann nur value übrig, gilt wieder die Kurzschreibweise.

    Deklaration

    public @interface Protokolliert {
    String value();
    boolean mitArgumenten() default false;
}

    Gültig

    @Protokolliert("Raum suchen")
void raumSuchen() { }

@Protokolliert(value = "Raum buchen", mitArgumenten = true)
void raumBuchen() { }

    Ungültig – das Pflicht-Attribut fehlt

    @Protokolliert(mitArgumenten = true)
void raumSuchen() { }

    RaumKatalog.java:2: error: annotation @Protokolliert is missing a default value for the element 'value'
    @Protokolliert(mitArgumenten = true)
    ^

    Faustregel: das wichtigste Attribut value nennen und ohne Default lassen, alles andere mit einem Default versehen – dann bleibt die häufigste Verwendung kurz.

    5 · Arrays

    Ein Attribut darf ein Array sein. Die Werte stehen in geschweiften Klammern; bei einem Element dürfen die Klammern entfallen. default {} macht das Attribut optional.

    Deklaration

    public @interface Protokolliert {
    String value();
    boolean mitArgumenten() default false;
    String[] schlagworte() default {};
}

    Gültig

    @Protokolliert(value = "Raum suchen", schlagworte = {"Suche", "Raum"})
void raumSuchen() { }

@Protokolliert(value = "Raum buchen", schlagworte = "Buchung")
void raumBuchen() { }

    Ungültig – eine Liste statt eines Array-Literals

    @Protokolliert(value = "Raum suchen", schlagworte = List.of("Suche", "Raum"))
void raumSuchen() { }

    RaumKatalog.java:4: error: expression not allowed as annotation value
    @Protokolliert(value = "Raum suchen", schlagworte = List.of("Suche", "Raum"))
                                                               ^

    List.of(…) ist ein Methodenaufruf – und der läuft erst zur Laufzeit. Annotationen stehen aber schon fest, wenn der Compiler die Klassendatei schreibt.

    Erlaubte Attributtypen

    Weil die Werte in der Klassendatei stehen, sind nur Typen erlaubt, deren Werte der Compiler dort ablegen kann:

    Erlaubt Beispiel
    primitive Typen int stufe();, boolean mitArgumenten();
    String String value();
    Class Class<?> ziel();
    Enums ElementType art();
    andere Annotationen Schlagwort[] value();
    eindimensionale Arrays davon String[] schlagworte();

    Alles andere lehnt der Compiler ab – auch Object und List:

    public @interface Protokolliert {
    Object wert();
}

    Protokolliert.java:2: error: invalid type for annotation interface element
    Object wert();
    ^

    Außerdem muss jeder Wert eine Konstante sein – ein Literal oder ein static final-Feld mit konstantem Wert. null ist keine Konstante, weder als Wert noch als Default:

    static final String SUCHEN = "Raum suchen";
static String buchen = "Raum buchen";

@Protokolliert(SUCHEN)
void raumSuchen() { }      // gültig: Konstante

@Protokolliert(buchen)
void raumBuchen() { }      // ungültig: Variable

@Protokolliert(null)
void aufräumen() { }       // ungültig: null

    RaumKatalog.java:8: error: element value must be a constant expression
    @Protokolliert(buchen)
                   ^
RaumKatalog.java:11: error: element value must be a constant expression
    @Protokolliert(null)
                   ^

    String value() default null; scheitert mit derselben Meldung. Wer „kein Wert“ ausdrücken will, nimmt einen Leerwert: default "" oder default {}.

    Meta-Annotationen: Annotationen an Annotationen

    Wie lange eine Annotation erhalten bleibt und wo sie stehen darf, legen Annotationen an ihrer Deklaration fest.

    @Retention: wie weit sie kommt

    RetentionPolicy im Quelltext in der .class-Datei zur Laufzeit lesbar typischer Leser
    SOURCE ja nein nein Compiler, Annotation Processor
    CLASS – Standard ja ja nein Werkzeuge, die Bytecode lesen
    RUNTIME ja ja ja Framework per Reflection

    Ohne @Retention gilt CLASS – die Annotation steht in der Klassendatei, Reflection sieht sie aber nicht. Für alles, was zur Laufzeit gelesen werden soll, ist @Retention(RetentionPolicy.RUNTIME) Pflicht. Die Probe mit vier Annotationen an einer Methode:

    @Retention(RetentionPolicy.SOURCE)  @interface NurQuelle { }
@Retention(RetentionPolicy.CLASS)   @interface InKlassendatei { }
@Retention(RetentionPolicy.RUNTIME) @interface ZurLaufzeit { }
@interface OhneAngabe { }

@NurQuelle @InKlassendatei @ZurLaufzeit @OhneAngabe
void raumSuchen() { }

    In der Klassendatei (javap -v, gekürzt)

    RuntimeVisibleAnnotations:
  0: #44()
    Aufbewahrung$ZurLaufzeit
RuntimeInvisibleAnnotations:
  0: #46()
    Aufbewahrung$InKlassendatei
  1: #47()
    Aufbewahrung$OhneAngabe

    Zur Laufzeit (methode.getAnnotations())

    [@Aufbewahrung.ZurLaufzeit()]

    @NurQuelle hat die Klassendatei nie erreicht; @InKlassendatei und @OhneAngabe stehen darin, aber als „unsichtbar“ – Reflection liefert nur @ZurLaufzeit.

    @Target: wo sie stehen darf

    Ohne @Target darf die Annotation fast überall stehen. Mit @Target beschränkt man sie auf bestimmte Stellen – ElementType.METHOD, FIELD, TYPE (Klasse, Interface, Enum, Record), PARAMETER, CONSTRUCTOR und einige mehr; mehrere als Array: @Target({ElementType.METHOD, ElementType.TYPE}).

    @Target(ElementType.METHOD)
public @interface Protokolliert {
    String value();
}

public class RaumKatalog {
    @Protokolliert("Räume")
    private String räume;
}

    RaumKatalog.java:2: error: annotation interface not applicable to this kind of declaration
    @Protokolliert("Räume")
    ^

    Drei weitere, kurz

    • @Documented – die Annotation erscheint in der Javadoc der annotierten Elemente.
    • @Inherited – eine Annotation an einer Klasse gilt auch für deren Unterklassen. Nur bei Klassen und nur von der Oberklasse: Eine Klasse, die ein annotiertes Interface umsetzt, erbt nichts. Gemessen mit @Inherited @Dienst: Ableitung.class.isAnnotationPresent(Dienst.class) liefert true, bei Umsetzung implements Schnittstelle dagegen false.
    • @Repeatable – die Annotation darf mehrfach an derselben Stelle stehen. Dafür braucht sie einen Behälter mit einem Array-Attribut value:
    @Retention(RetentionPolicy.RUNTIME) @Repeatable(Schlagworte.class)
@interface Schlagwort { String value(); }

@Retention(RetentionPolicy.RUNTIME)
@interface Schlagworte { Schlagwort[] value(); }

@Schlagwort("Suche") @Schlagwort("Raum")
void raumSuchen() { }

    Gelesen wird sie mit getAnnotationsByType(Schlagwort.class); getAnnotation findet sie nicht, weil der Compiler die beiden in einen @Schlagworte-Behälter verpackt hat:

    [@Meta.Schlagwort("Suche"), @Meta.Schlagwort("Raum")]
null

    Auslesen per Reflection

    Jetzt bekommt die Annotation ihre Bedeutung: ein Leser, der sie sucht. Die Deklaration mit RUNTIME und METHOD:

    @Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Protokolliert {
    String value();
    boolean mitArgumenten() default false;
}

    Annotiert sind zwei von drei Methoden:

    public class RaumKatalog {
    @Protokolliert("Raum suchen")
    public void raumSuchen(String nummer) { }

    @Protokolliert(value = "Raum buchen", mitArgumenten = true)
    public void raumBuchen(String nummer, int stunden) { }

    public void aufräumen() { }
}

    Der Leser fragt jede Methode nach der Annotation. getAnnotation liefert ein Objekt vom Typ Protokolliert – die Attribute sind dessen Methoden:

    Method[] methoden = RaumKatalog.class.getDeclaredMethods();
Arrays.sort(methoden, Comparator.comparing(Method::getName));   // Reihenfolge festlegen
for (Method methode : methoden) {
    if (methode.isAnnotationPresent(Protokolliert.class)) {
        Protokolliert p = methode.getAnnotation(Protokolliert.class);
        System.out.println(methode.getName() + ": " + p.value()
                + ", mitArgumenten = " + p.mitArgumenten());
    } else {
        System.out.println(methode.getName() + ": nicht protokolliert");
    }
}

    Ausgabe mit RetentionPolicy.RUNTIME

    aufräumen: nicht protokolliert
raumBuchen: Raum buchen, mitArgumenten = true
raumSuchen: Raum suchen, mitArgumenten = false

    Ausgabe mit RetentionPolicy.CLASS (oder ohne Angabe)

    aufräumen: nicht protokolliert
raumBuchen: nicht protokolliert
raumSuchen: nicht protokolliert

    Der Default-Wert kommt mit: raumSuchen nennt mitArgumenten gar nicht und liefert trotzdem false. Ohne RUNTIME übersetzt alles fehlerfrei – nur findet der Leser nichts, und getAnnotation gibt null zurück. Kein Compiler warnt davor.

    Die Falle: Annotationen am Interface

    Steht die Annotation an der Methode eines Interfaces, sieht man sie an der umsetzenden Methode nicht – auch mit @Inherited nicht, das nur für Klassen gilt.

    public interface Katalog {
    @Protokolliert("Raum suchen")
    void raumSuchen(String nummer);
}

public class RaumKatalog implements Katalog {
    @Override
    public void raumSuchen(String nummer) { }
}

    System.out.println(Katalog.class.getMethod("raumSuchen", String.class)
        .getAnnotation(Protokolliert.class));
System.out.println(RaumKatalog.class.getMethod("raumSuchen", String.class)
        .getAnnotation(Protokolliert.class));

    @Protokolliert("Raum suchen")
null

    Wer Annotationen auch am Interface finden will, muss dort selbst nachsehen. Frameworks wie Spring tun das mit eigenen Hilfsklassen – Reflection allein tut es nicht.

    Merksatz: Eine Annotation ist ein Etikett, das nichts tut, bis jemand es liest. Attribute sind Methoden ohne Parameter, ihre Werte Konstanten – und wer sie zur Laufzeit lesen will, braucht @Retention(RUNTIME), denn der Standard ist CLASS.
