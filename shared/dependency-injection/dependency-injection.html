Dependency Injection und Mocks

    Eine Klasse, die sich ihre Helfer selbst baut, nimmt sie überallhin mit – auch in den Test. Dependency Injection dreht das um: Die Klasse sagt nur, was sie braucht, und jemand anderes entscheidet, welches Objekt sie bekommt. Erst dadurch kann ein Test einen Stellvertreter hineinreichen.

    Inversion of Control Jakarta CDI · Spring gemessen mit Mockito 5.24

    Das Problem: fest verdrahtet

    Ein Buchungsdienst prüft, ob ein Raum existiert und groß genug ist, und benachrichtigt danach die Haustechnik. Seinen Katalog und seine Benachrichtigung erzeugt er selbst:

    public class Buchungsdienst {

    private final RaumKatalog katalog;
    private final Benachrichtigung benachrichtigung;

    public Buchungsdienst() {
        this.katalog = new SpeicherKatalog();                 // holt sich selbst
        this.benachrichtigung = new EMailBenachrichtigung();  // schickt echte E-Mails
    }

    public boolean buche(String kennung, int personen) {
        Optional<Raum> raum = katalog.finde(kennung);
        if (raum.isEmpty() || raum.get().plätze() < personen) {
            return false;
        }
        benachrichtigung.sende("Raum " + kennung + " für " + personen + " Personen gebucht");
        return true;
    }
}

    Die Felder haben zwar Interface-Typen – aber welche Umsetzung dahintersteht, steht im Konstruktor fest. Dasselbe gilt für einen statischen Zugriff wie Mailserver.standard().sende(…) oder ein Singleton: Die Klasse greift sich ihre Abhängigkeit selbst, niemand kann ihr eine andere geben.

    Für einen Test heißt das:

    • Kein Austausch: Jeder Test bucht gegen den echten Katalog und verschickt echte E-Mails – langsam, abhängig von der Umgebung, mit Nebenwirkungen.
    • Keine Kontrolle: Der Test kann nicht festlegen, welche Räume es gibt.
    • Kein Einblick: Ob eine Benachrichtigung hinausging und mit welchem Text, sieht der Test nicht – „abgelehnt, ohne E-Mail“ lässt sich gar nicht prüfen.

    Die Wende: Die Abhängigkeit kommt von außen

    Die Lösung ist klein: Der Konstruktor nimmt Katalog und Benachrichtigung entgegen, statt sie zu erzeugen. Der Buchungsdienst kennt danach nur noch die Interfaces; welche Umsetzung er bekommt, entscheidet, wer ihn erzeugt. Diese Umkehr der Zuständigkeit heißt Inversion of Control – die Klasse steuert nicht mehr selbst, woher ihre Helfer kommen.

    Vorher: Der Dienst erzeugt seine Helfer

    KlasseBuchungsdienst
    erzeugt selbst mit new
    konkrete KlasseSpeicherKatalog
    konkrete KlasseEMailBenachrichtigung
    public Buchungsdienst() {
    this.katalog = new SpeicherKatalog();
    this.benachrichtigung = new EMailBenachrichtigung();
}

    Wer einen Buchungsdienst will, bekommt beide Umsetzungen mit – ein Test ebenso wie die Anwendung. Dazwischen passt nichts.

    Nachher: Jemand anderes erzeugt und reicht hinein

    verdrahtetmain, ein Container oder ein Test
    erzeugt
    UmsetzungSpeicherKatalog
    UmsetzungEMailBenachrichtigung
    über den Konstruktor in
    KlasseBuchungsdienst
    kennt nur
    InterfaceRaumKatalog
    InterfaceBenachrichtigung
    public Buchungsdienst(RaumKatalog katalog, Benachrichtigung benachrichtigung) {
    this.katalog = katalog;
    this.benachrichtigung = benachrichtigung;
}

    Im Buchungsdienst steht kein new mehr. Die Felder bleiben final, buche bleibt Zeichen für Zeichen gleich – geändert hat sich nur, wer die Objekte erzeugt.

    Wer verdrahtet?

    Irgendwo müssen die Objekte doch erzeugt und zusammengesteckt werden. Diese Arbeit wandert an eine Stelle am Rand der Anwendung – von Hand oder durch ein Framework.

    Von Hand: main erzeugt und steckt zusammen

    public static void main(String[] args) {
    RaumKatalog katalog = new SpeicherKatalog();
    Benachrichtigung benachrichtigung = new EMailBenachrichtigung();
    Buchungsdienst dienst = new Buchungsdienst(katalog, benachrichtigung);

    System.out.println(dienst.buche("R1", 3));
    System.out.println(dienst.buche("R1", 8));
}

    Ausgabe (Raum R1 hat 4 Plätze)

    E-Mail gesendet: Raum R1 für 3 Personen gebucht
true
false

    Für eine kleine Anwendung reicht das völlig. Diese Stelle heißt auch Composition Root: der einzige Ort, der die konkreten Klassen kennt.

    Ein Container erledigt dieselbe Arbeit

    In größeren Anwendungen übernimmt ein Container die Rolle von main: Er findet die Klassen, erzeugt die Objekte, erkennt am Konstruktor, was sie brauchen, und reicht die passenden Objekte hinein. Der Buchungsdienst bekommt dafür nur eine Annotation.

    Jakarta CDI

    @Singleton
public class Buchungsdienst {

    @Inject
    public Buchungsdienst(RaumKatalog katalog,
                          Benachrichtigung benachrichtigung) {
        …
    }
}

    Spring

    @Service
public class Buchungsdienst {

    // nur ein Konstruktor: @Autowired ist nicht nötig
    public Buchungsdienst(RaumKatalog katalog,
                          Benachrichtigung benachrichtigung) {
        …
    }
}

    Findet der Container genau eine Umsetzung je Interface, nimmt er sie; gibt es mehrere, muss man ihm sagen, welche gilt. Der Rest des Dienstes bleibt unverändert – und im Test braucht man den Container gar nicht: new Buchungsdienst(…, …) genügt.

    Konstruktor, Setter oder Feld?

    Ein Container kann eine Abhängigkeit auf drei Wegen hineinreichen:

    Art So sieht es aus Folge
    Konstruktor public Buchungsdienst(RaumKatalog katalog, …) Felder final, Objekt nach new vollständig
    Setter @Inject void setzeKatalog(RaumKatalog katalog) Feld nicht final, bis zum Aufruf null
    Feld @Inject private RaumKatalog katalog; nur per Reflection zu setzen – ohne Container gar nicht

    Bevorzuge den Konstruktor. Ohne seine Abhängigkeiten lässt sich das Objekt dann gar nicht erzeugen; es gibt keinen halbfertigen Zustand, die Felder können final sein, und die Signatur zeigt auf einen Blick, was die Klasse braucht – werden es zu viele, ist das ein Hinweis, dass sie zu viel tut. Vor allem kommt ein Test ohne Container und ohne Reflection aus. Setter-Injektion bleibt für Abhängigkeiten, die wirklich optional sind oder sich später ändern dürfen.

    Im Test: Stellvertreter einsetzen

    Weil der Buchungsdienst nur Interfaces verlangt, kann ein Test ihm Stellvertreter geben: Objekte, die sich wie Katalog und Benachrichtigung verhalten, aber nichts nachschlagen und nichts verschicken.

    verdrahtetder Test
    erzeugt
    Stellvertreter fürRaumKatalog – liefert vorbereitete Räume
    Stellvertreter fürBenachrichtigung – schreibt mit, statt zu senden
    über den Konstruktor in
    wird getestetBuchungsdienst, unverändert

    Die beiden Stellvertreter haben verschiedene Aufgaben. Der Katalog ist eine Abfrage: Er liefert Antworten, über ihn prüft der Test nichts. Die Benachrichtigung ist eine Wirkung nach außen: An ihr prüft der Test, ob und was gesendet wurde. Faustregel: Abfragen vorbereiten, Wirkungen prüfen.

    Von Hand: ein Fake und ein Spy

    Der Fake ist eine einfache, aber funktionierende Umsetzung – hier ein Katalog, dem der Test seine Räume selbst gibt. Liefert ein Stellvertreter nur fest vorbereitete Antworten, heißt er Stub.

    class FakeKatalog implements RaumKatalog {

    private final Map<String, Raum> räume = new HashMap<>();

    void füge(Raum raum) {
        räume.put(raum.kennung(), raum);
    }

    @Override
    public Optional<Raum> finde(String kennung) {
        return Optional.ofNullable(räume.get(kennung));
    }
}

    Der Spy schreibt mit, wie er aufgerufen wurde – der Test liest die Mitschrift danach:

    class MitschreibendeBenachrichtigung implements Benachrichtigung {

    final List<String> texte = new ArrayList<>();

    @Override
    public void sende(String text) {
        texte.add(text);
    }
}

    class BuchungsdienstTest {

    private final FakeKatalog katalog = new FakeKatalog();
    private final MitschreibendeBenachrichtigung benachrichtigung = new MitschreibendeBenachrichtigung();
    private final Buchungsdienst dienst = new Buchungsdienst(katalog, benachrichtigung);

    @Test
    void passenderRaumLöstBenachrichtigungAus() {
        katalog.füge(new Raum("R1", 4));

        assertTrue(dienst.buche("R1", 3));
        assertEquals(List.of("Raum R1 für 3 Personen gebucht"), benachrichtigung.texte);
    }

    @Test
    void zuKleinerRaumBleibtStill() {
        katalog.füge(new Raum("R1", 4));

        assertFalse(dienst.buche("R1", 8));
        assertTrue(benachrichtigung.texte.isEmpty());
    }
}

    Das funktioniert ohne jede Bibliothek – kostet aber je Interface eine Klasse, und jede neue Methode im Interface muss in jedem Stellvertreter nachgezogen werden.

    Mockito: Stellvertreter zur Laufzeit

    Mockito erzeugt die Stellvertreter selbst. Drei Aufrufe tragen alles:

    • mock(RaumKatalog.class) – ein Stellvertreter, der jede Methode kennt und zunächst nur Standardantworten gibt.
    • when(katalog.finde("R1")).thenReturn(…) – bereitet eine Antwort vor (der Stub).
    • verify(benachrichtigung).sende(…) – prüft in der Mitschrift, ob ein Aufruf stattfand (der Mock im engeren Sinn).
    class BuchungsdienstMockitoTest {

    private final RaumKatalog katalog = mock(RaumKatalog.class);
    private final Benachrichtigung benachrichtigung = mock(Benachrichtigung.class);
    private final Buchungsdienst dienst = new Buchungsdienst(katalog, benachrichtigung);

    @Test
    void passenderRaumLöstBenachrichtigungAus() {
        when(katalog.finde("R1")).thenReturn(Optional.of(new Raum("R1", 4)));

        assertTrue(dienst.buche("R1", 3));
        verify(benachrichtigung).sende("Raum R1 für 3 Personen gebucht");
    }

    @Test
    void unbekannterRaumBleibtStill() {
        // kein when: finde(…) liefert die Standardantwort Optional.empty()
        assertFalse(dienst.buche("R9", 3));
        verify(benachrichtigung, never()).sende(anyString());
    }
}

    Keine Stellvertreter-Klassen mehr: Was der Fake und der Spy von Hand taten, legt jeder Test in zwei Zeilen selbst fest. Vorsicht beim Wort: Mockitos spy(objekt) ist etwas anderes als der Spy von Hand – er umhüllt ein echtes Objekt und ruft dessen Methoden auf, solange nichts anderes vorbereitet ist.

    Wenn verify scheitert, sagt Mockito genau, was fehlte. Erwartet ein Test eine Nachricht, obwohl der Dienst den zu kleinen Raum abgelehnt hat:

    org.mockito.exceptions.verification.WantedButNotInvoked

Wanted but not invoked:
benachrichtigung.sende(
    "Raum R1 für 8 Personen gebucht"
);
-> at …
Actually, there were zero interactions with this mock.

    Kam der Aufruf, aber mit anderem Text, zeigt Mockito beide nebeneinander:

    org.mockito.exceptions.verification.opentest4j.ArgumentsAreDifferent

benachrichtigung.sende(
    "Raum R1 für 4 Personen gebucht"

Actual invocations have different arguments:
benachrichtigung.sende(
    "Raum R1 für 3 Personen gebucht"

    Was ein Mock ist: ein Dynamic Proxy

    mock(RaumKatalog.class) gibt ein Objekt zurück, dessen Klasse niemand geschrieben hat. Sie entsteht zur Laufzeit und folgt dem Prinzip des Dynamic Proxy: Jede Methode tut nur eines – sie reicht den Aufruf an einen Handler weiter. Der Handler ist das Gedächtnis des Mocks.

    AufruferBuchungsdienst ruft katalog.finde("R1")
    jeder Aufruf geht an
    zur Laufzeit erzeugtRaumKatalog$MockitoMock$… – setzt RaumKatalog um
    gibt weiter an
    Handler
    1. schreibt den Aufruf mit – für verify
    2. sucht eine vorbereitete Antwort – aus when(…).thenReturn(…)
    3. sonst: Standardantwort

    Spiel die drei Fälle durch:

    Vorbereitete Antwort

    when(katalog.finde("R1")).thenReturn(Optional.of(new Raum("R1", 4)));
System.out.println(katalog.finde("R1"));

    Ausgabe

    Optional[Raum[kennung=R1, plätze=4]]

    Der Handler schreibt finde("R1") mit und findet eine Antwort, deren Argumente passen. Auch when(…) selbst ruft finde("R1") auf – diesen Aufruf merkt sich der Handler als „hier kommt gleich eine Antwort“ und nimmt ihn wieder aus der Mitschrift.

    Nichts vorbereitet: die Standardantwort

    System.out.println(katalog.finde("R2"));

    Ausgabe

    Optional.empty

    Für R2 gibt es keine passende Antwort. Der Handler gibt dann eine Standardantwort, die zum Rückgabetyp passt – nie eine Exception. An einem Interface mit mehr Methoden gemessen:

    Rückgabetyp Standardantwort
    Optional<Raum> Optional.empty
    List<Raum> [] – leere Liste
    int 0
    boolean false
    String null
    Raum (eigene Klasse) null

    Zahlen und Wahrheitswerte also neutral, Collections, Optional und Streams leer, alles andere null. Deshalb lehnt der Dienst einen unbekannten Raum schon ohne jedes when ab.

    Nachher prüfen: die Mitschrift

    dienst.buche("R1", 3);
verify(benachrichtigung).sende("Raum R1 für 3 Personen gebucht");

    verify(benachrichtigung) schaltet den Mock für einen Aufruf in den Prüfmodus: Das folgende .sende(…) sendet nichts, sondern fragt den Handler, ob seine Mitschrift diesen Aufruf enthält – genau einmal, sofern times(…) oder never() nichts anderes sagen. Die Mitschrift selbst zeigt mockingDetails(katalog).getInvocations():

    Ausgabe nach finde("R1") und finde("R2")

    [raumKatalog.finde("R1");, raumKatalog.finde("R2");]

    Wie Mockito die Klasse erzeugt

    Das Prinzip ist das des Dynamic Proxy, das Werkzeug ein anderes: Mockito 5 nutzt nicht java.lang.reflect.Proxy, sondern die Bibliothek Byte Buddy, die Bytecode zur Laufzeit schreibt. Standard ist der Inline Mock Maker; er arbeitet per Instrumentierung über einen Java-Agenten. Gemessen:

    RaumKatalog katalog = mock(RaumKatalog.class);
System.out.println(katalog.getClass().getName());
System.out.println(Proxy.isProxyClass(katalog.getClass()));

EMailBenachrichtigung email = mock(EMailBenachrichtigung.class);
System.out.println(email.getClass().getName());
email.sende("Test");

    Ausgabe

    di.RaumKatalog$MockitoMock$ewbYc8xd
false
di.EMailBenachrichtigung
    • Für ein Interface erzeugt Byte Buddy eine neue Klasse, die es umsetzt – wie ein Dynamic Proxy, nur mit eigenem Namensschema (die Endung ist zufällig und wechselt je Lauf). Ein Proxy von java.lang.reflect.Proxy hieße dagegen etwa jdk.proxy2.$Proxy73; deshalb liefert Proxy.isProxyClass hier false.
    • Für eine Klasse erzeugt der Inline Mock Maker gar keine neue: Er schreibt den Bytecode der vorhandenen Klasse um, sodass ihre Methoden für Mocks beim Handler nachfragen. Darum heißt der Mock wie das Original – und email.sende("Test") gibt nichts aus, die echte Methode läuft nicht. Ein java.lang.reflect.Proxy kann nur Interfaces; Mockito kann so auch Klassen ersetzen.

    Den Agenten hängt Mockito beim ersten Mock selbst an die laufende JVM. Das funktioniert heute noch, aber Mockito und die JVM warnen davor:

    Mockito is currently self-attaching to enable the inline-mock-maker. This will no longer work in future releases of the JDK. Please add Mockito as an agent to your build as described in Mockito's documentation: https://javadoc.io/doc/org.mockito/mockito-core/latest/org.mockito/org/mockito/Mockito.html#0.3
WARNING: A Java agent has been loaded dynamically (…/byte-buddy-agent-1.17.7.jar)

    Die Abhilfe – den Agenten beim Start der Tests mit -javaagent angeben – beschreibt die Dokumentation von Mockito an der verlinkten Stelle.

    Merksatz: Eine Klasse soll ihre Abhängigkeiten bekommen, nicht erzeugen – über den Konstruktor und als Interface. Dann entscheidet, wer verdrahtet: main, ein Container oder ein Test. Und ein Mock ist nichts anderes als ein Stellvertreter nach dem Prinzip des Dynamic Proxy: Jeder Aufruf landet bei einem Handler, der mitschreibt und antwortet.
