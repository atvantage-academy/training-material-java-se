Die Oberklasse Object

    Jede Klasse in Java hat eine Oberklasse – und wenn Du keine angibst, ist es Object. Damit erbt jedes Objekt ein paar Methoden, die Collections, println, Tests und Threads voraussetzen. Klicke eine Methode an: Du bekommst ihren Zweck, ein kurzes Beispiel und wofür sie verwendet wird.

    java.langObject
    Room class Room { … } Deine Klasse – ohne extends
    String überschreibt equals, hashCode, toString
    Integer über Number, ebenso
    int[] auch Arrays sind Objekte

    erbt von + public · # protected – nur in Unterklassen und im selben Package sichtbar Fett: die Methoden, die Du in eigenen Klassen am häufigsten überschreibst

    Jede Klasse erbt von Object

    Implizit: extends Object

    Gibst Du keine Oberklasse an, setzt der Compiler Object ein. Beide Zeilen bedeuten dasselbe:

    public class Room { … }
public class Room extends Object { … }

    Hat eine Klasse eine andere Oberklasse, erbt sie Object über diese – an der Spitze jeder Hierarchie steht immer Object.

    Eine Variable für alles

    Weil jedes Objekt ein Object ist, passt jedes in eine Variable vom Typ Object – auch ein Array:

    Object a = new Room("R268", "Seminar 1");
Object b = "Text";
Object c = new int[3];

    Darauf bauen equals(Object), List.remove(Object) oder Map.get(Object): Sie nehmen jedes Objekt an. Primitive Werte wie int sind keine Objekte; sie werden dafür in einen Wrapper verpackt (Autoboxing).

    Erben heißt: überschreiben dürfen

    Die geerbten Fassungen von equals, hashCode und toString kennen Deine Felder nicht. Sie vergleichen Identität und geben den Klassennamen mit einer Hexzahl aus. Was ein Raum fachlich ist, legst Du fest, indem Du sie überschreibst – mit @Override, damit der Compiler einen Tippfehler in der Signatur meldet.

    getClass, wait und notify sind final: Die kannst Du nur aufrufen.

    Auch new Object() geht

    Object ist keine abstrakte Klasse – Du kannst sie selbst instanziieren:

    Object o = new Object();
System.out.println(o);   // java.lang.Object@6b95977

    Ein solches Objekt hat keine Felder und kann nur, was Object kann: Es hat eine eigene Identität, ist nur sich selbst gleich, und Threads können sich mit synchronized darauf abstimmen.

    public

    boolean equals(Object obj)

    Sind zwei Objekte fachlich gleich?

    Zweck

    == fragt, ob zwei Variablen auf dasselbe Objekt zeigen. equals fragt, ob zwei Objekte gleich sind – was „gleich“ heißt, legt die Klasse fest. Die geerbte Fassung aus Object kennt keine Felder und prüft deshalb nur this == obj.

    @Override
public boolean equals(Object o) {
    if (o == null || getClass() != o.getClass()) {
        return false;
    }
    Room other = (Room) o;
    return number.equals(other.number);   // ein Raum ist seine Nummer
}
    Room a = new Room("R268", "Seminar 1");
Room b = new Room("R268", "Seminar 1");
System.out.println(a == b);       // false – zwei Objekte
System.out.println(a.equals(b));  // true  – fachlich gleich

    Der Vertrag

    Jede Fassung von equals muss diese Regeln einhalten (Javadoc von Object.equals):

    • reflexiv: a.equals(a) ist true
    • symmetrisch: a.equals(b) genau dann, wenn b.equals(a)
    • transitiv: aus a.equals(b) und b.equals(c) folgt a.equals(c)
    • konsistent: gleiches Ergebnis, solange sich die verglichenen Felder nicht ändern
    • a.equals(null) ist false

    Wer es verwendet

    • List.contains, indexOf, remove(Object)
    • HashSet und HashMap – zusammen mit hashCode
    • assertEquals in JUnit

    Stolpersteine

    • Den Parameter als Room statt Object deklariert: Das überlädt, statt zu überschreiben – @Override deckt es auf.
    • instanceof statt getClass(): Vergleicht eine Unterklasse zusätzliche Felder, bricht die Symmetrie.
    • equals überschrieben, hashCode nicht.
    public

    int hashCode()

    Eine Zahl, die sagt, in welchem Fach ein Objekt liegt.

    Zweck

    HashSet und HashMap verteilen ihre Elemente auf Fächer (Buckets). Das Fach berechnen sie aus hashCode(). Beim Suchen schauen sie nur in diesem einen Fach nach und vergleichen dort mit equals. Deshalb müssen gleiche Objekte im selben Fach liegen – also denselben Hashwert haben.

    Die geerbte Fassung liefert für jedes Objekt einen eigenen Wert (die „Identität“). Zwei gleiche Räume landen dann in verschiedenen Fächern, und ein HashSet findet den zweiten nicht.

    @Override
public int hashCode() {
    return Objects.hash(number);   // dieselben Felder wie in equals
}
    Set<Room> rooms = new HashSet<>();
rooms.add(new Room("R268", "Seminar 1"));
System.out.println(rooms.contains(new Room("R268", "Seminar 1")));   // true

    Der Zusammenhang mit equals

    gleich nach equals⇒gleicher HashwertPflicht
    ungleich⇒möglichst verschiedener HashwertLaufzeit
    gleicher Hashwert⇏gleiche ObjekteKollision

    Kollisionen gibt es zwangsläufig – ein int hat weniger Werte, als es Strings gibt:

    System.out.println("Aa".hashCode());     // 2112
System.out.println("BB".hashCode());     // 2112
System.out.println("Aa".equals("BB"));   // false

    Das ist erlaubt: Im selben Fach entscheidet equals. Liefert aber jedes Objekt denselben Wert, liegt alles in einem Fach, und jede Suche vergleicht mit allen – richtig, aber langsam.

    Faustregeln

    • Dieselben Felder wie in equals, nicht mehr.
    • Objects.hash(…) oder erzeugen lassen.

    Stolpersteine

    • Ändert sich ein Feld, das im Hashwert steckt, während das Objekt im Set liegt, sucht das Set im falschen Fach – das Objekt ist „verschwunden“.
    public

    String toString()

    Das Objekt als Text – für Menschen.

    Zweck

    Java ruft toString() überall auf, wo ein Objekt zu Text werden muss: in System.out.println, beim Verketten mit +, in Fehlermeldungen von Tests, in Logs und im Debugger. Die geerbte Fassung liefert den Klassennamen, ein @ und den Hashwert als Hexzahl:

    System.out.println(new Room("R268", "Seminar 1"));
// ohne toString: de.schulung.Room@7344699f
    @Override
public String toString() {
    return "Room " + number + " (" + name + ")";
}
// mit toString:  Room R268 (Seminar 1)

    Wofür

    • Lesbare Ausgaben beim Testen, Loggen und Debuggen – expected: <Room R268> sagt mehr als eine Hexzahl.

    Stolpersteine

    • Keine Passwörter oder persönlichen Daten hinein – toString landet in Logs.
    • Nicht zum Parsen verwenden: Das Format ist für Menschen, nicht für Programme.
    public final

    Class<?> getClass()

    Von welcher Klasse ist dieses Objekt wirklich?

    Zweck

    getClass() liefert die Klasse, mit der das Objekt erzeugt wurde – nicht den Typ der Variablen. Die Methode ist final: Kein Objekt kann über seine Klasse lügen.

    Object o = "Text";
System.out.println(o.getClass().getSimpleName());   // String
System.out.println(o.getClass().getName());         // java.lang.String
System.out.println(o.getClass() == String.class);   // true

    Wofür

    • In equals: getClass() != o.getClass() lässt nur Objekte derselben Klasse gleich sein.
    • In toString einer Oberklasse: getClass().getSimpleName() nennt die Unterklasse.
    • Einstieg in Reflection: Felder, Methoden und Annotationen einer Klasse lesen.

    Stolpersteine

    • Für Fallunterscheidungen im Fachcode ist instanceof oder Polymorphie meist die bessere Wahl – getClass() == schließt Unterklassen aus.
    protected

    Object clone()

    Eine Kopie des Objekts – flach.

    Zweck

    clone() erzeugt ein neues Objekt mit denselben Feldwerten. Die Methode ist protected, und sie funktioniert nur, wenn die Klasse das Marker-Interface Cloneable implementiert – sonst wirft sie CloneNotSupportedException. Im Alltag begegnet sie Dir vor allem bei Arrays, dort ist sie öffentlich:

    int[] original = { 1, 2, 3 };
int[] copy = original.clone();
copy[0] = 99;
System.out.println(Arrays.toString(original));   // [1, 2, 3]
System.out.println(Arrays.toString(copy));       // [99, 2, 3]

    Die Kopie ist flach: Felder mit Referenzen zeigen danach auf dieselben Objekte.

    List<String>[] lists = new List[] { new ArrayList<>(List.of("a")) };
List<String>[] shallow = lists.clone();
shallow[0].add("b");
System.out.println(lists[0]);   // [a, b] – dieselbe Liste

    Besser für eigene Klassen: ein Kopierkonstruktor oder eine Fabrikmethode (new ArrayList<>(list), List.copyOf(list)). Die sind lesbar, brauchen kein Cloneable und legen fest, wie tief kopiert wird.
    protected · veraltet

    void finalize()

    Der „Destruktor“, auf den man sich nicht verlassen kann.

    Zweck

    Der Garbage Collector ruft finalize() auf, bevor er ein Objekt wegräumt, das niemand mehr erreicht. Gedacht war das wie ein Destruktor in C++: Ressourcen freigeben, Dateien schließen, eine Lampe ausschalten.

    @Override
protected void finalize() {        // Warnung: [removal] finalize() in Object ist veraltet
    projector.switchOff();         // … und wurde zum Entfernen markiert
}

    Warum das nicht trägt

    • Der Garbage Collector läuft asynchron, wann er will – vielleicht Sekunden später, vielleicht gar nicht, wenn genug Speicher da ist oder das Programm vorher endet. System.gc() ist nur eine Bitte.
    • Abschaltbar: Mit java --finalization=disabled (seit Java 18) ruft die JVM finalize() überhaupt nicht mehr auf.
    • Abgekündigt: seit Java 9 veraltet, seit Java 18 zum Entfernen markiert (JEP 421, @Deprecated(since="9", forRemoval=true)).
    • Dazu: Exceptions darin gehen verloren, ein eigener Thread führt es aus, und Objekte mit finalize bremsen den Garbage Collector.

    Besser: AutoCloseable und try-with-resources. Die Klasse implementiert close(), und der try-Block ruft es sofort und garantiert auf – auch wenn eine Exception fliegt. Wie das geht, zeigt die Visualisierung Exceptions im Reiter try-with-resources.

    try (Projector projector = new Projector("INV-17", 3000)) {
    projector.switchOn();
    // … präsentieren …
}   // hier ruft Java projector.close() auf – die Lampe ist aus
    public final

    wait() · notify() · notifyAll()

    Threads, die aufeinander warten.

    Zweck

    Jedes Objekt kann als Monitor dienen, auf den Threads mit synchronized zugreifen. wait() legt den aktuellen Thread schlafen und gibt den Monitor frei; notify() weckt einen wartenden Thread, notifyAll() alle. Deshalb stehen diese Methoden in Object und nicht in Thread.

    class Mailbox {
    private String message;

    synchronized void put(String m) {
        message = m;
        notifyAll();                  // Wartende wecken
    }

    synchronized String take() throws InterruptedException {
        while (message == null) {     // in einer Schleife prüfen, nicht mit if
            wait();
        }
        String m = message;
        message = null;
        return m;
    }
}

    Regeln

    • Nur innerhalb von synchronized auf demselben Objekt aufrufen – sonst IllegalMonitorStateException.
    • wait() immer in einer Schleife: Ein Thread kann ohne notify aufwachen.
