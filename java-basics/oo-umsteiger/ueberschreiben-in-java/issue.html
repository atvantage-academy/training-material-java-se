    Kontoarten unterschiedlich prüfen lassen

    Als Entwickler:in möchte ich, dass jede Kontoart selbst entscheidet, wie viel abgehoben werden darf, damit ich beim Abheben nicht nach der Kontoart fragen muss.

    Lernziele

    • Du machst eine Oberklasse abstrakt und siehst, was der Compiler daraufhin verbietet.
    • Du überschreibst eine Methode und sicherst das mit @Override ab.
    • Du lässt ein Verhalten je Unterklasse variieren, ohne den Aufrufer zu ändern.
    • Du implementierst equals fachlich und grenzt es gegen == ab.

    Definition of Done

    • Konto ist abstrakt; new Konto(...) kompiliert nicht mehr.
    • Die Prüfung, ob genug verfügbar ist, ist eine eigene Methode; abheben ruft sie auf.
    • Das Girokonto überschreibt die Prüfung (Dispolimit), das Sparkonto nicht.
    • Jede überschriebene Methode trägt @Override.
    • Ein Giro- und ein Sparkonto in einem Konto[] reagieren in derselben Schleife unterschiedlich auf dieselbe Abhebung.
    • Zwei Konten mit derselben IBAN sind laut equals gleich.
    • Du hast die Kontrollfragen beantwortet

    Hinweis: Polymorphie kennst Du. Hier geht es um die Java-Mittel dafür: abstract, @Override, protected und die Methoden, die jede Klasse von Object erbt.

    Arbeitsschritte

    Die Oberklasse abstrakt machen

    Es gibt kein Konto, das weder Giro- noch Sparkonto ist. Sorg dafür, dass der Compiler das durchsetzt.

    Hinweis: Probier danach bewusst new Konto(...) aus und lies die Meldung.

    Die Prüfung herausziehen

    Beim Abheben stellt sich immer dieselbe Frage: Ist genug da? Was „genug“ bedeutet, unterscheidet sich je Kontoart – die Frage selbst nicht. Trenne beides: Das Abheben bleibt in der Oberklasse, die Prüfung wird eine eigene Methode.

    Hinweis: Damit die Unterklasse die Prüfung ersetzen kann, muss sie sie sehen. Welche Sichtbarkeit passt – und was bedeutet sie in Java zusätzlich?

    Das Girokonto anders prüfen lassen

    Beim Girokonto darf bis zum Dispolimit ins Minus gegangen werden. Überschreib die Prüfung entsprechend – und fass das Abheben nicht an.

    Hinweis: Setz @Override davor. Bau danach einmal absichtlich einen Tippfehler in den Methodennamen und sieh Dir an, was die Annotation meldet. Und dann: Nimm die Annotation weg und lass den Tippfehler stehen. Was passiert jetzt?

    Beide Konten gemeinsam behandeln

    Leg ein Giro- und ein Sparkonto in ein Konto[] und versuch in einer Schleife, bei jedem denselben Betrag abzuheben.

    Hinweis: Überleg vor dem Start, was passieren wird, und vergleich es danach mit der Ausgabe.

    Gleichheit festlegen

    Zwei Konten sind dasselbe Konto, wenn ihre IBAN übereinstimmt. Überschreib die Methode, die das festlegt.

    Hinweis: Die Methode erbst Du – wie toString() – aus Object. Achte auf den Typ des Parameters. Vergleich anschließend zwei Objekte mit derselben IBAN einmal mit == und einmal mit Deiner Methode.

    Hinweis: Wenn solche Objekte später in ein HashSet wandern, gehört noch eine zweite Methode dazu. Das kommt im Kurs noch – für heute genügt equals.

    Für Schnelle

    • Ergänze eine dritte Kontoart mit einer eigenen Regel und lauf die Schleife erneut – wie viel bestehenden Code musstest Du anfassen?
    • Schreib equals einmal von Hand und lass es danach von der IDE erzeugen. Was macht die IDE anders?

    Reflexionsfragen

    • Warum musstest Du das Abheben nicht ändern, obwohl sich das Verhalten je Kontoart unterscheidet?
    • Was ist ohne @Override beim Tippfehler passiert – und warum ist das gefährlicher als ein Compilerfehler?
    • Warum muss der Parameter von equals den Typ Object haben?
    • Wie gibt Deine bisherige Sprache eine Methode zum Überschreiben frei – und wie macht es Java?
