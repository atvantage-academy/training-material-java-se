    Raumbuchungen auswerten

    User Story

    Als Entwickler:in der Raumbuchung möchte ich Auswertungen über Räume und Buchungen als Pipelines formulieren, damit im Code steht, was ich wissen will, und nicht, wie die Schleife läuft.

    Lernziele
    • Du baust eine Schleife zu einer Stream-Pipeline um, ohne dass sich ihr Ergebnis ändert.
    • Du übergibst Bedingungen und Sortierungen als Lambda oder Methodenreferenz und kombinierst sie.
    • Du nutzt removeIf, forEach und Map.merge bzw. computeIfAbsent, statt Collections von Hand zu durchlaufen.
    • Du wertest mit groupingBy, partitioningBy, toMap und joining aus.
    • Du gibst ein Ergebnis, das fehlen kann, als Optional zurück und unterscheidest orElse von orElseGet.
    • Du rufst eine Methode mit Checked Exception aus einem Lambda auf.
    Definition of Done
    • In ReportsTest trägt kein Test mehr @Disabled, alle sind grün, und largeMeetingRoomNames kommt ohne Schleife aus.
    • Die Vorhersagen in PredictionsTest hast Du notiert, geprüft und die Assertions auf das tatsächliche Verhalten korrigiert.
    • In ExceptionsInLambdasTest trägt kein Test mehr @Disabled, alle sind grün, und executeAction liest die Datei über ein Lambda.
    • mvn test läuft ohne Fehler und ohne übersprungene Tests durch.
    • Du hast die Kontrollfragen beantwortet

    Die Raumbuchung kennt Räume und Buchungen. Gefragt sind Auswertungen: Welche Räume sind groß genug, wer hat wie viele Stunden gebucht, was war am 1. Dezember belegt? Eine Auswertung gibt es schon – als Schleife. Die übrigen beschreiben Tests, die Du freischaltest und grün machst.

    Starte die Tests:

    mvn test

    Der Bau ist grün: largeMeetingRoomNames und cancellationOfFirstBookingOfRoomR102 laufen, alle anderen Tests tragen @Disabled – sie sind Deine Aufträge. Entferne @Disabled an einem Test, sobald Du die Methode dazu angehst, und mach ihn grün.

    Bau die Schleife zur Pipeline um

    Lies largeMeetingRoomNames und sag in einem Satz, was die Methode liefert. Bau sie dann zu einer Stream-Pipeline um: filtern, sortieren, auf den Namen abbilden, mit Komma verbinden. Der Test bleibt grün.

    Hinweis: Für die Sortierung gibt es Comparator.comparingInt(…), fürs Verbinden Collectors.joining(…).

    Übergib Bedingungen und Sortierungen als Lambda

    Implementier namesWhere: Die Bedingung kommt als Predicate<Room> herein. Sieh Dir im Test namesOfLargeTrainingRooms an, wie zwei Lambdas mit and zu einer Bedingung werden.

    Im Test roomsSortedByFloorThenLargestFirst ist der Comparator noch unvollständig. Entferne dort @Disabled und ergänz ihn so, dass innerhalb eines Stockwerks der größte Raum zuerst kommt.

    Hinweis: thenComparing nimmt auch einen zweiten Comparator für die Richtung.

    Zähle mit der Collections-API

    Implementier bookedHoursPerPerson: Stornierte Buchungen zählen nicht. Arbeite auf einer Kopie der Liste und entferne die stornierten Buchungen mit removeIf; summiere dann je Person mit forEach und Map.merge.

    Implementier roomIdsPerPerson ebenso ohne Stream: Für jede aktive Buchung holst Du mit computeIfAbsent die Menge der Person – oder legst sie an – und fügst die Raum-ID hinzu.

    Hinweis: SampleData.BOOKINGS ist mit List.of angelegt und lässt sich nicht ändern. Was passiert, wenn Du removeIf direkt darauf aufrufst?

    Werte mit Collectors aus

    Implementier mit Streams:

    • roomCountPerType mit Collectors.groupingBy und einem nachgelagerten Collector,
    • namesBySeatsAtLeast mit Collectors.partitioningBy – die Werte sind Namen, keine Räume,
    • roomNamesBookedOn: Bau Dir zuerst mit Collectors.toMap eine Map von Raum-ID zu Raumname, dann bildest Du die Buchungen des Tages darauf ab. Jeder Raum steht nur einmal im Ergebnis.

    Benutze Optional richtig

    Implementier findRoom so, dass sie ein Optional<Room> liefert. Sieh Dir im Test findRoom an, wie der Aufrufer mit map und orElse umgeht, ohne isPresent und get.

    Der Test cancellationOfFirstBookingOfRoomR102 ist schon grün. Lies ihn und erklär, warum dort flatMap steht.

    Hinweis: Optional ist ein Rückgabetyp. Als Feld oder Parameter macht es den Code nicht sicherer, nur länger – Booking speichert deshalb cancelledOn und gibt erst in cancellation() ein Optional heraus.

    Sag das Verhalten vorher

    Die beiden Tests in PredictionsTest tragen @Disabled und eine naheliegende Erwartung. Kopiere die Klasse nach src/test/java/aufbau/lambdas.

    PredictionsTest.java:

    package aufbau.lambdas;

import static aufbau.lambdas.SampleData.ROOMS;
import static org.junit.jupiter.api.Assertions.assertEquals;

import java.util.ArrayList;
import java.util.List;
import java.util.Optional;
import java.util.concurrent.atomic.AtomicInteger;
import org.junit.jupiter.api.Disabled;
import org.junit.jupiter.api.Test;

class PredictionsTest {

    @Test
    @Disabled("Predict the result first, then remove @Disabled")
    void howManyRoomsAreChecked() {
        List<String> checked = new ArrayList<>();

        Optional<Room> firstLargeRoom = ROOMS.stream()
                .filter(room -> {
                    checked.add(room.id());
                    return room.seats() > 10;
                })
                .findFirst();

        assertEquals("Munich", firstLargeRoom.orElseThrow().name());
        assertEquals(8, checked.size());
    }

    @Test
    @Disabled("Predict the result first, then remove @Disabled")
    void howOftenIsTheFallbackCreated() {
        AtomicInteger calls = new AtomicInteger();

        String name = Optional.of("Berlin").orElse(fallbackName(calls));

        assertEquals("Berlin", name);
        assertEquals(0, calls.get());
    }

    private static String fallbackName(AtomicInteger calls) {
        calls.incrementAndGet();
        return "unknown";
    }
}

    Geh für jeden Test so vor:

    1. Notier Deine Erwartung: Wie viele Räume prüft der Filter? Wie oft wird fallbackName aufgerufen?
    2. Entferne @Disabled und starte den Test.
    3. Erklär das Ergebnis.
    4. Korrigier die Assertion auf das tatsächliche Verhalten, bis der Test grün ist.

    Ersetz danach in howOftenIsTheFallbackCreated das orElse durch orElseGet und pass die Assertion wieder an.

    Ändere nur executeAction und readAll:

    • executeAction soll die Datei über ein Lambda lesen, wie im Kommentar. Entferne die Kommentarzeichen und lies die Meldung des Compilers. Finde einen Weg, bei dem die IOException trotzdem beim Aufrufer ankommt – der Test exceptionReachesTheCaller bleibt grün.
    • readAll soll alle Dateien mit einem Stream lesen, wie im Kommentar. Hier soll eine fehlende Datei als UncheckedIOException ankommen. Entferne an den beiden Tests zu readAll das @Disabled.

    Hinweis: Zwei Wege sind üblich: ein eigenes funktionales Interface, dessen Methode throws IOException deklariert, oder die IOException im Lambda fangen und in eine UncheckedIOException einpacken. Probier beide aus.
