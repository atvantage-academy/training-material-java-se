    Exceptions: früh scheitern, nicht spät

    User Story

    Als Java-Entwickler:in möchte ich, dass ungültige Daten sofort auffallen, damit ich den Fehler dort finde, wo er entsteht – und nicht zehn Aufrufe später.

    Lernziele
    • Du sagst voraus, was passiert, wenn ein Objekt mit fehlender Angabe benutzt wird, und begründest es.
    • Du prüfst Argumente im Konstruktor, lehnst ungültige mit einer IllegalArgumentException ab und testest das mit try-catch.
    • Du definierst eine eigene, geprüfte Exception, wirfst sie und erwartest sie im Test.
    • Du misst, was eine Exception als Abbruchbedingung einer Schleife kostet.
    Definition of Done
    • Das Package aufbau.exceptions enthält Person unter src/main/java sowie ExceptionTimeTest und ExceptionControlFlowTest unter src/test/java, keiner trägt mehr @Disabled.
    • Der Konstruktor von Person lehnt ein fehlendes Geburtsdatum mit einer IllegalArgumentException ab; ein Test prüft das mit try-catch und der Meldung.
    • Room lehnt eine zweite Buchung desselben Tages mit einer RoomAlreadyBookedException ab, die Raum und Tag nennt; secondBookingOfTheSameDayIsRejected prüft Typ, Raum und Tag.
    • Der Maven-Build läuft grün.
    • Du hast die beiden Laufzeiten aus ExceptionControlFlowTest notiert und kannst den Unterschied erklären.
    • Du hast die Kontrollfragen beantwortet

    Eine Exception ist eine Nachricht: Hier stimmt etwas nicht. Wie nützlich sie ist, hängt davon ab, wann sie fliegt – und ob sie überhaupt einen Fehler meldet.

    Arbeitsschritte

    Das Package anlegen

    Im Ordner src/main/java und im Ordner src/test/java Deines Projekts java-aufbau lege je das Package aufbau.exceptions an.

    Vorhersagen, wann es knallt

    Leg im Package aufbau.exceptions unter src/main/java die Klasse Person an:

    package aufbau.exceptions;

import java.time.LocalDate;
import java.time.Period;

public class Person {

    private static final int ADULT_AGE = 18;

    private final String name;
    private final LocalDate birthDate;

    public Person(String name, LocalDate birthDate) {
        this.name = name;
        this.birthDate = birthDate;
    }

    public String getName() {
        return name;
    }

    public LocalDate getBirthDate() {
        return birthDate;
    }

    public boolean isAdult() {
        return Period.between(birthDate, LocalDate.now()).getYears() >= ADULT_AGE;
    }
}

    Leg danach im Package aufbau.exceptions unter src/test/java den Test ExceptionTimeTest an:

    package aufbau.exceptions;

import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.api.Disabled;
import org.junit.jupiter.api.Test;

@Disabled("Predict the result first, then remove @Disabled")
class ExceptionTimeTest {

    @Test
    void personWithoutBirthDate() {
        Person person = new Person("Max", null);
        System.out.println("Person created: " + person.getName());

        // imagine many more lines of code here ...

        boolean adult = person.isAdult();
        assertEquals(false, adult);
    }
}

    Was passiert, wenn Du den Test startest? Notier Deine Erwartung, entferne @Disabled und starte den Test in der IDE.

    Lies die Meldung der Exception genau: Welche Zeile nennt sie, und welche Zeile hat den Fehler verursacht?

    Den Fehler an den Anfang verlegen

    Eine Person ohne Geburtsdatum soll gar nicht erst entstehen. Ersetze den Test personWithoutBirthDate durch diesen:

    @Test
void personWithoutBirthDateIsRejected() {
    try {
        new Person("Max", null);
        fail("IllegalArgumentException expected");
    } catch (IllegalArgumentException exception) {
        assertEquals("birthDate must not be null", exception.getMessage());
    }
}

    Kommt der Test hinter new Person(…), ist keine Exception geflogen – dann lässt fail ihn scheitern. Ergänze den Import import static org.junit.jupiter.api.Assertions.fail; und starte den Test in der IDE – er muss zuerst scheitern.

    Ändere dann den Konstruktor von Person so, dass er ein fehlendes Geburtsdatum mit einer IllegalArgumentException und genau dieser Meldung ablehnt. Starte den Test erneut, bis er grün ist.

    Lösung 
    public Person(String name, LocalDate birthDate) {
    if (birthDate == null) {
        throw new IllegalArgumentException("birthDate must not be null");
    }
    this.name = name;
    this.birthDate = birthDate;
}

    Die Doppelbuchung ablehnen

    Der Room aus Den Raum mit JUnit testen nimmt eine zweite Buchung desselben Tages stillschweigend hin. Das soll er ablehnen – mit einer eigenen Exception, die den Raum und den Tag mitliefert, damit der Aufrufer darauf reagieren kann.

    1. Leg im Package aufbau.junit unter src/main/java die Klasse RoomAlreadyBookedException an. Sie erbt von Exception, bekommt im Konstruktor den Raum und den Tag und gibt beide über Getter heraus. Als Meldung eignet sich etwa Seminar 1 is already booked on 2026-03-02.
    2. Schreib in RoomTest einen Test secondBookingOfTheSameDayIsRejected: Nach einer ersten Buchung am Montag wirft eine zweite die RoomAlreadyBookedException, und sie nennt diesen Raum und diesen Tag.
    3. Ändere book in Room, bis der Test grün ist. Was meldet der Compiler danach für die übrigen Tests, die book aufrufen? Korrigier sie.

    Hinweis: Erwarte die Exception wie bei Person mit try-catch und fail. Im catch-Block hast Du die Exception in der Hand; dass sie denselben Raum nennt, prüft assertSame.

    Lösung: die Exception 
    package aufbau.junit;

import java.time.LocalDate;

public class RoomAlreadyBookedException extends Exception {

    private final Room room;
    private final LocalDate day;

    public RoomAlreadyBookedException(Room room, LocalDate day) {
        super(room.getName() + " is already booked on " + day);
        this.room = room;
        this.day = day;
    }

    public Room getRoom() {
        return room;
    }

    public LocalDate getDay() {
        return day;
    }
}
    Lösung: Test und Room

    Im Test dazu die statischen Importe Assertions.fail und Assertions.assertSame. Jeder Test, der book aufruft, kündigt die Exception mit throws an.

    // RoomTest
@Test
void secondBookingOfTheSameDayIsRejected() throws RoomAlreadyBookedException {
    room.book(MONDAY);
    try {
        room.book(MONDAY);
        fail("RoomAlreadyBookedException expected");
    } catch (RoomAlreadyBookedException exception) {
        assertSame(room, exception.getRoom());
        assertEquals(MONDAY, exception.getDay());
    }
}

// Room
public void book(LocalDate day) throws RoomAlreadyBookedException {
    if (!bookedDays.add(day)) {
        throw new RoomAlreadyBookedException(this, day);
    }
}

    Baue danach erneut mit Maven.

    Exceptions als Schleifenende messen

    Beide Tests laufen 100 000-mal über eine Liste mit zwei Elementen und zählen dabei die Buchstaben – beide kommen auf denselben Wert. Der erste hört auf, wenn next() eine NoSuchElementException wirft, der zweite fragt vorher hasNext(). Bevor Du startest: Schätze, um welchen Faktor die erste Variante langsamer ist. Speichere den Test als ExceptionControlFlowTest.java:

    package aufbau.exceptions;

import static org.junit.jupiter.api.Assertions.assertEquals;

import java.util.Iterator;
import java.util.List;
import java.util.NoSuchElementException;

import org.junit.jupiter.api.Disabled;
import org.junit.jupiter.api.Test;

@Disabled("Predict the result first, then remove @Disabled")
class ExceptionControlFlowTest {

    // Adjust to your machine: smaller if the test runs too long, larger if the times are too short to compare.
    static final int REPETITIONS = 100_000;
    static final List<String> MESSAGES = List.of("x", "y");
    static final int EXPECTED_LETTERS = REPETITIONS * 2;

    @Test
    void stopWithException() {
        long start = System.nanoTime();
        int letters = 0;
        for (int i = 0; i < REPETITIONS; i++) {
            Iterator<String> iterator = MESSAGES.iterator();
            try {
                while (true) {
                    letters += iterator.next().length();
                }
            } catch (NoSuchElementException e) {
                // done
            }
        }
        long millis = (System.nanoTime() - start) / 1_000_000;
        System.out.println("Exception: " + millis + " ms");
        assertEquals(EXPECTED_LETTERS, letters);
    }

    @Test
    void stopWithHasNext() {
        long start = System.nanoTime();
        int letters = 0;
        for (int i = 0; i < REPETITIONS; i++) {
            Iterator<String> iterator = MESSAGES.iterator();
            while (iterator.hasNext()) {
                letters += iterator.next().length();
            }
        }
        long millis = (System.nanoTime() - start) / 1_000_000;
        System.out.println("hasNext(): " + millis + " ms");
        assertEquals(EXPECTED_LETTERS, letters);
    }
}

    Entferne @Disabled und starte den Test in der IDE.

    Die Laufzeiten stehen in der Konsole. Vergleiche sie mit Deiner Schätzung.

    Für Schnelle: Was ist erwachsen?

    Ein Geburtsdatum in der Zukunft ist ebenso unsinnig wie keines. Schreib einen Test, der dafür eine IllegalArgumentException erwartet, und erweitere den Konstruktor. Wie testest Du das, ohne dass der Test vom heutigen Datum abhängt?

    Reflexionsfragen

    • Für das fehlende Geburtsdatum – den Parameter null – wirft der Konstruktor von Person eine IllegalArgumentException und keine NullPointerException. Warum?
    • Warum ist die Schleife mit Exception so viel langsamer als die mit hasNext()?
    • Warum musste book die RoomAlreadyBookedException mit throws ankündigen, der Konstruktor von Person die IllegalArgumentException aber nicht?
