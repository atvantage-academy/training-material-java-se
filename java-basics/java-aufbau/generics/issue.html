    Ein generischer Raumkatalog

    User Story

    Als Entwickler:in der Raumbuchung möchte ich einen Katalog, der Besprechungs- und Schulungsräume typsicher verwaltet, damit ich keine Casts schreibe und der Compiler Verwechslungen findet.

    Lernziele
    • Du machst eine Klasse generisch und schränkst ihren Typparameter mit extends ein.
    • Du erklärst, warum ein Array kovariant ist und eine Liste nicht.
    • Du setzt ? extends für Quellen und ? super für Ziele ein (Producer Extends, Consumer Super) – an Collections und an einem eigenen generischen Typ.
    • Du nennst Folgen der Type Erasure für Deinen Code.
    Definition of Done
    • Catalog ist generisch (Catalog<T extends Room>), und CatalogTest kommt ohne Cast aus.
    • Die Vorhersagen in PredictionsTest hast Du notiert, geprüft und die Assertions auf das tatsächliche Verhalten korrigiert.
    • In WildcardTest sind alle Kommentarzeichen und jedes @Disabled entfernt, und alle Tests sind grün.
    • In EquipmentTest ist jedes @Disabled entfernt; announce nimmt auch Räume mit Videoanlage, upgradeToVideo auch Räume mit Beamer, und alle Tests sind grün.
    • Der Maven-Build läuft ohne Fehler und ohne übersprungene Tests durch.
    • Du hast die Kontrollfragen beantwortet

    Die Raumbuchung hat einen Katalog, der Räume verwaltet – Besprechungsräume mit Videoanlage, Schulungsräume mit Rechnern. Er funktioniert, aber wer einen Besprechungsraum herausholt, muss casten. Du machst ihn generisch und lernst dabei, wo der Compiler zu streng scheint und wie Wildcards ihn überzeugen.

    Catalog.java:

    package aufbau.generics;

import java.util.ArrayList;
import java.util.Collection;
import java.util.Comparator;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;

public class Catalog {

    private final Map<String, Room> rooms = new LinkedHashMap<>();

    public void add(Room room) {
        rooms.put(room.id(), room);
    }

    public Optional<Room> find(String id) {
        return Optional.ofNullable(rooms.get(id));
    }

    public List<Room> all() {
        return List.copyOf(rooms.values());
    }

    public void addAll(Collection<Room> newRooms) {
        for (Room room : newRooms) {
            add(room);
        }
    }

    public void copyTo(Collection<Room> target) {
        target.addAll(rooms.values());
    }

    public List<Room> sorted(Comparator<Room> order) {
        List<Room> result = new ArrayList<>(rooms.values());
        result.sort(order);
        return result;
    }
}

    Lists.java:

    package aufbau.generics;

import java.util.List;

public final class Lists {

    public static <T> void copy(List<T> source, List<T> target) {
        target.addAll(source);
    }

    private Lists() {
    }
}

    CatalogTest.java:

    package aufbau.generics;

import static org.junit.jupiter.api.Assertions.assertTrue;

import org.junit.jupiter.api.Test;

class CatalogTest {

    private final MeetingRoom berlin = new MeetingRoom("R101", "Berlin", 6, true);

    @Test
    void findsMeetingRoom() {
        Catalog meetingRooms = new Catalog();
        meetingRooms.add(berlin);

    }

    Baue erneut mit Maven.

    Der Test ist grün – aber nur dank des Casts.

    Mach den Katalog generisch

    Mach aus Catalog einen Catalog<T extends Room>: Wo heute Room als Elementtyp steht, steht danach T. Pass CatalogTest an: Catalog<MeetingRoom>, kein Cast mehr.

    Probier danach im Test new Catalog<String>(). Was sagt der Compiler, und welche Zeile in Catalog sorgt dafür?

    Hinweis: Methoden, deren Parameter oder Rückgabe Room war, bekommen überall T – auch addAll, copyTo und sorted. Die passen wir gleich an.

    Vier Tests tragen @Disabled, weil der eigentliche Aufruf auskommentiert ist. Nimm sie Dir einzeln vor: @Disabled und die Kommentarzeichen entfernen, die Meldung des Compilers lesen, die Signatur in Catalog bzw. Lists so ändern, dass der Aufruf kompiliert und der Test grün wird.

    Hinweis: Frag Dich bei jedem Parameter: Liest die Methode daraus (Producer) oder gibt sie etwas hinein (Consumer)? Producer Extends, Consumer Super.

    Der Test largestMeetingRoom ist von Anfang an grün. Sieh Dir die Signatur von Collections.max in der Javadoc an: Warum darf dort ein Comparator<Room> eine Liste von Besprechungsräumen vergleichen?

    Gib Räumen eine Ausstattung

    Nicht nur der Katalog kann generisch sein, auch ein Raum: Ein EquippedRoom<E> hat eine Ausstattung vom Typ E – einen Beamer, eine Videoanlage, ein Whiteboard. Eine Videoanlage ist ein Beamer. Kopiere die folgenden Typen ins Package aufbau.generics unter src/main/java.

    Equipment.java:

    package aufbau.generics;

public interface Equipment {

    String label();
}

    Projector.java:

    package aufbau.generics;

public class Projector implements Equipment {

    @Override
    public String label() {
        return "projector";
    }
}

    VideoSystem.java:

    package aufbau.generics;

public class VideoSystem extends Projector {

    @Override
    public String label() {
        return "video system";
    }
}

    Whiteboard.java:

    package aufbau.generics;

public class Whiteboard implements Equipment {

    @Override
    public String label() {
        return "whiteboard";
    }
}

    EquippedRoom.java:

    package aufbau.generics;

public class EquippedRoom<E extends Equipment> implements Room {

    private final String id;
    private final String name;
    private final int seats;
    private E equipment;

    public EquippedRoom(String id, String name, int seats, E equipment) {
        this.id = id;
        this.name = name;
        this.seats = seats;
        this.equipment = equipment;
    }

    @Override
    public String id() {
        return id;
    }

    @Override
    public String name() {
        return name;
    }

    @Override
    public int seats() {
        return seats;
    }

    public E equipment() {
        return equipment;
    }

    public void replaceEquipment(E equipment) {
        this.equipment = equipment;
    }
}

    Presentations.java – zwei Methoden der Raumbuchung, die einen ausgestatteten Raum brauchen:

    package aufbau.generics;

public final class Presentations {

    // announces a talk in the room; the room needs a projector
    public static String announce(EquippedRoom<Projector> room) {
        return "Talk in " + room.name() + " with " + room.equipment().label();
    }

    // replaces the equipment of the room by a new video system
    public static void upgradeToVideo(EquippedRoom<VideoSystem> room) {
        room.replaceEquipment(new VideoSystem());
    }

    private Presentations() {
    }
}

    Geh vor wie beim Katalog: @Disabled und Kommentarzeichen entfernen, die Meldung des Compilers lesen, die Signatur in Presentations ändern.

    1. Ein Raum mit Videoanlage soll einen Vortrag ankündigen können. announce liest die Ausstattung aus dem Raum – welcher Wildcard passt?
    2. Ein Raum mit Beamer soll auf eine Videoanlage aufgerüstet werden können. upgradeToVideo gibt dem Raum eine Ausstattung – welcher Wildcard passt jetzt?

    Sag die Type Erasure vorher

    Nimm Dir in PredictionsTest den Test listsOfDifferentTypesHaveDifferentClasses vor, genauso wie oben: erwarten, @Disabled entfernen, starten, erklären, korrigieren.

    Schreib danach in Catalog testweise eine Methode T createRoom() { return new T(); } und lies die Meldung des Compilers. Lösch die Methode wieder.

    Für Schnelle

    • Gib Catalog eine Methode largest(Comparator<? super T> order), die ein Optional<T> liefert. Welcher Rückgabetyp entsteht für einen Catalog<TrainingRoom>?
    • Schreib eine generische Methode static <T extends Room> int totalSeats(Collection<? extends T> rooms). Braucht sie den Typparameter T überhaupt – oder reicht Collection<? extends Room>?

    Reflexionsfragen

    • Warum lässt der Compiler List<Room> rooms = meetingRooms; nicht zu, Room[] rooms = new MeetingRoom[2]; aber schon?
    • Woran erkennst Du, ob ein Parameter ? extends T oder ? super T braucht?
    • Warum kann Catalog<T> kein new T() und keinen Test instanceof List<MeetingRoom> enthalten?
    • Warum darfst Du über EquippedRoom<? extends Equipment> die Ausstattung lesen, aber keine neue einsetzen?
    • Wo in der Javadoc des JDK bist Du schon über ? super gestolpert, ohne es zu bemerken?
