    Räume als Record, Raumarten als Enum

    User Story

    Als Entwickler:in der Raumbuchung möchte ich Räume und Raumarten mit möglichst wenig Code beschreiben, damit Gleichheit, Prüfung und Fallunterscheidungen stimmen, ohne dass ich sie von Hand pflege.

    Lernziele
    • Du baust eine Klasse mit Feldern, Gettern, Settern, equals, hashCode und toString als Record um.
    • Du prüfst die Komponenten eines Records in einem kompakten Konstruktor.
    • Du ersetzt einen Setter durch eine Methode, die eine veränderte Kopie liefert.
    • Du schreibst eine Enum mit Feld, Konstruktor und Methode und wertest sie in einem switch-Ausdruck aus.
    • Du verwendest EnumMap und EnumSet.
    Definition of Done
    • Room ist ein Record; RoomTest läuft weiter – angepasst nur dort, wo ein Aufruf gebrochen ist.
    • Ein Room mit Kapazität 0 oder ohne Namen lässt sich nicht anlegen.
    • Room.withCapacity liefert einen neuen Raum, der ursprüngliche bleibt unverändert.
    • Du hast notiert, was beim Umbau weggefallen ist und welche Aufrufe gebrochen sind.
    • Die Enum RoomType und die Klasse RoomPricing existieren, und RoomTypeTest läuft grün.
    • Du hast die Kontrollfragen beantwortet

    Die Raumbuchung braucht Räume: Name, Stockwerk, Kapazität. Eine Klasse dafür ist schnell geschrieben – und dann siebzig Zeilen lang, von denen nur drei etwas über Räume sagen. Du baust sie als Record um und hältst fest, was sich ändert. Danach beschreibst Du die Raumarten als Enum.

    Arbeitsschritte

    Die Klasse und ihre Tests anlegen

    Im Ordner src/main/java und im Ordner src/test/java Deines Projekts java-aufbau lege je das Package aufbau.records an. Speichere die Klasse als Room.java im Package aufbau.records unter src/main/java:

    package aufbau.records;

import java.util.Objects;

public class Room {

    private String name;
    private int floor;
    private int capacity;

    public Room(String name, int floor, int capacity) {
        Objects.requireNonNull(name, "name must not be null");
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        this.name = name;
        this.floor = floor;
        this.capacity = capacity;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        Objects.requireNonNull(name, "name must not be null");
        this.name = name;
    }

    public int getFloor() {
        return floor;
    }

    public void setFloor(int floor) {
        this.floor = floor;
    }

    public int getCapacity() {
        return capacity;
    }

    public void setCapacity(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        this.capacity = capacity;
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) {
            return true;
        }
        if (obj == null || getClass() != obj.getClass()) {
            return false;
        }
        Room other = (Room) obj;
        return floor == other.floor
                && capacity == other.capacity
                && name.equals(other.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(name, floor, capacity);
    }

    @Override
    public String toString() {
        return "Room{name='" + name + "', floor=" + floor + ", capacity=" + capacity + "}";
    }
}

    Die Klasse als Record umbauen

    Bevor Du umbaust: Notiere, welche der fünf Tests nach dem Umbau Deiner Meinung nach noch kompilieren und grün sind.

    Ersetze die Klasse durch einen Record Room mit den Komponenten name, floor und capacity. Übernimm die Prüfungen aus dem Konstruktor in einen kompakten Konstruktor. Alles andere lässt Du weg.

    Starte die Tests in der IDE.

    Notier, was weggefallen ist und welche Aufrufe der Compiler jetzt anmahnt.

    Hinweis: Ein kompakter Konstruktor hat keine Parameterliste: public Room { … }. Die Zuweisung an die Felder ergänzt der Compiler.

    Die gebrochenen Aufrufe reparieren

    Pass RoomTest an, ohne die Absicht eines Tests zu ändern:

    • Lies den Namen und die Kapazität über die Accessoren des Records.
    • Ein Record hat keine Setter. Schreib im Record eine Methode withCapacity(int capacity), die einen neuen Room mit geänderter Kapazität zurückgibt. Prüf im Test changeCapacity die Kapazität des neuen Raums und, dass der ursprüngliche Raum unverändert ist.

    Starte die Tests in der IDE, bis alle fünf grün sind.

    Lass Dir zum Schluss einen Room ausgeben und vergleiche das Format von toString mit dem der alten Klasse.

    Lösung

    Der kompakte Konstruktor prüft nur; die Zuweisung an die Felder ergänzt der Compiler. withCapacity erzeugt einen neuen Raum, der alte bleibt, wie er ist.

    package aufbau.records;

import java.util.Objects;

public record Room(String name, int floor, int capacity) {

    public Room {
        Objects.requireNonNull(name, "name must not be null");
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
    }

    public Room withCapacity(int capacity) {
        return new Room(name, floor, capacity);
    }
}

    Im Test lesen room.name() und room.capacity() statt der Getter. changeCapacity prüft beide Räume:

    @Test
void changeCapacity() {
    Room room = new Room("Atlas", 2, 12);

    Room larger = room.withCapacity(20);

    assertEquals(20, larger.capacity());
    assertEquals(12, room.capacity());
}

    Die Ausgabe hat jetzt das Format des Records: Room[name=Atlas, floor=2, capacity=12].

    Die Raumarten als Enum beschreiben

    Leg im Package aufbau.records unter src/main/java eine Enum RoomType an. Sie kennt vier Raumarten mit ihrer höchsten Personenzahl:

    Konstante höchste Personenzahl
    PHONE_BOOTH 1
    MEETING_ROOM 12
    TRAINING_ROOM 20
    AUDITORIUM 150

    Die Personenzahl steht in einem Feld, das ein Konstruktor setzt. Dazu kommen zwei Methoden: maxCapacity() liefert sie, fits(int attendees) sagt, ob so viele Personen hineinpassen.

    Leg daneben eine Klasse RoomPricing mit einer statischen Methode hourlyRateInCents(RoomType type) an, die den Stundenpreis als switch-Ausdruck liefert: Telefonzelle 0, Besprechungsraum 2 000, Schulungsraum 5 000, Saal 20 000 Cent. Schreib dabei kein default.

    Lösung

    Jede Konstante ruft den Konstruktor der Enum mit ihrer Personenzahl auf; der Konstruktor ist automatisch private.

    package aufbau.records;

public enum RoomType {

    PHONE_BOOTH(1),
    MEETING_ROOM(12),
    TRAINING_ROOM(20),
    AUDITORIUM(150);

    private final int maxCapacity;

    RoomType(int maxCapacity) {
        this.maxCapacity = maxCapacity;
    }

    public int maxCapacity() {
        return maxCapacity;
    }

    public boolean fits(int attendees) {
        return attendees <= maxCapacity;
    }
}

    Ohne default prüft der Compiler, dass der switch-Ausdruck jede Konstante abdeckt:

    package aufbau.records;

public class RoomPricing {

    public static int hourlyRateInCents(RoomType type) {
        return switch (type) {
            case PHONE_BOOTH -> 0;
            case MEETING_ROOM -> 2_000;
            case TRAINING_ROOM -> 5_000;
            case AUDITORIUM -> 20_000;
        };
    }
}

    Die Enum testen

    Speichere den Test als RoomTypeTest.java im Package aufbau.records unter src/test/java:

    package aufbau.records;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertTrue;

import java.util.EnumMap;
import java.util.EnumSet;
import java.util.List;
import java.util.Map;

import org.junit.jupiter.api.Test;

class RoomTypeTest {

    @Test
    void thereAreFourRoomTypes() {
        assertEquals(4, RoomType.values().length);
    }

    @Test
    void meetingRoomFitsTwelvePeople() {
        assertEquals(12, RoomType.MEETING_ROOM.maxCapacity());
        assertTrue(RoomType.MEETING_ROOM.fits(12));
        assertFalse(RoomType.MEETING_ROOM.fits(13));
    }

    @Test
    void phoneBoothIsFree() {
        assertEquals(0, RoomPricing.hourlyRateInCents(RoomType.PHONE_BOOTH));
        assertEquals(5_000, RoomPricing.hourlyRateInCents(RoomType.TRAINING_ROOM));
    }

    @Test
    void enumMapKeepsDeclarationOrder() {
        Map<RoomType, Integer> roomsPerType = new EnumMap<>(RoomType.class);
        roomsPerType.put(RoomType.AUDITORIUM, 1);
        roomsPerType.put(RoomType.PHONE_BOOTH, 4);
        roomsPerType.put(RoomType.MEETING_ROOM, 6);

        List<RoomType> types = List.copyOf(roomsPerType.keySet());

        assertEquals(List.of(RoomType.PHONE_BOOTH, RoomType.MEETING_ROOM, RoomType.AUDITORIUM), types);
    }

    @Test
    void enumSetComplement() {
        EnumSet<RoomType> largeRooms = EnumSet.of(RoomType.TRAINING_ROOM, RoomType.AUDITORIUM);

        EnumSet<RoomType> smallRooms = EnumSet.complementOf(largeRooms);

        assertEquals(EnumSet.of(RoomType.PHONE_BOOTH, RoomType.MEETING_ROOM), smallRooms);
    }
}

    Bevor Du startest: In welcher Reihenfolge stehen die Schlüssel in roomsPerType.keySet()? Starte dann den Test in der IDE.
