    Die Doppelbuchung mit Concurrency Utilities

    User Story

    Als Entwickler:in der Raumbuchung möchte ich gleichzeitige Buchungen mit den Werkzeugen von java.util.concurrent absichern, damit ich nicht jede Sperre von Hand bauen muss und weiß, welches Werkzeug wann passt.

    Lernziele
    • Du übergibst Aufgaben als Callable an einen ExecutorService und wertest ihre Futures aus.
    • Du beendest einen ExecutorService sauber mit shutdown().
    • Du erklärst, warum ein anderer Executor einen Fehler in der Thread Safety nicht behebt.
    • Du schützt einen kritischen Abschnitt mit ReentrantLock.
    • Du ersetzt die Sperre durch einen AtomicInteger und vergleichst die Laufzeit.
    Definition of Done

    Last erzeugen

    • Deine Vorhersage ist notiert, bevor Du @Disabled entfernst.
    • Der Test ist ohne Schutz rot – mit festem Thread-Pool.

    Lösen

    • Room schützt Prüfen und Hochzählen mit einem ReentrantLock; der Test ist grün.
    • Eine zweite Fassung von Room kommt mit einem AtomicInteger ohne Sperre aus; der Test ist grün.
    • Die Laufzeiten beider Fassungen sind notiert.

    Optional – ab Java 21

    • Mit JDK 21 und Release 21 ist der Test ohne Schutz auch mit virtuellen Threads rot.

    Für die ganze Seite

    • Du hast die Kontrollfragen beantwortet

    Die Anmeldungen für die große Veranstaltung laufen jetzt über einen ExecutorService, und jede Aufgabe meldet, wie viele Buchungen sie bestätigt hat. Der Saal ist wieder ungeschützt.

    Arbeitsschritte

    Den Saal anlegen

    Im Ordner src/main/java des Projekts java-aufbau lege das Package aufbau.concurrency an und kopiere die Klasse Room hinein:

    package aufbau.concurrency;

public class Room {

    private final String name;
    private final int capacity;
    private int bookedSeats;

    public Room(String name, int capacity) {
        this.name = name;
        this.capacity = capacity;
    }

    public boolean bookSeat() {
        if (bookedSeats < capacity) {
            bookedSeats++;
            return true;
        }
        return false;
    }

    public int bookedSeats() {
        return bookedSeats;
    }

    public String name() {
        return name;
    }
}

    Die Last mit einem ExecutorService erzeugen

    Kopiere den Test ins Package aufbau.concurrency unter src/test/java. Jede der vier Aufgaben ist ein Callable, das seine bestätigten Buchungen zählt; der ExecutorService führt sie auf einem Pool mit vier Threads aus:

    package aufbau.concurrency;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;

import java.util.List;
import java.util.concurrent.Callable;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import org.junit.jupiter.api.Disabled;
import org.junit.jupiter.api.Test;

class RoomTest {

    @Test
    @Disabled("Predict the result first, then remove @Disabled")
    void parallelBookingsFillTheHallExactly() throws InterruptedException, ExecutionException {
        Room hall = new Room("Hall", 10_000_000);
        Callable<Integer> registrations = () -> {
            int confirmed = 0;
            for (int i = 0; i < 2_500_000; i++) {
                if (hall.bookSeat()) {
                    confirmed++;
                }
            }
            return confirmed;
        };

        int confirmed = 0;
        long start = System.nanoTime();
        ExecutorService executor = Executors.newFixedThreadPool(4);
        try {
            List<Future<Integer>> results = executor.invokeAll(
                    List.of(registrations, registrations, registrations, registrations));
            for (Future<Integer> result : results) {
                confirmed += result.get();
            }
        } finally {
            executor.shutdown();
        }
        long millis = (System.nanoTime() - start) / 1_000_000;

        System.out.println("Confirmed: " + confirmed + ", booked seats: " + hall.bookedSeats()
                + ", " + millis + " ms");
        assertEquals(confirmed, hall.bookedSeats());
        assertFalse(hall.bookSeat(), "The hall is full, no further booking allowed");
    }
}

    Notiere, bevor Du ihn startest: Behebt der ExecutorService die Doppelbuchung? Entferne dann @Disabled, starte den Test einige Male und notiere die Ausgabe.

    Hinweis: invokeAll wartet, bis alle Aufgaben fertig sind. shutdown() im finally beendet danach den Pool; ohne den Aufruf blieben seine vier Threads am Leben. Wer nach shutdown() auf noch laufende Aufgaben warten muss, ruft zusätzlich awaitTermination auf. Ab Java 19 ist ein ExecutorService AutoCloseable und lässt sich in try-with-resources verwenden.

    Optional – ab Java 21: Die Last mit virtuellen Threads erzeugen

    Diesen Schritt kannst Du überspringen. Er setzt voraus, dass Du auf Java 21 hochschaltest: Ein JDK 21 oder neuer ist installiert, und in Deiner pom.xml steht maven.compiler.release auf 21.

    Ersetze Executors.newFixedThreadPool(4) durch:

    Executors.newVirtualThreadPerTaskExecutor()

    Jede Aufgabe bekommt jetzt ihren eigenen virtuellen Thread. Notiere vorher, was Du erwartest, und starte den Test einige Male. Bleib danach bei einer der beiden Varianten. Willst Du wieder mit Java 17 bauen, stell Executor und Release zurück.

    Mit ReentrantLock lösen

    Schütz in Room die Prüfung und das Hochzählen mit einem ReentrantLock aus java.util.concurrent.locks. Leg ihn als Feld an:

    private final Lock lock = new ReentrantLock();

    Nimm die Sperre in bookSeat() und gib sie in jedem Fall wieder frei – auch beim return:

    lock.lock();
try {
    // check and count here
} finally {
    lock.unlock();
}

    Lies auch in bookedSeats() den Zähler unter der Sperre. Starte den Test mehrmals und notiere die Laufzeit.

    Mit AtomicInteger lösen

    Sag zuerst voraus: Wird eine Lösung ohne Sperre schneller oder langsamer?

    Ersetze dann in Room Sperre und int-Zähler durch einen AtomicInteger aus java.util.concurrent.atomic. Prüfen und Hochzählen müssen ein Schritt bleiben. getAndUpdate wendet eine Funktion atomar an und gibt den Wert vor der Änderung zurück:

    public boolean bookSeat() {
    int before = bookedSeats.getAndUpdate(seats -> seats < capacity ? seats + 1 : seats);
    return before < capacity;
}

    Pass bookedSeats() an, starte den Test mehrmals und vergleiche die Laufzeit mit der Lösung mit ReentrantLock.

    Für Schnelle

    • Sieh in der Javadoc des Pakets java.util.concurrent nach, wofür Semaphore und CountDownLatch da sind. Welches davon würdest Du nehmen, um höchstens 20 Anfragen gleichzeitig an ein Fremdsystem zu schicken?
    • Schreib eine Methode freeSeats(String roomName), die mit Thread.sleep(1_000) eine langsame Abfrage vortäuscht. Frag zwei Räume mit CompletableFuture.supplyAsync ab, führ die Ergebnisse mit thenCombine zusammen und miss die Dauer. Wie lange dauert es nacheinander?

    Reflexionsfragen

    • Warum behebt der feste Thread-Pool die Doppelbuchung nicht – und warum täte es ein Executor mit virtuellen Threads auch nicht?
    • Warum steht unlock() in einem finally-Block?
    • Du hast vorhergesagt, welche Lösung schneller ist. Lagst Du richtig – und warum ist es so?
