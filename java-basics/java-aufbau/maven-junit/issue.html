    Das Projekt aufbau anlegen, testen und die Abdeckung messen

    User Story

    Als Java-Entwickler:in möchte ich ein eigenes Maven-Projekt mit JUnit und einer Messung der Testabdeckung aufsetzen, damit ich meine Erwartungen an Code als Tests festhalten kann und sehe, welcher Code noch ungetestet ist.

    Lernziele
    • Du legst in Deiner IDE ein Maven-Projekt mit sinnvollen Koordinaten an und stellst es auf maven.compiler.release 17 um.
    • Du ordnest die Ausgabe von mvn verify den Phasen, Plugins und Goals des Lifecycles zu.
    • Du findest mit mvn help:effective-pom heraus, woher eine Plugin-Version kommt, und legst sie in pluginManagement fest.
    • Du bindest JUnit über die junit-bom ein und deklarierst junit-jupiter ohne Version.
    • Du schreibst Tests mit assertEquals, assertThrows, assertAll, @BeforeEach, @DisplayName und parametrisierten Tests.
    • Du misst die Testabdeckung mit JaCoCo, liest den Bericht und leitest daraus fehlende Tests ab.
    • Du lässt den Build mit jacoco:check scheitern, solange eine Klasse nicht ausreichend getestet ist, und erklärst, warum mvn test dabei grün bleibt.
    Definition of Done

    Das Projekt

    • Das Projekt aufbau hat groupId de.academy, artifactId aufbau, eine -SNAPSHOT-Version und maven.compiler.release 17 statt source/target; die Beispielklasse der IDE ist gelöscht.
    • Die Version des Surefire-Plugins steht in pluginManagement; die Version stammt von Maven Central.
    • JUnit kommt über die junit-bom ins Projekt; junit-jupiter steht ohne Version im POM, und mvn dependency:tree zeigt es.

    Der Code und die ersten Tests

    • CafeBabeTest ist erst übersprungen, dann rot und nach Deiner Korrektur des Codes grün.
    • RoomTest prüft Name und Kapazität, einen ungebuchten Raum, eine Buchung, die abgelehnte Doppelbuchung und einen ersten Fall von canHost.

    Die Testabdeckung

    • mvn test erzeugt den Bericht target/site/jacoco/index.html; Du hast darin die roten und gelben Stellen in Room gefunden.
    • jacoco:check verlangt für Room die volle Zweig- und Zeilenabdeckung; mvn verify ist damit erst gescheitert.
    • RoomTest prüft zusätzlich die abgelehnten Kapazitäten 0 und -1 und canHost an den Grenzen 0, 1, 12 und 13.
    • mvn verify endet mit BUILD SUCCESS, und der Bericht zeigt Room vollständig grün.

    Für die ganze Seite

    • Du hast die Kontrollfragen beantwortet

    Im Einstieg stand Deine Erwartung als Kommentar im Code. Jetzt legst Du das Projekt an, in dem Du für den Rest des Kurses arbeitest, und hältst Erwartungen als Tests fest. Danach misst Du, welchen Code Deine Tests tatsächlich durchlaufen, und lässt den Build scheitern, solange etwas Wichtiges ungetestet ist. Das Projekt legst Du in der IDE an; gebaut wird im Terminal mit mvn, damit sichtbar bleibt, was Maven tut.

    Arbeitsschritte

    Das Projekt in der IDE anlegen

    Leg in Deiner IDE ein neues Maven-Projekt an – ohne Archetype, mit einem JDK 17 oder neuer. Die Koordinaten des Projekts:

    Angabe Wert Bedeutung
    groupId de.academy Wer das Projekt herausgibt, meist ein umgedrehter Domainname
    artifactId aufbau Der Name des Projekts, zugleich der Name des JARs
    version 1.0-SNAPSHOT -SNAPSHOT heißt: in Arbeit, noch keine fertige Version

    In IntelliJ IDEA zum Beispiel geht das so: File → New → Project…, links Java, als Build system Maven, als Name aufbau. Die groupId und artifactId findest Du unter Advanced Settings. In anderen IDEs heißen die Schritte anders, die Angaben sind dieselben.

    Das POM auf Java 17 festlegen

    Öffne die erzeugte pom.xml und lies sie. Viele IDEs, darunter IntelliJ IDEA, tragen die Java-Version als zwei Properties ein, maven.compiler.source und maven.compiler.target. Ersetze beide durch eine Property maven.compiler.release mit dem Wert 17. Nur release prüft auch, dass Du keine API benutzt, die es in Java 17 noch nicht gibt.

    Hat Deine IDE eine Beispielklasse erzeugt (in IntelliJ IDEA Main, wenn Add sample code angehakt war), lösch sie. Dein POM sieht danach im Kern so aus:

    <?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>de.academy</groupId>
    <artifactId>aufbau</artifactId>
    <version>1.0-SNAPSHOT</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>
</project>

    Hinweis: Nach jeder Änderung am POM fragt die IDE, ob sie es neu laden soll (in IntelliJ IDEA das Maven-Symbol im Editor). Lade neu, damit die IDE denselben Stand kennt wie Maven im Terminal.

    Das Projekt im Terminal bauen

    Öffne ein Terminal im Projektordner aufbau und bau das Projekt:

    mvn verify

    Lies die Ausgabe. Jede Zeile der Form --- compiler:3.x.y:compile (default-compile) @ aufbau --- ist ein Goal eines Plugins, das an eine Phase gebunden ist. Notier, welche Plugins in welcher Reihenfolge laufen. Wo steht in Deinem POM, dass sie laufen sollen?

    Die Surefire-Version festlegen

    Lass Dir das POM so ausgeben, wie Maven es sieht, und schreib es in eine Datei:

    mvn help:effective-pom -Doutput=effective-pom.xml

    Such in effective-pom.xml nach maven-surefire-plugin. Welche Version steht dort – und woher kommt sie, wenn sie nicht in Deinem POM steht?

    Schlag auf Maven Central (https://central.sonatype.com) die neueste stabile Version von org.apache.maven.plugins:maven-surefire-plugin nach – ohne Vorabversionen wie -M1 oder -RC1, die Maven Central oft als neueste führt. Ergänze Dein POM nach </properties> um diesen Block und ersetze VERSION durch die gefundene Version:

    <build>
    <pluginManagement>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-surefire-plugin</artifactId>
                <version>VERSION</version>
            </plugin>
        </plugins>
    </pluginManagement>
</build>

    Erzeuge das effektive POM noch einmal und prüf, dass nun Deine Version gilt.

    JUnit über die BOM einbinden

    Schlag auf Maven Central die neueste stabile Version von org.junit:junit-bom nach. Ergänze Dein POM vor <build> um die BOM und die Abhängigkeit – VERSION ersetzt Du wieder durch die gefundene Version:

    <dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.junit</groupId>
            <artifactId>junit-bom</artifactId>
            <version>VERSION</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>

    Lass Dir anzeigen, welche Artefakte damit ins Projekt kommen:

    mvn dependency:tree

    Woher kennt Maven die Version von junit-jupiter, obwohl sie nicht dasteht?

    Die erste Erwartung als Test festhalten

    Leg den Ordner src/test/java/aufbau/junit an und darin CafeBabeTest.java:

    package aufbau.junit;

import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.api.Disabled;
import org.junit.jupiter.api.Test;

class CafeBabeTest {

    @Test
    @Disabled("Predict the result first, then remove @Disabled")
    void addsCafeBabeAndOneFollowedByEightZeros() {
        long l1 = 0x0_cafe_babe;
        long l2 = 0x1_0000_0000L;
        assertEquals(0x1_cafe_babeL, l1 + l2);
    }
}

    Starte die Tests:

    mvn test

    Der Build ist grün, der Test aber übersprungen (Skipped: 1). So kommen ab jetzt alle Rätsel des Kurses: Das Projekt baut immer, und Du entscheidest, wann Du ein Rätsel startest.

    Entferne nun @Disabled und starte nur diese Testklasse:

    mvn test -Dtest=CafeBabeTest

    Lies die Fehlermeldung: Was ist expected, was but was, und in welcher Zeile ist der Test gescheitert? Korrigiere dann den Code so, dass die Addition stimmt, und starte den Test noch einmal, bis er grün ist.

    Hinweis: Die Zahlen in der Meldung sind dezimal. Die Ursache kennst Du aus dem Einstieg; hier geht es darum, die Meldung lesen zu können.

    Einen Raum der Raumbuchung übernehmen

    Durch den Kurs zieht sich eine kleine Raumbuchung. Leg den Ordner src/main/java/aufbau/junit an und darin Room.java:

    package aufbau.junit;

import java.time.LocalDate;
import java.util.HashSet;
import java.util.Set;

public class Room {

    private final String name;
    private final int capacity;
    private final Set<LocalDate> bookedDays = new HashSet<>();

    public Room(String name, int capacity) {
        if (capacity < 1) {
            throw new IllegalArgumentException("capacity must be at least 1, but was " + capacity);
        }
        this.name = name;
        this.capacity = capacity;
    }

    public String getName() {
        return name;
    }

    public int getCapacity() {
        return capacity;
    }

    public boolean canHost(int persons) {
        return persons > 0 && persons <= capacity;
    }

    public void book(LocalDate day) {
        if (!bookedDays.add(day)) {
            throw new IllegalStateException(name + " is already booked on " + day);
        }
    }

    public boolean isBooked(LocalDate day) {
        return bookedDays.contains(day);
    }
}

    Den Raum testen

    Leg unter src/test/java/aufbau/junit die Datei RoomTest.java an. Sie bringt schon einen frischen Raum für jeden Test und einen ersten Test mit:

    package aufbau.junit;

import static org.junit.jupiter.api.Assertions.assertTrue;

import java.time.LocalDate;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

class RoomTest {

    private static final LocalDate MONDAY = LocalDate.of(2026, 3, 2);

    private Room room;

    @BeforeEach
    void createRoom() {
        room = new Room("Seminar 1", 12);
    }

    @Test
    void bookingMarksTheDayAsBooked() {
        room.book(MONDAY);
        assertTrue(room.isBooked(MONDAY));
    }
}

    Ergänze die Klasse um diese Tests und starte nach jedem mvn test:

    1. Ein neuer Raum behält Name und Kapazität – geprüft mit einem assertAll, das zwei assertEquals enthält. Gib dem Test mit @DisplayName einen Namen, der im Bericht lesbar ist.
    2. Ein neuer Raum ist an keinem Tag gebucht.
    3. Eine zweite Buchung desselben Tages wird abgelehnt: assertThrows mit IllegalStateException. Prüf auch die Nachricht der Ausnahme – assertThrows gibt sie Dir zurück.
    4. Der Raum für 12 Personen kann eine Gruppe von 6 Personen aufnehmen.

    Prüf zwischendurch, ob ein Test wirklich etwas prüft: Ändere eine Erwartung absichtlich, sieh ihn rot werden und nimm die Änderung zurück.

    Die Testabdeckung messen

    Fünf grüne Tests für den Raum – aber welchen Code von Room haben sie durchlaufen? Das misst JaCoCo: Das Goal prepare-agent hängt einen Agenten an die JVM der Tests, der jede ausgeführte Zeile und jeden Zweig mitzählt; das Goal report macht daraus einen Bericht.

    Schlag auf Maven Central die neueste stabile Version von org.jacoco:jacoco-maven-plugin nach. Ergänze Dein POM in <build> nach </pluginManagement> um diesen Block:

    <plugins>
    <plugin>
        <groupId>org.jacoco</groupId>
        <artifactId>jacoco-maven-plugin</artifactId>
        <version>VERSION</version>
        <executions>
            <execution>
                <id>prepare-agent</id>
                <goals>
                    <goal>prepare-agent</goal>
                </goals>
            </execution>
            <execution>
                <id>report</id>
                <phase>test</phase>
                <goals>
                    <goal>report</goal>
                </goals>
            </execution>
        </executions>
    </plugin>
</plugins>

    Der Bericht hängt an der Phase test: So entsteht er bei jedem mvn test gleich nach den Tests. JaCoCo steht unter plugins, nicht nur in pluginManagement – warum?

    Starte die Tests:

    mvn test

    Öffne target/site/jacoco/index.html im Browser und klick Dich über das Paket aufbau.junit zur Klasse Room und in ihren Quelltext. Rot markierte Zeilen hat kein Test ausgeführt; eine gelbe Raute vor einer Zeile heißt, dass nur ein Teil ihrer Zweige durchlaufen wurde. Fahr mit der Maus über die Raute: Wie viele Zweige fehlen? Notier für jede rote und gelbe Stelle, welcher Test fehlt.

    Eine Mindestabdeckung verlangen

    Messen allein ändert nichts. Lass den Build deshalb scheitern, solange Room nicht vollständig getestet ist. Ergänze die <executions> des JaCoCo-Plugins um eine dritte:

    <execution>
    <id>check</id>
    <phase>verify</phase>
    <goals>
        <goal>check</goal>
    </goals>
    <configuration>
        <rules>
            <rule>
                <element>CLASS</element>
                <includes>
                    <include>aufbau.junit.Room</include>
                </includes>
                <limits>
                    <limit>
                        <counter>BRANCH</counter>
                        <value>COVEREDRATIO</value>
                        <minimum>1.0</minimum>
                    </limit>
                    <limit>
                        <counter>LINE</counter>
                        <value>COVEREDRATIO</value>
                        <minimum>1.0</minimum>
                    </limit>
                </limits>
            </rule>
        </rules>
    </configuration>
</execution>

    Die Regel gilt nur für die Klasse Room und verlangt, dass jeder Zweig und jede Zeile durchlaufen wird. Später legst Du Code an, dessen Tests mit @Disabled auf Dich warten – eine Regel für das ganze Projekt würde den Build dann brechen, obwohl alles in Ordnung ist.

    Starte zuerst die Tests:

    mvn test

    Starte dann den ganzen Build:

    mvn verify

    mvn test ist grün, mvn verify scheitert. Lies die Meldung: Welche Regel ist verletzt, für welche Klasse, und wie hoch ist die gemessene Abdeckung? Warum hat mvn test davon nichts gemerkt?

    Die fehlenden Tests schreiben

    Schreib die Tests, die der Bericht verlangt, und starte nach jedem Test mvn verify, bis der Build grün ist:

    1. Ein Raum mit Kapazität 0 oder -1 lässt sich nicht anlegen: ein parametrisierter Test mit @ParameterizedTest und @ValueSource(ints = { 0, -1 }).
    2. canHost liefert für 1 und 12 Personen true, für 0 und 13 false: ein parametrisierter Test mit @CsvSource, je Zeile Personenzahl und Erwartung, etwa "13, false".

    Hinweis: @ParameterizedTest, @ValueSource und @CsvSource liegen in den Paketen org.junit.jupiter.params und org.junit.jupiter.params.provider. Sie sind schon im Projekt – junit-jupiter bringt sie mit; der Abhängigkeitsbaum zeigt es.

    Öffne den Bericht noch einmal: Room ist jetzt vollständig grün.

    Für Schnelle: Meldung lesbar machen und verpacken

    Mach die Fehlermeldung des CafeBabeTest lesbar: Vergleich statt der Zahlen ihre Hex-Darstellung (Long.toHexString(…)) und bau den Fehler kurz wieder ein, um die neue Meldung zu sehen.

    Verpacke das Projekt danach:

    mvn package

    Sieh in target/ nach, was entstanden ist, und vergleich die Ausgabe mit der von mvn verify: Welche Goals laufen nur bei verify?

    Reflexionsfragen

    • Was ist der Unterschied zwischen pluginManagement und build/plugins – und warum genügt für Surefire das erste, für JaCoCo aber nicht?
    • Warum steht junit-jupiter ohne Version im POM – und was passiert, wenn Du später ein weiteres JUnit-Artefakt brauchst?
    • Warum war mvn test grün, während mvn verify an der Abdeckung gescheitert ist?
    • Warum hast Du beim CafeBabeTest den Code korrigiert und nicht die Assertion?
    • Für die volle Zweigabdeckung von canHost genügen die Werte 0, 6 und 13. Warum testest Du trotzdem 1 und 12?
    • Ein Test, der canHost aufruft, aber das Ergebnis nicht prüft, bringt dieselbe Abdeckung wie Dein Test mit Assertion. Was misst die Zahl also?
    • Was ist Test-Driven Development (TDD) – und welche Vorteile und Herausforderungen siehst Du, wenn Du es mit Deinem Vorgehen in dieser Übung vergleichst?
