    Thread Safety: die Doppelbuchung

    User Story

    Als Entwickler:in der Raumbuchung möchte ich, dass gleichzeitige Buchungen nie mehr Plätze vergeben, als der Saal hat, damit niemand mit Bestätigung vor einem besetzten Platz steht.

    Lernziele
    • Du startest Threads mit einem Runnable und wartest mit join auf ihr Ende.
    • Du sagst das Ergebnis eines nebenläufigen Tests voraus und erklärst, warum es abweicht.
    • Du erklärst, warum bookedSeats++ unter mehreren Threads Buchungen verliert.
    • Du schützt Prüfen und Hochzählen gemeinsam mit einem synchronized-Block.
    Definition of Done
    • Deine Vorhersage für den Test ist notiert, bevor Du @Disabled entfernst.
    • Du hast den Test mindestens dreimal ohne Schutz gestartet und die gebuchten Plätze notiert.
    • Du kannst erklären, warum der Test mit run() statt start() grün ist.
    • Room schützt Prüfen und Hochzählen in einem synchronized-Block; der Test ist grün.
    • Du hast die Kontrollfragen beantwortet

    Für eine große Veranstaltung gehen die Anmeldungen über mehrere Threads gleichzeitig ein. Jede Anmeldung bucht einen Platz im Saal. Der Saal darf nie mehr Plätze vergeben, als er hat – und genau das passiert.

    Arbeitsschritte

    Den Saal anlegen

    Im Ordner src/main/java des Projekts java-aufbau lege das Package aufbau.threads an und kopiere die Klasse Room hinein:

    package aufbau.threads;

public class Room {

    private final String name;
    private final int capacity;
    private int bookedSeats;

    public Room(String name, int capacity) {
        this.name = name;
        this.capacity = capacity;
    }

    public boolean bookSeat() {
        if (bookedSeats < capacity) {
            bookedSeats++;
            return true;
        }
        return false;
    }

    public int bookedSeats() {
        return bookedSeats;
    }

    public String name() {
        return name;
    }
}

    Den Test anlegen und vorhersagen

    Kopiere den Test ins Package aufbau.threads unter src/test/java. Vier Threads buchen je 2,5 Millionen Plätze in einem Saal mit 10 Millionen Plätzen – die großen Zahlen machen sichtbar, was sonst nur selten auftritt:

    package aufbau.threads;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;

import org.junit.jupiter.api.Disabled;
import org.junit.jupiter.api.Test;

class RoomTest {

    @Test
    @Disabled("Predict the result first, then remove @Disabled")
    void parallelBookingsFillTheHallExactly() throws InterruptedException {
        Room hall = new Room("Hall", 10_000_000);
        Runnable registrations = () -> {
            for (int i = 0; i < 2_500_000; i++) {
                hall.bookSeat();
            }
        };

        Thread first = new Thread(registrations);
        Thread second = new Thread(registrations);
        Thread third = new Thread(registrations);
        Thread fourth = new Thread(registrations);
        first.start();
        second.start();
        third.start();
        fourth.start();
        first.join();
        second.join();
        third.join();
        fourth.join();

        System.out.println("Booked seats: " + hall.bookedSeats());
        assertEquals(10_000_000, hall.bookedSeats());
        assertFalse(hall.bookSeat(), "The hall is full, no further booking allowed");
    }
}

    Notiere, bevor Du ihn startest: Wird der Test grün? Wie viele Plätze sind am Ende gebucht?

    Starten und beobachten

    Entferne @Disabled und starte den Test mindestens dreimal. Notiere jedes Mal die Ausgabe Booked seats.

    • Stimmt das Ergebnis mit Deiner Vorhersage überein?
    • Warum ist es bei jedem Lauf anders?
    • Alle 10 Millionen Anmeldungen haben true bekommen. Was bedeutet es für die nächste Anmeldung, wenn der Zähler weniger anzeigt?

    start gegen run tauschen

    Ersetze die vier Aufrufe von start() durch run() und starte den Test erneut. Was ändert sich, und warum? Stell danach wieder auf start() zurück.

    Mit synchronized beheben

    Ein synchronized-Block lässt immer nur einen Thread zugleich hinein; die anderen warten davor:

    synchronized (this) {
    // only one thread at a time per Room object
}

    Schütz damit in bookSeat() die Prüfung und das Hochzählen gemeinsam. Lies auch in bookedSeats() den Zähler in einem solchen Block. Starte den Test mehrmals – er ist grün.

    Hinweis: Der Test schreibt die Erwartung fest, die fachlich richtig ist. Hier korrigierst Du deshalb nicht die Assertion, sondern den Code.

    Für Schnelle

    • Miss mit System.nanoTime(), wie lange der Test mit synchronized braucht, und vergleiche mit der Variante mit run(). Was sagt Dir das über Gleichzeitigkeit?
    • Mach statt des Blocks die ganze Methode synchronized. Worin unterscheiden sich die beiden Schreibweisen hier?

    Reflexionsfragen

    • Warum ist der Test mit run() statt start() grün – und was hast Du dabei verloren?
    • bookedSeats++ steht in einer Zeile. Warum ist es trotzdem kein einzelner Schritt?
    • Würde es genügen, nur bookedSeats++ in den synchronized-Block zu setzen?
    • Der Test ist jetzt grün. Buchen die vier Threads noch gleichzeitig?
