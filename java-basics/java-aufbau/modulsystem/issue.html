    Modulsystem: die Raumbuchung in Module schneiden

    User Story

    Als Entwickler:in möchte ich festlegen, welche Pakete meines Codes andere verwenden dürfen, damit interne Klassen intern bleiben und fehlende Abhängigkeiten schon beim Übersetzen auffallen.

    Lernziele
    • Du schreibst für drei Module je eine module-info.java mit requires und exports.
    • Du übersetzt die Module mit javac --module-source-path und startest sie mit java --module-path.
    • Du sagst voraus, was der Compiler bei einem nicht exportierten Paket und einem fehlenden requires transitive meldet.
    • Du erklärst, warum Reflection auf private Felder ein opens braucht.
    • Du meldest einen Service mit provides … with an und lädst ihn mit uses über den ServiceLoader.
    • Du schlägst mit --list-modules, --describe-module und jdeps nach, was ein Modul anbietet und braucht.
    Definition of Done

    Module

    • booking.api, booking.core und booking.app übersetzen mit einem einzigen javac-Aufruf nach out.
    • BookingApp läuft auf dem Modulpfad und verschickt die Buchung über EmailChannel.

    Kapselung

    • Du hast die Meldungen zum nicht exportierten Paket und zum fehlenden requires transitive gesehen und erklären können.
    • ChannelInspector läuft mit opens booking.core to booking.app und gibt die Zahl der Kanäle aus.

    Service und Nachschlagen

    • Du hast gesehen, was ohne provides und was ohne uses passiert, und beides wieder eingetragen.
    • --describe-module zeigt für booking.core alle Direktiven, jdeps die Abhängigkeiten von booking.app.

    Für die ganze Seite

    • Du hast die Kontrollfragen beantwortet

    Die Raumbuchung besteht aus drei Teilen: der API mit Room und dem Interface für Benachrichtigungskanäle, dem Kern mit dem BookingService und einem internen E-Mail-Kanal, und der Anwendung, die bucht. Du machst aus jedem Teil ein Java-Modul und übersetzt alles direkt mit javac – ohne Maven.

    Arbeitsschritte

    Die Module anlegen

    Leg neben Deinem Projekt java-aufbau einen Ordner java-aufbau-modules an. Darin entsteht diese Struktur – unter src je Modul ein Ordner mit dem Namen des Moduls, darin die module-info.java und die Paketordner:

    java-aufbau-modules/
└── src/
    ├── booking.api/
    │   ├── module-info.java
    │   └── booking/api/
    │       ├── NotificationChannel.java
    │       └── Room.java
    ├── booking.core/
    │   ├── module-info.java
    │   └── booking/core/
    │       ├── BookingService.java
    │       └── internal/
    │           └── EmailChannel.java
    └── booking.app/
        ├── module-info.java
        └── booking/app/
            ├── BookingApp.java
            └── ChannelInspector.java

    Modul booking.api – exportiert sein einziges Paket. src/booking.api/module-info.java:

    module booking.api {
    exports booking.api;
}

    src/booking.api/booking/api/Room.java:

    package booking.api;

public record Room(String id, int capacity) {
}

    src/booking.api/booking/api/NotificationChannel.java:

    package booking.api;

public interface NotificationChannel {

    String name();

    void send(String message);
}

    Modul booking.core – braucht die API, exportiert nur booking.core, lädt Kanäle und bietet selbst einen an. src/booking.core/module-info.java:

    module booking.core {
    requires transitive booking.api;
    exports booking.core;
    uses booking.api.NotificationChannel;
    provides booking.api.NotificationChannel with booking.core.internal.EmailChannel;
}

    src/booking.core/booking/core/BookingService.java:

    package booking.core;

import booking.api.NotificationChannel;
import booking.api.Room;
import java.util.ArrayList;
import java.util.List;
import java.util.ServiceLoader;

public class BookingService {

    private final List<NotificationChannel> channels = new ArrayList<>();

    public BookingService() {
        for (NotificationChannel channel : ServiceLoader.load(NotificationChannel.class)) {
            channels.add(channel);
        }
    }

    public boolean book(Room room, int attendees) {
        if (room.capacity() < attendees) {
            return false;
        }
        String message = "Room " + room.id() + " booked for " + attendees + " people";
        for (NotificationChannel channel : channels) {
            channel.send(message);
        }
        return true;
    }
}

    src/booking.core/booking/core/internal/EmailChannel.java:

    package booking.core.internal;

import booking.api.NotificationChannel;

public class EmailChannel implements NotificationChannel {

    @Override
    public String name() {
        return "email";
    }

    @Override
    public void send(String message) {
        // Imagine a real e-mail to the facility management here.
        System.out.println("[email] " + message);
    }
}

    Modul booking.app – braucht nur den Kern. src/booking.app/module-info.java:

    module booking.app {
    requires booking.core;
}

    src/booking.app/booking/app/BookingApp.java:

    package booking.app;

import booking.api.Room;
import booking.core.BookingService;

public class BookingApp {

    public static void main(String[] args) {
        BookingService service = new BookingService();
        boolean booked = service.book(new Room("R1", 4), 3);
        System.out.println("Booked: " + booked);
    }
}

    src/booking.app/booking/app/ChannelInspector.java – sie liest per Reflection ein privates Feld des Service:

    package booking.app;

import booking.core.BookingService;
import java.lang.reflect.Field;
import java.util.List;

public class ChannelInspector {

    public static void main(String[] args) throws Exception {
        BookingService service = new BookingService();

        Field field = BookingService.class.getDeclaredField("channels");
        field.setAccessible(true);
        List<?> channels = (List<?>) field.get(service);

        System.out.println("Channels inside the service: " + channels.size());
    }
}

    Übersetzen und starten

    Alle folgenden Befehle laufen im Ordner java-aufbau-modules, unter Windows genauso wie unter macOS und Linux.

    Übersetze alle drei Module in einem Aufruf nach out – --module-source-path sagt javac, wo die Modulordner liegen, --module nennt die Module:

    javac -d out --module-source-path src --module booking.api,booking.core,booking.app

    Sieh Dir den Ordner out an: Je Modul ist ein Ordner entstanden, jeder mit einer module-info.class.

    Starte BookingApp auf dem Modulpfad – -m nennt Modul und Klasse:

    java --module-path out -m booking.app/booking.app.BookingApp

    Die Buchung geht per E-Mail hinaus, und Booked: true steht darunter – obwohl booking.app den EmailChannel nirgends nennt.

    Ein internes Paket verwenden

    Leg in booking.app eine Klasse an, die den E-Mail-Kanal direkt verwendet, src/booking.app/booking/app/DirectEmail.java:

    package booking.app;

import booking.core.internal.EmailChannel;

public class DirectEmail {

    public static void main(String[] args) {
        new EmailChannel().send("Hello");
    }
}

    Vorhersage: EmailChannel ist public. Übersetzt das? Notier Deine Erwartung und übersetze wie oben. Lösche DirectEmail.java danach wieder.

    Die API weiterreichen

    Ändere in booking.core/module-info.java die Zeile requires transitive booking.api; in requires booking.api;.

    Vorhersage: booking.app nennt booking.api in seiner module-info.java gar nicht, BookingApp verwendet aber Room. Was meldet der Compiler jetzt – und an welcher Stelle? Übersetze, vergleiche und stell requires transitive wieder her.

    Reflection auf ein privates Feld

    Vorhersage: booking.core exportiert das Paket booking.core. Kann ChannelInspector das private Feld channels lesen? Notier Deine Erwartung und starte:

    java --module-path out -m booking.app/booking.app.ChannelInspector

    Erklär die Meldung. Ergänze dann in booking.core/module-info.java unter exports die Zeile:

    opens booking.core to booking.app;

    Übersetze und starte ChannelInspector erneut.

    Den Service anmelden

    Nimm in booking.core/module-info.java die Zeile mit provides heraus, übersetze und starte BookingApp. Was fehlt in der Ausgabe?

    Vorhersage: Stell provides wieder her und nimm stattdessen die Zeile mit uses heraus. Übersetzt das noch – und was passiert beim Start? Prüf Deine Erwartung und stell die Zeile danach wieder her.

    Nachschlagen

    Liste die Module Deines JDK auf:

    java --list-modules

    Lass Dir den Deskriptor von booking.core zeigen, wie die JVM ihn liest:

    java --module-path out --describe-module booking.core

    Dasselbe geht für jedes Modul des JDK. Sieh Dir java.sql an und such die Zeile mit uses:

    java --describe-module java.sql

    Lass Dir von jdeps zusammenfassen, welche Module booking.app braucht:

    jdeps --module-path out -s --module booking.app

    Für Schnelle

    • Ein Kanal als eigenes Modul: Leg ein Modul booking.chat an, das booking.api liest und mit provides … with eine Klasse booking.chat.ChatChannel anbietet. Übersetze mit --module booking.api,booking.core,booking.app,booking.chat und starte BookingApp – ohne eine Zeile in booking.core oder booking.app zu ändern.
    • Opens von außen: Nimm opens wieder heraus und starte ChannelInspector mit der Option --add-opens booking.core/booking.core=booking.app vor -m. Genau so öffnen Start-Skripte Pakete des JDK für Frameworks.
    • Zurück auf den Klassenpfad: Starte BookingApp und ChannelInspector mit -cp out/booking.api:out/booking.core:out/booking.app statt Modulpfad (unter Windows mit ; getrennt und in Anführungszeichen) und mit dem Klassennamen statt -m. Was bleibt von den module-info.class-Dateien übrig?

    Reflexionsfragen

    • EmailChannel ist public. Warum kann booking.app die Klasse trotzdem nicht verwenden?
    • Warum braucht booking.app kein requires booking.api, obwohl BookingApp die Klasse Room verwendet?
    • Warum genügt exports booking.core nicht, damit ChannelInspector das private Feld lesen kann?
    • Was ändert sich, wenn ein Modul ohne provides gestartet wird, und was, wenn uses fehlt?
