    Maven-Plugins festlegen, binden und die Abdeckung verlangen

    User Story

    Als Java-Entwickler:in möchte ich verstehen, welche Plugins mein Build ausführt, und die Testabdeckung im Build verlangen, damit wichtiger Code nicht ungetestet ausgeliefert wird.

    Lernziele
    • Du ordnest die Ausgabe von mvn verify den Phasen, Plugins und Goals des Lifecycles zu.
    • Du findest mit mvn help:effective-pom heraus, woher eine Plugin-Version kommt.
    • Du trennst die Festlegung eines Plugins (Version und Konfiguration in pluginManagement) von seiner Bindung an den Lifecycle (Executions in plugins).
    • Du misst die Testabdeckung mit JaCoCo, liest den Bericht und leitest daraus fehlende Tests ab.
    • Du lässt den Build mit jacoco:check scheitern, solange eine Klasse nicht ausreichend getestet ist, und erklärst, warum mvn test dabei grün bleibt.
    • Du schreibst einen Test vor dem Code (Red – Green – Refactor).
    Definition of Done

    Plugins festlegen und binden

    • Unter pluginManagement stehen Surefire und JaCoCo mit Version, JaCoCo zusätzlich mit seiner Regel; die Versionen stammen von Maven Central und stehen als Properties.
    • Unter plugins steht JaCoCo ohne Version und ohne Konfiguration, nur mit den Executions prepare-agent, report (Phase test) und check (Phase verify).

    Die Testabdeckung

    • mvn test erzeugt den Bericht target/site/jacoco/index.html; Du hast darin die roten und gelben Stellen in Room gefunden.
    • mvn verify ist an der Regel für Room erst gescheitert.
    • RoomTest prüft zusätzlich die abgelehnte Kapazität 0 und canHost an den Grenzen 0, 1, 12 und 13.
    • mvn verify endet mit BUILD SUCCESS, und der Bericht zeigt Room vollständig grün.
    • Room kann eine Buchung mit cancel stornieren; den Test cancellingABookingFreesTheDay hast Du vor dem Code geschrieben.

    Für die ganze Seite

    • Du hast die Kontrollfragen beantwortet

    Deine Tests für den Raum sind grün. Jetzt siehst Du nach, was Maven beim Bauen eigentlich tut, legst die Plugins fest, mit denen es das tut – und lässt den Build scheitern, solange Room nicht ausreichend getestet ist.

    Dabei gilt eine Trennung, an die Du Dich im ganzen POM hältst:

    Abschnitt Was dort steht Wirkung
    build/pluginManagement/plugins Version und Konfiguration eines Plugins legt fest, führt nichts aus
    build/plugins das Plugin mit seinen Executions: welches Goal in welcher Phase bindet an den Lifecycle

    Arbeitsschritte

    Den Lifecycle in der Ausgabe lesen

    Bau das Projekt im Terminal:

    mvn verify

    Lies die Ausgabe. Jede Zeile der Form --- compiler:3.x.y:compile (default-compile) @ java-aufbau --- ist ein Goal eines Plugins, das an eine Phase gebunden ist. Notier, welche Plugins in welcher Reihenfolge laufen. Wo steht in Deinem POM, dass sie laufen sollen? Welche Phasen und Goals ein Befehl durchläuft, kannst Du in der Visualisierung Maven nachklicken.

    Die Surefire-Version festlegen

    Lass Dir das POM so ausgeben, wie Maven es sieht, und schreib es in eine Datei:

    mvn help:effective-pom -Doutput=effective-pom.xml

    Such in effective-pom.xml nach maven-surefire-plugin. Welche Version steht dort – und woher kommt sie, wenn sie nicht in Deinem POM steht?

    Schlag auf Maven Central (https://central.sonatype.com) die neueste stabile Version von org.apache.maven.plugins:maven-surefire-plugin nach – ohne Vorabversionen wie -M1 oder -RC1. Leg die Version wie bei JUnit als Property an – in <properties>, VERSION ersetzt durch die gefundene Version:

    <maven-surefire-plugin.version>VERSION</maven-surefire-plugin.version>

    Ergänze Dein POM dann am Ende, vor </project>, um diesen Block:

    <build>
    <pluginManagement>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-surefire-plugin</artifactId>
                <version>${maven-surefire-plugin.version}</version>
            </plugin>
        </plugins>
    </pluginManagement>
</build>

    Erzeuge das effektive POM noch einmal und prüf, dass nun Deine Version gilt. Surefire musst Du nicht unter plugins eintragen – warum nicht?

    JaCoCo festlegen und binden

    Drei grüne Tests für den Raum – aber welchen Code von Room haben sie durchlaufen? Das misst JaCoCo: Das Goal prepare-agent hängt einen Agenten an die JVM der Tests, der jede ausgeführte Zeile und jeden Zweig mitzählt; das Goal report macht daraus einen Bericht.

    Schlag auf Maven Central die neueste stabile Version von org.jacoco:jacoco-maven-plugin nach und leg sie als Property jacoco-maven-plugin.version an. Leg das Plugin fest: Ergänze in pluginManagement nach dem Surefire-Plugin:

    <plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>${jacoco-maven-plugin.version}</version>
</plugin>

    Binde es an den Lifecycle: Ergänze in <build> nach </pluginManagement> diesen Block – ohne Version, die kommt aus pluginManagement:

    <plugins>
    <plugin>
        <groupId>org.jacoco</groupId>
        <artifactId>jacoco-maven-plugin</artifactId>
        <executions>
            <execution>
                <id>prepare-agent</id>
                <goals>
                    <goal>prepare-agent</goal>
                </goals>
            </execution>
            <execution>
                <id>report</id>
                <phase>test</phase>
                <goals>
                    <goal>report</goal>
                </goals>
            </execution>
        </executions>
    </plugin>
</plugins>

    prepare-agent bringt seine Phase selbst mit (initialize); den Bericht hängst Du an die Phase test, so entsteht er bei jedem mvn test gleich nach den Tests.

    Die Testabdeckung messen

    Starte die Tests:

    mvn test

    Öffne target/site/jacoco/index.html im Browser und klick Dich über das Paket aufbau.junit zur Klasse Room und in ihren Quelltext. Rot markierte Zeilen hat kein Test ausgeführt; eine gelbe Raute vor einer Zeile heißt, dass nur ein Teil ihrer Zweige durchlaufen wurde. Fahr mit der Maus über die Raute: Wie viele Zweige fehlen? Notier für jede rote und gelbe Stelle, welcher Test fehlt.

    Eine Mindestabdeckung verlangen

    Messen allein ändert nichts. Lass den Build deshalb scheitern, solange Room nicht ausreichend getestet ist. Dafür brauchst Du wieder beide Abschnitte.

    Die Regel ist Konfiguration: Ergänze das JaCoCo-Plugin in pluginManagement nach <version> um:

    <configuration>
    <rules>
        <rule>
            <element>CLASS</element>
            <includes>
                <include>aufbau.junit.Room</include>
            </includes>
            <limits>
                <limit>
                    <counter>BRANCH</counter>
                    <value>COVEREDRATIO</value>
                    <minimum>0.8</minimum>
                </limit>
                <limit>
                    <counter>LINE</counter>
                    <value>COVEREDRATIO</value>
                    <minimum>0.8</minimum>
                </limit>
            </limits>
        </rule>
    </rules>
</configuration>

    Die Prüfung ist eine Bindung: Ergänze die <executions> des JaCoCo-Plugins unter plugins um eine dritte:

    <execution>
    <id>check</id>
    <phase>verify</phase>
    <goals>
        <goal>check</goal>
    </goals>
</execution>

    Die Regel gilt nur für die Klasse Room und verlangt, dass mindestens 80 % der Zweige und der Zeilen durchlaufen werden – eine Schwelle, wie Projekte sie in der Praxis ansetzen. Später legst Du Code an, dessen Tests mit @Disabled auf Dich warten – eine Regel für das ganze Projekt würde den Build dann brechen, obwohl alles in Ordnung ist.

    Starte zuerst die Tests:

    mvn test

    Starte dann den ganzen Build:

    mvn verify

    mvn test ist grün, mvn verify scheitert. Lies die Meldung: Welche Regel ist verletzt, für welche Klasse, und wie hoch ist die gemessene Abdeckung? Warum hat mvn test davon nichts gemerkt?

    Die fehlenden Tests schreiben

    Schreib in RoomTest die Tests, die der Bericht verlangt, und starte nach jedem Test mvn verify, bis der Build grün ist:

    1. Keine leeren Räume. Ein Raum mit Kapazität 0 lässt sich nicht anlegen.

    Hinweis: Dass ein Aufruf eine Exception wirft, prüfst Du mit try-catch: Ruf ihn im try-Block auf. Kommt der Test hinter den Aufruf, ist keine Exception geflogen – dann lässt fail(…) ihn scheitern.

    Lösung

    Dazu der statische Import Assertions.fail. Der catch-Block bleibt leer: Die Exception ist das erwartete Ergebnis.

    @Test
void roomWithoutCapacityIsRejected() {
    try {
        new Room("R101", "Seminar 1", 0);
        fail("IllegalArgumentException expected");
    } catch (IllegalArgumentException expected) {
        // the room was rejected – that is what we want
    }
}

    2. canHost an den Grenzen. Für 1 und 12 Personen liefert canHost true, für 0 und 13 false.

    Lösung 
    @Test
void canHostChecksTheLimits() {
    assertFalse(room.canHost(0));
    assertTrue(room.canHost(1));
    assertTrue(room.canHost(12));
    assertFalse(room.canHost(13));
}

    Öffne den Bericht noch einmal: Room ist jetzt vollständig grün.

    Erst der Test, dann der Code

    Ein Raum soll eine Buchung auch wieder stornieren können. Diesmal schreibst Du zuerst den Test – so, wie es Test-Driven Development vorsieht:

    1. Red: Schreib in RoomTest einen Test cancellingABookingFreesTheDay: Den Montag buchen, mit room.cancel(MONDAY) stornieren, dann ist er wieder frei. Die Methode cancel gibt es noch nicht – der Test übersetzt nicht. Auch das ist „rot“.
    2. Green: Ergänze in Room gerade so viel Code, dass der Test grün wird.
    3. Refactor: Sieh Dir Test und Code noch einmal an – gibt es etwas aufzuräumen? Baue danach erneut mit Maven: Die Abdeckungsregel hält, denn der neue Code ist von Anfang an getestet.
    Lösung 
    // RoomTest
@Test
void cancellingABookingFreesTheDay() {
    room.book(MONDAY);
    room.cancel(MONDAY);
    assertFalse(room.isBooked(MONDAY));
}

// Room
public void cancel(LocalDate day) {
    bookedDays.remove(day);
}

    • Was ist der Unterschied zwischen pluginManagement und plugins – und warum genügt für Surefire das erste, für JaCoCo aber nicht?
    • Was kann mit dem Maß der Testabdeckung ausgesagt werden, und was nicht? Wie hoch der Anteil an getestetem Code ist – ob die Tests korrekt und sinnvoll sind – ob und wie viel toten Code es gibt?
