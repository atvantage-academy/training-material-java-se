    Den Buchungsservice mit Dependency Injection und Mockito testen

    User Story

    Als Entwickler:in möchte ich den Buchungsservice ohne Raumdatenbank und ohne echte E-Mails testen, damit meine Tests schnell, wiederholbar und unabhängig von der Umgebung sind.

    Lernziele
    • Du baust eine Klasse, die ihre Abhängigkeiten selbst erzeugt, auf Konstruktor-Injektion um.
    • Du verdrahtest die Objekte in main von Hand.
    • Du schreibst Stellvertreter für Interfaces selbst und testest damit.
    • Du ersetzt die Stellvertreter durch Mocks von Mockito und prüfst Aufrufe mit verify.
    • Du bindest Mockito über eine zweite BOM ein und deklarierst mockito-junit-jupiter ohne Version.
    • Du trägst den Agenten von Mockito so in Surefire ein, dass der Agent von JaCoCo erhalten bleibt und der Testlauf ohne Warnungen zum Agenten auskommt.
    Definition of Done

    Konstruktor-Injektion

    • BookingService bekommt RoomCatalog und Notification über den Konstruktor; im Service steht kein new mehr.
    • BookingApp.main erzeugt Katalog, Benachrichtigung und Service und bucht einen Raum.

    Stellvertreter von Hand

    • BookingServiceTest prüft mit FakeRoomCatalog und RecordingNotification, dass eine Buchung benachrichtigt und ein zu kleiner Raum ohne Benachrichtigung abgelehnt wird.

    Mockito

    • BookingServiceMockitoTest prüft dieselben Fälle und einen unbekannten Raum mit mock, when und verify.
    • Eine Testklasse nutzt @ExtendWith(MockitoExtension.class), @Mock und @InjectMocks.

    Build

    • Die mockito-bom steht neben der junit-bom im selben dependencyManagement; mockito-junit-jupiter steht ohne Version im POM.
    • Die argLine von Surefire beginnt mit @{argLine} und trägt danach den Agenten von Mockito.
    • Der Maven-Build ist grün, gibt keine Warnung von Mockito oder der JVM zum Agenten aus und schreibt den JaCoCo-Bericht weiter.

    Für die ganze Seite

    • Du hast die Kontrollfragen beantwortet

    Der BookingService der Raumbuchung prüft, ob ein Raum existiert und groß genug ist, und benachrichtigt danach die Haustechnik per E-Mail. Seinen Raumkatalog und seine Benachrichtigung erzeugt er selbst. Du machst ihn testbar. Wer erzeugt wen, und was ein Mock eigentlich ist, zeigt die Visualisierung Dependency Injection und Mocks.

    Arbeitsschritte

    Den Ausgangsstand anlegen

    Im Ordner src/main/java des Projekts java-aufbau lege das Package aufbau.testing an und kopiere die folgenden Klassen hinein, jede in ihre eigene Datei.

    Ein Raum mit Kennung und Zahl der Plätze:

    package aufbau.testing;

public record Room(String id, int capacity) {
}

    Der Katalog, in dem der Service Räume nachschlägt:

    package aufbau.testing;

import java.util.Optional;

public interface RoomCatalog {

    Optional<Room> findById(String roomId);
}

    Die Benachrichtigung nach einer Buchung:

    package aufbau.testing;

public interface Notification {

    void send(String message);
}

    Ein Katalog mit zwei fest eingetragenen Räumen:

    package aufbau.testing;

import java.util.Map;
import java.util.Optional;

public class InMemoryRoomCatalog implements RoomCatalog {

    private final Map<String, Room> rooms = Map.of(
            "R1", new Room("R1", 4),
            "R2", new Room("R2", 12));

    @Override
    public Optional<Room> findById(String roomId) {
        return Optional.ofNullable(rooms.get(roomId));
    }
}

    Eine Benachrichtigung, die eine E-Mail an die Haustechnik vortäuscht:

    package aufbau.testing;

public class EmailNotification implements Notification {

    @Override
    public void send(String message) {
        // Imagine a real e-mail to the facility management here.
        System.out.println("E-mail sent: " + message);
    }
}

    Und der Service, um den es geht:

    package aufbau.testing;

import java.util.Optional;

public class BookingService {

    private final RoomCatalog catalog = new InMemoryRoomCatalog();
    private final Notification notification = new EmailNotification();

    public boolean book(String roomId, int attendees) {
        Optional<Room> room = catalog.findById(roomId);
        if (room.isEmpty() || room.get().capacity() < attendees) {
            return false;
        }
        notification.send("Room " + roomId + " booked for " + attendees + " people");
        return true;
    }
}

    Überleg Dir einen Test für den Fall „Ein zu kleiner Raum wird abgelehnt, und es geht keine E-Mail hinaus“. Was davon kannst Du mit diesem BookingService prüfen – und was nicht?

    Die Abhängigkeiten von außen geben

    Bau BookingService so um, dass er RoomCatalog und Notification über seinen Konstruktor bekommt. Die Felder bleiben final; im Service steht kein new mehr.

    Schreib dann eine Klasse BookingApp mit einer main-Methode, die einen InMemoryRoomCatalog, eine EmailNotification und daraus den BookingService erzeugt und zwei Buchungen versucht: Raum R1 für 3 und für 8 Personen. Starte sie.

    Hinweis: Genau diese Arbeit – Objekte erzeugen und zusammenstecken – übernehmen in größeren Anwendungen Frameworks wie CDI oder Spring.

    Mit eigenen Stellvertretern testen

    Im Ordner src/test/java lege ebenfalls das Package aufbau.testing an und darin zwei Stellvertreter. Der erste ist ein Katalog, dem der Test seine Räume selbst gibt:

    package aufbau.testing;

import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

class FakeRoomCatalog implements RoomCatalog {

    private final Map<String, Room> rooms = new HashMap<>();

    void add(Room room) {
        rooms.put(room.id(), room);
    }

    @Override
    public Optional<Room> findById(String roomId) {
        return Optional.ofNullable(rooms.get(roomId));
    }
}

    Der zweite schreibt mit, was gesendet wurde, statt eine E-Mail zu schicken:

    package aufbau.testing;

import java.util.ArrayList;
import java.util.List;

class RecordingNotification implements Notification {

    final List<String> messages = new ArrayList<>();

    @Override
    public void send(String message) {
        messages.add(message);
    }
}

    Der erste Test steht schon; leg ihn als BookingServiceTest an:

    package aufbau.testing;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import org.junit.jupiter.api.Test;

class BookingServiceTest {

    private final FakeRoomCatalog catalog = new FakeRoomCatalog();
    private final RecordingNotification notification = new RecordingNotification();
    private final BookingService service = new BookingService(catalog, notification);

    @Test
    void bookingASuitableRoomSendsANotification() {
        catalog.add(new Room("R1", 4));

        boolean booked = service.book("R1", 3);

        assertTrue(booked);
        assertEquals(1, notification.messages.size());
    }
}

    Ergänze den Test tooSmallRoomIsRejectedWithoutNotification: Ein Raum mit 4 Plätzen, eine Buchung für 8 Personen – abgelehnt, und die Liste der Nachrichten bleibt leer.

    Mockito über die BOM einbinden

    Mockito bringt wie JUnit eine BOM mit, die die Versionen aller Mockito-Artefakte festlegt. Schlag auf Maven Central die aktuelle Version von org.mockito:mockito-bom nach. Leg die Version wie bei JUnit als Property mockito.version in <properties> an. Ergänze dann in Deiner pom.xml das vorhandene dependencyManagement nach der junit-bom um diesen Eintrag:

    <dependency>
    <groupId>org.mockito</groupId>
    <artifactId>mockito-bom</artifactId>
    <version>${mockito.version}</version>
    <type>pom</type>
    <scope>import</scope>
</dependency>

    Ergänze dann in den dependencies neben junit-jupiter die Abhängigkeit – ohne Version, die kommt aus der BOM:

    <dependency>

    <scope>test</scope>
</dependency>

    Mit Mockito testen

    Leg die Testklasse BookingServiceMockitoTest an. Statt der Fake-Klassen erzeugt Mockito die Stellvertreter:

    package aufbau.testing;

import static org.junit.jupiter.api.Assertions.assertTrue;
import static org.mockito.Mockito.mock;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

import java.util.Optional;
import org.junit.jupiter.api.Test;

class BookingServiceMockitoTest {

    private final RoomCatalog catalog = mock(RoomCatalog.class);
    private final Notification notification = mock(Notification.class);
    private final BookingService service = new BookingService(catalog, notification);

    @Test
    void bookingASuitableRoomSendsANotification() {
        when(catalog.findById("R1")).thenReturn(Optional.of(new Room("R1", 4)));

        boolean booked = service.book("R1", 3);

        assertTrue(booked);
        verify(notification).send("Room R1 booked for 3 people");
    }
}

    Ergänze zwei Tests: einen zu kleinen Raum und einen unbekannten Raum (findById liefert Optional.empty()). Beide werden abgelehnt, und send wird nie aufgerufen.

    Hinweis: verify nimmt als zweites Argument, wie oft ein Aufruf erwartet wird – never() heißt keinmal. Damit jeder Text passt, gibt es anyString() aus org.mockito.ArgumentMatchers.

    Die Kurzform mit der Extension

    Schreib einen der Tests in einer neuen Testklasse noch einmal – diesmal mit @ExtendWith(MockitoExtension.class) an der Klasse, @Mock an den Feldern catalog und notification und @InjectMocks am Feld service. Den Konstruktor ruft dann Mockito auf.

    Den Agenten im Build eintragen

    Mockito lädt seinen Agenten zur Laufzeit nach. Ab JDK 21 warnen Mockito und die JVM davor, künftige JDKs verbieten es; unter JDK 17 meldet die JVM nur „Sharing is only supported for boot loader classes …“. Die Mockito-Doku empfiehlt, den Agenten beim Start der Tests anzugeben – das gilt für JDK 17 wie für jedes neuere.

    Dafür brauchst Du das maven-dependency-plugin; sein Ziel properties legt für jede Abhängigkeit eine Property mit dem Pfad zu ihrer JAR an. Schlag die Version wieder auf Maven Central nach, leg sie als Property maven-dependency-plugin.version an und leg das Plugin in pluginManagement fest:

    <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-dependency-plugin</artifactId>
    <version>${maven-dependency-plugin.version}</version>
</plugin>

    Binde es dann in build/plugins, neben dem jacoco-maven-plugin, an den Lifecycle – ohne Version:

    <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-dependency-plugin</artifactId>
    <executions>
        <execution>
            <goals>
                <goal>properties</goal>
            </goals>
        </execution>
    </executions>
</plugin>

    Gib Surefire die Property als Agenten mit. Ergänze dazu im vorhandenen maven-surefire-plugin in pluginManagement die configuration (die Version bleibt, wie sie ist):

    <configuration>
    <argLine>@{argLine} -javaagent:${org.mockito:mockito-core:jar} -Xshare:off</argLine>
</configuration>

    Hinweis: @{argLine} am Anfang ist kein Tippfehler. Das Goal prepare-agent von JaCoCo legt seinen eigenen Agenten in der Property argLine ab – und eine argLine in der Surefire-Konfiguration ersetzt sie. Mit @{argLine} nimmt Surefire den Agenten von JaCoCo mit. Die Schreibweise mit @ löst Surefire erst beim Start der Tests auf, nachdem JaCoCo die Property gesetzt hat; ${argLine} ersetzte Maven schon beim Einlesen des POM.

    Baue erneut mit Maven.

    Die Tests sind grün, die Warnungen sind weg, und target/site/jacoco/index.html zeigt weiterhin die Abdeckung – jetzt auch für das Package aufbau.testing.

    Hinweis: -Xshare:off schaltet das Class Data Sharing der JVM für den Testlauf ab. Ohne die Option meldet die JVM, sobald ein Agent den Klassenpfad erweitert, „Sharing is only supported for boot loader classes …“.

    Für Schnelle

    • Was liefert ein Mock, dessen Methode Du nicht mit when vorbereitet hast – für Optional, für int, für String? Probier es aus.
    • Prüf mit verify(…).send(contains("R1")), dass die Nachricht den Raum nennt, ohne den ganzen Text festzuschreiben.
    • Nimm @{argLine} probehalber aus der argLine, lösch den Ordner target und baue erneut mit Maven. Was meldet JaCoCo – und warum ist der Bau trotzdem grün? Stell die Zeile danach wieder her.
