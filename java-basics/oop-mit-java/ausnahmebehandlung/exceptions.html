Exceptions in Java

Wenn etwas schiefgeht, hat eine Methode in Java einen zweiten Ausgang: Sie wirft ein Exception-Objekt, und das fliegt den Aufrufstapel zurück, bis es jemand fängt. Diese Seite zeigt, welche Arten es gibt, wie das Werfen und Fangen abläuft, was der Compiler dabei prüft – und wie man es im Code schreibt. Alle Ausgaben stammen aus echten Läufen mit Java 25.

1Die Familie der Ausnahmen

Jede Ausnahme ist ein Objekt einer Klasse, die von Throwable erbt. Nur solche Objekte lassen sich mit throw werfen und mit catch fangen. Darunter teilt sich die Familie in drei Zweige – und an der Stelle im Baum entscheidet sich, ob der Compiler auf die Ausnahme achtet.

  • Error – Probleme der JVM selbst. Nicht fangen: Das Programm kann sie nicht sinnvoll beheben.
  • Exception – erwartbare Fehlerfälle. Checked: Der Compiler verlangt, dass jemand sich kümmert.
  • RuntimeException – meist Programmierfehler. Unchecked: Der Compiler prüft nichts.

Ob eine Ausnahme checked ist, hängt allein an der Oberklasse: Erbt sie von Exception, aber nicht von RuntimeException, ist sie checked. Alles unter RuntimeException und unter Error ist unchecked.

2Ein Objekt – mit eigenem Ausgang

Eine Exception ist zunächst ein ganz gewöhnliches Objekt: mit new erzeugt, mit Feldern und Methoden. Besonders wird sie erst durch throw. Dann verlässt die Methode nicht über return, sondern über einen zweiten Ausgang – und der Aufrufer landet nicht in der nächsten Zeile, sondern im passenden catch.

Nur ein Objekt 
KeineDeckungException e = new KeineDeckungException("DE01", 50_00);
System.out.println(e.getMessage());
System.out.println(e.getFehlbetrag());
System.out.println(e instanceof Exception);

Ohne throw passiert nichts Besonderes – das Objekt wird erzeugt und benutzt wie jedes andere.

Statt Fehlercode 
// Fehlercode als Rückgabewert:
boolean ok = konto.abheben(150_00);
// … und wenn niemand ok prüft?
nach.einzahlen(150_00);   // Geld aus dem Nichts

Einen Rückgabewert kann man übersehen. Eine geworfene Ausnahme nicht: Der normale Ablauf bricht ab, bis jemand sie fängt. Und der Rückgabewert bleibt frei für das, was die Methode eigentlich liefert.

3Werfen, ducken, fangen

Methoden rufen einander auf: main ruft überweisen, überweisen ruft abheben. Wirft abheben, fliegt die Ausnahme diesen Weg zurück. Wer kein passendes catch hat, duckt sich – seine Methode endet sofort, und die Ausnahme fliegt weiter. Der Erste mit passendem catch fängt sie.

Jemand fängt
Konto.java – wirft 
public void abheben(long betrag) throws KeineDeckungException {
    if (betrag <= 0) {
        throw new IllegalArgumentException("Betrag muss positiv sein: " + betrag);
    }
    if (betrag > kontostand) {
        throw new KeineDeckungException(iban, betrag - kontostand);
    }
    kontostand -= betrag;
}
Bank.java – duckt sich 
public class Bank {

    public static void überweisen(Konto von, Konto nach, long betrag)
            throws KeineDeckungException {
        von.abheben(betrag);
        nach.einzahlen(betrag);
    }
}
Main.java – fängt 
public static void main(String[] args) {
    Konto giro = new Konto("DE01", 100_00);
    Konto spar = new Konto("DE02", 0);
    try {
        Bank.überweisen(giro, spar, 150_00);
        System.out.println("Überwiesen.");
    } catch (KeineDeckungException e) {
        System.out.println("Überweisung abgelehnt – " + e.getMessage());
    }
    System.out.println("Weiter geht's.");
}

Weiter geht's.

Nach dem catch läuft das Programm normal weiter. einzahlen wurde nie aufgerufen – kein Geld aus dem Nichts.

Niemand fängt – die JVM

Die JVM fängt, was niemand sonst fängt: Sie gibt den Stacktrace aus und beendet das Programm. „Weiter geht's.“ erscheint nie.

Der Stacktrace ist die Flugbahn, von oben nach unten gelesen: oben die Stelle, an der geworfen wurde (Konto.java:16), darunter jede Methode, die sich geduckt hat – bis main.

Die oberste Zeile nennt Klasse und Nachricht der Ausnahme – genau das, was getMessage() liefert.

4Checked: Der Compiler passt auf

Bei einer checked Exception prüft der Compiler jeden Aufruf: Steht in der Signatur throws KeineDeckungException, muss der Aufrufer sie fangen oder selbst weitergeben. Wer das vergisst, bekommt kein Programm.

    public static void main(String[] args) {

5Die Formen von try

try-catch

Was schiefgehen kann, steht im try-Block. Fliegt dort eine Ausnahme, wird der Rest des Blocks übersprungen und der catch-Block ausgeführt, dessen Typ passt – auch für Unterklassen dieses Typs.

String eingabe = "12a";
try {
    int betrag = Integer.parseInt(eingabe);
    System.out.println("Betrag: " + betrag);
} catch (NumberFormatException e) {
    System.out.println("Keine Zahl: " + e.getMessage());
}
Keine Zahl: For input string: "12a"
Multi-Catch

Sollen mehrere Ausnahmen gleich behandelt werden, stehen sie mit | in einem einzigen catch. Das spart doppelten Code. Die Typen dürfen nicht voneinander erben – sonst wäre einer überflüssig, und der Compiler lehnt ab.

public class MultiCatch {

    static int anteil(String gesamt, String personen) {
        try {
            return Integer.parseInt(gesamt) / Integer.parseInt(personen);
        } catch (NumberFormatException | ArithmeticException e) {
            System.out.println("Ungültige Eingabe: " + e.getMessage());
            return 0;
        }
    }

    public static void main(String[] args) {
        System.out.println(anteil("90", "3"));
        System.out.println(anteil("90", "0"));
        System.out.println(anteil("90", "drei"));
    }
}

Reihenfolge

Die catch-Blöcke werden von oben nach unten geprüft; der erste passende gewinnt. Deshalb gilt: speziell vor allgemein. FileNotFoundException ist eine Unterklasse von IOException – steht IOException oben, käme der zweite Block nie zum Zug. Der Compiler erkennt das.

finally

Der finally-Block läuft immer: nach normalem Ende, nach return und auch, wenn eine Ausnahme hinausfliegt. Dort gehört hin, was in jedem Fall passieren muss – typischerweise Aufräumen. Ein catch braucht es dafür nicht.

public class TryFinally {

    static String abfragen(boolean gestört) {
        System.out.println("Verbindung öffnen");
        try {
            System.out.println("Kontostand lesen");
            if (gestört) {
                throw new IllegalStateException("Leitung gestört");
            }
            return "100,00 €";
        } finally {
            System.out.println("Verbindung schließen");
        }
    }

    public static void main(String[] args) {
        System.out.println("Ergebnis: " + abfragen(false));
        try {
            System.out.println("Ergebnis: " + abfragen(true));
        } catch (IllegalStateException e) {
            System.out.println("Fehler: " + e.getMessage());
        }
    }
}

try-with-resources

Für das häufigste finally – eine Ressource schließen – gibt es eine Kurzform. Was in den runden Klammern nach try geöffnet wird, schließt Java selbst: am Ende des Blocks, auch bei einer Ausnahme, und zwar in umgekehrter Reihenfolge und vor dem catch.

Voraussetzung: Die Klasse implementiert das Interface java.lang.AutoCloseable mit seiner einzigen Methode close(). Dateien, Datenbankverbindungen und Streams tun das bereits.

Verbindung.java 
public class Verbindung implements AutoCloseable {

    private final String name;

    public Verbindung(String name) {
        this.name = name;
        System.out.println(name + " geöffnet");
    }

    public void senden(String text) {
        if (text.isEmpty()) {
            throw new IllegalArgumentException("Leere Nachricht an " + name);
        }
        System.out.println(name + " sendet: " + text);
    }

    @Override
    public void close() {
        System.out.println(name + " geschlossen");
    }
}
Benutzen 
try (Verbindung bank = new Verbindung("Bank");
     Verbindung archiv = new Verbindung("Archiv")) {
    bank.senden("Kontostand?");
    archiv.senden("");
} catch (IllegalArgumentException e) {
    System.out.println("Fehler: " + e.getMessage());
}

Wrapping

Eine Methode sollte Ausnahmen werfen, die zu ihrer Aufgabe passen. Wer ein Konto lädt, will „Konto nicht gefunden“ hören, nicht „Datei fehlt“. Also fängt man die technische Ausnahme und wirft eine fachliche – und gibt die alte als Ursache (cause) mit. So geht nichts verloren: Der Stacktrace zeigt sie unter „Caused by“.

KontoNichtGefundenException.java 
public class KontoNichtGefundenException extends Exception {

    private final String iban;

    public KontoNichtGefundenException(String iban, Throwable ursache) {
        super("Kein Konto mit IBAN " + iban, ursache);
        this.iban = iban;
    }

    public String getIban() {
        return iban;
    }
}
KontoArchiv.java – einpacken 
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class KontoArchiv {

    public static String laden(String iban) throws KontoNichtGefundenException {
        try {
            return Files.readString(Path.of("konten", iban + ".txt"));
        } catch (IOException e) {
            throw new KontoNichtGefundenException(iban, e);
        }
    }
}

6Eigene Exceptions

Eine eigene Exception ist eine gewöhnliche Klasse, die von Exception (checked) oder RuntimeException (unchecked) erbt. Sie bekommt einen fachlichen Namen und Felder für alles, was der Fänger wissen muss – nicht nur einen Text.

KeineDeckungException.java 
public class KeineDeckungException extends Exception {

    private final String iban;
    private final long fehlbetrag;   // in Cent

    public KeineDeckungException(String iban, long fehlbetrag) {
        super("Konto " + iban + ": es fehlen " + fehlbetrag + " Cent");
        this.iban = iban;
        this.fehlbetrag = fehlbetrag;
    }

    public String getIban() {
        return iban;
    }

    public long getFehlbetrag() {
        return fehlbetrag;
    }
}

Darauf kommt es an

  • Name endet auf Exception und sagt, was fachlich passiert ist.
  • Oberklasse bewusst wählen: checked für erwartbare Situationen, unchecked für Programmierfehler (siehe 4).
  • Konstruktor ruft super(…) mit der Nachricht – und, beim Einpacken, mit der Ursache (siehe Wrapping).
  • Felder private final, nur Getter. Eine Exception ist ein Bericht über einen vergangenen Moment: Sie wird geworfen, wandert über viele Ebenen und wird dort gelesen. Unterwegs darf niemand den Fehlbetrag ändern – sonst erzählt sie, was nie passiert ist.
Der Fänger nutzt die Felder 
try {
    Bank.überweisen(giro, spar, 150_00);
} catch (KeineDeckungException e) {
    System.out.println("Bitte zahle noch " + e.getFehlbetrag() + " Cent ein.");
}

Merksatz: Eine Ausnahme ist ein Objekt, das über einen zweiten Ausgang zurückfliegt – bis zum ersten passenden catch, und wenn es keines gibt, bis zur JVM.
