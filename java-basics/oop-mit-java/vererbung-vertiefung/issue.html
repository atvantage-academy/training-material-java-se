    Kontoarten sich unterschiedlich verhalten lassen

    Als Entwickler:in möchte ich Konten unterschiedlicher Art einheitlich behandeln und trotzdem das jeweils richtige Verhalten auslösen, damit eine neue Kontoart die bestehende Abhebe-Logik nicht anfassen muss.

    Hinweis: Du baust an der Hierarchie von eben weiter – es entsteht keine neue Klasse von Grund auf.

    Lernziele

    Du…

    • machst eine Oberklasse abstrakt, wenn es von ihr keine sinnvollen Objekte gibt.
    • überschreibst eine geerbte Methode und kennzeichnest das mit @Override.
    • erklärst, warum zur Laufzeit das Objekt entscheidet, welche Implementierung läuft.
    • legst mit equals fest, wann zwei Konten fachlich gleich sind.

    Definition of Done

    • Konto lässt sich nicht mehr direkt instanziieren.
    • Das Abheben steht nur einmal – in der Oberklasse – und fragt eine Prüfmethode.
    • Das Girokonto überschreibt diese Prüfung, sodass das Dispolimit zählt; das Sparkonto überschreibt sie nicht.
    • Ein Konto[] mit beiden Kontoarten wird in einer Schleife durchlaufen und verhält sich je Konto korrekt unterschiedlich.
    • equals in Konto beruht auf der IBAN.
    • Du hast die Reflexionsfragen schriftlich beantwortet.

    Arbeitsschritte

    Die Oberklasse abstrakt machen

    Es gibt kein Konto, das weder Giro- noch Sparkonto ist. Sorg dafür, dass der Compiler das durchsetzt.

    Hinweis: Probier danach bewusst new Konto(...) aus und lies die Meldung – genau diese Zusicherung wolltest Du haben.

    Die Verfügbarkeitsprüfung herausziehen

    Beim Abheben stellt sich immer dieselbe Frage: Ist genug da? Was „genug“ bedeutet, unterscheidet sich je Kontoart – die Frage selbst nicht. Trenne beides: Das Abheben bleibt in der Oberklasse, die Prüfung wird eine eigene Methode.

    Hinweis: Damit die Unterklasse die Prüfung ersetzen kann, muss sie sie sehen. Ein private reicht dafür nicht – welche Sichtbarkeit passt hier?

    Das Girokonto anders prüfen lassen

    Beim Girokonto darf bis zum Dispolimit ins Minus gegangen werden. Überschreib die Prüfung entsprechend – und fass das Abheben nicht an.

    Hinweis: Setz @Override davor. Bau danach einmal absichtlich einen Tippfehler in den Methodennamen und sieh Dir an, was die Annotation dann meldet.

    Hinweis: Das Sparkonto bekommt nichts. Es erbt die strengere Prüfung – auch das ist eine bewusste Entscheidung.

    Beide Konten gemeinsam behandeln

    Leg ein Giro- und ein Sparkonto in ein Konto[] und versuch in einer Schleife, bei jedem denselben Betrag abzuheben.

    Hinweis: Überleg vor dem Start, was passieren wird – und vergleich es danach mit der Ausgabe. Wo im Code steht eigentlich, welche Prüfung für welches Konto gilt?

    Gleichheit festlegen

    Zwei Konten sind dasselbe Konto, wenn ihre IBAN übereinstimmt. Sorg dafür, dass Dein Code das auch so sieht.

    Hinweis: Die Methode dafür erbst Du – wie toString() – aus Object. Vergleich anschließend zwei Objekte mit derselben IBAN einmal mit == und einmal mit Deiner Methode.

    Hinweis: Wenn solche Objekte später in ein HashSet wandern, gehört noch eine zweite Methode dazu. Das kommt im Kurs noch – für heute genügt equals.

    Für Schnelle

    • Ergänze eine dritte Kontoart mit einer eigenen Regel und lauf die Schleife erneut – wie viel bestehenden Code musstest Du anfassen?
    • Gib in der Schleife zusätzlich aus, um welche Kontoart es sich handelt, ohne instanceof zu verwenden.

    Reflexionsfragen

    • Warum musstest Du das Abheben nicht ändern, obwohl sich das Verhalten je Kontoart unterscheidet?
    • Was wäre für eine neue Kontoart zu tun – und was ausdrücklich nicht?
    • Wo liegt der Unterschied zwischen dem deklarierten und dem tatsächlichen Typ?
    • Warum ist das besser als eine Fallunterscheidung if (art == GIRO) … else …?
