Wissens-Check: Java- und OO-Grundlagen

  1. Was macht „Write once, run anywhere“ technisch möglich?
    • Der Compiler erzeugt Bytecode, den die JVM der Plattform ausführt.
    • Der Quellcode wird auf jedem Zielrechner vor dem Start neu kompiliert.
    • Java wird ohne Compiler direkt aus dem Quelltext interpretiert.
    • Der Compiler erzeugt Maschinencode für alle Systeme zugleich.
  2. int a = 7; int b = 2; double d = a / b;
    Welchen Wert hat d danach?
    • 3.0
    • 3.5
    • 3
    • Compilerfehler
  3. Warum kann die IDE ein laufendes Programm an einem Breakpoint anhalten?
    • Die JVM läuft im Debug-Modus, die IDE steuert sie über einen Port.
    • Die IDE baut Haltebefehle in den Code ein und kompiliert neu.
    • Die IDE führt den Quelltext im Debug-Modus selbst Zeile für Zeile aus.
    • Das Betriebssystem friert den Prozess an der markierten Zeile ein.
  4. In der Anforderung steht: „Ein Kunde kann mehrere Konten besitzen.“
    Wie hältst Du das im Klassendiagramm fest?
    • Als Linie zwischen Kunde und Konto, am Konto-Ende ein *.
    • Als Vererbungspfeil von Konto zu Kunde: Konto erbt von Kunde.
    • Als Eigenschaft konten: String in der Klasse Kunde.
    • Als Fähigkeit besitzen() in der Klasse Kunde.
  5. class Konto { private String iban; Konto(String iban) { this.iban = iban; } } … Konto a = new Konto("DE01"); Konto b = new Konto("DE01");
    Was liefert a.equals(b)?
    • false – das geerbte equals prüft die Identität.
    • true – beide Konto-Objekte haben dieselbe IBAN.
    • true – equals vergleicht alle Felder einzeln.
    • Compilerfehler – Konto hat gar kein equals.
  6. class Konto { private double kontostand; void einzahlen(double betrag) { kontostand += betrag; } } … Konto a = new Konto(); Konto b = a; b.einzahlen(100);
    Was gilt danach für a?
    • Auch a hat 100 mehr – a und b zeigen auf dasselbe Objekt.
    • a ist unverändert – b ist eine Kopie von a.
    • a ist unverändert – Änderungen über b sind lokal.
    • Compilerfehler – ein Objekt darf nur eine Variable haben.
  7. class Konto { private double kontostand; static void zeige() { System.out.println(kontostand); } }
    Warum kompiliert zeige() nicht?
    • Sie läuft ohne Objekt – es gibt kein this, also keinen Kontostand.
    • static-Methoden sind automatisch private und sehen deshalb keine Felder.
    • static-Methoden dürfen nur final-Felder, also Konstanten, lesen.
    • Felder entstehen erst nach main, static-Methoden laufen davor.
  8. package bank; public class Konto { double kontostand; }
    Wer darf auf das Feld kontostand zugreifen?
    • Alle Klassen im selben Package.
    • Alle Klassen, wie bei public.
    • Nur die Klasse selbst, wie bei private.
    • Die Klasse und ihre Unterklassen.
  9. public class Konto { private final String iban; public Konto() { } }
    Was passiert beim Übersetzen?
    • Compilerfehler – iban muss im Konstruktor gesetzt werden.
    • iban bleibt null und lässt sich später einmal setzen.
    • Es kompiliert; beim ersten Lesen kommt ein Laufzeitfehler.
    • Es kompiliert; final verhindert nur das Vererben.
  10. class Konto { private final String iban; Konto(String iban) { this.iban = iban; } } class Girokonto extends Konto { Girokonto(String iban) { } }
    Was passiert beim Übersetzen?
    • Compilerfehler – das implizite super() findet nichts.
    • Es kompiliert; das Feld iban bleibt im Girokonto einfach null.
    • Es kompiliert; Java übergibt für iban null.
    • Es kompiliert; der Konto-Teil wird danach erzeugt.
  11. class Konto { Konto(String iban) { … } } class Girokonto extends Konto { … } class Sparkonto extends Konto { … } … Konto k = new Girokonto("DE02");
    Welche Zeile kompiliert?
    • Konto x = new Girokonto("DE01");
    • Girokonto x = new Konto("DE01");
    • Sparkonto x = new Girokonto("DE01");
    • Girokonto x = k;
  12. class Konto { double gebühr() { return 2; } } class Girokonto extends Konto { @Override double gebühr() { return 5; } } class Sparkonto extends Konto { @Override double gebühr() { return 0; } } … Konto[] konten = { new Girokonto(), new Sparkonto() }; double summe = 0; for (Konto k : konten) { summe += k.gebühr(); }
    Welchen Wert hat summe danach?
    • 5.0
    • 4.0
    • 9.0
    • Compilerfehler
  13. class Konto { String art() { return "Konto"; } String beschreibe() { return "Ich bin " + art(); } } class Girokonto extends Konto { @Override String art() { return "Giro"; } }
    Was liefert new Girokonto().beschreibe()?
    • "Ich bin Giro"
    • "Ich bin Konto"
    • "Ich bin KontoGiro"
    • Compilerfehler
  14. class Konto { … } class Girokonto extends Konto { void dispoSetzen(double betrag) { … } } … Konto k = new Girokonto(); k.dispoSetzen(500);
    Was passiert beim Übersetzen?
    • Compilerfehler – Konto kennt dispoSetzen nicht.
    • Es läuft – im Objekt steckt ja ein Girokonto.
    • Es kompiliert; zur Laufzeit folgt ein Fehler.
    • Es kompiliert; der Aufruf wird still ignoriert.
  15. class Girokonto extends Konto { @Override public String tostring() { return "Girokonto"; } }
    Was passiert beim Übersetzen?
    • Compilerfehler – tostring() überschreibt keine Methode.
    • Es kompiliert; tostring() wird eine zusätzliche Methode.
    • Es kompiliert; Java ignoriert dabei Groß-/Kleinschreibung.
    • Es kompiliert; der Fehler zeigt sich erst beim Aufruf.
  16. public abstract class Konto { private double kontostand; public void einzahlen(double betrag) { kontostand += betrag; } } class Girokonto extends Konto { … }
    Was bewirkt abstract hier?
    • new Konto(…) kompiliert nicht mehr.
    • Unterklassen müssen alle Methoden überschreiben.
    • Konto darf keinen Konstruktor mehr haben.
    • Konto darf keine Felder mehr haben.
  17. class Kunde { private String kundennummer; … } class Girokonto extends Konto { … } – beide sollen eine getId() anbieten und gemeinsam in einer Liste verwaltet werden.
    Welcher Weg passt?
    • Ein Interface Identifizierbar, das beide Klassen implementieren.
    • Eine abstrakte Klasse Identifizierbar als gemeinsame Oberklasse.
    • Kunde erbt von Konto und bekommt so auch dessen getId().
    • getId() in beiden Klassen – ganz ohne gemeinsamen Typ.
  18. Warum schreibt man List konten = new ArrayList<>(); statt ArrayList auf der linken Seite?
    • Die Implementierung bleibt austauschbar.
    • ArrayList ist abstrakt.
    • Über List ist der Zugriff schneller.
    • Links verlangt der Compiler ein Interface.
  19. class Rechteck { void setzeBreite(double b) { … } void setzeHöhe(double h) { … } } class Quadrat extends Rechteck { @Override void setzeBreite(double b) { super.setzeBreite(b); super.setzeHöhe(b); } @Override void setzeHöhe(double h) { super.setzeBreite(h); super.setzeHöhe(h); } }
    Die Aussage „Ein Quadrat ist ein Rechteck“ stimmt. Warum ist dieser Entwurf trotzdem fragwürdig?
    • Code, der Breite und Höhe getrennt setzt, wird mit Quadraten falsch.
    • Das Quadrat erbt ein überflüssiges Feld und verschwendet Speicher.
    • super.setzeBreite(b) landet wieder im Quadrat – eine Endlosschleife.
    • Der Satz „ist ein“ stimmt fachlich nicht – darum passt der Pfeil nicht.
  20. public class KeineDeckungException extends Exception { … } public class Konto { public void abheben(double betrag) throws KeineDeckungException { … } }
    Was folgt daraus für den Code, der abheben aufruft?
    • Er muss sie fangen oder per throws weitergeben.
    • Nichts – der Compiler prüft Ausnahmen grundsätzlich nicht.
    • Das Programm bricht beim Wurf in jedem Fall ab.
    • Sie muss schon in abheben(…) gefangen werden.
  21. Konten sollen schnell per IBAN nachgeschlagen werden. Welche Struktur passt?
    • Map
    • ArrayList
    • LinkedHashSet
    • Konto[]
  22. class Konto { private String iban; @Override public boolean equals(Object o) { if (!(o instanceof Konto)) return false; return iban.equals(((Konto) o).iban); } } … Set konten = new HashSet<>(); konten.add(new Konto("DE01")); konten.add(new Konto("DE01"));
    Was passiert in aller Regel – hashCode ist nicht überschrieben?
    • Beide landen im Set.
    • Nur eines landet im Set.
    • Es gibt einen Compilerfehler.
    • Es gibt eine Exception.
  23. public interface Identifizierbar { String getId(); } public class Repository { private final Map elemente = new HashMap<>(); public void save(T element) { … } }
    Wozu dient die Schranke extends Identifizierbar?
    • Innen ist getId() auf T aufrufbar.
    • Der Aufrufer kommt ohne Casts aus.
    • Für T ist nur noch Konto erlaubt.
    • T wird zur Laufzeit geprüft.
