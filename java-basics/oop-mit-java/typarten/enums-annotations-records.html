Zum Inhalt springen

Enums, Annotations und Records

Drei Typarten, die mehr können als eine gewöhnliche Klasse – oder bewusst weniger. Jede hat einen Reiter: wozu es sie gibt, wie man sie schreibt und was der Compiler daraus macht. Alle Ausgaben auf dieser Seite stammen aus echten Läufen mit Java 25.

Enums

1Wozu ein Enum?

Manche Werte stehen von vornherein fest: die vier Farben eines Kartenspiels, die Wochentage, die Zustände einer Bestellung. Ein enum (seit Java 5) ist ein Typ mit genau diesen Werten und keinem anderen. Der Compiler prüft das – ein Tippfehler oder eine erfundene Zahl fällt beim Übersetzen auf, nicht erst beim Kunden.

Vorher: Zahlenkonstanten 
public static final int KREUZ = 0;
public static final int PIK   = 1;
public static final int HERZ  = 2;
public static final int KARO  = 3;

static void ausspielen(int farbe) { … }

ausspielen(HERZ);
ausspielen(42);               // kompiliert – leider
System.out.println(HERZ);     // 2

Jede int-Zahl ist „eine Farbe“, und die Ausgabe sagt nichts.

Mit Enum 
public enum Kartenfarbe {
    KREUZ, PIK, HERZ, KARO
}

static void ausspielen(Kartenfarbe farbe) { … }

ausspielen(Kartenfarbe.HERZ);
ausspielen(42);               // Compilerfehler
System.out.println(Kartenfarbe.HERZ);   // HERZ

Nur die vier Konstanten passen, und jede kennt ihren Namen.

2Syntax: das einfache Enum

Das Schlüsselwort enum steht dort, wo sonst class steht; dahinter folgen die Konstanten, durch Komma getrennt. Konstanten schreibt man in GROSSBUCHSTABEN. Jedes Enum bringt ein paar Methoden fertig mit:

Kartenfarbe trumpf = Kartenfarbe.HERZ;
System.out.println(trumpf);                        // HERZ
System.out.println(trumpf.name());                 // HERZ
System.out.println(trumpf.ordinal());              // 2
System.out.println(trumpf == Kartenfarbe.HERZ);    // true
System.out.println(Kartenfarbe.valueOf("PIK"));    // PIK

for (Kartenfarbe f : Kartenfarbe.values()) {
    System.out.print(f + " ");
}

switch (trumpf) {
    case KREUZ, PIK -> System.out.println("schwarz");
    case HERZ, KARO -> System.out.println("rot");
}

Was Du mitbekommst

  • name() und toString() – der Name der Konstante als Text.
  • ordinal() – die Position, ab 0. Nicht für Fachlogik verwenden: Wer die Reihenfolge ändert, ändert die Zahl.
  • values() – alle Konstanten als Array, in Deklarationsreihenfolge.
  • valueOf(String) – vom Text zur Konstante; unbekannter Text wirft eine IllegalArgumentException.
  • Vergleich mit == ist richtig: Jede Konstante gibt es genau einmal.
  • switch kennt Enums – in den case-Zweigen ohne Kartenfarbe. davor.

3Syntax: Enum mit Instanzvariable

Ein Enum ist eine Klasse – es darf Felder, Konstruktoren und Methoden haben. Beim Skat hat jede Farbe einen Grundwert. Den gibt man jeder Konstante in Klammern mit; die Klammern rufen den Konstruktor auf.

public enum Kartenfarbe {
    KREUZ(12), PIK(11), HERZ(10), KARO(9);   // ← Semikolon!

    private final int wert;

    Kartenfarbe(int wert) {                  // automatisch private
        this.wert = wert;
    }

    public int getWert() {
        return wert;
    }
}
for (Kartenfarbe f : Kartenfarbe.values()) {
    System.out.println(f + " = " + f.getWert());
}
int spielwert = Kartenfarbe.KREUZ.getWert() * 2;
System.out.println(spielwert);
KREUZ = 12
PIK = 11
HERZ = 10
KARO = 9
24

Die Regeln dazu

  • Die Konstanten stehen zuerst; sobald noch etwas folgt, schließt ein Semikolon die Liste ab.
  • Der Konstruktor ist immer private – auch ohne das Wort. new Kartenfarbe(8) geht nicht: Es bleibt bei den vier.
  • Felder macht man final. Eine Konstante, deren Wert sich ändert, wäre keine.

4Dasselbe ohne Enum – was der Compiler daraus macht

Ein Enum ist Kurzschrift für eine Klasse. Der erste Reiter zeigt, was Du schreibst; der zweite, was der Compiler daraus erzeugt – als Java-Code ausgeschrieben, damit man es lesen kann.

Das schreibst Du 
public enum Kartenfarbe {
    KREUZ(12), PIK(11), HERZ(10), KARO(9);

    private final int wert;

    Kartenfarbe(int wert) {
        this.wert = wert;
    }

    public int getWert() {
        return wert;
    }
}
Das macht der Compiler daraus 
public final class Kartenfarbe extends Enum<Kartenfarbe> {   // final: keine Unterklassen

    public static final Kartenfarbe KREUZ = new Kartenfarbe("KREUZ", 0, 12);
    public static final Kartenfarbe PIK   = new Kartenfarbe("PIK",   1, 11);
    public static final Kartenfarbe HERZ  = new Kartenfarbe("HERZ",  2, 10);
    public static final Kartenfarbe KARO  = new Kartenfarbe("KARO",  3, 9);

    private static final Kartenfarbe[] $VALUES = { KREUZ, PIK, HERZ, KARO };

    private final int wert;

    private Kartenfarbe(String name, int ordinal, int wert) {
        super(name, ordinal);            // name(), ordinal(), toString() … kommen aus Enum
        this.wert = wert;
    }

    public int getWert() {
        return wert;
    }

    public static Kartenfarbe[] values() {
        return $VALUES.clone();          // Kopie – das Original bleibt heil
    }

    public static Kartenfarbe valueOf(String name) {
        return Enum.valueOf(Kartenfarbe.class, name);
    }
}

Der Beleg: javap -p zeigt, was wirklich in der Kartenfarbe.class steht. Jede Konstante ist ein public static final-Feld, die Klasse ist final und erbt von java.lang.Enum, values() und valueOf() hat der Compiler ergänzt.

Compiled from "Kartenfarbe.java"
public final class Kartenfarbe extends java.lang.Enum<Kartenfarbe> {
  public static final Kartenfarbe KREUZ;
  public static final Kartenfarbe PIK;
  public static final Kartenfarbe HERZ;
  public static final Kartenfarbe KARO;
  private final int wert;
  private static final Kartenfarbe[] $VALUES;
  public static Kartenfarbe[] values();
  public static Kartenfarbe valueOf(java.lang.String);
  private Kartenfarbe(int);
  public int getWert();
  private static Kartenfarbe[] $values();
  static {};
}

Der Konstruktor heißt dort nur scheinbar Kartenfarbe(int): Seine echte Signatur ist (String, int, int) – Name und Position reicht der Compiler unsichtbar mit durch. Im statischen Initialisierer steht dann new Kartenfarbe("KREUZ", 0, 12), genau wie im zweiten Reiter oben.

Warum dann nicht gleich selbst schreiben?

Weil man es nicht darf: Diese Klasse kann nur der Compiler erzeugen. Schreibt man sie selbst, meldet javac: „Klassen können java.lang.Enum nicht direkt erweitern“. Und es ist gut so – über die Oberklasse Enum bekommt ein echtes Enum compareTo in Deklarationsreihenfolge, ein equals, das niemand überschreiben kann, Schutz davor, dass beim Serialisieren eine fünfte „Kreuz“-Instanz entsteht, die Unterstützung im switch und die schnellen Sammlungen EnumSet und EnumMap.

5Vertiefung: abstrakte Methoden und Interfaces

Weil ein Enum eine Klasse ist, darf es Interfaces implementieren und abstrakte Methoden deklarieren. Dann bekommt jede Konstante einen eigenen Rumpf in geschweiften Klammern – das Verhalten unterscheidet sich je Konstante, ohne switch.

public interface Symbol {
    char symbol();
}

public enum Kartenfarbe implements Symbol {
    KREUZ(12) {
        public boolean istRot() { return false; }
        public char symbol()    { return '♣'; }
    },
    PIK(11) {
        public boolean istRot() { return false; }
        public char symbol()    { return '♠'; }
    },
    HERZ(10) {
        public boolean istRot() { return true; }
        public char symbol()    { return '♥'; }
    },
    KARO(9) {
        public boolean istRot() { return true; }
        public char symbol()    { return '♦'; }
    };

    private final int wert;

    Kartenfarbe(int wert) {
        this.wert = wert;
    }

    public int getWert() {
        return wert;
    }

    public abstract boolean istRot();   // jede Konstante MUSS sie liefern
}
for (Kartenfarbe f : Kartenfarbe.values()) {
    System.out.println(f.symbol() + " " + f + " rot? " + f.istRot());
}
Symbol s = Kartenfarbe.PIK;           // über das Interface ansprechbar
System.out.println(s.symbol());
System.out.println(Kartenfarbe.HERZ.getClass());
System.out.println(Kartenfarbe.HERZ.getDeclaringClass());

♠ PIK rot? false
♥ HERZ rot? true
♦ KARO rot? true

Was der Compiler daraus macht

Jeder Konstantenrumpf wird eine anonyme Unterklasse: Neben Kartenfarbe.class liegen Kartenfarbe$1.class bis Kartenfarbe$4.class. Die Enum-Klasse selbst ist jetzt abstract statt final:

public abstract class Kartenfarbe extends java.lang.Enum<Kartenfarbe> implements Symbol {
  public static final Kartenfarbe KREUZ;
  …
  public abstract boolean istRot();
  …
}

Deshalb liefert getClass() für HERZ die Unterklasse Kartenfarbe$3. Wer die Enum-Klasse braucht – etwa für einen Vergleich –, nimmt getDeclaringClass().

Interface oder abstrakte Methode? Ein Interface lohnt sich, wenn auch andere Typen dieselbe Fähigkeit haben sollen (eine Symbol-Methode haben auch Spielfiguren). Eine abstrakte Methode reicht, wenn nur dieses Enum sie braucht. Beides lässt sich, wie oben, kombinieren. Ist das Verhalten nur ein anderer Wert, genügt ein Feld wie wert – ein eigener Rumpf je Konstante lohnt erst bei echt unterschiedlicher Logik.

Merksatz: Ein Enum ist eine Klasse mit einer festen, vom Compiler bewachten Liste von Instanzen – mit Feldern, Methoden und sogar eigenem Verhalten je Konstante.

Annotations

1Wozu Annotations?

Eine Annotation (seit Java 5) ist eine Markierung am Code – an einer Klasse, einer Methode, einem Feld, einem Parameter. Sie heftet eine Information an, verändert aber selbst nichts: Kein Befehl wird durch eine Annotation ausgeführt. Sie wirkt erst, wenn jemand sie ausliest – der Compiler oder ein Framework (siehe unten).

Man kann sie sich wie einen Klebezettel vorstellen: „Diese Methode soll eine geerbte überschreiben.“ – „Diese Methode beantwortet HTTP-GET-Anfragen.“ Der Zettel tut nichts; wer ihn liest, handelt danach.

2Syntax: drei Formen

Eine Annotation beginnt mit @ und steht vor dem, was sie markiert. Je nachdem, ob sie Attribute hat, gibt es drei Schreibweisen:

Marker – ohne Attribute 
@Override
public String toString() {
    return "Konto[" + saldo + "]";
}

@FunctionalInterface
interface Prüfer {
    boolean prüfe(int wert);
}

Die bloße Anwesenheit ist die Information.

Mit dem Attribut value 
@SuppressWarnings("unchecked")
static List<String> roh() { … }

// ausführlich – dasselbe:
@SuppressWarnings(value = "unchecked")

Heißt das einzige angegebene Attribut value, darf man value = weglassen. Mehrere Werte stehen in geschweiften Klammern: @SuppressWarnings({"unchecked", "removal"}).

Mit mehreren Attributen 
@Deprecated(since = "2.0", forRemoval = true)
public static void altesVerfahren() { … }

Jedes Attribut mit Namen, durch Komma getrennt; die Reihenfolge ist egal. Attribute mit Standardwert darf man weglassen – @Deprecated allein geht auch.

3Annotations sind auch nur Typen

@Override ist kein Schlüsselwort und keine Magie, sondern ein Typ – genau wie eine Klasse oder ein Interface. Man kann eigene deklarieren: mit @interface. Die Attribute sind Methoden ohne Parameter, default gibt den Standardwert.

Java-Code

Eine eigene Datei, ein eigener Name, ein Package:

package de.bank.annotationen;

public @interface Geprüft {
    String value();
    String von() default "unbekannt";
    int stufe() default 1;
}
package de.bank.annotationen;

public @interface Vorläufig {
}
Bytecode

Der Compiler macht daraus eine .class-Datei – und zwar ein Interface, das java.lang.annotation.Annotation erweitert:

Compiled from "Geprüft.java"
public interface de.bank.annotationen.Geprüft
    extends java.lang.annotation.Annotation {
  public abstract java.lang.String value();
  public abstract java.lang.String von();
  public abstract int stufe();
}

Ein Marker wie Vorläufig ist ein Interface ohne Methoden.

Packages

Wer sie verwendet, muss sie importieren – wie jeden anderen Typ:

package de.bank;

import de.bank.annotationen.Geprüft;
import de.bank.annotationen.Vorläufig;

@Vorläufig
@Geprüft("2026-10-08")
public class Konto {

    @Geprüft(value = "2026-10-01", von = "Mia", stufe = 2)
    public void einzahlen(double betrag) { }
}
out/de/bank/Konto.class
out/de/bank/annotationen/Geprüft.class
out/de/bank/annotationen/Vorläufig.class

Auch die eingebauten liegen in Packages: @Override, @Deprecated, @SuppressWarnings und @FunctionalInterface stehen in java.lang – deshalb braucht man für sie keinen import.

4Wer liest sie aus?

Eine Annotation ohne Leser ist ein Kommentar mit Syntaxprüfung. Gelesen wird sie entweder vom Compiler oder von einem Framework.

Der Compiler

@Override verspricht: „Diese Methode überschreibt eine geerbte.“ Ein Tippfehler im Namen fällt sofort auf:

    private double saldo;

    @Override
    public String tostring() {          // kleines s!
        return "Konto[" + saldo + "]";

}

Ein Framework – mit eigenen Annotations

Frameworks definieren ihre eigenen Annotations und lesen sie zur Laufzeit. Beispiel JAX-RS (Jakarta REST): Die Annotations sagen dem Server, welche Methode welche HTTP-Anfrage beantwortet. Aufrufen tut die Methode niemand im eigenen Code – das Framework findet sie über die Annotations.

import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.PathParam;
import jakarta.ws.rs.Produces;
import jakarta.ws.rs.core.MediaType;

@Path("/konten")
public class KontoRessource {

    @GET
    @Path("/{iban}")
    @Produces(MediaType.APPLICATION_JSON)
    public Konto finde(@PathParam("iban") String iban) {
        return kontoService.finde(iban);
    }
}

Eine Anfrage GET /konten/DE89… landet in finde, das Stück hinter /konten/ im Parameter iban, und die Antwort geht als JSON zurück. Und auch hier: jakarta.ws.rs.Path ist nur ein Typ aus einer Bibliothek –

public interface jakarta.ws.rs.Path extends java.lang.annotation.Annotation {
  public abstract java.lang.String value();
}

Wie lange eine Annotation erhalten bleibt, legt ihre Deklaration mit @Retention fest: nur im Quelltext (für den Compiler) oder bis zur Laufzeit (für Frameworks). Wie man sie selbst ausliest, ist nicht Thema dieser Seite.

Merksatz: Eine Annotation ist ein Typ – im Code mit @interface deklariert, im Bytecode ein Interface, in einem Package zu Hause. Sie markiert nur; wirken lässt sie erst ein Leser: der Compiler oder ein Framework.

Records

1Wozu Records?

Viele Klassen sind nichts als ein Behälter für ein paar Werte: eine Spielkarte aus Farbe und Bild, ein Punkt aus x und y, eine Adresse. Für so eine Klasse schreibt man von Hand Felder, Konstruktor, Zugriffsmethoden, equals, hashCode und toString – viel Code, in dem sich leicht ein Fehler versteckt. Ein record (seit Java 16) erklärt nur noch die Daten; den Rest leitet der Compiler daraus ab.

„Records […] are classes that act as transparent carriers for immutable data.“

Records sind Klassen, die als durchsichtige Träger für unveränderliche Daten dienen.

JEP 395, „Records“ (JDK 16) – Summary

2Syntax am Beispiel

Hinter dem Namen stehen in Klammern die Komponenten – Typ und Name, wie Parameter. Ein Rumpf darf eigene Methoden und einen kompakten Konstruktor zur Prüfung enthalten (ohne Parameterliste; die Zuweisung an die Felder ergänzt der Compiler).

Beispiel 
public record Spielkarte(Kartenfarbe farbe, String bild) {

    public Spielkarte {                        // kompakter Konstruktor
        if (bild == null || bild.isBlank()) {
            throw new IllegalArgumentException("Bild fehlt");
        }
    }

    public boolean istTrumpf(Kartenfarbe trumpf) {
        return farbe == trumpf || bild.equals("Bube");
    }
}
Spielkarte a = new Spielkarte(Kartenfarbe.HERZ, "Dame");
Spielkarte b = new Spielkarte(Kartenfarbe.HERZ, "Dame");

System.out.println(a);                    // toString
System.out.println(a.farbe());            // Zugriffsmethode
System.out.println(a.equals(b));          // equals nach Inhalt
System.out.println(a == b);               // zwei Objekte
System.out.println(a.hashCode() == b.hashCode());
System.out.println(a.istTrumpf(Kartenfarbe.KREUZ));

Was der Compiler daraus macht

Aus einer Zeile Komponenten wird eine vollständige Klasse:

public final class Spielkarte extends java.lang.Record {
  private final Kartenfarbe farbe;
  private final java.lang.String bild;
  public Spielkarte(Kartenfarbe, java.lang.String);
  public boolean istTrumpf(Kartenfarbe);
  public final java.lang.String toString();
  public final int hashCode();
  public final boolean equals(java.lang.Object);
  public Kartenfarbe farbe();
  public java.lang.String bild();
}
  • je Komponente ein private final-Feld – keine Setter;
  • ein Konstruktor mit allen Komponenten (der „kanonische“);
  • je Komponente eine Zugriffsmethode – farbe(), nicht getFarbe();
  • equals, hashCode, toString aus allen Komponenten;
  • die Klasse ist final und erbt von java.lang.Record – Interfaces implementieren darf sie.

3Hintergrund: Warum heißt es farbe() und nicht getFarbe()?

Die Frage kam schon während der Vorschauphase auf: Fast jede Java-Klasse mit Daten hat Getter nach dem Muster getX(), viele Frameworks erwarten sie – warum also nicht auch Records? Die Antwort der Sprachdesigner bei Oracle (Projekt Amber, federführend Brian Goetz) steht in der JEP, in einem Designpapier und auf der Mailingliste amber-dev. Sie hat vier Teile:

  1. Records sind kein Ersatz für Java Beans – das war ausdrücklich nicht das Ziel.

    „It is not a goal to declare a ‚war on boilerplate‘. In particular, it is not a goal to address the problems of mutable classes which use the JavaBeans naming conventions.“

    Es ist kein Ziel, dem Schreibaufwand den Krieg zu erklären – und insbesondere nicht, die Probleme veränderlicher Klassen nach den JavaBeans-Namenskonventionen zu lösen.

    JEP 395 – Non-Goals
  2. getX/setX ist eine Konvention aus einer anderen Zeit – kein Standard der Sprache. Die JavaBeans-Spezifikation von 1997 beschreibt Bausteine für grafische Oberflächen-Editoren: „A Java Bean is a reusable software component that can be manipulated visually in a builder tool.“ Ein Editor erzeugt das Objekt mit einem leeren Konstruktor und setzt danach die Eigenschaften – dafür braucht es zu jedem getX ein setX.

    „[…] that was fine in the days when JavaBeans were only intended to model visual components in a GUI builder and the object lifecycle was based on calling a no-arg constructor and then setting properties. We're far, far from those days […]“

    Das passte, solange Java Beans nur Oberflächen-Bausteine im GUI-Editor waren, die man leer erzeugt und dann befüllt. Von dieser Zeit sind wir weit entfernt.

    Brian Goetz, amber-dev, 5. 8. 2020
  3. Eine Sprache soll keine Namensverstümmelung festschreiben. getX ist eine Umformung des Namens: Präfix davor, ersten Buchstaben groß – und bei boolean heißt es plötzlich isX. Was Bibliotheken als Konvention pflegen, ist für eine Sprache, die Methoden selbst erzeugt, eine viel höhere Hürde. Der Komponentenname selbst ist die einzige vertretbare Wahl – möglich nur, weil Felder und Methoden in Java getrennte Namensräume haben.

    „Languages should not be in the business of exposing name mangling like this; this is the domain of libraries and frameworks. […] if there is any justifiable choice here, x() is really the only possible one […]“

    Namen so umzuformen ist Sache von Bibliotheken und Frameworks, nicht der Sprache. Wenn überhaupt eine Wahl zu rechtfertigen ist, dann x().

    Brian Goetz, amber-dev, 5. 8. 2020
  4. Ein Record ist sein Zustand – und die Zugriffsmethode ist garantiert ein reiner Zugriff. Bei einer gewöhnlichen Klasse kann man nur raten, dass getX(), setX(…) und der Konstruktorparameter x dasselbe meinen. Beim Record ist es festgelegt: Komponente, Feld, Konstruktorparameter und Zugriffsmethode tragen denselben Namen, und die Reflection weiß es (Spielkarte.class.getRecordComponents() liefert zu farbe die Methode farbe()).

    „The API for a data class models the state, the whole state, and nothing but the state.“

    Die Schnittstelle einer Datenklasse bildet den Zustand ab – den ganzen Zustand und nichts als den Zustand.

    Brian Goetz, „Data Classes and Sealed Types for Java“, Februar 2019

Die Folge für Frameworks, die nach get suchen, hat Goetz in Kauf genommen: Sie müssten Records eben kennenlernen – „frameworks (and there are only a few of them) will have to update to recognize the new conventions (and it's easy for them to do so.)“ Die gängigen haben das inzwischen getan; manche – etwa JPA für Entitäten – brauchen aber weiterhin eine veränderliche Bean.

Typisch fürObjekte, die ein Framework leer erzeugt und befüllt (z. B. JPA-Entitäten), Formular-Modelle, veränderliche Fachobjekte.Werte und Datentransfer: Rückgabe mehrerer Werte, DTOs, Schlüssel in einer Map, Nachrichten zwischen Schichten.

Merksatz: Ein Record ist kein kürzer geschriebenes Bean, sondern ein anderes Versprechen: „Ich bin genau diese Daten – unveränderlich und durchsichtig.“ Deshalb heißt der Zugriff wie die Komponente, und deshalb gibt es keine Setter.
