Grenzen prozeduraler Strukturierung

Ein Stück Bank – prozedural gedacht

Unser Beispiel für die Woche: eine kleine Bank

  • Worum es geht Konten mit Inhaber und Kontostand, dazu Buchungen: einzahlen, abheben, überweisen
  • Regeln, die gelten müssen ein Girokonto darf höchstens bis zum Dispo ins Minus, ein Sparkonto gar nicht; jede Buchung muss nachvollziehbar bleiben
  • Verschiedene Kontoarten Giro, Spar, Kredit – vieles gleich, manches anders

Diese Fachlichkeit trägt die Übungen dieses Kurses. Sehen wir sie uns zunächst prozedural an.

So sähe das prozedural aus

// Alle Konten der Bank – parallele Arrays, zusammengehalten über den Index
static String[] inhaber     = new String[1000];
static long[]   standInCent = new long[1000];
static char[]   art         = new char[1000];   // 'G'iro, 'S'par, 'K'redit
static int      anzahl      = 0;

static void abheben(int konto, long betragInCent) {
    standInCent[konto] -= betragInCent;
}

static void zinsenGutschreiben(int konto) {
    if (art[konto] == 'S') {
        standInCent[konto] += standInCent[konto] * 15 / 1000;
    } else if (art[konto] == 'K') {
        // Kredit: ganz andere Rechnung, andere Vorzeichen …
    }
}

Was wird hier mühsam – und wo entstehen die Fehler?

Was daran mühsam wird

  • Daten und Regeln liegen getrennt Der Kontostand steht im Array, die Regel „nicht ins Minus“ irgendwo in einer Funktion – oder eben nicht. Jede Stelle im Programm darf standInCent[i] direkt ändern.
  • Zusammengehöriges hält nur der Index zusammen Inhaber, Stand und Art gehören zu einem Konto – dass das so bleibt, garantiert niemand. Ein falscher Index bucht auf dem falschen Konto.
  • Jede Erweiterung strahlt aus Ein neues Feld (IBAN, Eröffnungsdatum) heißt: neues Array, und jede Funktion, die Konten anfasst, muss nachgezogen werden.
  • Nichts schützt den Zustand Es gibt keine Stelle, an der man die Regeln einmal hinschreiben und erzwingen könnte – nur Disziplin.

Und dann kommt die Komplexität dazu

Drei Kontoarten – vieles gemeinsam, einiges verschieden:

Prozedural landet dieser Unterschied in Fallunterscheidungen: if (art[konto] == 'S') … – in jeder Funktion erneut, und bei jeder neuen Kontoart überall nachzutragen.

Das eigentliche Problem

  • Das Programm kennt keine „Konten“ Es kennt Arrays, Indizes und Funktionen. Das Ding, um das sich alles dreht, kommt im Code gar nicht vor.
  • Gemeinsamkeiten lassen sich nicht ausdrücken „Ein Sparkonto ist ein Konto, das anders abhebt“ – dafür gibt es prozedural keine Form, nur Kopien und if.
  • Wissen liegt verstreut Wer die Regeln eines Kontos verstehen will, muss das ganze Programm lesen.

Wo wir hinwollen

  • Kapselung Was zusammengehört, liegt an einer Stelle – die Daten eines Kontos und die Regeln, die für sie gelten. Was nichts miteinander zu tun hat, bleibt getrennt.
  • Erweiterbarkeit Eine neue Anforderung – etwa eine weitere Kontoart – soll möglichst neuen Code bedeuten und nicht das Ändern von bestehendem, der heute funktioniert.
  • Keine Wiederholung (DRY) Was für alle Konten gleich ist, wird einmal beschrieben – statt in jeder Funktion erneut nach der Kontoart zu fragen.
